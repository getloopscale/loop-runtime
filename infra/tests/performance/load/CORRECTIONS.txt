## Corrections Applied Manually (need definitive fix later)

### 1. Manifest Gate — Certificate CR Blocked (FIXED in ec12233)
- Problem: manifest_gate.go blocked ALL Certificate CRs, including those
  required for platform-managed subdomains (*.dev.getloopscale.com).
- Root cause: Gate was designed to prevent CF-managed domain Certificate CRs
  (which get stuck "Progressing"), but was applied universally.
- Manual fix: Removed "kind: Certificate" from blockedResourceKinds.
  ClusterIssuer/Issuer remain blocked (infra-level).
- Definitive fix TODO: Move validation to renderer layer. Gate should check
  structural correctness (no ClusterIssuer in tenant manifests), not
  blanket-block resource kinds. The renderer already handles the CF/non-CF
  branching correctly via CFManaged flag.
- Impact: ALL new tenant deploys were broken. Only pre-existing tenants
  (deployed before the gate) worked.
- **STATUS 2026-05-13:** RESOLVED ✓ — FIXED in commit ec12233 (and superseded by item G's YAML-aware rewrite).

### 2. seed.go renamed to seed_test.go
- Problem: Go only runs test functions from *_test.go files. The seed
  functions (TestSeed_CreateTenants, etc.) were in seed.go and invisible.
- Fix: Renamed to seed_test.go.
- go.mod: pgx/v5 promoted from indirect to direct dependency.
- **STATUS 2026-05-13:** RESOLVED ✓ — one-shot file rename committed.

### 3. DB Firewall — PG only accessible from K8s clusters
- Problem: Load test scripts can't connect to DO Managed PG from local
  machine (firewall only allows K8s cluster IPs).
- Workaround: Added local IP to firewall via doctl.
- Definitive fix: Load tests should run as K8s Jobs in the mgmt cluster
  (same VPC, no firewall issues). Or use a Taskfile task that handles
  the firewall add/remove automatically.
- **STATUS 2026-05-13:** DEFERRED_BY_ADR ✓ — `decisions/2026-05-13-load-tests-github-actions-deferral.md` documents conscious deferral with revisit criteria (firewall-IP rotation pain, in-VPC resource access need, 50k+ scale). Plan T5.1.

### 4. LoopRuntime.yaml version field — must be int, not string

- Impact: Load test fixture YAML was rejected with 422.
- Fix: Use unquoted integer.
- **STATUS 2026-05-13:** DOCUMENTED ✓ — validation rule clarification; enforced at API boundary.

### 5. App must have port or type

### 6. Root package.json + lockfile required

### 7. Service Auth works for load testing
- The X-Service-Auth header (cloud→engine internal auth) is the correct
  bypass for load testing. No GitHub OAuth needed.
- Requires: users + tenants + memberships seeded in DB first.
- Projects MUST be created via API (triggers EnsureTenant → Tenant CR).
- **STATUS 2026-05-13:** SUPERSEDED+EXTENDED ✓ — single-secret X-Service-Auth extended with Ed25519 dual-control per `decisions/2026-05-13-service-auth-ed25519-adoption.md` + `pkg/serviceauth/`. Memory `reference_ed25519_service_auth_2026_05_13.md`.

### G. Manifest gate disabled (no-op) — substring matching too aggressive
- Problem: Gate used strings.Contains("kind: ClusterIssuer") which matched
  the issuerRef.kind field INSIDE Certificate CRs, not just top-level resources.
  Every Certificate with issuerRef.kind: ClusterIssuer was rejected.
- Manual fix: Made validateManifests() a no-op (returns nil).
  The renderer already handles CF/non-CF branching via CFManaged flag.
- Definitive fix: Implement YAML-aware validation that parses documents
  and checks top-level apiVersion+kind, not substring matching. Block
  only infra resources (Namespace, ClusterRole, etc.).
- API image built+pushed directly, pods restarted.
- **STATUS 2026-05-13:** IMPLEMENTED ✓ — `api/internal/gitops/manifest_gate.go:46-97` uses `yaml.NewDecoder` for multi-doc YAML parsing, checks top-level kind via `forbiddenKinds` map, fails-closed on malformed YAML, skips empty docs. Pre-A.2 fix.

### I. PVC Multi-Attach failure — workflow steps on different nodes
- Problem: VolumeClaimTemplates create RWO PVCs. When Argo schedules
  steps on different nodes, the PVC can't attach to the second node.
  This caused 1/10 build failure in L1 clean run.
- Root cause: DO Block Storage is RWO only. K8s scheduler may split
  steps across nodes when under resource pressure.
- Manual fix: None applied — 9/10 success rate is acceptable for L1.
- Definitive fix: Add nodeAffinity or podAffinity in loop-runtime-forge
  Workflow spec to pin all steps to the same node. Or switch to
  ReadWriteMany storage (NFS/DO Spaces FUSE mount).
  loop-runtime-forge is external: github.com/getloopscale/argo-workflows-go
- **STATUS 2026-05-13:** PARTIALLY ✓ — `api/internal/argo/workflow_builder.go:262-288` adds `podAffinity` rule at LoopRuntime's renderer layer. Symptom resolved in production. Cross-repo RFC drafted at `concepts/operations/rfc-2026-05-13-loop-runtime-forge-node-affinity.md` for upstream loop-runtime-forge default. ADR D4 in plan documents the boundary. T3.1.

### K. Build cluster scaled: small→medium + autoscale 2→5
- Change: buildNodeClass small→medium, buildMaxNodes 3→5
- Reason: s-4vcpu-8gb fits ~4-5 builds per node, reducing PVC
  Multi-Attach probability (~70% less splits). Autoscale to 5 for
  burst capacity (20-25 concurrent builds).
- Cost: +$24/mo base. Extra nodes ~$0.036/hr (temporary).
- Definitive fix for Multi-Attach: still needs nodeAffinity in
  loop-runtime-forge. Medium nodes are mitigation, not elimination.
- **STATUS 2026-05-13:** IMPLEMENTED ✓ — `infra/pulumi-infra/src/config/stack.ts:34-36` parametrizes buildNodeClass / buildMinNodes / buildMaxNodes (operator-configurable per stack). `infra/pulumi-infra/src/components/infra.ts:159` enables autoScale when buildMaxNodes is set. Plus item I closes the Multi-Attach symptom at renderer layer.

### N. Manual node pool change breaks scoped kubeconfigs
- Problem: Changing the build cluster node pool via doctl (adding pool
  "build-medium", deleting old pool) invalidates the scoped SA tokens
  stored in the tenant-controller-kubeconfig Secret. The controller
  can't authenticate to the build cluster.
- Root cause: The scoped kubeconfigs are created by Pulumi via
  createScopedKubeconfig() which creates a SA + ClusterRole + token
  on the build/runtime clusters. When the old node pool is deleted,
  the SA token may become invalid.
- Impact: TenantController can't create build namespaces → tenants
  stay in <none> phase → load tests can't run
- Fix needed: Re-run Pulumi to regenerate scoped kubeconfigs, OR
  manually recreate the SA + token on the new build cluster nodes.
- Lesson: NEVER change node pools manually. All infra changes must
  go through Pulumi to maintain consistency of cross-cluster credentials.
- **STATUS 2026-05-13:** IMPLEMENTED ✓ — `task k3d:regen-scoped` (Taskfile target) + `infra/scripts/regen-all-scoped-kubeconfigs.sh` orchestrator + 9/9 hermetic tests. flock prevents concurrent races (EC-3), cell-0 excluded (EC-1), optimistic-concurrency Secret patch (EC-3), creates Secret if absent (EC-6). Plan T2.1.

### O. Pipeline orphan SA cleanup deletes Pulumi-managed SAs
- Problem: Pipeline cleanup step deletes SAs without Helm annotations.
  But tenant-controller and loop-runtime-api SAs are created by Pulumi (no Helm
  annotations). Deleting them breaks the controller and API pods.
- Fix needed: Exclude SAs with names matching known Pulumi resources
  from the orphan cleanup, OR remove the orphan SA cleanup entirely.
- **STATUS 2026-05-13:** RESOLVED ✓ — T1.1 comprehensive grep audit (4 patterns) confirmed orphan-SA-cleanup script NOT present in current repo. Cleanup script removed entirely sometime between 2026-04-09 and now. Finding doc: `concepts/operations/finding-2026-05-13-item-O-resolution.md`.

### M. Promtail removed from Pulumi — gRPC provider crash
- Problem: Pulumi K8s provider crashes with "grpc: client connection
  is closing" when managing Helm releases on runtime cluster during
  node pool resize. Both attempt 1 and retry fail with same error.
- Root cause: Provider binary (pulumi-resource-kubernetes) exits
  prematurely during long operations on the runtime cluster. May be
  related to the 4.27.0 version we pinned to avoid the 4.28.0 crash.
- Manual fix: Removed Promtail from Pulumi management. Pipeline
  cleanup removes it from state. Promtail remains running (Helm).
- Definitive fix: Upgrade pulumi-kubernetes when a stable version
  without these provider crashes is available.
- **STATUS 2026-05-13:** IMPLEMENTED ✓ (engineering; operator gate pending) — ADR `decisions/2026-05-13-pulumi-kubernetes-upgrade.md` documents phased upgrade plan (current pin 4.28.0 → target ^4.30.0, drill 7-day soak → prod cutover). Engineering deliverable complete. Operator-led `npm install + pulumi up` against drill stack remains (~16d wall-clock). Plan T4.1.

### H. Image cache on DOKS nodes — :dev tag not re-pulled
- Problem: `imagePullPolicy: Always` + `:dev` tag, but node-level cache
  served the old image. `kubectl set image` with SHA tag was needed.
- Workaround: Push with SHA tag + `kubectl set image` to force new RS.
- Definitive fix: Use SHA-based image tags in production (already done
  by CI pipeline). The `:dev` tag is inherently racy.
- **STATUS 2026-05-13:** IMPLEMENTED ✓ — `charts/loop-runtime-api/values.yaml:8` uses `pullPolicy: IfNotPresent` (prod chart); CI publishes SHA-based tags. `infra/helm/loop-runtime-api/values.yaml:10` uses `Always` for local dev (acceptable divergence). Pre-A.2 fix.

### E. GitOps push produces empty repo — RESOLVED
- Root cause was the manifest gate blocking ClusterIssuer reference
  inside Certificate CRs (see correction G above).
- After gate was made no-op, deploy succeeded in 186s.
- Problem: Build reaches RELEASING state (manifest gate passed), but the
  gitops repo remains empty (only Initial commit). The manifests are
  generated but never pushed to Gitea.
- Hypothesis: The Gitea API credentials used by the gitops pusher may
  not have write access to the loadtest tenant's repo. The bootstrap
  Job creates repo creds for the platform, but new tenants created via
  API may not have the ArgoCD repo-creds configured.
- Status: INVESTIGATING — this blocks all L1+ load tests.
- Definitive fix: Verify that EnsureTenant creates all necessary Gitea
  permissions and ArgoCD repo credentials for new tenants.
- **STATUS 2026-05-13:** RESOLVED ✓ — self-resolved via item G's YAML-aware manifest gate rewrite (in-file annotation: "After gate was made no-op, deploy succeeded in 186s"). No standalone E fix needed.

### F. Liveness probe kills non-leader pods during election
- Same as D above, but documenting the root cause chain:
  Leader election = 60s → HTTP server not started → liveness probe
  fails at 45s → pod killed → restart → election again → infinite loop.
- This means: with current config, you can NEVER have more than 1 API
  replica with the new image (12-attempt election).
- Definitive fix: Start HTTP server BEFORE leader election. The health
  endpoint should respond immediately. Background loops start only
  after election completes.
- **STATUS 2026-05-13:** IMPLEMENTED ✓ — same fix as item D. `api/cmd/main.go` runs `setupLeaderElection` in goroutine per MEET-ASYNC-AMENDMENT-2026-05-12-003. Non-leader probes return 200 because HTTP server is up before election completes.

## Learnings

1. Load testing exposes bugs that never appear in normal operation:
   - The manifest gate bug only affects NEW tenants, not existing ones.
   - Would have been a showstopper for first external user signup.

2. DB seed should be auth-only (users/tenants/members). Everything else
   through the real API to trigger the full provisioning chain.

3. The fixture bundle must match production structure exactly:
   - Root package.json + lockfile
   - Subdirectory app with proper path in loopzero.yaml
   - port field required for server apps

4. L1 Results — CLEAN RUN (10 tenants, concurrent):
   - 9/10 SUCCEEDED (90%)
   - 1/10 FAILED: restore-cache timeout (resource contention, 2 build nodes)
   - 0 infrastructure failures
   - 0 manifest gate blocks
   - 0 PG lock conflicts
   - Latency: 293s (fastest) to 521s (slowest)
   - loop-runtime-packs-runner v0.2.0 (Go binary) — all Dockerfile generations OK

   Previous L1 Results (10 tenants, concurrent):
   - 8/10 SUCCEEDED (80%)
   - 2/10 FAILED in generate-dockerfile (app fixture issue, not infra)
   - 0 infra failures with correct image
   - Latency: 186s (L0 single) to 275-331s (L1 concurrent)
   - 9 simultaneous builds on 2-node build cluster = OK
   - Zero PG lock conflicts, zero circuit breaker trips

5. The TenantController provisioning is fast (~30s for 10 tenants):
   - Gitea repos created
   - ArgoCD apps created
   - Build/runtime namespaces created
   - All automated via Tenant CR reconciliation
