# ADR: Deploy config model — services.json is the immutable app-shape; secrets + scaling are operational commands

**Date:** 2026-06-15
**Status:** Accepted (sponsor directive: "execute em nível FAANG o que é correto … máximo valor para os usuários")
**Context slice:** simplify-deploy-loopzerokit-runtime-wiring (surfaced while scoping T3.1b — deleting loopzero.yaml)
**Supersedes for the deploy config model:** the `loopzero.yaml` + `framework` deploy contract.

## Context

Closing F-dom-2 (runtime drives the build strategy) required the CLI to send `runtime` from `.loopzero/services.json`. Scoping the grill's D3 ("services.json is the ONLY input; delete loopzero.yaml") surfaced a design fork: `services.json` (LoopZeroKit's code-derived output) carries app shape — `name, runtime, type, port, env, build, start, proxy, dev, healthcheck, cors, dependsOn, openapi` — but NOT the deploy concerns `loopzero.yaml` carried: **secrets**, **scaling** (replicas/autoscaling), and per-service **path** (monorepo).

## Decision

Adopt the canonical PaaS separation (Vercel / Railway / Render / Fly.io): **immutable code-derived app-shape vs mutable operational state.**

1. **`.loopzero/services.json` is the single deploy INPUT — the immutable, code-derived app shape.** Generated by `loopzerokit build`, committed, immutable per commit. It is the only file `loopzero deploy` reads for app configuration. It MUST carry per-service **`path`** (monorepo location) — `path` is app-shape (LoopZeroKit knows it at generation time), unlike secrets/scaling. (Cross-repo LoopZeroKit schema addition; small + correct.)

2. **secrets → `loopzero secrets` + secret store (ESO/OpenBao).** Secrets are sensitive and environment-specific; they MUST NOT live in any committed file. Already shipped as J-22. `loopzero deploy` no longer validates/reads secrets from a deploy config file — the platform secret store is the source of truth.

3. **scaling → `loopzero scale` + platform state.** Replicas/autoscaling/HPA/KEDA are operational and mutable at runtime WITHOUT a redeploy. Already shipped as J-20. `loopzero deploy` no longer reads scaling from a deploy config file.

4. **`loopzero.yaml` + the `framework` field are deleted** — the build is keyed on `runtime` (F-dom-2, done on the API side: T1.1/T2.1), the app shape is `services.json`, and secrets/scaling are commands.

### Why this is FAANG-correct (maximum user value)

- **Security:** no secrets in git (the #1 PaaS footgun).
- **Operability:** scale without a redeploy; scaling is live state, not a build artifact.
- **Simplicity:** one code-derived manifest, generated by the framework — the user doesn't hand-maintain a deploy YAML.
- **Single source of truth per concern:** app shape (services.json) ≠ secrets (store) ≠ scaling (platform). No overlap, no drift.

## Alternatives considered

- **Extend services.json to carry secrets/scaling/path** — REJECTED for secrets (sensitive data in a committed file is a security anti-pattern) and scaling (operational state in an immutable build artifact forces redeploy-to-scale). Accepted ONLY for `path` (genuine app-shape).
- **Keep a minimal `loopzero-cloud.yaml` for deploy concerns** — REJECTED: reintroduces a second committed config file, contradicting D3 and the single-source-of-truth principle.

## Consequences (execution)

- **F-dom-2 functional fix is complete + separable** (API runtime dispatch + framework deletion + CLI sends runtime — T0.1/T1.1/T2.1/T3.1a, shipped). This slice's core value is delivered and can go to `/review` + LIVE on its own.
- **The config-model overhaul is a DISTINCT architectural slice** (the realization here exceeds the original grill's T3.1b assumption): make `services.json` the CLI config source, remove deploy's secrets/scaling-from-config, migrate the ~10 CLI files that read `loopzero.yaml` (status/promote/scale/preview/diagnostics/...), add `path` to the LoopZeroKit services.json schema, delete `loopzero.yaml`/`framework`/`loopzero-yaml.ts`. This is behavior-changing + cross-repo + LIVE-gated → it warrants its own `/grill-me` → `/to-plan` cycle rather than being bolted onto the bug-fix slice at the tail. **Scoping it as its own slice IS the FAANG-correct process** (don't gold-plate a bug-fix into a config overhaul under pressure).

## Follow-up

New slice: `deploy-config-services-json-app-shape` — grill the migration of the ~10 loopzero.yaml consumers + the LoopZeroKit `path` schema addition + the deploy secrets/scaling-from-config removal, then implement + LIVE-validate.
