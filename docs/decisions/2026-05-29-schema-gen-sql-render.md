## 1. Context

### 1.1 The schema-source problem

ADR-1 adopts sqlc as the canonical database access layer. sqlc requires a **schema source** to generate typed Go code: a single declared shape from which `INSERT` / `SELECT` / `Scan` triples are derived. There are two patterns supported by sqlc upstream:

- **Pattern (a) — direct migration-file parsing.** Set `schema: "db/migrations"` in `sqlc.yaml` and let sqlc's PostgreSQL parser walk the `.up.sql` files in order, materializing the schema in memory.
- **Pattern (b) — rendered post-replay artifact.** Replay all migrations against an ephemeral PostgreSQL instance, dump the resulting schema, and feed sqlc that single rendered file.

LoopZero's schema source of truth is the 20 forward-only `.up.sql` files under `api/internal/db/migrations/` (numbered 000001..000020; 000003 retired). golang-migrate is the canonical migrator in production: `infra/scripts/production/run-migrations.sh` invokes it against the DOKS managed PostgreSQL 16 instance. The migrations include PG-specific features:

- Partial indexes (e.g., 000008 `archive_stale_releases` excludes ARCHIVED from active queries via partial index)
- CHECK constraints with version-specific state-machine encodings (e.g., 000010 + 000011 add `ROLLING_BACK` / `ROLLED_BACK` states; 000020 enforces write-once for `image_attestation_rekor_url`)
- Custom types and trigger functions (e.g., audit-log triggers)

sqlc's built-in PostgreSQL parser is good but not bug-for-bug compatible with real PostgreSQL 16. Pattern (a) risks subtle misinterpretation. Pattern (b) feeds sqlc the **ground truth** as PostgreSQL itself sees it.

### 1.2 Why this is a separate ADR, not a footnote in ADR-1

The schema-render pipeline is a non-trivial new CI surface:

- New ephemeral PostgreSQL container in CI (small but real infra cost).
- New shell script `infra/scripts/ci/render-schema-gen-sql.sh` (which requires `.claude/rules/shell-scripts-allowlist.md` entry per D3 of the 2026-05-22 shell-script strategic plan).
- New `task quality:gates` participant for drift detection on `schema.gen.sql`.
- New version-pin coupling between CI and `infra/scripts/production/run-migrations.sh`.

Each of those four items is independently reviewable. Bundling them into ADR-1 would obscure them. Splitting them out keeps ADR-1 about the **decision** (sqlc) and lets ADR-2 own the **pipeline** that feeds it.

### 1.3 Why T3

The render pipeline touches:

- **Stack:** new ephemeral PG container in CI; new sqlc CLI dependency; new shell script.
- **Architecture:** how schema source of truth is materialized for code generation.
- **Critical flow:** the production migrator's version is pinned to the render pipeline's version. A mismatch silently produces a schema CI can't verify against production.

Per `.claude/rules/pre-release-governance.md`, this MUST pass through the full T3 meeting flow with mandatory ADR. MEET-2026-05-29-001 covered both ADR-1 and ADR-2 in one session; both VETO holders APPROVE conditional.

## 2. Decision

**Adopt Pattern (b): a CI job renders `api/internal/db/schema.gen.sql` from `golang-migrate up` against an ephemeral PostgreSQL 16 instance, then commits the rendered file. A CI gate fails if `git diff schema.gen.sql` after replay is non-empty. golang-migrate REMAINS the canonical migrator — production migration tool unchanged; only the rendered artifact is new.**

### 2.1 What this means concretely

- New script: `infra/scripts/ci/render-schema-gen-sql.sh` (registered in `.claude/rules/shell-scripts-allowlist.md`).
- New `task db:render-schema` target (per ADR-1 M-12) that wraps the script for local developer regeneration.
- New CI job that runs the script and verifies `git diff schema.gen.sql` is empty after replay.
- New file: `api/internal/db/schema.gen.sql` (committed, generated, headed with `// Code generated by golang-migrate replay against ephemeral PG 16. DO NOT EDIT.`).
- New `task quality:gates` participant `schemarender` (or similar) that calls the render script in `--verify` mode (compares against committed file without overwriting).

### 2.2 FAANG-grade reproducibility requirements

For the render to be a useful CI gate, it must be **byte-identical** across runners. Five requirements ensure this:

1. **PostgreSQL version pinned to 16** (matches DOKS managed prod). Specific minor version pinned in CI workflow (e.g., `postgres:16.3-alpine`). When DOKS bumps minor, CI bump is a coordinated PR.
2. **golang-migrate version pinned** in BOTH the CI render job AND `infra/scripts/production/run-migrations.sh` (per ADR-1 M-4). A version mismatch fails a dedicated CI gate (`pkg/quality/migrateversion/` or similar) — drift between CI render and production migrator is forbidden.
3. **sqlc CLI version pinned** in CI + documented in `docs/operations/dev-loop.md` for local regeneration (per ADR-1 M-3).
4. **`pg_dump --no-owner --no-privileges --schema-only`** + post-process to strip:
   - serial / identity sequence generation artifacts (timestamps, current values)
   - ALTER ... OWNER statements (security hygiene; CI role differs from prod role)
   - PostgreSQL version comment headers (vary by patch level)
   - Standard comments that PG inlines into dumps
5. **CI replay runs as a non-superuser role** with CREATE on a scratch schema only. Render must not require superuser to reproduce. This makes local developer reproduction possible against any modern PG 16 without elevated privileges.

### 2.3 What this does NOT change

- **golang-migrate stays canonical.** The production migration path is `infra/scripts/production/run-migrations.sh` → `migrate -path migrations/ -database "$POSTGRES_DSN" up`. Unchanged.
- **Migration files stay canonical.** `.up.sql` files under `api/internal/db/migrations/` remain the only place schema mutations are authored.
- **Production PostgreSQL is untouched by the render pipeline.** The render runs only against an ephemeral CI container.
- **No new state in production.** `schema.gen.sql` is a CI artifact committed to the repo; it never reaches production.

## 3. Alternatives Considered

| Option | Rationale | Why rejected |
|---|---|---|
| **Pattern (a) — direct migration-files parsing in sqlc** | Native sqlc support; no separate CI job; one less moving part | sqlc's PG parser may misinterpret PG-specific DDL (partial indexes, custom types, trigger functions, complex CHECK constraints). Replay against real PG 16 is ground truth. The migration history contains exactly these features (000008 partial index, 000010+11+20 CHECK constraints, audit-log triggers). |
| **Operator-captured schema (manual)** | Operator runs `pg_dump` against prod periodically and commits the result | Reproducibility nil. Operator drift is invisible. No CI gate possible. |
| **Schema dumped from prod periodically by CI** | Highest fidelity | Security risk (prod credentials in CI). Prod schema may diverge from migration set transiently during deploys. Couples CI to prod uptime. Rejected by Security & Blast Radius reviewer. |
| **Hand-authored schema.sql alongside migrations** | sqlc-native pattern for greenfield projects | LoopZero is not greenfield — 20 migrations exist. Hand-authoring would duplicate them and create a new drift class. |
| **Embed migrations into sqlc directly without rendering** | No new artifact in repo | Loses the CI gate (no committed file to diff against). Loses the developer-facing `task db:render-schema` reproducibility check. Loses auditability (what schema is THIS commit's code generated against?). |
| **Use PostgreSQL container via docker-in-docker without explicit pinning** | Less infra config | Reproducibility tax — minor version drift produces dump-format changes that look like real schema drift. Pinning is non-negotiable for byte-identical CI. |

## 4. Trade-offs Accepted

| Trade-off | Why accepted | Mitigation |
|---|---|---|
| New ephemeral PG container required in CI | Reproducibility ratchet + ground-truth schema source | Container is alpine-based and lightweight; lifecycle is per-CI-run; cost is seconds, not minutes |
| New shell script `infra/scripts/ci/render-schema-gen-sql.sh` | Must be in `shell-scripts-allowlist.md` per D3 of 2026-05-22 plan | Allowlist entry added in same PR; script is CI-orchestrator type (wraps `migrate` + `pg_dump`); justified under "Anti-Pattern #8 — CI orchestrators are acceptable shell" |
| `task quality:gates` execution-time budget grows | Render + diff is single-digit seconds; gate counter moves to 11 (+ ADR-1 sqlcsync) → 12 | Pre/post measurement in ADR-1 M-20; budget delta ≤ +20s acceptable for both gates combined |
| Developer onboarding adds one tool (sqlc CLI) | Don't-reinvent-the-wheel (Rule 9); same as ADR-1 | Documented in `docs/operations/dev-loop.md` per ADR-1 M-3 + M-22 |
| Version-pin coupling between CI render and `infra/scripts/production/run-migrations.sh` | Drift between them silently produces invalid CI schema | Dedicated CI gate enforces version match; mismatch fails fast |
| `schema.gen.sql` lives in repo as committed artifact | Generated files in repos can become noisy in diffs | Headed with `DO NOT EDIT`; CI gate fails on hand-edits; sqlc-generated files follow the same convention |

## 5. Consequences

### 5.1 Positive

- **Reproducibility ratchet.** Same migrations → same `schema.gen.sql`, byte-identical across runners. This makes the schema a reviewable artifact in every PR.
- **Correctness gate.** `git diff schema.gen.sql` empty after replay proves the migration set is self-consistent — no partial migrations, no drift between hand-authored and reality.
- **golang-migrate remains canonical.** Production migration path unchanged; the render artifact is purely a CI-side derivation.
- **Developer-facing.** New `task db:render-schema` lets contributors regenerate locally without waiting for CI.
- **Auditability.** Every commit can answer "what schema is this code generated against?" by inspecting `schema.gen.sql` at that commit.
- **Decouples sqlc fidelity from sqlc parser maturity.** sqlc parses the ground-truth dump, not the source migrations.

### 5.2 Negative (accepted)

- **New ephemeral PG container in CI.** Small infra cost, but real.
- **Render script enters shell allowlist.** D3 of 2026-05-22 plan tracks this; allowlist entry required.
- **Quality-gates execution-time budget grows.** Single-digit seconds; measured in ADR-1 M-20.
- **Version-pin discipline required.** golang-migrate version drift between CI and production migrator becomes a CI gate; missing the pin during a tool bump fails CI.

### 5.3 Risks (explicit, with mitigations)

| Risk | Severity | Mitigation |
|---|---|---|
| Ephemeral PG container is flaky in CI | Medium | Pinned alpine PG image; retry-budget configurable via CI runner; failure is visible (not silent) |
| `pg_dump` output format changes between PG 16 minor versions | Medium | Pin to specific 16.x patch; bump is a coordinated PR with `schema.gen.sql` regenerate |
| golang-migrate bug produces different schema in CI vs production | High | Version pin shared between CI and `infra/scripts/production/run-migrations.sh`; dedicated CI gate fails on mismatch |
| Render script accumulates business logic | Medium | Script kept ≤200 LOC; logic stays in `migrate` + `pg_dump`; post-process is awk/sed only |
| Developer accidentally edits `schema.gen.sql` by hand | Low | `DO NOT EDIT` header + CI gate fails on diff |
| sqlc CLI emits surprising code for a particular schema feature | Medium | Same risk-mitigation as ADR-1: pair-review per migrated store; escape to `api/internal/db/raw/` allowed with allowlist comment |

- **V2** (ADR-1): `schema.gen.sql` renders reproducibly: byte-identical output across 3 fresh CI runs.

| Phase | Description |
|---|---|
| V2.a | Run `task db:render-schema` locally on a clean checkout; verify `git diff schema.gen.sql` is empty |
| V2.b | Run `task db:render-schema` on a checkout with deliberate hand-edit to `schema.gen.sql`; verify CI gate detects the drift |
| V2.c | Run `task db:render-schema` after bumping `infra/scripts/production/run-migrations.sh` golang-migrate version without bumping CI; verify mismatch gate fires |
