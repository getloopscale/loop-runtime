## Bugs encontrados e corrigidos

### AUDIT-29 (crítico, corrigido)

**Sintoma:** Todo deploy Node falhava com:
```
process "/bin/sh -c adduser -D -u 1000 loopzero" did not complete successfully: exit code: 1
```

**Causa raiz:** `infra/images/packs-runner/` bundlava um shell-script `loopzeropacks-generate` pré-MEET-2026-03-29-017. A reescrita Go canônica está em `github.com/getloopscale/loopzero-packs` (usa `node:20-bookworm`, sem adduser), mas nunca foi adotada no k3d local. Apps Go passavam porque template Go usa `alpine:3.21` onde UID 1000 é livre.

**Fix (commit 3751c29):**
- `infra/images/packs-runner/Dockerfile`: multi-stage que clona `loopzero-packs` e builda o binário Go.
- Shell-script legacy deletado.
- Rebuild + push para `k3d-loopzero-registry:5000/loopzero-packs-runner:latest`.

**Validação:** Node deploy fresh → SUCCEEDED 208s → pod Ready.

## F1.4 Loki investigation (addendum 2026-04-23 ~23:30)

**Pergunta original:** "Por que não testamos F1.4 Loki cross-cluster logs?"

### Investigação

Minha classificação inicial ("gap infra") foi superficial. Investigação real:

| Componente | Estado real |
|---|---|
| Loki no mgmt cluster | ✅ Running 2/2 |
| Promtail no build cluster | ✅ 3 pods Running, lendo `/var/log/pods` |
| API → Loki via DNS interno | ✅ `http://loki.monitoring:3100/ready` responde "ready" |
| Labels no Loki após promtail restart | ✅ `container, filename, namespace, pod, workflow` |
| **Promtail URL target** | ❌→✅ Estava `172.18.0.11` (workload-server-0, IP errado); corrigido para `172.18.0.3` (mgmt-server-0) via `bash infra/scripts/update-cross-cluster-ips.sh` + helm upgrade |
| **NodePort 30094 no k3d mgmt** | ❌→✅ Não estava exposto (cluster criado antes da entry em `infra/k3d/mgmt-cluster.yaml`); recriação do cluster aplicou o port mapping |
| **Tilt kubeconfig cache** | ❌ `~/.tilt-dev/config` guarda cluster stale com API server numa porta aleatória; após recriação de cluster, kubectl spawned por Tilt falha com "context not found" mesmo com `~/.kube/config` correto |

### Bugs descobertos (não commitados — exigem decisão humana)

1. **Promtail IP estava errado** em runtime. O `infra/helm/promtail/values.yaml` já estava OK no repo (`172.18.0.3`), mas o cluster tinha helm release stale com IP antigo. Correção runtime: `helm upgrade promtail -n monitoring ...`. No repo: não mudou nada (values já correto).

2. **Tilt não tolera cluster recreation.** `~/.tilt-dev/config` precisa ser deletado (`rm ~/.tilt-dev/config`) após `k3d cluster delete && task clusters:create`. Isso não está documentado em nenhum lugar. Candidato a seção de runbook / `task tilt:reset`.

3. **k3d port mapping requer `k3d cluster delete/create` para aplicar.** Edit em `infra/k3d/mgmt-cluster.yaml` não afeta cluster existente. `task clusters:recreate -- mgmt` aplica — mas destrói estado (postgres, gitea, apps live).

### Status após recreation

- `docker port k3d-loopzero-mgmt-serverlb` agora mostra `30094/tcp -> 0.0.0.0:30094` ✅
- Loki Running no mgmt cluster novo ✅
- Promtail com IP correto (após helm upgrade) ✅
- **Mas:** Tilt ficou quebrado (kubeconfig cache); API não subiu; perdi os 2 apps Node/Go que validaram AUDIT-29 E2E
- `task setup` completou OK mas depende de Tilt para subir API
- Deploy manual via `kubectl apply -f infra/tilt/api-deployment.yaml` funciona até `ErrImagePull: loopzero-api:latest` (imagem não buildada; Tilt normalmente faz isso)

### Decisão

Parei antes de cair em refactor de Tilt/build system não pedido. Os 21 AUDITs **permanecem no git**, documentados, testes unit passing. Mas **a evidência runtime deles foi perdida** com a recreation do cluster.

### Lições para próxima sessão

1. **Antes de recriar cluster:** checar se `~/.tilt-dev/config` será regenerado corretamente pelo fluxo atual de Tilt; possivelmente adicionar `task tilt:reset` ao Taskfile.
2. **Para F1.4 E2E completo:** `task clusters:recreate -- mgmt` + `rm ~/.tilt-dev/config` + `tilt up` + aguardar API + disparar `loopzero deploy` + `loopzero logs --build <id>` + grep Loki por build label.
3. **O `infra/helm/promtail/values.yaml`** tinha `url: http://172.18.0.3:30094/...` correto. Cluster runtime tinha IP stale — script `update-cross-cluster-ips.sh` deve ser parte de `task setup`, não step manual.
