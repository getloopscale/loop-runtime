## Fixes sistêmicos shipped (cada um com commit isolado)

### Achado #17 — S0 produção — colisão K8s resource names entre projetos
**Commit**: `14c87203` `fix(manifests): project-scope K8s resource names to prevent collision`
- **Sintoma**: dois projetos com app de mesmo nome (`api`) colidem em Deployment/Service/Cert/IngressRoute. Service.spec.selector match cross-project (label-based).
- **Discovery**: journey-01 retornou body de pods do projeto anterior (compartilhamento de namespace tenant + selector label `app: api`).
- **Fix**: `manifests/renderer_helpers.go:resourceName(project, app) = "<project>-<app>"`. Aplicado em 9 sites (Deployment/Service/HPA/PDB/IngressRoute/Cert/ScaledObject/HTTPSO/Middleware). UX user-facing inalterado (hostname já contém project, loopzero logs/scale continuam usando label `loopzero.io/app-name`).
- **Test regression**: `renderer_collision_test.go:TestRender_NoCollisionBetweenProjectsWithSameAppName`.
- **Live validated**: journey-01/02/03 produziram resources project-scoped sem colisão.

### Achado #19 — S0 produção — ESO ClusterSecretStore não bootstrap em helmfile L2
**Commit**: `eee057fd` `fix(dogfood): bootstrap ESO ClusterSecretStore + journeys 03/06 + preflight T0.9`
- **Sintoma**: pods com `secrets:` declarado em loopzero.yaml ficavam CreateContainerConfigError. ESO ExternalSecret reportava "could not get ClusterSecretStore loopzero-mgmt-store: not found".
- **Discovery**: journey-03 secrets lifecycle quebrou no primeiro deploy.
- **Root cause**: `ClusterSecretStore loopzero-mgmt-store` é provisionado por Pulumi (`runtime-bootstrap.ts:288`) em prod, mas helmfile L2 (standalone-multi) não tinha paridade.
- **Fix**: `infra/helmfile/scripts/bootstrap-eso-cluster-secret-store.sh` (NEW) reproduz exatamente o que Pulumi faz: SA scoped + RBAC + long-lived token + Secret runtime + CSS. Idempotente.
- **Preflight**: T0.9 detecta regression se CSS sumir.
- **Live validated**: journey-03 secrets set/list/delete + ESO sync + Rule fail-fast — todos passaram após bootstrap.

### Achado #20 — S0 produção — sync_client filter desincronizado com Achado #17
**Commit**: `02bf5bf4` `fix(release-convergence): pass project-scoped resource name to ArgoCD health filter`
- **Sintoma**: TODAS releases SYNC_FAILED no DB mesmo com ArgoCD App Healthy + pod respondendo HTTP 200. `loopzero status` retornava `active_release: null`. `loopzero rollback` falhava com `NO_ACTIVE_RELEASE`.
- **Discovery**: journey-06 rollback.
- **Root cause**: second-order do Achado #17. `sync_client.go:329` faz match `appSet[res.Name]` onde res.Name é Deployment K8s name (project-scoped) mas appSet vem de raw `app.Name`. Match nunca acontece → matchedCount=0 → healthy=false → release stuck SYNC_FAILED até timeout 5min.
- **Fix**: `release_convergence_loop.go` linhas 250 e 428 passam `fmt.Sprintf("%s-%s", release.ProjectID, app.Name)` para deployedAppNames.
- **Live validated via API direta**: POST /api/v1/projects/versioned-app/rollback → 200 com `rolled_back_release: rel-c6a15...` + `reactivated_release: rel-dab68f...`. DB transitions corretas (v1 ACTIVE, v2 ROLLED_BACK).

### F7 — S0 — static_delivery silent-success eliminado
**Commit incluído em** `a1220eb2` (sessão anterior) + ADR-0019 `eee057fd`.
- Branch `if kvClient == nil { return nil }` substituído por fail-loud quando ambos kvClient e localProvisioner são nil.
- Nova interface `LocalStaticProvisioner` injectable.
- Novo type guard: safety net retorna nil quando 0 static apps no result.
- 3 testes regression.

### Achado #18 — migration legacy resources
**Documentado**: manifests gerados pré-Achado-#17 (com nomes antigos `web`, `api`) em projetos legacy bloqueavam ArgoCD sync após upgrade. Cleanup manual + re-deploy resolve. Em produção, migration script seria necessário.

### Achado #21 — Rollback v1→v2 manifest commit chain ✓ working but race-prone
- API direct rollback funciona ✅.
- Race condition entre journeys consecutivos sharing ArgoCD App pode causar revision mismatch warnings transient.
- Não é regressão de produto — é cluster-state pollution entre testes.

## Veredito GO/NO-GO

### NO-GO para release próxima sem rebuild + redeploy completo

**Razão**: bugs Achado #17 + Achado #20 afetam **TODO PaaS multi-tenant**. Em produção, hoje:
- Dois projetos no mesmo tenant env com app de mesmo nome (caso comum: `api`, `web`) colidem silenciosamente.
- Releases ficam SYNC_FAILED mesmo com cluster healthy → rollback impossível, loopzero status mente.

Esses bugs **estavam em produção** antes desta sessão. Não foi descoberta nova de produto — foi descoberta nova de **dogfood**. Cobertura unitária + componente passou; só dogfood real quebrou.

### GO se:
1. Os 6 commits desta sessão forem deployed em produção (`14c87203`, `02bf5bf4`, `eee057fd`, `a1220eb2`, `010cbd9c`, `fa60ef70`)
2. Migration script para resources legacy (Achado #18) for executado em prod (delete + re-deploy de cada projeto existente)
3. ESO ClusterSecretStore for verificado em DOKS (já provisionado por Pulumi, mas check explícito recomendado)
4. Journeys 4-11 + Phase 14 final completados em iteração subsequente

### Recomendação
- **Hold release** até journeys 4-11 (scale/promote/preview/admin) terem validação live em standalone-multi.
- **Patch release** dos 6 commits desta sessão para produção sem aguardar journeys faltantes — Achado #17 + #20 são show-stoppers, prioridade alta.
- **CSS bootstrap** deveria virar parte do helmfile mainline (não script separado) na próxima iteração de bootstrap.
