## Problem Statement

ArgoCD sync has been the #1 failure point across 7+ rounds of fixes spanning months:
1. Wrong cluster targeting (BLOCKER-1)
2. Cross-environment contamination (shared Application path) (BLOCKER-2/3)
3. Expired session tokens (24h TTL) broke all deploys
4. Resource name collisions (RepeatedResourceWarning)
5. Static app timeouts (no Deployment to health-check)
6. Circuit breaker redesign (DB to in-memory)
7. RELEASING state for crash recovery
8. **Current (2026-03-27): 100% deploy failure due to sync timeout, 19 orphaned pods**

## Critical Bug Discovered During Meeting

### Sync Policy Contradiction (CRITICAL — Pre-existing)

**The operator provisioner and the Helm template disagree on sync policy:**

| Component | Sync Policy | File |
|-----------|-------------|------|
| `real_provisioner.go:164-168` | `selfHeal: true, prune: true` (AUTO-SYNC) | Operator code (runs in production) |
| `tenant-app-template.yaml:35` | `automated: null` (MANUAL SYNC) | Helm template (documentation) |
| `argocd_app_test.go:124-128` | Asserts `automated: null` | Infra test (contradicts production) |
| `values.yaml:99` | `controller.self.heal.enabled: false` | Global config (contradicts provisioner) |

**Impact:** The provisioner wins (it creates the Applications). ArgoCD Applications currently have auto-sync enabled. The API also triggers manual sync via `POST /sync`. This creates a **race condition**: auto-sync may sync the old Git revision while the API just pushed a new one.

### Rollback ArgoCD App Name Mismatch (HIGH)

**`container_delivery.go:136` uses `ProjectName` for rollback, not `TenantID`:**
```go
// Rollback uses:
argoAppName := fmt.Sprintf("%s-%s", req.ProjectName, req.Environment)  // e.g., "my-saas-production"

// Deploy uses:
argoAppName := fmt.Sprintf("%s-%s", build.TenantID, build.Environment)  // e.g., "acme-production"
```

The rollback sync trigger hits a non-existent Application. This is a **silent rollback failure**.

## Key Findings by Agent

### Principal Architect
> "ArgoCD is the wrong tool for the job LoopZero needs it to do. LoopZero is doing procedural deployment wearing a GitOps costume."

- The API pushes to Git, then immediately calls POST /sync, then polls. This is `kubectl apply` with extra steps.
- True GitOps: push to git, reconciler converges autonomously.
- **Recommendation:** Remove ArgoCD from deploy hot path. API applies directly via server-side apply. ArgoCD becomes drift detector.

### GitOps/Delivery Engineer
> "LoopZero uses Gitea as a write-through cache, not a source of truth. The spec itself states PostgreSQL is canonical."

- ArgoCD provides 3 capabilities: sync trigger, health polling, AppProject RBAC.
- Sync trigger = `kubectl apply`. Health polling = watch Deployments. Only AppProject RBAC is unique.
- **Recommendation:** Fix the model contradiction. Switch to auto-sync with webhook callbacks.

### Distributed Systems Engineer
> "The API goroutine blocks for 600s in WaitForSync. 10 slow syncs saturate the semaphore and stall ALL builds for ALL tenants."

- Phase D (600s sync wait) blocks the reconcile loop semaphore.
- No commit SHA verification after sync — ArgoCD could sync wrong revision.
- Releases stuck in PENDING have no convergence loop (only builds have reconcile + reaper).
- **Recommendation:** Decouple Phase D into async Release Convergence Loop.

### SRE (VETO)
> "Deploy fails 100%. Health check says OK. Rollback lies about success. System is non-functional."

- `/api/v1/health` returns 200 while 0% of deploys succeed (lying health check).
- `/api/v1/health/deep` only checks PostgreSQL, not ArgoCD/Gitea/Argo Workflows.
- Rollback sync failure is swallowed — rollback "succeeds" while cluster unchanged.
- 6 critical failure modes have no alerting.
- **VETO until:** Deep health verifies all deps, orphans cleaned, rollback verified.

### DX Engineer (BLOCKS DELIVERY)
> "2/10 against Vercel quality bar. 5-10 minute feedback black hole."

- API emits `deploy.delivering`, `deploy.verifying`, `deploy.live` SSE events — CLI drops all 3.
- Error suggestion (`loopzero logs`) leads to dead end (Loki not deployed).
- 600s timeout = user waits 10 minutes with zero feedback before failure.
- Internal term `"argocd wait: sync timeout"` leaks to CLI via `reason` field.
- **BLOCKS DELIVERY until:** SSE events wired, error reasons sanitized.

## Chosen Approach: Progressive ArgoCD Reform (3 Phases)

**Architecture:** Keep ArgoCD but systematically fix the model mismatch and decouple sync from the request path.

### Rationale for NOT replacing ArgoCD:

1. ArgoCD is already deployed, configured, and understood by the team.
2. The root causes are configuration bugs (sync policy contradiction, name mismatch) and coupling patterns (synchronous wait), not ArgoCD itself.
3. Replacing ArgoCD mid-product-development would cost 2-4 weeks with high risk.
4. The direct-apply alternative (Architect's Option B) requires building a Deployment rollout watcher, health aggregator, and credentials management — all things ArgoCD already does.

### Phase 0 — Emergency Fixes (P0, 1-2 days)

Fix the bugs that make 100% of deploys fail RIGHT NOW.

| # | Action | Owner | File |
|---|--------|-------|------|
| **0.1** | Fix sync policy: change provisioner to `automated: null` (manual sync) matching Helm template and test | operator-engineer | `operators/internal/argocd/real_provisioner.go:164-168` |
| **0.2** | Fix rollback app name: use `TenantID`, not `ProjectName` | api-engineer | `api/internal/services/container_delivery.go:136` |
| **0.3** | Clean 19 orphaned pods manually. Force ArgoCD sync with prune. | infra-engineer | kubectl + ArgoCD CLI |
| **0.4** | Verify deploy succeeds E2E after 0.1-0.3 | orchestrator | `loopzero deploy --json` + Prova de Vida |

### Phase 1 — Decouple & Harden (P1, 1-2 weeks)

Make the sync path resilient.

| # | Action | Owner | File |
|---|--------|-------|------|

## Alternatives Rejected

| Alternative | Reason |
|-------------|--------|
| **Argo Rollouts now** | Unanimous rejection. Progressive delivery on broken sync = more failure modes. Revisit after 30 days of 95% success. |
| **Direct kubectl apply** | Correct long-term direction but too much scope now. Requires Deployment watcher, health aggregator, credential management. ArgoCD does all of this. Revisit if Phase 1 fails. |
| **Flux CD** | Same model mismatch. Flux is designed for continuous reconciliation. Would need same decoupling work. |
| **Auto-sync + webhooks** | GitOps Engineer's proposal is technically sound but requires notification-controller deployment, webhook endpoint in API, and changes the entire sync model. Higher risk than fixing the current manual sync. Consider as Phase 3 evolution. |

---

## Trade-offs Accepted

1. **ArgoCD remains a dependency.** We accept the operational overhead of ArgoCD in exchange for not rebuilding rollout watching, health aggregation, and RBAC isolation.
2. **Manual sync (not auto-sync).** We fix the provisioner to match the documented manual sync model. This means the API controls deploy timing precisely, at the cost of no drift detection between deploys.
3. **Async deploy feedback.** Phase D becomes async, meaning `loopzero deploy --wait` returns faster (after gitops push, not after sync). The CLI receives sync status via SSE. Users see intermediate states instead of a black hole.
4. **180s sync timeout (down from 600s).** Reduces wait time but means monorepos with slow image pulls may time out. Mitigation: pre-pull images or increase per-environment.
