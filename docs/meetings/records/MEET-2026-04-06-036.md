## Stage 1 — Context

**Problem:** DigitalOcean blocks SMTP ports 25, 465, and 587 on ALL Droplets and DOKS nodes. This is a permanent, documented restriction that cannot be lifted. MEET-035 added a Kratos-scoped NetworkPolicy for ports 465/587, but the underlying DO-level block means SMTP will never work regardless of NetworkPolicy rules. Kratos currently cannot send verification emails, recovery emails, or any transactional email.

**Decision Required:** How should Kratos deliver email on DigitalOcean when SMTP is permanently blocked? Specifically: (1) Which integration pattern — native HTTP courier, cloud service webhook proxy, or SMTP relay sidecar? (2) What is the exact configuration? (3) How is the Resend API key managed securely?

**Constraints:**
- DigitalOcean permanently blocks ports 25, 465, 587 on all nodes (documented policy)
- Port 443 (HTTPS) IS allowed and already in the NetworkPolicy egress allow-list
- Resend is the chosen email provider (API key already provisioned)
- Kratos v1.3.1 (Helm chart v0.59.0) deployed in `platform-system` namespace
- The cloud Go service exists at `cloud/` with chi router, already deployed to mgmt cluster
- Pre-release: backward compatibility not required; cleanest design preferred

**Known Context:**
- MEET-035: diagnosed as NetworkPolicy issue, but DO itself blocks SMTP — NetworkPolicy fix is necessary but insufficient
- `infra/helm/ory-kratos/values.yaml`: current SMTP courier config (lines 109-115)
- `infra/pulumi/src/components/mgmt-bootstrap.ts` lines 540-555: Pulumi overrides for courier config
- `infra/pulumi/src/config/stack.ts` lines 79-81, 165-168: `smtpConnectionUri` config field
- `cloud/cmd/main.go`: cloud service entry point (Go + chi)
- Kratos docs: `courier.delivery_strategy: http` sends POST to a webhook endpoint

**Proposal:** Three options under evaluation:
- **Option A:** Kratos native HTTP courier (`delivery_strategy: http`) + Jsonnet body template calling Resend directly
- **Option B:** Webhook handler in the cloud Go service (`/internal/send-email`)
- **Option C:** SMTP-to-HTTP relay sidecar container

---

## Stage 2 — Analyses

### Principal Architect

**Assessment:** The initial analysis favored Option A+B (HTTP courier to a cloud service webhook). However, deeper investigation of Kratos HTTP courier revealed that Kratos supports Jsonnet body templates in `courier.http.request_config.body`, which can format the request body to match ANY HTTP API format — including Resend's `{from, to, subject, html}`.

This means Kratos can call Resend directly with zero intermediary code. The cleanest architecture is pure configuration.

**Risks identified:**
1. (medium) Kratos HTTP courier payload format must be validated against actual Kratos v1.3.1 behavior
2. (low) Jsonnet template correctness — wrong template means silent delivery failure

**Objections:** None.

**Recommendation:** Option A (pure Kratos config with Jsonnet template). Zero new code.

**Conditions for approval:**
1. Verify Kratos HTTP courier Jsonnet template context variables from Kratos source/docs
2. Resend API key managed via Pulumi secrets
3. Integration test before production deploy

**Impact if ignored:** Email delivery permanently broken. No verification, no recovery, no account security.

### Platform Security Engineer

**Assessment:** Option A (pure config) is strictly superior from a security perspective:

1. **Eliminates SMTP attack surface entirely.** No SMTP ports need to be opened.
2. **API key in Kratos config is acceptable** — same security posture as the SMTP password was (injected via Pulumi secret, never in Git).
3. **No new services** — no webhook means no new attack surface.
4. **Kratos admin API** is ClusterIP only (not externally exposed), and `leak_sensitive_values: false` prevents API key leakage.

**Risks identified:**
1. (high) Resend API key MUST be stored as Pulumi secret, injected into Helm values. NOT in Git.
2. (medium) Remove the SMTP NetworkPolicy from MEET-035 — dead code opening ports for no purpose.

**Objections:** None — pure config is simpler and more secure than a webhook.

**Recommendation:** Option A. Remove SMTP NetworkPolicy.

**Conditions for approval:**
1. Resend API key sourced from `pulumi config set --secret resendApiKey`
2. SMTP NetworkPolicy removed
3. `leak_sensitive_values: false` verified in Kratos config

**Impact if ignored:** Dead NetworkPolicy rules open unused ports.

### SRE/Production Engineer

**Assessment:** Option A is operationally the simplest — zero new deployments, zero new containers, zero new services to monitor. Kratos courier has built-in queue and retry for failed deliveries.

**Risks identified:**
1. (medium) If Jsonnet template is wrong, deliveries fail silently until someone checks courier logs
2. (low) Resend rate limits — pre-release volumes are well below free tier

**Objections:** None.

**Recommendation:** Option A. Monitor Kratos courier logs for HTTP response codes after deployment.

**Conditions for approval:**
1. After deployment: verify courier logs show HTTP 200 from Resend
2. Trigger a test registration and confirm email delivery

**Impact if ignored:** Blind to delivery failures.

### API/Domain Architect

**Assessment:** Pure configuration is the right approach. No code in the cloud service for email translation — this keeps the cloud service focused on its actual responsibilities (auth, consent, billing).

**Risks identified:**
1. (low) Scope creep — resist the temptation to add email features later. Kratos owns email delivery.

**Objections:** None.

**Recommendation:** Option A. If in the future Kratos needs richer email capabilities (e.g., custom templates beyond what Kratos supports), revisit then.

**Conditions for approval:** None additional.

**Impact if ignored:** Unnecessary code in cloud service.

## Stage 3 — Confrontation

### Conflict 1: Pure Config (Option A) vs Webhook (Option B)

| Agent | Position |
|-------|----------|
| Principal Architect | Pure config — Kratos Jsonnet templating eliminates need for webhook |
| Platform Security Engineer | Pure config — fewer moving parts, less attack surface |
| SRE/Production Engineer | Pure config — no new services to monitor |
| API/Domain Architect | Pure config — keeps cloud service focused |

**Analysis:** Initial analysis assumed Kratos HTTP courier sends a fixed payload format requiring translation. Investigation revealed Kratos supports Jsonnet body templates, enabling direct Resend API calls. This makes the webhook handler unnecessary.

**Resolution:** Unanimous agreement on pure config. No dissent.

### Conflict 2: Remove vs Keep SMTP NetworkPolicy from MEET-035

| Agent | Position |
|-------|----------|
| Platform Security Engineer | Remove — dead code opening ports for no reason |
| SRE/Production Engineer | Initially wanted to keep as fallback |
| Principal Architect | Remove — YAGNI, misleading to keep |

**Resolution:** Remove. DO blocks SMTP permanently. The NetworkPolicy opens ports that can never be used. Keeping it suggests SMTP works when it does not. If a future provider needs SMTP, it can be re-added.

### Consensus Challenge (Orchestrator)

All agents agree on pure config. Challenging:

1. **What if Kratos Jsonnet template context does not expose the rendered HTML body?** If Kratos only exposes raw template data (not rendered HTML), the Resend API call would fail.
   - **Mitigation:** Verify from Kratos source code. The HTTP courier is specifically designed to send rendered emails, so the body SHOULD be available. Test in dev before production.

2. **What if Resend rejects the request format?** Minor field mismatches (e.g., `to` as string vs array) could cause 422 errors.
   - **Mitigation:** Resend API docs specify `to` accepts both `string` and `string[]`. Test with actual API call.

3. **What if Kratos courier retry storms Resend on transient 5xx?** Kratos retries with backoff, but aggressive retry could hit rate limits.
   - **Mitigation:** Kratos default courier retry is reasonable (exponential backoff). Monitor after deployment.

4. **What about email templates?** Kratos has built-in templates for verification, recovery, etc. Do they render correctly for HTTP delivery?
   - **Mitigation:** Kratos renders templates identically for SMTP and HTTP. The courier layer only changes the delivery mechanism, not the rendering.

## Stage 4 — Decision

**Chosen:** Pure Kratos HTTP courier configuration (Option A). Kratos calls Resend HTTP API directly using `courier.delivery_strategy: http` with Jsonnet body template. Zero new code. Configuration-only change in Helm values and Pulumi overrides.

**Rejected:**

| Alternative | Reason |
|-------------|--------|
| Option B (cloud service webhook) | Unnecessary — Kratos Jsonnet templating can format Resend API requests directly. Extra code, extra failure point, zero benefit. |
| Option C (SMTP relay sidecar) | Adds container, still requires SMTP ports (blocked by DO), adds latency and failure modes. |
| Keep SMTP config | Non-functional. DO permanently blocks SMTP ports. Emails never delivered. |

**Trade-offs consciously accepted:**
1. Resend API key embedded in Kratos config (via Pulumi secret). Same posture as SMTP password.
2. No buffering between Kratos and Resend. Accepted — Kratos courier has built-in queue/retry.
3. Tight coupling to Resend API format in Jsonnet template. Accepted — switching providers requires template change anyway.

**Risks Accepted:**

| Resend API key leaked via Kratos admin API | low | Admin API is ClusterIP only; `leak_sensitive_values: false` | Security |
| Resend rate limits | low | Monitor delivery; upgrade plan if needed | SRE |
| Kratos HTTP courier behavior differs from docs | medium | Integration test before production | Infra Engineer |

**Risks Blocked:** None.

## Appendix: Kratos HTTP Courier Configuration Reference

The Kratos HTTP courier uses `courier.delivery_strategy: http` with a `request_config` that supports Jsonnet body templates. The template receives the rendered email content from Kratos and formats it for the target HTTP API.

Key Kratos config structure:
```yaml
courier:
  delivery_strategy: http
  http:
    request_config:
      url: https://api.resend.com/emails
      method: POST
      headers:
        Authorization: "Bearer <resend-api-key>"
        Content-Type: "application/json"
      body: "base64://<jsonnet-template>"
```

Resend API expected format:
```json
{
  "from": "LoopZero <noreply@loopzero.example>",
  "to": ["recipient@example.com"],
  "subject": "Verify your email address",
  "html": "<rendered HTML>"
}
```

**IMPORTANT:** The exact Kratos Jsonnet template context variable names must be verified against Kratos v1.3.1 source code before implementation. Check the Ory Kratos courier HTTP documentation for the template data model.
