## Background

An external consultant reviewed the LoopZero deploy flow and produced 7 recommendations:

1. Git Push is in the critical path — GitOps adds latency, contention, and indirection
2. ArgoCD Sync as primary convergence — polling-based, slow for PaaS UX
3. CLI→API is synchronous deploy — should be 202 Accepted + event stream
4. Manifest render coupled to Git — should be deterministic pure function
5. Callbacks are fragile — should use persisted event log
6. Release activation not separate from deploy complete
7. No durable state machine — needs explicit states

Consultant's recommended architecture: remove Git from hot path, replace ArgoCD with direct-apply controller, use Git as async audit mirror.

Key quote: "Git é trilha de auditoria; o control plane é quem orquestra a verdade operacional."

---

## Stage 1 — Context

**Problem:** Evaluate whether LoopZero's deploy pipeline architecture needs fundamental changes based on an external consultant's 7-point critique.

**Decision Required:** For each recommendation: (a) is the critique valid? (b) act now or defer? (c) if acting, what's the minimal change?

**Constraints:**
- Pre-release, ~1 tenant. Target: thousands, not millions.
- Platform works E2E today (git push → auto-deploy → live in ~4min).
- Solo developer — capacity is the bottleneck.
- Pre-release: breaking changes are acceptable but costly.

**Known Context:**
- Build state machine: QUEUED→RUNNING→RELEASING→SUCCEEDED/FAILED with timeouts (`pkg/statemachine/build.go`)
- Release state machine: READY→PENDING→ACTIVE with GIT_MIRROR_FAILED, SYNC_FAILED recovery (`pkg/statemachine/release.go`)
- BuildReconcileLoop polls Argo Workflows — NOT HTTP callbacks (`api/internal/services/build_reconcile_loop.go`)
- ReleaseConvergenceLoop polls ArgoCD for PENDING releases (`api/internal/services/release_convergence_loop.go`)
- SSE events persisted in PostgreSQL with NOTIFY/LISTEN (`api/internal/sse/event_store.go`)
- Advisory locks on (tenant, project, environment) for all mutations
- 202 Accepted on build submission with SSE stream URL
- Manifest render is a pure function (`api/internal/manifests/render.go`)
- DeliveryActivator is polymorphic: container vs static (MEET-009)
- Known production issues: ArgoCD stuck on Certificate Progressing, revision mismatches, ~2s Gitea latency

## Stage 2 — Analyses

### Principal Architect

**Assessment:** The consultant's analysis has merit in its principles but is calibrated for Google/Meta scale (millions of deploys/day), not a pre-release PaaS targeting thousands of users.

5 of 7 points are factually incorrect about what LoopZero already has:
- Point 3 (synchronous CLI): Already 202 + SSE
- Point 4 (manifest coupled to Git): manifests.Render() is a pure function
- Point 5 (fragile callbacks): PostgreSQL event store with NOTIFY/LISTEN, BuildReconcileLoop replaces HTTP callbacks
- Point 6 (activation not separate): Build and Release are separate state machines
- Point 7 (no durable state machine): 7 state machines in pkg/statemachine/, all PostgreSQL-backed

Point 1 (Git in critical path) is partially valid — 2s latency is negligible but Git push failure blocks releases. The GIT_MIRROR_FAILED state handles this correctly.

Point 2 (ArgoCD convergence) identifies a REAL issue — per-tenant Application blast radius.

**Risks:** [medium] ArgoCD per-tenant Application blast radius at 1000+ tenants; [low] Gitea SPOF in release path
**Recommendation:** Reject wholesale rewrite. Cherry-pick per-project ArgoCD Applications as the one actionable improvement.
**Conditions:** No approval for full rewrite. Targeted improvements only.
**Impact if ignored:** ArgoCD contention at scale. Future problem, not launch blocker (except blast radius).

### Distributed Systems Engineer

**Assessment:** The consultant's core insight (Git in critical path introduces synchronous dependency) is loopzeroretically correct but severity is wrong for LoopZero's scale.

Current convergence model analysis:
- BuildReconcileLoop (polling Argo Workflows): Correct — build plane is observed, not called back
- ReleaseConvergenceLoop (polling ArgoCD + notifications): Belt-and-suspenders convergence
- SSE EventStore (PostgreSQL + NOTIFY/LISTEN): IS a durable event log

Real distributed systems concern: per-tenant ArgoCD Application blast radius. One degraded resource (Certificate stuck Progressing) blocks ALL deploys to that tenant. Production-validated issue.

The proposed RECEIVED→VALIDATED→RENDERED→STAGED→APPLYING→CONVERGED→ACTIVE is equivalent to our Build(QUEUED→RUNNING→RELEASING) + Release(READY→PENDING→ACTIVE) with different naming. We are not missing states.

**Risks:** [high] Per-tenant ArgoCD Application blast radius; [medium] Gitea availability
**Objections:** "Direct apply controller" replaces battle-tested ArgoCD with custom code — violates KISS
**Recommendation:** Keep ArgoCD, keep Gitea. Fix blast radius with per-project Applications.
**Impact if ignored:** Cascading deploy failures at multi-tenant scale.

### SRE/Production Engineer

**Assessment:** The system works. The consultant is 80% wrong about what we have, 20% right about what hurts.

Current operational state (honest):
- Build failures: Well-handled (BuildReaper, BRC-003 retry limits, timeout safety nets)
- Release failures: GIT_MIRROR_FAILED, SYNC_FAILED with explicit recovery. ReleaseReaper for stuck PENDING.
- SSE events: PostgreSQL-backed, survives API restart. NOTIFY/LISTEN for real-time.
- ArgoCD stuck Certificate: THIS IS THE REAL PROBLEM. Production-validated.

Priority order for fixes:
1. **[P0] Per-project ArgoCD Applications** — Eliminate blast radius. MUST before multi-tenant.
2. **[P2] Gitea push timeout tuning** — Faster GIT_MIRROR_FAILED retry loop.
3. **[P3] Convergence loop scaling** — Optimize at 1000+ tenants with real data.

**Risks:** [critical] Per-tenant ArgoCD Application blast radius
**Objections:** VETO on any rewrite of convergence system before launch. VETO on replacing ArgoCD with custom code.
**Recommendation:** Fix blast radius surgically. Ship everything else as-is.
**Conditions:** (1) No ArgoCD replacement. (2) Per-project migration must have rollback path. (3) No state machine changes.

### Platform Security Engineer

**Assessment:** The "remove Git from hot path" recommendation raises a critical security concern.

Current audit chain: deploy request → build → manifest commit (Git SHA) → ArgoCD sync from commit → runtime state. Unbroken chain. Verifiable.

If Git becomes async mirror:
- Window where runtime state has no Git record
- If async mirror fails: deployed state with no audit trail
- Drift detection impossible during async gap
- Compromised API could deploy arbitrary manifests without Git verification

Git is NOT just audit — it's defense-in-depth. ArgoCD syncs FROM Git, so deployed state is what Git says, not what the API says.

**Risks:** [critical] Removing Git from hot path eliminates defense-in-depth; [high] Async mirror creates unaudited window
**Objections:** **VETO** on any design that allows deploys without synchronous Git recording. Git-then-apply is a security invariant.
**Recommendation:** Keep Git synchronous. Fix blast radius. Do NOT decouple Git from deploy hot path.
**Conditions:** (1) Git push MUST remain synchronous before ArgoCD sync. (2) GIT_MIRROR_FAILED must remain blocking. (3) Commit-SHA-to-runtime audit chain must be maintained.
**Impact if ignored:** SOC 2 / ISO 27001 audit failure for multi-tenant PaaS without synchronous audit trail.

### DX Engineer

**Assessment:** The current deploy UX is good:
1. `loopzero deploy` returns immediately (202 Accepted)
2. SSE stream shows build progress in real-time
3. Build errors are clear and actionable
4. Deploy completes with clickable URL

Consultant's DX-relevant critique: "CLI→API is synchronous" — factually wrong. Already async.

Deploy latency (~4min) is competitive with Vercel/Railway. The 2s Gitea push is invisible to users.

**Risks:** [low] No DX emergency
**Recommendation:** No changes needed. Focus engineering on features users need (preview environments, `loopzero promote`).
**Conditions:** Any architectural changes must not degrade current deploy UX.

### API/Domain Architect

**Assessment:** The API boundary is already correctly designed:
- `POST /api/v1/builds` returns 202 + build_id + stream_url (command API)
- Build lifecycle managed by BuildOrchestrator + BuildReconcileLoop (not request handler)
- Release lifecycle managed by DeliveryActivator + ReleaseConvergenceLoop (not API)
- API is a thin command-acceptance layer — exactly what the consultant recommends

The consultant's proposed merged state machine (RECEIVED→...→ACTIVE) would merge Build and Release. Opposed because:
- Build and Release have different lifecycles
- Releases can be reactivated (rollback), builds cannot
- Separate machines reflect physical reality (build plane ≠ workload plane)
- Easier to test and reason about

**Risks:** [low] API boundary is clean
**Recommendation:** No API boundary changes needed.
**Conditions:** Build and Release must remain separate state machines.

## Stage 3 — Confrontation

### Conflict 1: Should Git be removed from the deploy hot path?

| Agent | Position |
|-------|----------|
| Principal Architect | Git in hot path adds risk but marginal latency. Defer removal. |
| Distributed Systems | Git should stay. Drift detection and convergence require it. |
| Security | **VETO on removal.** Git is a trust boundary and audit chain. |
| SRE | Keep Git. GIT_MIRROR_FAILED handles failures. Don't create new failure modes. |

**Resolution:** UNANIMOUS — Git stays. Security veto is absolute. 2s latency is irrelevant vs 240s total. Git is a security boundary, not a performance optimization.

### Conflict 2: Should ArgoCD be replaced with a direct-apply controller?

| Agent | Position |
|-------|----------|
| Principal Architect | No. Battle-tested tool. Replacement introduces years of edge cases. |
| Distributed Systems | No. Drift detection and convergence would be lost. |
| SRE | **Absolutely not.** Highest-risk change possible. |
| DX | No. Users don't care about internal convergence. |

**Resolution:** UNANIMOUS — ArgoCD stays. "Direct apply controller" rejected as high-risk, high-cost, low-benefit.

### Conflict 3: Is per-tenant ArgoCD Application blast radius worth fixing NOW?

| Agent | Position |
|-------|----------|
| SRE | YES. Launch blocker for multi-tenant. Production-validated issue. |
| Principal Architect | Yes, but T2 change requiring careful migration design. |
| Distributed Systems | Yes. One resource affecting all projects is a correctness violation. |
| Security | Yes. Project isolation within a tenant is a security concern. |

**Resolution:** UNANIMOUS — Per-project ArgoCD Applications is the one change worth making. Priority: HIGH. Requires dedicated meeting for migration design.

| Agent | Response |

| SRE | Ship and measure. Premature optimization without data is worse. |

## Stage 4 — Decision

**Chosen:** SELECTIVE IMPROVEMENT — Accept 1 of 7 consultant points, reject 6.

| # | Consultant Point | Verdict | Rationale |
|---|---|---|---|
| 1 | Git in critical path | **REJECT** | 2s/240s = 0.8%. Security VETO on removal. GIT_MIRROR_FAILED handles failures. |
| 2 | ArgoCD convergence | **PARTIALLY ACCEPT** | ArgoCD stays. Per-project Applications needed for blast radius. |
| 3 | Synchronous CLI→API | **REJECT (already done)** | 202 + SSE already implemented. |
| 4 | Manifest coupled to Git | **REJECT (already done)** | manifests.Render() is a pure function. |
| 5 | Callbacks fragile | **REJECT (already done)** | PostgreSQL event store + NOTIFY/LISTEN. BuildReconcileLoop. |
| 6 | Activation not separate | **REJECT (already done)** | Separate Build + Release state machines. ActivateReleaseKernel. |
| 7 | No durable state machine | **REJECT (already done)** | 7 state machines in pkg/statemachine/, PostgreSQL-backed, with timeouts. |

**Alternatives rejected:**
- Full rewrite to direct-apply controller — replaces battle-tested ArgoCD with custom code
- Async Git audit mirror — Security VETO (removes trust boundary, breaks audit chain)
- Merged Build+Release state machine — violates physical reality of separate planes

**Trade-offs consciously accepted:**
1. Git push adds ~2s — accepted (security > 2 seconds)
2. ArgoCD polling adds ~10-30s to convergence — accepted (drift detection is worth it)
3. Per-tenant ArgoCD Application continues temporarily — accepted until per-project migration

**Risks accepted:**
- [medium] Convergence loop scaling at 1000+ tenants — Mitigation: indexes, batch API calls. Owner: API Engineer. Timeline: 100+ tenants.
- [medium] Gitea write contention at high concurrency — Mitigation: Gitea HA or push queue. Owner: Infra Engineer. Timeline: 50+ concurrent deploys.
- [low] BuildReconcileLoop API calls at scale — Mitigation: K8s informers. Owner: API Engineer. Timeline: 200+ concurrent builds.

**Risks NOT accepted (blocking):**
- [critical] Per-tenant ArgoCD Application blast radius — Must be fixed before multi-tenant launch. Requires dedicated design meeting.

**Mandatory Actions:**
1. **[P0]** Schedule dedicated meeting for per-project ArgoCD Application migration design. Owner: Meeting Orchestrator.
2. **[P2]** Profile convergence loop performance at 100 tenants. Owner: SRE Engineer.
3. **[P3]** Write ADR documenting deploy flow architecture rationale and scaling limits. Owner: Principal Architect.

**Vetoes:**
- Security: VETO on removing Git from deploy hot path. Condition to lift: never (Git-then-apply is an invariant).
- SRE: VETO on replacing ArgoCD with custom code. Condition to lift: never (at current scale).
- SRE: VETO on rewriting convergence system before launch.

## Summary

The consultant's report identified mostly problems that LoopZero already solved (5 of 7 points), one non-problem framed as a problem (Git latency), and one real issue (ArgoCD blast radius). The recommendation to remove Git from the hot path and replace ArgoCD with a custom controller is rejected as high-risk architectural astronautics inappropriate for the platform's scale.

The one actionable finding — per-tenant ArgoCD Application blast radius — is accepted as a real production concern that needs a dedicated design meeting before multi-tenant launch.

**Key takeaway:** The LoopZero deploy pipeline is architecturally sound for its target scale. The state machines, event persistence, async patterns, and failure handling are already at a level the consultant assumed was missing. The priority should be shipping features (preview environments, promote) and fixing the one real blast radius issue, not rewriting working infrastructure.
