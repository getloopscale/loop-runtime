## Stage 1 — Context

**Problem:** The LoopZero dashboard auth (Ory Kratos v1.3.1, Helm chart v0.61.0) is functional with GitHub, Google, and email/password flows. However, it lacks bot protection (captcha), has minimal password strength requirements (`min_password_length: 8` only), no brute-force protection beyond what Cloudflare's default WAF provides, and no account lockout. These are standard security hardening measures for any public-facing auth system.

**Decision Required:**
1. Which captcha provider to use, which flows need it, and where validation occurs
2. Password strength configuration (haveibeenpwned, complexity, max attempts)
3. Brute-force protection strategy (rate limiting layers, account lockout)
4. Session security improvements (idle timeout, rotation)

**Constraints:**
- Cloudflare is already the edge proxy for all traffic (DNS proxied, CF Tunnel to runtime)
- Ory Kratos v1.3.1 deployed via Helm chart v0.61.0 — must use features native to this version
- Kratos Self-Service UI Node (v1.3.0) renders login/registration/recovery at `accounts.{domain}`
- Pre-release: aggressive security is acceptable (no backward compatibility concern)
- Social login (GitHub/Google) must NOT be impacted by captcha
- CLI auth uses Device Code Flow via Hydra (not Kratos browser flows) — must NOT be impacted
- Traefik already has rate-limit middleware: 100 req/s average, 200 burst per source IP

**Known Context:**
- `infra/helm/ory-kratos/values.yaml` — current config: `min_password_length: 8`, `identifier_similarity_check_enabled: true`, `session.lifespan: 24h`, `cookie.same_site: Lax`, Argon2 hasher
- `infra/pulumi/src/components/mgmt-bootstrap.ts` — Kratos deployed via Pulumi with production DSN override, SMTP via Resend, kratos-ui deployed at `accounts.{domain}`
- `infra/helm/traefik/middlewares.yaml` — existing rate-limit (100/s), body-limit (10MiB), security-headers (HSTS, X-Frame-Deny, etc.)
- Dashboard login/register forms submit directly to Kratos flow action via JSON POST
- Recovery flow uses email-based code verification

**Proposal:** Add Cloudflare Turnstile to registration and recovery flows, enable haveibeenpwned check, add Traefik rate limiting on auth endpoints, and configure session idle timeout.

## Stage 2 — Analyses

### Platform Security Engineer

**Assessment:**
The current auth setup has several gaps that are standard attack surfaces for any SaaS platform:

1. **No bot protection:** Registration and recovery are wide open to automated attacks. Mass account creation, credential stuffing on login, and email bombing on recovery are all possible.
2. **Weak password policy:** `min_password_length: 8` with no breach database check means users can register with `password1` or any password from known breaches.
3. **No account lockout:** Unlimited login attempts per identity. Argon2 provides hashing resistance but does not prevent online brute-force.
4. **Session fixation risk:** No idle timeout means a session stolen from a shared computer remains valid for 24 hours even if unused.

**Recommended approach:**

**Captcha — Cloudflare Turnstile (strongly preferred):**
- Turnstile is free, privacy-preserving (no tracking cookies), and Cloudflare is already our edge provider
- Kratos does NOT have native Turnstile integration as of v1.3.x. However, there are two viable approaches:
  - **Option A (recommended):** Validate Turnstile token in the Kratos Self-Service UI Node before submitting to Kratos. The UI Node is a server-side rendering application — it can call the Turnstile siteverify API server-side before forwarding the form submission to Kratos. This is a clean integration point.
  - **Option B:** Use a Cloudflare WAF Managed Challenge rule on the `accounts.{domain}` routes. This is zero-code but less granular — it protects at the page level, not the form level.
  - **Option C (rejected):** Custom webhook/hook in Kratos — Kratos pre-registration hooks exist but adding Turnstile validation there requires custom Go code or a sidecar webhook service. Overly complex for the benefit.
- Turnstile should be applied to: **registration** (mandatory), **recovery** (mandatory), **login** (optional, recommended in managed/invisible mode only).
- Social login flows (GitHub/Google OIDC) do NOT need captcha — the provider handles bot protection.

**Password strength — haveibeenpwned:**
- Kratos has native `haveibeenpwned` support via `password.haveibeenpwned_enabled: true`. This checks passwords against the k-anonymity API of HIBP (no full password is ever sent). Zero privacy risk.
- Increase `min_password_length` from 8 to 10. NIST SP 800-63B recommends minimum 8, but 10 provides better entropy without user friction.
- `identifier_similarity_check_enabled` is already on — good.
- Do NOT add complexity requirements (uppercase, special char). NIST explicitly advises against this. Length + breach check is superior.

**Brute-force protection — layered defense:**
- **Layer 1 (edge):** Cloudflare Bot Management / Rate Limiting Rules on `accounts.{domain}` — free tier includes basic bot score. Add a CF WAF rule: rate-limit to 10 requests per 10 seconds on `/self-service/login` and `/self-service/registration` paths.
- **Layer 2 (ingress):** Dedicated Traefik rate-limit middleware on Kratos routes — tighter than the global 100/s. Suggest 10 req/min per source IP on login/registration endpoints.
- **Layer 3 (application):** Kratos has no native account lockout. Implement a "soft lockout" via Cloudflare WAF: after 5 failed login attempts from the same IP in 5 minutes, issue a Managed Challenge (Turnstile).

**Session security:**
- Add `session.cookie.persistent: false` — session cookie dies when browser closes
- Add idle timeout: Kratos does not have native idle timeout. The session lifespan of 24h is absolute. To simulate idle timeout, the dashboard can check session freshness via `/sessions/whoami` and force re-auth if `authenticated_at` is older than N hours. This is a client-side concern.
- Enable `session.cookie.same_site: Strict` for the accounts subdomain (currently Lax — Lax is actually correct for OIDC flows that redirect, so keep Lax).

**Risks:**
- [medium] Turnstile integration in kratos-ui requires customizing the UI Node — forking or extending `oryd/kratos-selfservice-ui-node`. Risk: upgrade burden.
- [low] haveibeenpwned API unavailability — Kratos handles this gracefully (allows registration if API is down, configurable via `ignore_network_errors`).
- [low] Aggressive rate limiting may impact legitimate users behind shared NATs (corporate offices).

**Objections:** None blocking. All recommendations use established, well-tested mechanisms.

**Recommendation:** Implement in phases: (1) haveibeenpwned + password length increase (config-only, zero risk), (2) Cloudflare WAF rate limiting rules (infrastructure, zero code), (3) Turnstile integration in kratos-ui (requires UI customization).

**Conditions for approval:**
1. Turnstile site key and secret key must be managed via Pulumi secrets, never hardcoded
2. haveibeenpwned must have `ignore_network_errors: true` to avoid blocking registration if HIBP is down
3. Rate limiting rules must be documented and tested before production deployment

**Impact if ignored:** Credential stuffing attacks, mass account creation by bots, email bombing via recovery flow. These are not loopzeroretical — they are guaranteed attacks on any public SaaS auth endpoint.

### DX/Tooling Engineer

**Assessment:**
Security hardening must not degrade the developer sign-up experience. LoopZero's value proposition is "deploy in under 5 minutes" — any friction in registration directly impacts conversion.

**Captcha impact analysis:**
- **Invisible/managed Turnstile on registration:** Acceptable. Most legitimate users will never see a challenge. Turnstile's managed mode is zero-friction for 95%+ of users.
- **Visible captcha on login:** Unacceptable for daily use. Developers log in frequently. A visible captcha every time would be hostile. Invisible mode only.
- **Captcha on recovery:** Acceptable. Recovery is a rare flow. A brief delay is tolerable.
- **Captcha must NOT appear for social login.** GitHub/Google buttons must remain zero-friction.

**Password policy impact:**
- `min_password_length: 10` — acceptable. Modern password managers generate 16+ characters.
- haveibeenpwned check — acceptable. It provides a clear, actionable error: "This password has appeared in a data breach. Please choose a different one." No ambiguity.
- NO complexity requirements — correct. "Must contain uppercase, number, special character" is the most hated UX pattern in auth. Length + breach check is better and users prefer it.

**Registration form UX:**
- Password field placeholder should change from "Password (min. 8 characters)" to "Password (min. 10 characters)"
- If haveibeenpwned rejects a password, the Kratos error message must be clear and actionable. Verify that Kratos provides a user-friendly message (it does: "This password has previously appeared in a data breach").
- Add a password strength indicator (visual bar) to the registration form — this is a DX improvement, not a blocker.

**Rate limiting impact:**
- 10 req/min on login is tight. A user who fat-fingers their password 5 times in a minute should not be locked out. Recommend 10 failed attempts per 5 minutes (not 10 total requests per minute).
- Rate limiting should be on failed attempts, not all requests. Cloudflare WAF can distinguish 4xx responses.

**CLI auth impact:**
- CLI uses Device Code Flow via Hydra (`loopzero login`), which redirects to the accounts page in the browser. The Turnstile captcha will appear on this flow IF the user needs to authenticate via email/password in the browser. This is acceptable — it is the same flow as dashboard login.
- `loopzero login` must NOT be rate-limited. The Device Code polling (`/oauth2/token`) is separate from Kratos and already has its own rate limiting via Hydra.

**Risks:**
- [medium] Password strength indicator in registration form is a new dependency (e.g., `zxcvbn` library). Should be client-side only, no server dependency.
- [low] Turnstile widget styling may clash with the current dark theme. Must test visually.

**Objections:**
1. Do NOT rate-limit by total requests per IP on login. Rate-limit by failed login responses (HTTP 400/422) only. A user refreshing the page should not count.
2. Password strength indicator is a nice-to-have, not a blocker. Can be added in a follow-up.

**Recommendation:** Approve with the constraint that captcha is invisible/managed mode only on login, and rate limiting targets failed attempts, not total requests.

**Conditions for approval:**
1. Turnstile must be in "managed" mode (invisible for most users)
2. Rate limiting must target failed auth attempts (4xx responses), not all requests
3. Social login (GitHub/Google) must remain captcha-free
4. CLI Device Code Flow must not be impacted

**Impact if ignored:** Developer frustration during onboarding, higher abandonment rate, negative perception of the platform.

### SRE/Production Engineer

**Assessment:**
The proposed changes are operationally sound but require careful deployment ordering and monitoring.

**Operational concerns:**

1. **Turnstile availability:** Cloudflare Turnstile depends on CF's edge infrastructure. If CF has an outage (rare but possible), users cannot register or recover accounts. Mitigation: Turnstile should be a soft requirement — if the siteverify API is unreachable, allow the flow to proceed (degrade gracefully). This is a standard pattern for captcha providers.

2. **haveibeenpwned availability:** The HIBP k-anonymity API has 99.9%+ uptime but is external. Kratos's `ignore_network_errors: true` config handles this correctly — registration proceeds if HIBP is down. This is the correct behavior.

3. **Rate limiting observability:** If we add CF WAF rate limiting and Traefik rate limiting, we need to know when legitimate users are being blocked. Requirements:
   - Cloudflare dashboard: monitor the WAF rule hit count
   - Traefik access logs already log 429 responses with correlation IDs — these flow to Loki
   - Add a Grafana dashboard panel for `traefik_entrypoint_requests_total{code="429"}` filtered to the accounts route
   - Alert on sustained 429 spike (could indicate attack OR misconfigured rate limit)

4. **Deployment ordering:** Must be:
   1. Deploy Kratos config changes (haveibeenpwned, password length) — zero downtime, config reload
   2. Deploy Cloudflare WAF rules — takes effect immediately at edge
   3. Deploy Turnstile integration in kratos-ui — requires pod restart
   4. Verify all flows work end-to-end before declaring success

5. **Rollback plan:**
   - Kratos config: revert `password.haveibeenpwned_enabled` to false, redeploy
   - CF WAF rules: disable in Cloudflare dashboard (instant)
   - Turnstile: remove widget from UI, redeploy kratos-ui
   - All rollbacks are independent and can be done in any order

6. **Existing rate limiting adequacy:** Current Traefik rate-limit is 100 req/s global. This is too permissive for auth endpoints specifically but fine for the API overall. A dedicated middleware for auth endpoints is correct.

**Risks:**
- [medium] Turnstile degradation during CF outage blocks registration — must degrade gracefully
- [low] Rate limiting false positives for users behind corporate NAT — monitor and adjust thresholds
- [low] HIBP API latency adds ~100ms to registration — acceptable

**Objections:** None blocking.

**Recommendation:** Approve with mandatory monitoring of 429 rates and Turnstile error rates in Grafana.

**Conditions for approval:**
1. Turnstile must degrade gracefully if CF siteverify is unreachable (allow flow to proceed)
2. Grafana dashboard must include 429 rate monitoring for accounts routes
3. Deployment must follow the phased ordering above
4. CF WAF rate limit rules must be documented in `infra/cloudflare/` for auditability

**Impact if ignored:** Blind spots in auth security posture, no observability into rate limiting effectiveness, potential user lockout during outages.

### Principal Architect

**Assessment:**
This is a well-scoped security hardening task. The architecture is clean: Cloudflare at edge, Kratos for identity, Traefik for ingress, and each layer handles a different concern.

**Architecture alignment:**
- Turnstile validation in kratos-ui (server-side, before Kratos) is architecturally correct. It keeps bot protection at the UI boundary, not deep in the identity system.
- Cloudflare WAF rate limiting at the edge is the correct layer for volumetric attack mitigation.
- Traefik rate limiting at the ingress is the correct layer for per-service protection.
- haveibeenpwned in Kratos is the correct layer for password policy enforcement.

**Boundary concerns:**
- The kratos-ui customization is the riskiest part. The official `oryd/kratos-selfservice-ui-node` image is being used directly. Adding Turnstile requires either:
  - **Fork the image:** Build a custom image with Turnstile integration. This is a maintenance burden but gives full control.
  - **Use environment-variable-based configuration:** The kratos-selfservice-ui-node does NOT support Turnstile out of the box. Forking is likely necessary.
  - **Alternative: CF Managed Challenge at the WAF level.** This adds a Turnstile challenge BEFORE the page loads, not integrated into the form. Less elegant but zero customization of kratos-ui.

**Recommendation on kratos-ui customization:**
Given pre-release status, I recommend **Option B: Cloudflare WAF Managed Challenge** for initial deployment, with kratos-ui Turnstile integration as a Phase 2 improvement. Rationale:
- CF WAF Managed Challenge is zero-code, instant to deploy, instant to roll back
- It protects the same routes (registration, recovery) at the edge level
- It avoids forking the kratos-ui image (which creates upgrade burden)
- Phase 2 can add form-level Turnstile when/if the managed challenge proves insufficient

**Source of truth for credentials:**
- Turnstile site key: public, can be in config
- Turnstile secret key: MUST be in Pulumi secrets, delivered via environment variable to kratos-ui (if Phase 2)
- CF WAF rules: managed via Cloudflare dashboard or Pulumi cloudflare provider

**Risks:**
- [medium] Forking kratos-ui creates upgrade burden — mitigated by using CF WAF instead for Phase 1
- [low] CF WAF Managed Challenge may show interstitial page to all first-time visitors — acceptable for accounts subdomain

**Objections:**
1. DISAGREE with immediate kratos-ui customization. CF WAF Managed Challenge achieves 80% of the protection with 0% of the code complexity. Start there.

**Recommendation:** Two-phase approach. Phase 1: Kratos config + CF WAF rules. Phase 2: kratos-ui Turnstile integration (only if Phase 1 proves insufficient).

**Conditions for approval:**
1. Phase 1 must be config-only and infrastructure-only — no application code changes
2. Phase 2 criteria must be defined (what "insufficient" means — e.g., bot bypass rate)
3. All secrets managed via Pulumi

**Impact if ignored:** Over-engineering in Phase 1, unnecessary fork maintenance burden, delayed deployment of essential protections.

## Stage 3 — Confrontation

### Conflict 1: Turnstile integration approach — kratos-ui form integration vs CF WAF Managed Challenge

| Agent | Position |
|-------|----------|
| Platform Security Engineer | Form-level Turnstile in kratos-ui (Option A). More precise, validates per-form-submission, better UX because the challenge is inline. |
| Principal Architect | CF WAF Managed Challenge (Option B) for Phase 1. Zero code, instant deploy, avoids forking kratos-ui. Form-level only if CF WAF proves insufficient. |
| DX Engineer | Supports form-level for UX (invisible widget is seamless), but acknowledges CF WAF is faster to deploy. |
| SRE Engineer | Supports CF WAF for Phase 1 — simpler to deploy, observe, and roll back. |

**Analysis:** This is a "good enough now vs perfect later" tradeoff. CF WAF Managed Challenge protects the same endpoints at the edge level. It may show a brief interstitial to first-time visitors, but this is the accounts subdomain (not the main marketing page). The form-level integration is better UX but requires forking the kratos-ui image.

**Resolution:** **Two-phase approach adopted.** Phase 1: CF WAF Managed Challenge on `accounts.{domain}` for `/self-service/registration/*` and `/self-service/recovery/*` paths. Phase 2 (triggered if bot bypass exceeds 5% of registrations): form-level Turnstile in a custom kratos-ui build. This gives immediate protection with zero code risk.

### Conflict 2: Rate limiting scope — all requests vs failed attempts only

| Agent | Position |
|-------|----------|
| Platform Security Engineer | Rate-limit all requests to auth endpoints (10 req/min per IP). Simple, effective. |
| DX Engineer | Rate-limit failed attempts only (4xx responses). A user refreshing the page should not be penalized. |
| SRE Engineer | Supports failed-attempts-only at the Traefik level. CF WAF can do response-code-based rate limiting. |

**Analysis:** DX Engineer raises a valid point. Rate-limiting all requests penalizes page refreshes, form reloads, and legitimate navigation. CF WAF rate limiting can be configured to trigger only on specific response codes (400, 422) or on a combination of path + method + response code.

**Resolution:** **Hybrid approach.** CF WAF: rate-limit on 4xx responses to `/self-service/login/` and `/self-service/registration/` — 5 failed attempts per 5 minutes per IP triggers Managed Challenge. Traefik: keep existing global rate limit (100/s) as a volumetric backstop. This protects against brute-force without penalizing legitimate navigation.

### Conflict 3: Session idle timeout

| Agent | Position |
|-------|----------|
| Platform Security Engineer | Wants session idle timeout (force re-auth after 2h of inactivity). |
| DX Engineer | Opposes short idle timeout for developer productivity. Developers leave tabs open for hours. |
| Principal Architect | This is a client-side concern, not a Kratos config. Dashboard can implement optional re-auth for sensitive operations. |

**Analysis:** Kratos does not natively support idle timeouts — only absolute session lifespan. Implementing idle timeout requires client-side logic in the dashboard (checking `authenticated_at` timestamp). For a developer tool, aggressive idle timeouts are hostile to the workflow. The 24h absolute lifespan is reasonable.

**Resolution:** **Defer session idle timeout.** Keep `session.lifespan: 24h`. If sensitive operations are added later (e.g., billing, team management), implement per-operation re-auth (Kratos `refresh` flow with `requested_aal`). No changes to session config now.

### Consensus Challenge (Orchestrator)

All agents agree on haveibeenpwned and password length increase. I challenge this: **What could go wrong?**

- **Risk: haveibeenpwned false positives.** Could a legitimate password be flagged? Yes, but only if it appeared in a breach. This is by design — the password IS compromised. The user gets a clear message and can choose another password. Not a real concern.
- **Risk: password length increase breaks existing accounts.** No — Kratos validates password strength on registration and password change only, not on login. Existing accounts with 8-character passwords continue to work. They will be prompted to strengthen their password on next password change (Kratos behavior). No breakage.
- **Risk: HIBP API adds latency.** The k-anonymity API typically responds in <100ms. Kratos makes this call asynchronously during registration. Worst case adds 100-200ms to registration submission. Acceptable.

**No additional risks surfaced. Consensus is genuine.**

## Stage 4 — Decision

**Chosen approach: Two-phase security hardening**

### Phase 1 — Config + Infrastructure (immediate, zero code changes)

1. **Kratos config updates:**
   - `password.haveibeenpwned_enabled: true`
   - `password.haveibeenpwned_host: "api.pwnedpasswords.com"` (default, explicit for clarity)
   - `password.ignore_network_errors: true` (degrade gracefully if HIBP is down)
   - `password.min_password_length: 10`
   - Keep `identifier_similarity_check_enabled: true`

2. **Cloudflare WAF rules (via CF dashboard or Pulumi):**
   - Rate-limit rule: 5 failed login attempts (4xx response) per 5 minutes per IP on `accounts.{domain}/self-service/login/*` → trigger Managed Challenge
   - Rate-limit rule: 3 registration attempts per 10 minutes per IP on `accounts.{domain}/self-service/registration/*` → trigger Managed Challenge
   - Rate-limit rule: 3 recovery requests per 10 minutes per IP on `accounts.{domain}/self-service/recovery/*` → trigger Managed Challenge

3. **Observability:**
   - Grafana dashboard panel for Traefik 429s on accounts routes
   - CF Analytics monitored for WAF rule triggers

### Phase 2 — Form-level Turnstile (triggered if Phase 1 insufficient)

Criteria to trigger Phase 2: bot bypass rate exceeds 5% of registrations (measured via Kratos metrics or manual review of account creation patterns).

1. Build custom kratos-ui image with Turnstile widget on registration and recovery forms
2. Turnstile secret key managed via Pulumi secrets
3. Server-side siteverify validation before forwarding to Kratos

**Alternatives rejected:**

| Alternative | Rejected because |
|-------------|-----------------|
| reCAPTCHA v3 | Google tracking, not privacy-friendly, conflicts with LoopZero's developer-first brand |
| hCaptcha | Paid for enterprise, less integration with existing CF infrastructure |
| Custom webhook for Kratos captcha validation | Over-engineering — requires sidecar service, complex deployment |
| Account lockout (Kratos-side) | Kratos does not support native account lockout. CF WAF rate limiting achieves the same goal at the edge. |
| Visible captcha on every login | Hostile to daily developer workflow. Invisible/managed mode only. |
| Session idle timeout | Kratos does not support natively. Client-side implementation deferred until sensitive operations exist. |

**Trade-offs consciously accepted:**
- CF WAF Managed Challenge may show a brief interstitial to first-time visitors on the accounts subdomain. This is acceptable — the accounts page is not the marketing site.
- haveibeenpwned adds ~100ms to registration. Acceptable for security benefit.
- No account lockout per identity — only per-IP rate limiting. A distributed brute-force attack is mitigated by CF Bot Management, not by Kratos.

**Risks accepted:**

| Severity | Risk | Mitigation | Owner |
|----------|------|------------|-------|
| medium | CF outage blocks registration (WAF managed challenge hangs) | CF WAF rule can be disabled instantly via dashboard | SRE |
| medium | Phase 2 kratos-ui fork creates upgrade burden | Pin to specific kratos-ui version, document customization, test on every Ory upgrade | Infra Engineer |
| low | Rate limiting false positives for corporate NAT users | Monitor 429 rates in Grafana, adjust thresholds if needed | SRE |
| low | HIBP API unavailability | `ignore_network_errors: true` — registration proceeds | N/A (auto-mitigated) |

**Risks NOT accepted (none):** No blocking risks identified. Security and SRE have not vetoed.

**Mandatory actions before implementation:**

1. **[Infra Engineer]** Update `infra/helm/ory-kratos/values.yaml` with haveibeenpwned and password length config
2. **[Infra Engineer]** Update Pulumi Kratos overrides in `mgmt-bootstrap.ts` to pass haveibeenpwned config to production
3. **[Infra Engineer]** Create Cloudflare WAF rate-limit rules (via Pulumi cloudflare provider or manual) and document in `infra/cloudflare/`
4. **[SRE]** Add Grafana dashboard panel for auth rate-limiting (429s on accounts routes)
5. **[DX Engineer]** Update registration form placeholder text from "min. 8 characters" to "min. 10 characters"
6. **[Infra Engineer]** Test all flows end-to-end: registration with weak password (blocked), registration with breached password (blocked), login with rate limiting (challenge shown after 5 failures), social login (unaffected), CLI `loopzero login` (unaffected)
