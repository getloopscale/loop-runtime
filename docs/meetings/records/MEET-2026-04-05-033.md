## Stage 1 — Context

**Problem:** LoopZero applications are served exclusively at auto-generated subdomains under `*.dev.loopzero.example`. Users cannot map their own domains (`api.mycompany.com`). This blocks production adoption — no serious product ships on a PaaS subdomain.

**Decision Required:** Approve or reject the custom domains design document (`docs/plans/custom-domains-design.md`), which proposes: DB-only state management (no new CRD), TXT verification + CNAME routing, HTTP-01 TLS via cert-manager, manifest re-rendering on verification, background health checker. Eight specific technical decisions (D1-D8) require formal review.

**Constraints:**
- Traffic currently flows through Cloudflare Tunnel with wildcard `*.{baseDomain}` ingress config
- The tunnel ingress rule ONLY matches `*.dev.loopzero.example` — custom hostnames like `api.mycompany.com` will NOT match this rule
- cert-manager uses `letsencrypt-prod` ClusterIssuer (currently DNS-01 via Cloudflare, not HTTP-01)
- ExposedRoute CRD + ExposureController already handle hostname health probes
- Single ArgoCD Application per tenant — known systemic pattern where one Degraded resource blocks all notifications
- `withEnvironmentLock` required for any mutation on (tenant, project, environment)
- Pre-release: backward compatibility not required, clean design preferred

**Known Context:**
- Manifest renderer (`api/internal/manifests/renderer.go`) generates IngressRoute + Certificate per app
- Tunnel config in `infra/pulumi/src/providers/cloudflare/tunnel.ts` routes `*.{baseDomain}` only
- ExposedRoute CRD tracks cert status and reachability probes
- `DeliveryActivator` interface handles gitops push for both container and static delivery

**Proposal:** As documented in `docs/plans/custom-domains-design.md` (sections 1-16).

## Stage 2 — Analyses

### Principal Architect

**Assessment:** The design is well-structured and respects the existing architecture. DB-only (D4) is the correct call — custom domains are user-intent metadata, not infrastructure desired-state that needs reconciliation. The API is the right layer for domain lifecycle management.

However, the design has a significant **source of truth gap**. The `custom_domains` table says a domain is "active", but the real truth is whether the IngressRoute + Certificate actually exist in the workload cluster. If ArgoCD sync fails silently, the DB claims "active" while traffic fails.

**Risks:**
1. [HIGH] DB status diverges from cluster reality — no reconciliation loop to converge them
2. [MEDIUM] Manifest re-rendering on verification couples domain lifecycle to the release flow — what if there is no active release?
3. [LOW] `per project+environment` scope (D8) inconsistent with per-app IngressRoutes in implementation

**Objections:**
- D8 is ambiguous. If there are 3 apps in a project, which one does `api.mycompany.com` route to?

**Recommendation:** Approve with conditions: (1) clarify D8 scope to per-app with `--app` flag, (2) add convergence mechanism for DB-vs-cluster state, (3) document what happens when there is no active release at verification time.

**Conditions for approval:** Scope ambiguity resolved, convergence mechanism documented.

**Impact if ignored:** Domain status lies to the user. "Active" domains that don't work erode trust in the platform.

---

### Platform Security Engineer

**Assessment:** The verification flow is sound in principle. TXT proves DNS control, CNAME routes traffic. Several security gaps identified.

**Risks:**
1. [CRITICAL] **Dangling domain takeover.** "Trust once + degrade on CNAME loss" (D7) leaves IngressRoute active after CNAME removal. A malicious actor who later acquires the domain could receive traffic.
2. [HIGH] **Platform domain bypass.** Blocklist must include ALL infrastructure subdomains, not just wildcard.
3. [MEDIUM] **Domain squatting.** Malicious tenant registers domains they don't own. 7-day cleanup creates a DoS window.
4. [MEDIUM] **HTTP-01 through CF Tunnel unvalidated.** If Cloudflare caches/blocks ACME challenges, TLS issuance fails silently.

**Objections:**
- D7 (trust-once) is too permissive. CNAME loss must trigger IngressRoute removal, not just DB status change.

**Recommendation:** Approve with mandatory mitigations for dangling takeover, platform blocklist, and HTTP-01 validation.

**Conditions for approval:**
1. CNAME loss → remove IngressRoute within configurable grace period (default 14 days)
2. Platform domain blocklist must be exhaustive and configurable
3. HTTP-01 through CF Tunnel validated in spike before Phase 2

**Impact if ignored:** Domain takeover vulnerability. Platform subdomain hijacking. Silent TLS failures.

---

### SRE/Production Engineer

**Assessment:** The operational model has concerns around certificate lifecycle, blast radius, and recovery.

**Risks:**
1. [HIGH] **Certificate lifecycle blindspot.** If cert-manager renewal fails (CNAME removed), cert expires and domain goes down. Health checker must take action, not just report.
2. [HIGH] **Blast radius of manifest re-rendering.** Re-rendering ALL manifests on domain verify could remove existing resources if buggy.
3. [MEDIUM] **No retry for failed provisioning.** User must remove + re-add.
4. [MEDIUM] **Missing metrics:** provisioning duration, health checker errors.

**Objections:**
- Manifest re-rendering outside deploy flow creates a second code path. Race condition with concurrent deploy.

**Recommendation:** Approve with conditions: environment lock for domain mutations, additive-only manifest changes, explicit retry path.

**Conditions for approval:**
1. `withEnvironmentLock` for all domain mutations touching gitops repo
2. Manifest changes must be additive only (no modify/remove of existing resources during domain operations)
3. Explicit provisioning retry path
4. Add provisioning duration metric

**Impact if ignored:** Domain add takes down running services. Silent cert expiry. No operational recovery.

---

### Distributed Systems Engineer

**Assessment:** The state management has consistency concerns between PostgreSQL and cluster state.

**Risks:**
1. [HIGH] **Two-source state split.** No convergence mechanism if gitops push succeeds but ArgoCD sync fails (or vice versa).
2. [HIGH] **Race between deploy and domain verify.** Both render manifests and push to same gitops path.
3. [MEDIUM] **DomainHealthChecker HA race.** Multiple API instances running the same background service.
4. [MEDIUM] **Delete ordering.** Gitops push failure during remove leaves orphaned DB row in "removing" state.

**Objections:**
- State machine needs additional transitions: `failed → verified` (retry), `active → failed` (degradation).

**Recommendation:** Approve with state machine enrichment and mandatory locking.

**Conditions for approval:**
1. `withEnvironmentLock` for all gitops-touching domain mutations
2. State machine supports recovery transitions: `failed → verified`, `active → failed`
3. `DomainHealthChecker` uses `SELECT FOR UPDATE SKIP LOCKED`
4. Delete must be idempotent (re-runnable on partial failure)

**Impact if ignored:** Split-brain between DB and cluster. Race conditions corrupt manifests. Duplicate background operations.

---

### DX Engineer

**Assessment:** CLI design is clean and follows industry conventions. Two-step add+verify flow is correct.

**Risks:**
1. [MEDIUM] `loopzero deploy` should show both auto-generated and custom domain URLs
2. [MEDIUM] DNS propagation latency frustrates users — need clear guidance in error messages
3. [LOW] Missing `loopzero domain status <domain>` command
4. [LOW] Error messages should detect common DNS mistakes (wrong CNAME target, A record instead of CNAME)

**Objections:**
- D8 scope needs `--app` flag. Users expect per-app routing.

**Recommendation:** Approve with scope clarification and deploy output change.

**Conditions for approval:**
1. Add `--app` flag (required)
2. `loopzero deploy` shows both URLs
3. Add `loopzero domain status` command
4. DNS propagation guidance in error messages

**Impact if ignored:** Users confused about routing. Poor custom domain onboarding experience.

---

### API/Domain Architect

**Assessment:** API design is clean. Domain lifecycle well-separated from deploy lifecycle.

**Risks:**
1. [HIGH] **Verify endpoint orchestration creep.** DNS lookup + DB update + manifest render + gitops push is too much for one endpoint. Must be async.
2. [MEDIUM] **Idempotency.** POST /domains needs Idempotency-Key support.
3. [LOW] **Missing pagination.** GET /domains needs limit/offset.

**Objections:**
- Verify returning 409 for "already verified" is wrong. Should return 200 (idempotent).

**Recommendation:** Approve with de-orchestration of verify endpoint.

**Conditions for approval:**
1. Verify = DNS check + DB update only. Provisioning is async background service.
2. POST /domains supports Idempotency-Key
3. Verify on already-verified domain returns 200
4. GET /domains supports pagination

**Impact if ignored:** API becomes second control plane. Verify endpoint hangs for 30+ seconds.

---

### GitOps/Delivery Engineer

**Assessment:** Design correctly extends manifest renderer. Single gitops source of truth maintained.

**Risks:**
1. [HIGH] **Manifest merge conflict.** Concurrent deploy + domain verify both push to gitops repo. Second push fails with non-fast-forward.
2. [MEDIUM] **ArgoCD resource explosion.** Each custom domain adds 2 resources (IngressRoute + Certificate).
3. [MEDIUM] **Prune behavior.** Removed domains need ArgoCD sync to clean up resources.

**Objections:**
- Index-based manifest naming (`{app}-custom-{i}`) is fragile. Removing a domain shifts indices, causing resource churn. Use domain-derived names.

**Recommendation:** Approve with naming fix and locking.

**Conditions for approval:**
1. Manifest names derived from domain (hash or sanitized), not array index
2. Gitops push for domain operations holds `withEnvironmentLock`
3. Document ArgoCD sync policy for domain changes

**Impact if ignored:** Index-based naming causes resource churn. Race with deploy corrupts gitops repo.

## Stage 3 — Confrontation

### Conflict 1: D8 Scope — Per-App vs Per-Environment

| Agent | Position |
|-------|----------|
| Principal Architect | Scope is ambiguous. Must be per-app |
| DX Engineer | Need `--app` flag. Users think in terms of "my API domain" |
| API/Domain Architect | Per-app is correct. Add `app_name` column |
| Design Document | Says "per project+environment" |

**Resolution:** UNANIMOUS — change D8 to per-app. Add `app_name TEXT NOT NULL` to `custom_domains` table. CLI adds required `--app` flag. Unique constraint remains `(domain)` globally; lookup index becomes `(tenant_id, project_name, environment, app_name)`.

### Conflict 2: D7 Re-verification — Trust-Once vs Periodic

| Agent | Position |
|-------|----------|
| Platform Security Engineer | Periodic re-check. CNAME loss must remove IngressRoute within 72h |
| SRE Engineer | Agrees with Security. Must remove infrastructure, not just DB column |
| Distributed Systems Engineer | Periodic DNS checks expensive/unreliable. Check CNAME only on cert renewal failure |

**Resolution:** COMPROMISE — Weekly CNAME re-check. If absent for 2 consecutive checks (14 days), transition to `failed` and remove IngressRoute via gitops push. Grace period configurable. Security accepts.

### Conflict 3: D3 TLS Issuance — HTTP-01 Through CF Tunnel

| Agent | Position |
|-------|----------|
| Platform Security Engineer | HTTP-01 through CF Tunnel unvalidated. Needs spike |
| SRE Engineer | DNS-01 is safer |
| GitOps Engineer | DNS-01 requires zone-write for user's domain — impossible |
| API/Domain Architect | HTTP-01 is the only viable option for user-owned domains |

**Resolution:** HTTP-01 is correct (cannot do DNS-01 on user domains). **Mandatory spike** to validate the challenge path before Phase 2 begins. If spike fails, fallback to manual certificate upload.

### Conflict 4: Verify Endpoint Orchestration

| Agent | Position |
|-------|----------|
| API/Domain Architect | Verify = DNS check only. Provisioning must be async |
| SRE Engineer | Agrees — synchronous provisioning is a latency bomb |
| DX Engineer | Async is fine if user can check progress via `loopzero domain status` |

**Resolution:** AGREED — Verify performs DNS check + DB update to `verified`, returns immediately. `DomainProvisioner` background service handles `verified → provisioning → active`. CLI shows progress via `loopzero domain status`.

### Conflict 5: DB-Only vs CRD (D4)

| Agent | Position |
|-------|----------|
| Principal Architect | DB-only correct — domain is API-layer concern |
| Distributed Systems Engineer | DB-only works IF DomainHealthChecker detects missing cluster resources |

**Resolution:** DB-only APPROVED. DomainHealthChecker enhanced to detect active domains whose IngressRoute/Certificate no longer exist, and re-provision if missing. Pragmatic reconciliation without CRD overhead.

### CRITICAL FINDING: CF Tunnel Routing Gap

The current CF Tunnel ingress config only matches `*.dev.loopzero.example`. Custom hostnames (`api.mycompany.com`) that CNAME to `cname.loopzero.example` will hit the catch-all `http_status:404` rule. **The tunnel must be updated to route custom domain traffic to Traefik.**

**Fix:** Add a catch-all rule or explicit `cname.loopzero.example` rule in the tunnel ingress config that routes to Traefik. Traefik handles hostname matching via IngressRoute Host() rules. This is a **BLOCKER** for the entire feature.

### Consensus Challenge: Apex Domain Support (D6)

All agents agreed CNAME-only is acceptable. Orchestrator challenged: what about DNS providers that don't support CNAME flattening for apex domains?

**Resolution:** D6 stands. This is an industry-wide limitation. Vercel, Netlify, Railway all have the same constraint. Document clearly. Do not attempt A record support (defeats CF Tunnel purpose).

## Stage 4 — Decision

**Chosen:** Approve the custom domains design with modifications.

**Modifications to design document:**
1. **D8 changed:** Per-app scope (add `app_name` column and `--app` CLI flag)
2. **D7 changed:** Weekly re-verification, 14-day grace, IngressRoute removal on failure
3. **D3 conditionally approved:** HTTP-01 requires validation spike before Phase 2
4. **D4 approved:** DB-only with enhanced DomainHealthChecker
5. **Verify endpoint de-orchestrated:** DNS check only, async provisioning
6. **Tunnel config fix required:** Route custom domain traffic to Traefik
7. **Manifest naming:** Domain-derived names, not index-based

**Alternatives rejected:**
- New CRD for domains — over-engineering for user-intent metadata
- DNS-01 for user domains — requires zone-write access to user's DNS
- Per-environment scope — multi-app projects need per-app routing
- Trust-once verification — security risk of dangling domain takeover

**Trade-offs consciously accepted:**
- DB-only means no native K8s reconciliation — mitigated by DomainHealthChecker
- Weekly re-verification adds operational load — acceptable at projected scale
- HTTP-01 through CF Tunnel is fragile — mitigated by validation spike
- Async provisioning means user does not get instant "active" — acceptable DX

**Risks accepted:**

| Severity | Risk | Mitigation | Owner |
|----------|------|------------|-------|
| HIGH | Manifest re-render corrupts gitops repo | withEnvironmentLock + additive-only | API Engineer |
| HIGH | HTTP-01 fails through CF Tunnel | Validation spike before Phase 2 | Infra Engineer |
| MEDIUM | DomainHealthChecker HA race | SELECT FOR UPDATE SKIP LOCKED | API Engineer |
| MEDIUM | 14-day grace period too long for takeover | Configurable, reduce if abuse detected | SRE |
| LOW | ArgoCD resource count growth | Monitor, document limits per plan | SRE |

**Risks NOT accepted (blocking):**

| Risk | Blocker For | Resolution Required |
|------|-------------|---------------------|
| CF Tunnel does not route custom hostnames | Entire feature | Fix tunnel ingress config |
| HTTP-01 challenge path unvalidated | Phase 2 (provisioning) | Spike must pass |

**Mandatory actions before implementation:**
1. [BLOCKER] Fix CF Tunnel ingress config to route custom domain hostnames to Traefik. Owner: Infra Engineer.
2. [BLOCKER] HTTP-01 spike — validate Let's Encrypt challenge through CNAME → CF Tunnel → cert-manager. Owner: Infra Engineer.
3. Update design doc with all meeting modifications. Owner: API Engineer.
4. Add `app_name` column to migration 000014. Owner: API Engineer.
5. Use domain-derived manifest resource names (not index-based). Owner: API Engineer.
6. Document exhaustive platform domain blocklist. Owner: API Engineer.
