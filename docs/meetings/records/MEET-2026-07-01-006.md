# MEET-2026-07-01-006 — MeterComputeSplit total-clamp (SC-7)

**Topic:** In the compute-metering money-writer (plan `metering-compute-loop`, ADR-9 period-split writer), should `MeterComputeSplit` clamp the TOTAL gap (`tail+head`) to `max_delta`, or accept the unclamped `head`?
**Type:** database / billing-semantics (T2 — money-writer SQL; observe-only PRODUCER feeding `usage_records` → Stripe)
**Verdict:** **APPROVED_WITH_CONDITIONS — Option 1 (clamp total, then split the clamped window). Option 2 REJECTED.**
**Convened by:** `/implement metering-compute-loop` (owner directive 2026-07-01: "convene state-guardian now, absorb into ADR-9, then decide wrapper").
**Review Board / Guardians:** state-guardian (Domain), tenant-guardian (Domain), distributed-systems-engineer, verification-architect. **Unanimous.**

## Context

`MeterCompute` (ADR-4) clamps `elapsed = GREATEST(LEAST(now()-expected, max_delta), '0')` — a stale cursor (leader outage) bills at most `max_delta`. `MeterComputeSplit` (ADR-9) returned `tail = period_end(expected)-expected` and `head = now()-period_end(expected)`, **neither clamped** → `tail+head = now()-expected` (raw gap, unbounded). The split fires only when an advance straddles a UTC month boundary — the plan's own note (`:146`) names this "the common leader-failover time".

## Key decision

**Option 1, unanimously.** The unclamped head is NOT a "rare accepted corner" — it is a **faithful-transcription bug against ADR-9's own invariant**. ADR-9 (`:144`) asserts *"With ADR-8's clamp < one period … `tail + head == elapsed`"*; ADR-8 (`:120`) mandates *"k×interval MUST be < one billing period"*. The clamp lives only in `MeterCompute`'s SQL; `MeterComputeSplit` re-derives tail/head from `expected/now()/B` and never sees `max_delta`, so the CTE contradicts the invariant it cites.

## Two money bugs closed by Option 1 (not one)

1. **Unbounded over-bill.** A leader resurrection after an hours-long outage whose resumption tick straddles the month boundary bills an unclamped `head` of hours → same outage bills differently depending on the calendar. Over-billing a tenant for OUR outage; feeds Stripe (real invoice).
2. **Multi-boundary misattribution** (surfaced by state-guardian + dist-systems + verification-architect; NOT in the original write-up). A ≥2-boundary outage (expected in Jan, now in Mar) bills `head = now()-period_end(Jan)` = Feb+Mar and keys P2 at `period_start(now())` = **March** — February's compute lands in March, and the middle-period rows never open. `tail+head==elapsed` is false for any gap > one period.

## Sub-divergence resolved: anchor-at-expected

3 agents (state, tenant, dist-systems) anchored the clamped window at `expected` (`[expected, LEAST(now(), expected+max_delta)]`); verification-architect's SQL sketch anchored at `now()` (`[now-g, now]`). **Resolved to anchor-at-expected** because it is the only formulation that satisfies BOTH test conditions the board required:

- `ClampsLongGap` — deterministic SUM invariant `value(P1)+value(P2) == metering_cost(req, max_delta)` (holds for either anchor).
- `TailToP1_HeadToP2` — verification-architect required `value(P1)` asserted **exactly** (`= metering_cost(req, tail)`, seed-controlled). `tail = period_end(expected) - expected` is a pure function of the seed ONLY under anchor-at-expected; anchor-at-now makes `tail` depend on `now()` → non-deterministic → the board's own exact-tail test cannot exist.

Anchor-at-expected also matches SC-4 continuity ("resume a bounded amount from where the cursor left off"). The closed-period back-dating of `tail` is a pre-existing concern (present in the normal split too) handled by `usage_records.reported_to_stripe` + the reconciliation oracle (ADR-12′), not by the anchor choice.

## Corrected CTE (folded into ADR-9 / plan v1.10)

```
adv:  UPDATE ... SET last_metered_at = now()          -- SC-4: raw now(), NEVER clamped/boundary
      WHERE <CAS + SC-1 monotonicity + SC-2 <> straddle predicate + SC-6 fence>
      RETURNING LEAST(now(), @expected + @max_delta) AS capped_end
tail = GREATEST(LEAST(metering_period_end(@expected), capped_end) - @expected, '0')
head = GREATEST(capped_end - metering_period_end(@expected), '0')
P1 → (period_start(@expected), period_end(@expected))                 value = metering_cost(req, tail)
P2 → (metering_period_end(@expected), period_end(period_end(@expected)))  value = metering_cost(req, head)   -- keyed off clamped end, NOT now()
delta (RETURNING) = (metering_cost(req, tail) + metering_cost(req, head))::bigint
```

Invariant `tail + head == capped_end - expected == LEAST(now()-expected, max_delta)` holds by construction; `capped_end < expected + 1 period` (ADR-8) ⇒ at most one boundary ⇒ P2 is exactly `period(expected)+1`, never a middle month. Degenerate: `capped_end ≤ period_end(expected)` ⇒ `head=0`, all to P1, cursor still advances to `now()` (a benign `value=0` new-period row is NOT created because P2's SELECT FROM adv yields the 0-head only when `head>0`… document: P2 upsert with `metering_cost(req,'0')=0` may open a 0-row — benign, correct period).
