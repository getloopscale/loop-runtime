## Stage 1 — Context

**Problem.** `api/internal/manifests/renderer.go` defines `RenderInput.ClusterIssuerName` (field documented as "Default: letsencrypt-prod") with an in-code fallback at lines 118-123:

```go
func (ri RenderInput) clusterIssuerName() string {
    if ri.ClusterIssuerName != "" {
        return ri.ClusterIssuerName
    }
    return "letsencrypt-prod"
}
```

None of the 4 call sites — `api/internal/services/build_reconcile_complete.go:66`, `build_reconcile_retry.go:117`, `domain_provisioner.go:315`, `domain_provisioner.go:433` — set `ClusterIssuerName`. Therefore every Certificate CR rendered by the API references the ClusterIssuer named `letsencrypt-prod`.

**Observed impact.**
- Local k3d dev: the cluster has `loopzero-ca-issuer` (see `infra/helm/cert-manager/templates/self-signed-issuer.yaml`) but no `letsencrypt-prod`. All generated Certificates hang in Pending, ArgoCD reports Degraded, release never reaches ACTIVE. This is the B14 regression that triggered the change.
- Production DO: `createClusterIssuer(... role=\"runtime\"|\"runtime-2\"|\"mgmt\")` at `infra/pulumi/src/components/bootstrap-cert-ingress.ts:181` unconditionally names the resource `letsencrypt-prod`. By coincidence, prod works today — the in-code default happens to match a hardcoded Pulumi name.

**Decision Required.** Adopt Option A (preserve the in-code default) vs Option B (fail-loud, no in-code default; require `LOOPZERO_CLUSTER_ISSUER` env).

**Constraints.**
- Pre-release governance: "no workarounds"; "redesign preferred over patching"; Rule 10 (local = prod) must hold.
- Rule 8 (state machines strict) + Rule 9 (CLI-first) are unaffected; no user-facing strings change.
- Any field read by `renderer.go` must have a deterministic source per call — tests and production must trace the same path (Rule 5: `--json` stability does not apply, but manifest determinism MOD-5 does).
- Startup validation is the canonical fail-fast point (`config.Config.Validate()` at `api/internal/config/config.go:356`); adding a required field there is the existing paved road.

**Known Context.**
- `docs/technical.md` §6 (four planes) and §16 (security model) place TLS issuer selection in the control plane.
- `CHG-2026-04-22-004` governance-gate precedent: explicit rejection of toggles, Rule 10 enforcement, fail-fast in Validate(). B14 fits the same doctrine.
- `config.Validate()` already returns fatal errors for missing prod credentials (`MINIO_ACCESS_KEY`, `CORS_ALLOWED_ORIGIN`, `LOOPZERO_SECRET_ENCRYPTION_KEY`, etc.). `LOOPZERO_CLUSTER_ISSUER` has exactly the same shape.
- The Pulumi `loopzero-api-config` ConfigMap (`infra/pulumi/src/components/mgmt-api.ts:160-193`) is the single source for env vars on both the API Deployment and the controller Deployment (both consume `envFrom: loopzero-api-config`).

**Proposal (Option B).**
1. Add `Config.ClusterIssuer string` — read from `LOOPZERO_CLUSTER_ISSUER`, no default.
2. `Validate()` returns fatal error if empty in *any* environment (not just production). Rule 10 demands identical behavior in dev.
3. Remove the in-code fallback in `renderer.go` (lines 118-123). `ClusterIssuerName` becomes required on `RenderInput`; empty input is a programming error (panic or typed error — see Stage 3).
4. All 4 `manifests.Render` call sites pass `r.cfg.ClusterIssuer` (mirroring how `BaseDomain` is wired today).
5. `infra/tilt/api-deployment.yaml` sets `LOOPZERO_CLUSTER_ISSUER=loopzero-ca-issuer` (matches the actual issuer that exists in k3d).
6. `infra/pulumi/src/components/mgmt-api.ts` adds `LOOPZERO_CLUSTER_ISSUER: \"letsencrypt-prod\"` to the `loopzero-api-config` ConfigMap *in the same PR*. Both API and controller Deployments inherit via `envFrom`.
7. TDD sequence: renderer_test (red: Render fails/panics on empty field) → config_test (red: Validate rejects empty env) → wire call sites → Pulumi / Tilt env vars → green.

## Stage 2 — Analyses

### api-domain-architect (Sponsor)

**Assessment.** The config surface is currently dishonest: a documented "default" that no caller can override without a struct field nobody sets. This is the "implemented but not wired" anti-pattern called out in `CLAUDE.md`. Option B collapses the surface into the existing `Config → service.cfg → Render` path already used for `BaseDomain`, `RegistryURL`, etc. Zero new abstractions (KISS). The field stops pretending to be optional.

**Risks identified.**
- R-A1: If the Pulumi ConfigMap is not updated in lockstep, production API will refuse to start on next rollout. Blast radius = full control-plane outage until `loopzero-api-config` is updated.
- R-A2: If we keep the default-value concept at the renderer layer but only change the wiring, we hide the coupling again (Option A-lite). Must be Option B end-to-end.

**Objections.** None to Option B. Strong objection to Option A: "preserve in-code default" is precisely the pattern that produced B14. In pre-release we fix the root cause.

**Recommendation.** Option B, atomic PR covering code + Pulumi + Tilt. Any partial merge is a regression.

**Conditions for approval.** (1) Pulumi mgmt-api.ts edited in the same PR. (2) `Config.Validate()` makes the env var fatal in *all* environments (Rule 10). (3) No "dev fallback" in renderer.go, no `envOr("LOOPZERO_CLUSTER_ISSUER", "letsencrypt-prod")` — the default must live in Pulumi/Tilt where ops owns it.

**Impact if ignored.** B14 recurs on the next cluster rebuild or next environment added (staging, per-tenant cell).

### platform-security-engineer (TLS issuer selection)

**Assessment.** TLS issuer is a security-critical selection: issuing against the wrong ACME endpoint can rate-limit the account, issuing with an untrusted CA silently breaks clients. Today the issuer name is an undocumented, hardcoded string shared by Pulumi and the renderer. Option B moves it to an explicit, audited env var. **This is a net security improvement**, not a risk.

**Risks identified.**
- R-S1: An operator can set `LOOPZERO_CLUSTER_ISSUER=letsencrypt-staging` in prod and silently issue untrusted certs. Mitigation: this is strictly better than today where the string is invisible; document the valid values in the Pulumi stack config and in `docs/technical.md` §16.
- R-S2: None. Fail-fast at startup is the correct failure mode for TLS misconfig. A running API that generates Certificates with a non-existent issuer is worse (Pending certs, ArgoCD Degraded, cascading failures — i.e. current B14).

**Objections.** One: the renderer must NOT accept an empty string (silent drop). If `ClusterIssuerName == ""` reaches the renderer, it is a programming error. The correct response is `panic` (consistent with Rule 8 — "invalid state transitions panic; they are programming errors"). Not a typed LoopZeroError, because Render() is pure and downstream of validation.

**Recommendation.** Option B. **No VETO.**

**Conditions for approval.**
1. Startup Validate() rejects empty `LOOPZERO_CLUSTER_ISSUER` in ALL environments.
2. Render() panics with a clear message if `ClusterIssuerName == ""` (programmer error, not operator error).
3. `docs/technical.md` §16 lists valid issuer names and their semantics.

**Impact if ignored.** Status quo: a silent default that ops cannot see and cannot control. This is a textbook supply-chain-adjacent misconfiguration pattern.

### production-design-reviewer (Challenger — prod default removal)

**Assessment.** Removing a production default is always load-bearing. The question is not "is Option B cleaner" (it is) but "is the rollout atomic enough to not break prod".

**Risks identified.**
- R-P1 (CRITICAL): Atomicity failure. If `loopzero-api-config` ConfigMap update lands *after* the image rollout, API pods CrashLoopBackOff on startup (Validate() fails). The initContainer `db-migrate` runs BEFORE the config check, so migrations might run and then the main container fails — no data loss risk (migrations are idempotent forward-only), but a visible outage of the control plane.
- R-P2: `envFrom: configMapRef` semantics: env vars are bound at pod start. A live ConfigMap update does NOT propagate until pod restart. Therefore a Pulumi `up` that updates the ConfigMap and also bumps the image tag will trigger a rolling restart — correct behavior. But a Pulumi `up` that changes only the image (CI/CD image promotion) without a ConfigMap change in the same plan will fail validation with the new image if ConfigMap hasn't been updated yet. **This must be a single Pulumi apply.**
- R-P3: Controller binary (`installLoopZeroController`) also consumes `loopzero-api-config`. Same restart dynamic applies.
- R-P4: Rollback path. If the ConfigMap is rolled back but the code is not, the old image is fine (the field existed before and was optional). If the code is rolled forward but the ConfigMap is not, API fails. The safe rollback is: revert the code commit, then Pulumi apply.

**Objections.** Option A ("preserve in-code default") is rejected: it perpetuates the root cause of B14 and produces no testable guarantee that prod's Pulumi ever sets the value. The coupling remains invisible.

**Recommendation.** Option B **with atomic rollout constraint**: one PR must include (a) api code change, (b) `infra/pulumi/src/components/mgmt-api.ts` ConfigMap update, (c) `infra/tilt/api-deployment.yaml` env var. Merge triggers a single Pulumi apply that updates the ConfigMap, which forces a rolling restart with the new image — all env vars present on first boot.

**Conditions for approval.**
1. Pulumi mgmt-api.ts edit is **in scope** of this gate (not deferred). Without it, approval is withdrawn.
2. A pre-merge dry-run: `pulumi preview --stack dev` shows both ConfigMap diff AND image tag diff (or at minimum ConfigMap diff — the rolling restart is what we need).
3. Validation `grep -rn "letsencrypt-prod" api/ pkg/ cli/` returns 0 matches outside of test fixtures.
4. Validation `grep -n "LOOPZERO_CLUSTER_ISSUER" infra/pulumi/src/components/mgmt-api.ts infra/tilt/api-deployment.yaml` returns at least one hit in each file.
5. CHANGELOG.md entry under `[Unreleased]` → `Changed` with ticket reference.

**Impact if ignored.** If Pulumi is deferred to a later PR, prod is guaranteed to break on next deploy of API. This is not a loopzeroretical risk — it is the direct mechanical consequence of Validate() fatal.

| Agent | Position |

## Stage 4 — Decision

**Chosen:** **Option B — fail-loud, no in-code default, required env var.**

**Rejected alternatives:**
- **Option A (preserve in-code default, only wire the field).** Rejected: leaves the "invisible default" pattern in place, recreates B14 on next cluster variant. Violates the pre-release "no workarounds" clause.
- **Option B' (Option B but Pulumi deferred to a follow-up PR).** Rejected by all five reviewers: guarantees prod outage on first API image roll. Non-atomic.
- **Option B'' (keep in-code `envOr("LOOPZERO_CLUSTER_ISSUER", "letsencrypt-prod")` as a silent default in dev).** Rejected: violates Rule 10 and reintroduces the exact invisible default we are removing. Hard SRE+Security VETO.

**Trade-offs consciously accepted:**
- TO-1: Slight increase in operator burden — every new environment (staging, per-cell) must set `LOOPZERO_CLUSTER_ISSUER`. Mitigation: the variable lives in Pulumi stack config; adding a cell inherits it. This is the correct ownership boundary.
- TO-2: Startup of a misconfigured API is now *loud* (CrashLoopBackOff) instead of *silent* (Certificates stuck Pending). This is the desired failure mode per the "fail-fast, fail-loud, fail-clear" doctrine in global principles.

**Risks accepted (with mitigation and owner):**
- RA-1 (R-P1 atomicity): api-engineer owns the single-PR guarantee; production-design-reviewer validates during PR review that all three scope files are touched.
- RA-2 (R-S1 wrong issuer value): platform-security-engineer owns documenting valid issuer names in `docs/technical.md` §16 as a follow-up T1 doc PR (not blocking this gate, tracked as a separate issue).
- RA-3 (R-SR1 out-of-order image promotion): sre-engineer owns the PR-description runbook paragraph. Tracked as a one-time ordering constraint for this commit.

**Risks blocked:** None. All identified risks have a named owner and mitigation.
