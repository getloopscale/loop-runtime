### Platform Security Engineer

**Assessment:** The security posture has critical gaps that are unacceptable for any production deployment, even pre-release:

1. **Pods as root (7.1):** CRITICAL. Container escape → node access → lateral movement to other tenants. DigitalOcean DOKS shares kernel with all pods. A container running as root with no seccomp profile can exploit kernel vulnerabilities.

2. **No PSA enforcement (7.2):** CRITICAL. Without PSA labels, ANY pod spec is admitted to tenant namespaces. A malicious or misconfigured application can request hostNetwork, hostPID, privileged mode.

3. **Conditional NetworkPolicy (7.3):** HIGH. The `if env.Spec.NetworkPolicy.Isolate` condition means NetworkPolicy is opt-in. Default is no isolation. Tenant-to-tenant network traffic is unrestricted.

4. **Default ServiceAccount (7.4):** HIGH. Pods using `default` SA can discover and interact with the Kubernetes API if the SA token is auto-mounted. In DOKS, the default SA has read access to its own namespace.

5. **Hardcoded callback secret (cb-loopzero-dev-2026):** MEDIUM for pre-release. The secret is cluster-internal (no external exposure). Acceptable as long as it does not leak in logs or error messages.

**Risks identified:**
1. [critical] Container escape + root → full node compromise
2. [critical] No PSA → privileged pod injection into tenant namespace
3. [high] No NetworkPolicy default → cross-tenant data exfiltration
4. [high] Default SA token → K8s API discovery from tenant pods
5. [medium] Image tag mutability (7.7) → supply chain attack surface (but registry is private)

**Objections:**
- **SECURITY VETO on production declaration without tasks 7.1, 7.2, 7.3, and 7.4.** These are the "big four" that create the tenant isolation boundary. Without them, there is no multi-tenancy isolation.
- Tasks 7.5, 7.6, 7.7 are MEDIUM/LOW and can be deferred to post-launch hardening.
- The ESO E2E validation is NOT a security blocker — ESO is deployed and the ClusterSecretStore is Ready. The risk is functional (secret sync may fail), not security.

**Recommendation:**
- Sprint 7 tasks 7.1-7.4 are MANDATORY before production. Non-negotiable.
- Tasks 7.5-7.7 can be deferred with documented risk acceptance.
- MEET-029 fixes are a reliability concern, not a security concern, so they do not require Security veto — but they should come first because they affect the core deploy flow needed to validate security changes.

**Conditions for approval:**
- ALL four critical/high security tasks (7.1, 7.2, 7.3, 7.4) complete and validated on DO
- PSA `restricted` enforcement verified: attempt to create a privileged pod in tenant namespace → rejected
- NetworkPolicy default deny verified: pod in tenant-A cannot reach pod in tenant-B
- Callback secret value does not appear in any CLI output, SSE event, or error message

**Impact if ignored:** Multi-tenant isolation does not exist. Any tenant can compromise any other tenant. Any container escape compromises the node.

### Consensus Challenge (Orchestrator)

All agents agree on the phased approach. Challenging: **What are we not seeing?**

1. **The 7 MEET-029 code changes (P1-P6) touch critical paths.** Leader election (P1), state machine timeout (P2), delivery flow (P3, P4), and convergence loop (P5) are all being modified simultaneously. A regression in any of these could make deploys MORE unreliable, not less.

   **Mitigation:** Each fix is independently testable and has a clear rollback. Implement and test one at a time. Do NOT batch all P1-P6 changes into a single commit.

2. **Sprint 7 task ordering is critical.** If PSA `restricted` is applied (7.2) BEFORE SecurityContext is added to the manifest renderer (7.1), ALL existing tenant pods will be rejected on reschedule. This is a hard dependency.

   **Mitigation:** The Sprint 7 ROADMAP already specifies this ordering. Enforce: 7.1 → 7.4 → 7.2 → 7.3. GATE between 7.4 and 7.2: deploy a test app and verify pod has correct SecurityContext BEFORE enabling PSA enforce.

3. **CLI binary on DO is stale.** The `build-images.yml` workflow rebuilds the CLI container. After MEET-028 content hash fixes, the CLI needs to be rebuilt and redeployed. This happens as part of the infra pipeline re-run.

   **Mitigation:** Phase 1 includes pipeline re-run which rebuilds all images.

## Stage 4 — Decision

**Chosen:** 4-phase execution plan, serialized, with explicit gates. Reliability first, then security, then validation, then polish.

### Phase 1 — Deploy Reliability (MEET-029 Implementation)
**Effort:** 4-6h code + 1 pipeline run
**Scope:**
- P0: Re-run infra pipeline to deploy committed ArgoCD callback auth fix
- P1: Leader election hardening (stale lock detection, heartbeat, metric, FATAL on loss)
- P2: Timeout hierarchy fix (ReleasePendingTimeout → 10min, fix stale error message)
- P3: TriggerSync 404 recovery (do not call phaseEFinalize on 404)
- P4: Convergence loop revision verification
- P5: Verify SetGitCommit fatality (test only)
- P6: Error message fixes (product language, actual timeout values)

**Gate 1:** 3 successful deploys on DO with release activated via callback path (not convergence loop). Leader metric exported. All new unit tests passing.

### Phase 2 — Workload Security (Sprint 7 Tasks 7.1-7.4)
**Effort:** 3-4h
**Scope (in strict order):**
1. Task 7.1: SecurityContext in manifest renderer (runAsNonRoot, runAsUser:1000, seccomp, readOnlyRootFilesystem, /tmp emptyDir)
2. Task 7.4: ServiceAccount `loopzero-workload` with automountServiceAccountToken:false
3. GATE: Deploy test app on DO → verify pod runs as UID 1000, correct SA, SecurityContext present
4. Task 7.2: PSA `restricted` labels on tenant namespaces
5. Task 7.3: NetworkPolicy always enforced (remove conditional)

**Gate 2:** All tenant pods run as UID 1000. PSA `restricted` enforced (privileged pod creation rejected). NetworkPolicy exists in ALL tenant namespaces. 3 stable deploys on DO.

### Phase 3 — Validation and Polish
**Effort:** 2-3h
**Scope:**
- ESO E2E: `loopzero secret set FOO=bar` → verify ExternalSecret created → K8s Secret synced → pod reads `FOO=bar`
- Fix 403 → "environment not found" for non-existent environment
- Verify `loopzero status` works on DO (already wired — just validate)
- Rebuild CLI image (happens with pipeline re-run if not done in Phase 1)

**Gate 3:** Full happy-path E2E on DO: login → init → deploy → status → logs → secret set → rollback → verify rollback version. All steps succeed. Results documented.

### Phase 4 — Deferred Hardening (Post-Launch)
**Scope (documented risk acceptance):**
- Task 7.5: PostgreSQL egress restriction (risk: PG can reach arbitrary hosts — mitigated by managed PG with no public IP)
- Task 7.6: MinIO ingress restriction (risk: open port 9000 in cluster — mitigated by cluster-internal only, no external exposure)
- Task 7.7: Image digest enforcement (risk: mutable tags — mitigated by private registry, no external contributors)
- Automated E2E test suite on DO (currently manual)
- Replace leader election with Kubernetes Lease (MEET-029 deferred)
- Move callback secret to Kubernetes Secret (MEET-029 TODO)

### Alternatives Rejected

1. **Ship without Sprint 7 tasks 7.1-7.4:** Rejected. Security veto (absolute). Root-running pods with no PSA on shared cloud infrastructure is unacceptable.

2. **Do security before reliability:** Rejected. Cannot validate security changes if deploys are unreliable. MEET-029 P0 is a zero-code-change pipeline re-run that immediately improves reliability.

3. **Implement all Sprint 7 tasks (7.1-7.7) before production:** Rejected. Tasks 7.5-7.7 are MEDIUM/LOW severity with adequate mitigations. Delaying production for incremental network policy tuning has negative ROI.

4. **Block production on automated E2E tests:** Rejected by pragmatism. Manual E2E validation is sufficient for pre-release. Automated E2E is Phase 4 work.

### Trade-offs Consciously Accepted

1. **PostgreSQL has open egress within the cluster** (Task 7.5 deferred) — mitigated by managed PG with no public IP and cluster-internal only networking
2. **MinIO ingress from any namespace** (Task 7.6 deferred) — mitigated by cluster-internal access, cross-cluster Docker networking limitation
3. **Image tags instead of digests** (Task 7.7 deferred) — mitigated by private registry, BuildKit does produce digests in metadata (enforcement is the gap)
4. **Manual E2E validation instead of automated** — mitigated by documented runbook checklist
5. **Hardcoded callback secret** — mitigated by cluster-internal only, no external exposure, pre-release
