## Context

**Problem:** The document `docs/validation/2026-04-10-roadmap-to-100k-pods.md` proposes a 6-phase maturity model (M0→M5) to take LoopZero from current state to 100,000 pod readiness. It claims to consolidate ADR-0008, load-test-plan, and runbooks into a single execution plan.

**Decision Required:** Should this document be accepted as the official scaling plan for LoopZero?

**Constraints:**
- LoopZero is pre-release with ~2 real tenants
- cell.ts in Pulumi returns placeholder values (TODO Phase 2)
- PlacementEngine is DefaultEngine ("cell-default" for all tenants)
- API background loops are singleton with `pg_try_advisory_lock` leader election
- Phase plan documents referenced in ADR-0008 (phase0.md through phase4.md) do not exist
- L1 load testing (2026-04-09) exposed 13 defects documented in CORRECTIONS.txt

**Known Context:**
- ADR-0008: Cell-Based Architecture (ACCEPTED 2026-03-31)
- `docs/plans/load-test-plan.md`: L0-L7 concrete test plan
- `docs/runbooks/api-scaling.md`: API singleton constraints
- `docs/runbooks/cell-operations.md`: Cell operations (for unbuilt infrastructure)
- `infra/tests/load/CORRECTIONS.txt`: 13 L1 defects

## Stage 2 — Agent Analyses

### Principal Platform Architect

**Assessment:** Structurally incomplete, internally inconsistent with ADR-0008, dishonest about current state.

**Key Findings:**
1. ADR-0008 has 5 phases (0-4) with triggers/sprints. This roadmap has 6 phases (M0-M5) with no triggers/dates. Phase boundaries DON'T align.
2. Current state claim "between M0 and M1" is false. Reality: M0 minus (only migration 000011 exists; everything else is stub/placeholder).
3. Phase plans referenced by ADR-0008 were never written.
4. Title claims 100k pods but content operates in tenants/apps with no conversion model.
5. Gitea bottleneck (identified in load-test-plan at 500 tenants) omitted.
6. PG partitioning (mandated by ADR-0008) omitted.
7. Session-scoped `pg_try_advisory_lock` in leader election violates Rule 7.

**Recommendation:** REJECT in current form. Revise or reclassify as maturity model.

**Risks:** [CRITICAL] Two competing plans, leader election bug, Gitea omission. [HIGH] No conversion model, missing PG partitioning, no cost model.

### Staff Distributed Systems Engineer

**Assessment:** Structurally sound as phased plan, dangerously incomplete as distributed systems design. Describes WHAT to build but never HOW convergence/consistency/failure change across phases.

**Key Findings:**
1. Phase 1 extraction ignores: leader re-election gap, `sync.Map` state loss, split-brain during PG flap.
2. Phase 2 has no backpressure model (ArgoCD saturation → unbounded PENDING queue).
3. Phase 3 ignores: shared PG as contention funnel, cell-scoped queries (global `FindPendingReleases`), tenant migration atomicity (no saga), event ordering across cells.
4. Phase 3 `RoundRobinEngine.AssignCell` has TOCTOU race condition.
5. Phase 4 load testing without failure injection proves capacity, not resilience.

**Recommendation:** CONDITIONAL REVISION. Add consistency boundary specification before Phase 3.

**Risks:** [CRITICAL] Global queries corrupt cell isolation, no fencing tokens. [HIGH] Tenant migration split-state, no admission control.

### Staff SRE / Production Readiness

**Assessment:** CONDITIONAL VETO. Directionally correct but operationally unvalidatable as written.

**Key Findings:**
1. Phase 0 rated 2/5 — evidence shows 3/5 minimum (L1 exposed 13 defects requiring manual intervention).
2. CORRECTIONS.txt (2026-04-09) documents: probe kills non-leader pods (correction F), manifest gate blocks all new tenants (correction G), 10% build failure rate at L1, PVC multi-attach failures. NONE referenced by roadmap written one day later.
3. Cell operations runbook documents procedures for infrastructure that doesn't exist.
4. No rollback plan for Phase 1 (API decoupling).
5. No SLO protection during migration.
6. DoD criteria are subjective ("documento revisado" — by whom? against what?).

**Recommendation:** Revise. Add Phase -1 (fix L1 defects). Fix complexity ratings. Add cost/timeline/rollback per phase.

**Risks:** [CRITICAL] L1 defects unacknowledged, cell.ts is placeholder. [HIGH] No timelines, no cost model, 10% build failure rate.

### Staff Test & Verification Architect

**Assessment:** Verification-immature. Every phase has acceptance criteria but none can be mechanically verified. Load test infrastructure exists but roadmap doesn't reference it.

**Key Findings:**
1. Multi-replica API duplication test doesn't exist (Phase 1 DoD unprovable).
2. Blast radius test has zero infrastructure (chaos suite: 6 `PIt` tests, zero implementations).
3. Rollback under concurrent load never tested.
4. PgBouncer (Phase 4) incompatible with `pg_advisory_xact_lock` in transaction mode.
5. Phase 5 readiness decision has no numeric criteria (political, not technical).
6. Load-test-plan.md (L0-L7) not referenced despite covering the same work.

**Recommendation:** CONDITIONAL APPROVAL with verification contracts added.

**Risks:** [CRITICAL] Phase 1 DoD already falsified by CORRECTIONS.txt. [HIGH] PgBouncer breaks locks, no chaos framework.

## Stage 4 — Decision

### Verdict: REJECTED — Requires Major Revision

### Justification

The document is directionally sound but fails on four axes:
1. **Honesty** — overstates current state, omits known defects, ignores known bottlenecks
2. **Consistency** — contradicts ADR-0008 phase structure, creates competing plan
3. **Operability** — no timelines, cost, team sizing, rollback plans, or SLO protection
4. **Verifiability** — no testable criteria, no reference to existing test infrastructure

### Alternatives Rejected

| Alternative | Rejected Because |
|---|---|
| Accept as-is | Operationally unvalidatable, contradicts ADR-0008, omits known bottlenecks |
| Retract entirely | Directional thinking is sound; has value as maturity assessment |
| Merge into ADR-0008 | ADR is an architectural decision, not a project plan |

### Trade-offs Accepted

- Requiring revision delays having a written scaling plan (acceptable — wrong plan worse than no plan)
- Demanding L1 fixes before scaling feels slow but prevents building on unstable foundations

### Risks NOT Accepted (Blockers)

| # | Severity | Risk | Blocker For |
|---|----------|------|-------------|
| 1 | CRITICAL | Two competing phase structures (ADR-0008 vs roadmap) | All phases |
| 2 | CRITICAL | Session-scoped `pg_try_advisory_lock` (Rule 7 violation) | Phase 1+ |
| 3 | CRITICAL | Global queries in reconciliation loops (no cell_id filter) | Phase 3+ |
| 4 | CRITICAL | 13 L1 defects unacknowledged (CORRECTIONS.txt) | Phase 0 |
| 5 | HIGH | Gitea bottleneck omitted (fails at 500 tenants) | Phase 2+ |
| 6 | HIGH | PG partitioning omitted (ADR-0008 mandates it) | Phase 3+ |
| 7 | HIGH | No conversion model (100k pods → tenants/apps/cells) | All phases |
