## Stage 1 — Context

**Problem:** Kratos is configured with Resend SMTP (`smtps://resend:***@smtp.resend.com:465`) but emails are NOT delivered. TCP connections to smtp.resend.com on ports 465, 587, and 2525 all TIME OUT from inside the DOKS cluster. DNS resolves correctly — the issue is at the network/firewall level.

**Decision Required:** (1) Identify root cause of SMTP port blocking. (2) Choose a production-quality solution that enables email delivery.

**Constraints:**
- Must be production-quality, no insecure workarounds
- Kratos v1.3.1 (Helm chart v0.61.0) with courier SMTP transport
- DigitalOcean DOKS in SFO3 region
- Platform uses `loopzero-system` namespace with explicit NetworkPolicy egress allow-list
- Resend is the chosen email provider (API key already provisioned)

**Known Context:**
- `infra/pulumi/src/components/mgmt-bootstrap.ts` lines 2354-2384: `platform-egress-policy` defines explicit egress allow-list
- `infra/helm/ory-kratos/values.yaml`: Kratos courier SMTP config
- `docs/plans/EMAIL-FLOWS-PLAN.md`: email delivery plan references SMTP via Resend
- `infra/pulumi/src/components/bootstrap-shared.ts` line 16: `PLATFORM_NAMESPACE = "loopzero-system"`

**Proposal (if any):** Multiple options under evaluation — add SMTP ports to NetworkPolicy, switch to Resend HTTP API, or deploy local SMTP relay.

## Stage 2 — Analyses

### SRE/Production Engineer

**Assessment:** The root cause is definitively the `platform-egress-policy` NetworkPolicy in `mgmt-bootstrap.ts` (lines 2357-2384). The egress allow-list explicitly enumerates allowed ports: 53 (DNS), 443/6443 (HTTPS/K8s API), 25060 (managed PG), 80/8080/9000 (HTTP services), and 30100 (cross-cluster). SMTP ports 465, 587, and 2525 are NOT in this list.

Since the NetworkPolicy declares `policyTypes: ["Egress"]` with explicit rules and no catch-all, any port not listed is DENIED. The Kratos pod cannot reach smtp.resend.com on any SMTP port.

DigitalOcean DOKS blocks outbound SMTP on port 25 (documented, to prevent spam). However, ports 465 and 587 are NOT blocked by DO infrastructure. The timeout behavior (silent hang, no RST) is consistent with a Kubernetes NetworkPolicy drop, not a cloud firewall drop.

**Risks identified:**
1. Adding SMTP ports to the blanket egress policy opens those ports for ALL pods in the namespace, not just Kratos
2. If DO blocks 465/587 in certain node pools (unlikely but unconfirmed), NetworkPolicy alone would not fix it

**Objections:** None to fixing the NetworkPolicy. Strong objection to deploying an SMTP relay (unnecessary complexity).

**Recommendation:** Add ports 465 and 587 to egress, scoped to Kratos pods only. Verify with `kubectl exec` curl test after deployment.

**Conditions for approval:**
1. Verify from a DO droplet (not inside k8s) that 465/587 are reachable, to rule out DO-level blocking
2. Add only the ports Kratos needs, not a blanket "all ports" rule

**Impact if ignored:** Email verification, password recovery, and account security flows are completely broken. Users cannot verify email addresses or recover accounts.

### Platform Security Engineer

**Assessment:** The NetworkPolicy egress allow-list is working as designed — it prevents unknown egress. The fix is straightforward but must be scoped correctly.

**Risks identified:**
1. **SMTP port exposure breadth:** Adding 465/587 to `podSelector: {}` means every pod in `loopzero-system` (Gitea, MinIO, ArgoCD, Prometheus, Grafana, Traefik, loopzero-api, tenant-controller) can now reach external SMTP servers. Unnecessary expansion of attack surface.
2. **Credential exfiltration via SMTP:** If any pod in the namespace is compromised, the attacker could use SMTP ports to exfiltrate data.
3. **Resend HTTP API alternative:** Resend offers an HTTP API on port 443, which is ALREADY allowed. If Kratos supports HTTP-based email delivery, this is strictly more secure.

**Objections:**
- **VETO** on adding SMTP ports to the blanket `podSelector: {}` policy. This opens SMTP for 10+ services that have zero need for it.
- If SMTP ports must be added, they MUST be scoped to a Kratos-specific NetworkPolicy with `podSelector` matching only the Kratos pod labels.

**Recommendation (ordered by preference):**
1. **Option A (Best):** Use Resend HTTP API instead of SMTP. Kratos v1.3.x supports HTTP courier via `courier.delivery_strategy: http`. Port 443 is already allowed. Zero NetworkPolicy changes needed.
2. **Option B (Acceptable):** Create a Kratos-specific NetworkPolicy that allows egress on 465/587 only for pods matching `app.kubernetes.io/name: ory-kratos`. Do NOT modify the blanket policy.
3. **Option C (Rejected/Vetoed):** Add SMTP ports to the blanket egress policy. Unacceptable attack surface expansion.

**Conditions for approval:**
- If Option A: verify Kratos HTTP courier actually works with Resend HTTP API format
- If Option B: pod selector must match ONLY Kratos pods, verified by label inspection
- Option C is vetoed

**Impact if ignored:** Unnecessary attack surface expansion if blanket policy is modified.

### Principal Architect

**Assessment:** This is a straightforward infrastructure configuration issue, not an architectural problem. The NetworkPolicy is doing its job — we just did not account for SMTP when we wrote the egress rules.

The key architectural question is: should Kratos use SMTP or HTTP API?

Kratos v1.3.x supports two courier delivery strategies:
1. `delivery_strategy: smtp` — traditional SMTP (current config)
2. `delivery_strategy: http` — sends a POST request with email payload to an endpoint

For Resend HTTP API, the payload format mismatch is the blocker: Kratos HTTP courier sends `{template_id, to, body, subject}`, while Resend expects `{from, to, subject, html}`. These are NOT directly compatible. Using HTTP courier would require a translation proxy/sidecar — adding operational complexity.

**Risks identified:**
1. Kratos HTTP courier may require a translation layer for Resend
2. Translation layer adds a new service to maintain

**Recommendation:** Option B (Kratos-scoped NetworkPolicy) is the pragmatic choice given the HTTP API incompatibility.

**Conditions for approval:** Verify Kratos HTTP courier payload format before ruling out Option A entirely.

**Impact if ignored:** Email delivery remains broken.

### K8s Controller Engineer

**Assessment:** From Kubernetes networking perspective, the diagnosis is clear. The `platform-egress-policy` uses an explicit egress allow-list. In K8s NetworkPolicy semantics, when a policy with `policyTypes: ["Egress"]` is applied, only traffic matching explicit rules is permitted. All other egress is denied.

DigitalOcean blocks port 25 (SMTP submission) on DOKS to prevent spam. Ports 465 (SMTPS) and 587 (SMTP+STARTTLS) are NOT blocked by DO. The timeout behavior (silent hang) is consistent with a NetworkPolicy drop, not a cloud-level firewall (which would send RST or ICMP unreachable).

**Risks identified:** None specific to the Kubernetes networking fix.

**Objections:** Agree with Security — the fix must be scoped to Kratos pods only, not blanket.

**Recommendation:** Option B (Kratos-scoped NetworkPolicy) is the safest Kubernetes-native fix.

**Conditions for approval:** Pod label selector must be verified against actual Kratos pod labels in the cluster.

**Impact if ignored:** Kratos courier will continue to fail silently, queuing emails that can never be delivered.

### Consensus Challenge (Orchestrator)

All agents agree on Option B. Challenging the consensus — what could go wrong?

1. **Pod label mismatch:** The Ory Kratos Helm chart may use non-standard labels. If `app.kubernetes.io/name: ory-kratos` is not correct, the scoped policy won't match. **Mitigation:** The chart uses `fullnameOverride: "ory-kratos"`, so standard Helm labels should apply. Verify with `kubectl get pods -n loopzero-system -l app.kubernetes.io/name=ory-kratos`.
2. **Resend IP blocking:** Resend might reject connections from DO IP ranges. **Mitigation:** Low probability; test after deployment.
3. **Queued email backlog:** Kratos courier may have queued emails that it cannot flush automatically. **Mitigation:** Kratos courier retries periodically. Force restart if needed.
4. **Multiple Kratos pods (courier + main):** The Helm chart may deploy separate pods for the courier worker. Both need the SMTP egress. **Mitigation:** Standard Helm labels should apply to all pods in the release.

## Stage 4 — Decision

**Chosen:** Option B — Create a Kratos-scoped NetworkPolicy that allows SMTP egress (ports 465 and 587) only for Kratos pods in the `loopzero-system` namespace. Implemented as a new `k8s.networking.v1.NetworkPolicy` resource in `createPlatformNetworkPolicies()` in `mgmt-bootstrap.ts`.

**Rejected:**
| Alternative | Reason |
|-------------|--------|
| Option A (Resend HTTP API) | Payload format mismatch between Kratos HTTP courier and Resend API requires a translation proxy — adds operational complexity for marginal benefit |
| Option C (Blanket egress modification) | Security VETO — opens SMTP for all 10+ pods unnecessarily |
| Local SMTP relay | Adds a new stateful service to maintain; unnecessary when the fix is a NetworkPolicy change |
| DO support ticket | Not needed — blocking is from our NetworkPolicy, not DO infrastructure (465/587 are not blocked by DO) |

**Trade-offs consciously accepted:**
- SMTP ports 465/587 are now reachable from Kratos pods to any external IP. A compromised Kratos pod could use these ports for exfiltration. Accepted because: (a) Kratos runs as non-root with read-only filesystem and drop ALL capabilities, (b) scope is limited to Kratos pods only, (c) the alternative (HTTP translation layer) adds more operational surface.

**Risks Blocked:** None.

## Root Cause Summary

**The SMTP port blocking is caused by our own NetworkPolicy, NOT by DigitalOcean.**

The `platform-egress-policy` in `mgmt-bootstrap.ts` (line 2357) uses an explicit egress allow-list that does not include SMTP ports (465, 587, 2525). Since Kubernetes NetworkPolicy with `policyTypes: ["Egress"]` denies all egress not explicitly allowed, Kratos cannot establish TCP connections to any SMTP server.

DigitalOcean DOKS blocks only port 25 (to prevent spam). Ports 465 and 587 are NOT blocked at the cloud infrastructure level.

**Fix:** Add a Kratos-scoped NetworkPolicy allowing egress on ports 465 and 587, matching only `app.kubernetes.io/name: ory-kratos` pods.
