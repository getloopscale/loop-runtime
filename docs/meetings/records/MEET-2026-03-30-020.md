## Stage 1 — Context

**Problem:** O fluxo de deploy do LoopZero cruza 4 planos (CLI → API → Build → Workload) em processos sincronos e assincronos. Troubleshooting depende de correlacionar logs manualmente pelo Correlation-ID em 3 clusters via Loki/LogQL. Nao ha distributed tracing.

**Decision Required:** Aprovar adicao de Grafana Tempo + OTel SDK na API Go para distributed tracing, conforme plano em `docs/plans/otel-distributed-tracing.md`.

**Constraints:**
- OTel Collector ja existe mas exporta traces para `debug` (descartadas)
- Correlation-ID middleware ja existe na API (UUID v4)
- Grafana ja no mgmt cluster com Prometheus + Loki datasources
- Zero instrumentacao OTel no codigo Go atual
- Pre-release: sem trafego externo, infra real em DigitalOcean
- 3 DOKS clusters (2 nodes each), recursos limitados

**Known Context:**
- Spec §15 (observability), §6 (architecture — 4 planes)
- Prometheus + Grafana + Loki stack funcional (Sprint H4)
- OTel Collector v0.96.0 deployado
- Plano detalhado: 3 fases, 16 tasks

## Stage 2 — Agent Analyses

### SRE / Production Readiness Engineer

**Assessment:** Proposta arquiteturalmente correta e bem-escopada. Porem, 4 gaps operacionais bloqueantes: zero alerting para o subsistema de tracing, sem health check para Tempo, sem rollback procedure, sem resource budget analysis.

**Key finding:** 7 failure modes identificados, 0 alerts dedicados. "Observability infrastructure without observing the observability infrastructure."

**Risks:**
- [HIGH] Zero alerting para tracing subsystem — silent failure
- [HIGH] Sem rollback procedure documentada — MTTR imprevisivel
- [MEDIUM] Correlation-ID format change quebra consumers
- [MEDIUM] Resource pressure no mgmt cluster (Tempo 256-512Mi em cluster ja pesado)
- [MEDIUM] Tempo PVC exhaustion sem alerta

**Objections:**
1. "Collector down perde traces" categorizado como Low no plano — deveria ser alerta critico
2. Task 1.6 (port-forward manual) nao e monitoring real — precisa ServiceMonitor
3. Correlation-ID unification sub-especificada — formato muda de UUID para W3C hex
4. Sem canary/progressive rollout

**Recommendation:** CONDITIONAL APPROVAL com 7 condicoes.

### Distributed Systems / Control Plane Engineer

**Assessment:** Plano "fundamentally misunderstands" como trace context propaga across async boundaries. A claim "uses trace linking, not child span" e a linha mais perigosa do documento inteiro.

**Key finding:** 4 async boundaries onde trace context e severed:
1. API → Argo Workflow CRD (K8s dynamic client, workflow pods sao processos separados)
2. BuildReconcileLoop (background goroutine com `context.Background()`)
3. ArgoCD callback (`SyncCallbackActivator` cria `context.Background()` na linha 66)
4. SSE event emission (PostgreSQL NOTIFY, sem trace context)

Resultado: traces cobrem ~30s iniciais do deploy, depois buraco de 2-10min onde os problemas reais moram.

**Risks:**
- [HIGH] Async boundary trace breaks criam traces incompletos e misleading
- [HIGH] Correlation-ID format change quebra Loki queries e dados persistidos
- [MEDIUM] OTel SDK no lock acquisition path adiciona risco de latencia
- [MEDIUM] Tempo local storage perde traces no pod restart

**Objections:**
1. "Trace linking for async" mencionado uma vez em risk table sem design concreto
2. Plano instrumenta a camada errada — operacoes longas sao externas (build, sync)
3. Correlation-ID unification e na verdade uma schema migration
4. ArgoCD nao propaga trace context nos webhooks
5. `context.Background()` em SyncCallbackActivator e load-bearing

**Recommendation:** DEFER Phase 2 ate resolver async trace linking.

Phase 2B e o trabalho real que exige armazenar `traceparent` na tabela `builds`. Distributed Systems correto no diagnostico; DEFER total excessivo.

### Confrontation 2: Correlation-ID — Manter ou Unificar?

**Agents:** Distributed Systems vs Architect

| Agent | Position |
|-------|----------|
| Distributed Systems | MANTER UUID v4, trace-id campo separado |
| Architect | UNIFICAR — pre-release permite breaking change |

**Resolution:** Distributed Systems correto. `correlation_id` persistido no banco como UUID v4. Mudar formato = migration + breaking change disfarçada. **Decisao: Correlation-ID permanece UUID v4. Trace-id e campo separado.**

### Confrontation 3: Alerting para Tracing Subsystem

**Agents:** SRE (unico defensor forte)

**Resolution:** SRE correto unanimemente. PrometheusRules + ServiceMonitor para Tempo obrigatorios na Phase 1.

### Consensus Challenge: Graceful Degradation

**Challenge by Orchestrator:** Todos aceitam "API funciona sem collector" mas ninguem questiona comportamento do gRPC exporter quando endpoint nao conecta. Default: retry com backoff exponencial infinito = goroutine leak.

**Resolution:** Export timeout = 1s, retry disabled no boot, bounded queue (2048 spans max).

## Stage 4 — Decision

### Chosen Approach

Implementar OpenTelemetry Distributed Tracing no LoopZero com Grafana Tempo como backend, OTel SDK na API Go, com escopo revisado em 4 phases (1, 2A, 2B, 3).

### Justification

1. O fluxo de deploy do LoopZero e o caso de uso ideal para distributed tracing — multi-cluster, async, com pontos de falha distribuidos
2. A infra base ja existe (Collector, Grafana, Correlation-ID)
3. Pre-release e o momento certo para estabelecer a base observacional
4. Escopo "tracing only" e correto — nao migrar metricas/logs
5. Graceful degradation garante zero risco para o deploy path

### Alternatives Rejected

| Alternative | Reason |
|-------------|--------|
| Jaeger instead of Tempo | Grafana stack complete exists; Tempo native integration (trace→log) |
| OTel for metrics+logs too | YAGNI — Prometheus and Loki are mature |
| Direct API→Tempo (no Collector) | Collector is routing plane — sampling, buffering, multi-consumer |
| Full DEFER | Troubleshooting cost grows with traffic; pre-release is the right time |
| Unify Correlation-ID with trace-id | Breaks Loki queries, PG data, CLI. Keep as separate fields. |

### Trade-offs Accepted

1. Partial traces in early releases (Phase 2A covers sync spans only; async gap stays for Phase 2B)
2. Additional resource on mgmt cluster (~256Mi RAM + 5Gi PVC) with lower PriorityClass
3. Tempo AGPL-3.0 — internal only, never exposed to end users

### Risks Accepted

| Severity | Risk | Mitigation | Owner |
|----------|------|------------|-------|
| Medium | Resource pressure on mgmt cluster | PriorityClass lower than PG/ArgoCD/API; resource audit before DO deploy | Infra Engineer |
| Medium | Tempo PVC full | PrometheusRule LoopZeroTempoStorageHigh (>80% for 10m) | Infra Engineer |
| Low | OTel SDK overhead | Export timeout 1s, bounded queue, latency test | API Engineer |
| Low | Tempo AGPL-3.0 | Internal only, documented | — |

### Risks NOT Accepted (resolved by conditions)

| Risk | Condition |
|------|-----------|
| Zero alerting for tracing subsystem | Condition 1 |
| Correlation-ID format break | Condition 2 |
| Async trace linking undefined | Condition 4 |
| Graceful degradation untested | Condition 5 |
| Existing tests broken | Condition 6 |

### Mandatory Actions (9 Conditions)

**BLOCKING Phase 1:**

1. **Alerting para tracing subsystem:**
   - `LoopZeroTempoDown`: `up{job="tempo"} == 0` for 2m (critical)
   - `LoopZeroTempoStorageHigh`: PVC >80% for 10m (warning)
   - `LoopZeroOTelCollectorDown`: `up{job="otel-collector"} == 0` for 2m (critical)
   - `LoopZeroCollectorExportErrors`: `otelcol_exporter_send_failed_spans_total` increasing for 5m (warning)
   - ServiceMonitor for Tempo (follow existing pattern)

**BLOCKING Phase 2:**

2. **Correlation-ID remains UUID v4.** Trace-id is separate field in slog and DB (new `trace_id` column in `builds` if needed). Grafana bridges via derived fields. NO changes to `Correlation-ID` header format.

3. **Span naming convention:** `loopzero.api.<operation>` (e.g., `loopzero.api.build.submit`, `loopzero.api.source.upload`). Document before instrumenting.

4. **Async trace linking design (for Phase 2B):** Store full `traceparent` (trace-id + span-id + flags) in `builds` table at submission. BuildReconcileLoop and SyncCallbackActivator reconstruct SpanContext and create linked spans. Design documented BEFORE implementation.

5. **Graceful degradation tested:** Export timeout = 1s, retry disabled on boot, bounded queue (2048 spans). Test: API without collector, 100 requests, p99 < 50ms, zero panics.

6. **Zero regression on existing tests:** `cd api && go test ./...` passes with OTel middleware active.

7. **Feature flag `LOOPZERO_TRACING_ENABLED`:** Default `true` in dev, `false` in prod initially. Flip to `true` after 48h validation on DO.

**RECOMMENDED Phase 1:**

8. **PriorityClass for Tempo:** Lower than PostgreSQL, ArgoCD, API, operators.

9. **Sampling config in Collector:** `probabilistic_sampler` processor with ratio 1.0 (default). Ready to tune without redeploy.
