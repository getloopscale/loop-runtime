## Stage 1 — Context

**Problem:** DigitalOcean Container Registry (Professional tier) has a hard cap of 100 GB storage. This is the highest tier offered — no upgrade exists. At 100k applications (~150 TB storage, ~1M live images, ~450 TB/month pull throughput), the current registry is mathematically infeasible. The registry must be migrated before Sprint 6 (image signing with cosign + syft).

**Decision Required:** Choose the container registry and storage backend for 100k concurrent applications. Decision includes: storage backend, registry runtime, HA topology, GC strategy, and migration plan.

**Constraints:**
- Pre-release: backward compatibility NOT required
- Must not block Sprint 6 (cosign + syft)
- YAGNI explicitly suspended — design for 100k from day zero
- 3 DOKS clusters in SFO3 (mgmt, build, workload)
- Cloudflare already in stack (Tunnel, Workers, KV, Zone Management)
- DO Spaces already in stack (4 buckets in production)
- Pull throughput: ~175 MB/s sustained at 100k
- ~1M live images (10 retained per app)

**Orchestrator Assumptions (validated by requester):**
1. Harbor back on the table as Option C
2. 100k apps = maturity target (24-36 months), architecture ready from day zero
3. No hard budget ceiling, but decisions >$10k/month need strong justification

**Known Context:**
- `pkg/naming/naming.go:257-259` — `ImageTag()` single source of truth for image references

## Stage 2 — Agent Analyses (Summary)

### Principal Architect
- **Recommendation:** Option A (DO Spaces + zot HA)
- **Key argument:** zot stays within "passive artifact store" boundary. Harbor introduces dual control plane (Harbor RBAC/GC compete with LoopZero's controllers). R2 splits storage topology across 2 vendors without justification.
- **Architectural modifications:** zot in build cluster (colocate with BuildKit), no Redis initially, replace DO API token with static htpasswd/OIDC auth.
- **VETO on Harbor:** Dual control plane — Harbor's projects/quotas/GC compete with LoopZero's TenantController, BuildReaper, ReleaseReaper.

### SRE / Production Readiness
- **Recommendation:** Option A (DO Spaces + zot HA + Redis)
- **VETO on Option B (R2):** Correlated failure with CF Tunnel. CF incident = total platform outage (runtime + static delivery + custom domains + registry + builds + cold pod starts). Unacceptable blast radius concentration.
- **VETO on Option C (Harbor):** Operational burden incompatible with team size. GC locks registry at scale.
- **Critical finding:** ZERO registry-specific alerts exist today. 8 of 9 failure modes have no alert. Monitoring package is non-negotiable BEFORE migration.
- **Conditions:** Dual-push migration, runbooks, synthetic canary, GC validation, readiness probe must verify S3 backend connectivity.

### Platform Security
- **Recommendation:** Option B (R2 + zot HA)
- **VETO on Option A (Spaces):** DO Spaces keys are account-scoped. Leaked Spaces key = access to ALL buckets (container images + source bundles + Pulumi state + Loki logs). Total platform compromise.
- **VETO on any option without fixing DO API Token as registry auth.** Current `buildkit-registry-config` contains the full DO API token — leaked build pod secret = full DO account control.
- **Critical pre-existing finding:** DO API Token used as Docker auth in build cluster. Blast radius: destroy all 3 DOKS clusters, delete PG, modify DNS, access Pulumi state.
- **Conditions:** Eliminate DO API Token as auth, bucket-scoped storage keys, OIDC auth with short-lived tokens, tenant image path authorization, admission policy to Deny mode, cosign key management plan.

### GitOps / Delivery
- **Recommendation:** Option A (DO Spaces + zot HA)
- **VETO on Option C:** Tag format change risk, operational weight disproportionate.
- **Critical finding:** Registry endpoint touches 11 distinct sites across 6 components. Migration requires atomic coordination.
- **Conditions:** Image mirroring before cutover, build quiescence during cutover, atomic config cutover, VAP update, immutable tags, dual-registry credential period (30 days), rollback test.

### Production Design Reviewer
- **Recommendation:** Option A (DO Spaces + zot HA), conditionally
- **Rejects Option B:** Cross-provider critical path architecturally incoherent for single-region.
- **Mandatory companion:** Spegel (P2P node cache) is non-negotiable at 100k. Reduces registry load 70-90%.
- **Conditions:** Load test Spaces throughput (200 MB/s sustained + 1 GB/s burst), load test zot at target scale, GC validation, fallback plan to Harbor documented.
- **Critical observation:** "The real question is not 'which registry' — it is 'can DO Spaces sustain the throughput.' Load test that first."

### Distributed Systems
- **Recommendation:** Option C (Harbor)
- **Core argument:** zot HA with BoltDB/Redis has no convergence proof for metadata layer. Push on replica A, pull on replica B → potential 404 during consistency window. PostgreSQL (Harbor) provides strong consistency. Only option with formal consistency guarantee.
- **Critical finding:** Tag-based image references (not digest-based) create correctness issue — retried build with same commit SHA produces different image, different nodes run different code.
- **Conditions (if zot chosen):** Empirical cross-replica consistency test, digest-based image references in manifests, failure injection testing.
- **DISSENT filed:** "zot HA does not have convergence proof. Load test is necessary but not sufficient."

## Stage 3 — Technical Confrontation

| Agent | Position |
|-------|----------|
| Distributed Systems | zot HA has no convergence proof. Split-brain metadata → push succeeds but pull returns 404. Recommends Harbor. |

**Resolution:** Empirical validation required as gate. Test: push on replica A, immediate pull on replica B, verify <1s latency. If test fails, Harbor returns as primary option with new meeting. Distributed Systems dissent registered.

## Stage 4 — Decision

**Chosen:** DO Spaces + zot HA (2-3 replicas + Redis for metadata coordination)

**Justification:**
1. Lowest operational surface (2-3 pods + Redis vs 15-20 for Harbor)
2. Same datacenter as compute (SFO3) — zero cross-cloud latency
3. Free egress within DO
4. Non-blocking GC (vs Harbor which locks)
5. ISP contract already exists in Pulumi — clean swap
6. Reversible: migration to Harbor is ~4 hours (same bucket, same OCI format)
7. Cost: ~$3k/month at 100k

### Alternatives Rejected

| Alternative | Rejected Because |
|-------------|-----------------|
| DO Container Registry | 100 GB hard cap. Infeasible above ~130 apps. |
| AWS ECR | Cross-cloud egress ~$12k/month at 10k apps. |
| GCP Artifact Registry | Worse egress than AWS. |
| GitHub Container Registry | Retail pricing (~$69k/month at 10k apps). |
| Cloudflare R2 + zot | SRE absolute veto: correlated blast radius with CF Tunnel. Production Design: cross-provider critical path incoherent for single-region. |
| Harbor + any backend | 4-agent supermajority against. Dual control plane, disproportionate opex, GC blocking at 1M images. Reserved as fallback. |

### Trade-offs Accepted

1. zot is CNCF sandbox (less mature than Harbor) — accepted: single Go binary, small codebase, OCI-compliant, replaceable
2. DO Spaces has no published throughput SLA — accepted conditionally: load test is mandatory gate
3. Metadata eventual consistency in zot HA — accepted conditionally: empirical cross-replica test is mandatory gate
4. DO lock-in for storage — accepted: all compute already on DO, incremental lock-in is marginal

### Risks Accepted

| Risk | Severity | Mitigation | Owner |
|------|----------|------------|-------|
| zot GC untested at 1M images | MEDIUM | Test GC with 100k synthetic images before reaching scale | Infra Engineer |

| zot project abandoned | LOW | OCI-compliant → replaceable by distribution/distribution or Harbor | — |

## Pre-existing Critical Findings (discovered during meeting)

These findings exist REGARDLESS of registry choice and should be addressed immediately:

1. **[CRITICAL] DO API Token used as Docker registry auth** — `buildkit-registry-config` contains base64(DO_TOKEN:DO_TOKEN). Leaked build pod secret = full DO account control. Files: `infra/pulumi/src/components/build-bootstrap.ts:70-71`, `infra/pulumi/src/components/mgmt-bootstrap.ts:2137`.

2. **[CRITICAL] No tenant isolation on image access** — any authenticated entity can pull any tenant's images. Only naming convention prevents cross-tenant access. At 100k tenants, this is a data breach vector.

3. **[HIGH] VAP admission policy in Audit mode** — `vap-restrict-image-registries` uses `validationActions: [Audit]`, not `Deny`. Compromised deployment can reference arbitrary registries.

4. **[HIGH] Zero registry-specific monitoring** — 8 of 9 failure modes have no alert. `LoopZeroAppImagePullFailed` is reactive (5 min delay).

5. **[MEDIUM] CI registry token expiry at 3600s** — `build-images.yml:163` uses `--expiry-seconds 3600`. Should be 300-600s (SEC-003).
