## Stage 1 — Context

**Problem:** Cross-validation LoopZero vs Epinio e analise de PaaS de referencia (Korifi, Heroku, Fly.io) revelaram que o modelo de convergencia do LoopZero — ArgoCD com manual sync — pode nao escalar e adiciona complexidade operacional desproporcional ao valor. Evidencias reais de benchmarks (CNOE: 50k apps testados, ApplicationSet controller single-threaded) e de PaaS alternativos (Korifi: zero ArgoCD, controller-runtime direto) fundamentam a discussao.

**Decision Required:** O LoopZero deve manter ArgoCD como mecanismo de convergencia, migrar para ApplicationSets, ou substituir por controller-runtime direto?

**Evidence Base (real data, not empirical):**
- CNOE benchmark (AWS EKS): 50k apps, sharding necessario acima de ~400/shard, single shard satura em 30k no m5.2xlarge
- GitHub Discussion #19113: 250 AppSets, 5k apps, 5-10 min reconcile, AppSet controller NAO escala horizontalmente
- Korifi (Cloud Foundry on K8s): zero ArgoCD, controller-runtime direto, CRDs reconcilados em StatefulSets
- Epinio: zero ArgoCD, Helm install direto via mittwald/go-helm-client
- Heroku: slug compiler + dyno manager imperativo, zero GitOps
- Fly.io: Machines API imperativa, Firecracker microVMs, zero K8s

**Constraints:**
- Pre-release phase — backward compatibility not required
- ArgoCD 2.13.3 deployed with manual sync policy
- 7 existing controllers in operators/
- ADR-0007 (ArgoCD Application model) already PROPOSED

---

## Stage 2 — Agent Analyses (Summary)

### Principal Architect — REMOVE ArgoCD

**Core argument:** "5 compensation mechanisms = abstraction is in the wrong place." ArgoCD with manual sync is imperative orchestration routed through a GitOps tool. The API triggers sync, polls status, terminates stuck operations, retries — re-implementing convergence around ArgoCD.

**Key evidence from code:**
- 6-hop deploy path: API → Gitea push → ArgoCD TriggerSync → ArgoCD applies → callback → API activates
- 5 workaround mechanisms: ReleaseConvergenceLoop, SyncCallbackActivator, CircuitBreakerSyncClient, triggerSyncWithRetry, TerminateOperation
- `ParseArgoAppName` relies on `LastIndex("-")` — breaks for hyphenated env names
- Phase plan: 4 weeks, phased migration, Korifi validates the pattern

### Distributed Systems — NEUTRAL (keep for now, decide later)

**Core argument:** Triple convergence path (callback + poll + reaper) is correct defense-in-depth. Each layer covers distinct failure modes. The idempotency guard in `ActivateReleaseKernel` is sound.

**New bug found:** `SetGitCommit` failure treated as non-fatal in `container_delivery.go:258-260`. If `SetGitCommit` fails, `release.GitCommit` is empty, and the revision guard in `SyncCallbackActivator` is bypassed — allowing wrong-version activation.

**Position:** ArgoCD vs direct apply is a T3 decision requiring its own meeting. Not ready to decide today.

### SRE — REMOVE ArgoCD

**Core argument:** Fewer components = lower MTTR. Rollback depends on Gitea being up (SPOF). Manual sync = paying operational cost without getting operational value.

**Critical finding:** Gitea is a SPOF for rollback. If Gitea PVC corrupts and app is broken, `loopzero rollback` cannot fetch old manifests from git history. No fallback path.

**Key operational comparison:**
- Current: 6 external dependencies in deploy critical path
- Direct apply: 3 external dependencies
- Current: ArgoCD stuck 409 at 3 AM requires understanding sync semantics
- Direct apply: "did apply succeed?" is a simpler question

### GitOps Engineer — KEEP ArgoCD

**Core argument:** Removing ArgoCD requires reimplementing sync, prune, health assessment, drift detection, and audit trail. This is 6-12 months of engineering. "Don't Reinvent the Wheel."

**Key analysis:**
- ArgoCD prune covers hundreds of K8s resource types with custom health checks
- CNOE tested at 50k apps — LoopZero is nowhere near scale limits
- Triple activation (callback + convergence + reaper) is defense-in-depth, not accidental complexity
- ApplicationSets not worth it at current scale (YAGNI)

### K8s Controller Engineer — KEEP ArgoCD

**Core argument:** Prune correctness is CRITICAL risk. WorkloadReconciler would be 3-5x more complex than any existing LoopZero controller. ArgoCD is MIT-licensed, 18k commits, battle-tested on exactly these problems.

**Function-by-function replacement assessment:**
| Function | Complexity to Replace | Risk |
|----------|----------------------|------|
| Manifest apply | Moderate (server-side apply) | LOW |
| Prune | HIGH (resource tracking, ordering, finalizers) | CRITICAL |
| Health status | HIGH (rollout semantics, per-resource) | MEDIUM |
| Sync notification | LOW (CRD status or event) | LOW |
| Multi-cluster apply | Moderate (existing pattern) | LOW |

## Stage 3 — Confrontations

### Confrontation 1: "5 Compensation Mechanisms" — Wrong Abstraction or Defense-in-Depth?

| Agent | Position |
|-------|----------|
| **Architect** | Compensation for ArgoCD's limitations, not resilience. Signal that the boundary is wrong. |
| **DistSys** | Defense-in-depth. Each layer covers distinct failure modes. Removing any one degrades reliability. |

**Resolution:** Both are partially correct. The mechanisms exist because LoopZero disables auto-sync (manual sync only). Auto-sync would eliminate 3 of 5 mechanisms, but creates race conditions with API-triggered deploys. **The root cause is using ArgoCD in a mode that negates its primary value proposition (declarative convergence).**

### Confrontation 2: Prune Risk — "Rebuild ArgoCD" or "Scoped Problem"?

| Agent | Position |
|-------|----------|
| **GitOps + K8s Controller** | Prune for hundreds of resource types requires years of battle-testing. Don't Reinvent. |
| **Architect** | LoopZero generates 4 resource types. Label-based prune for 4 types is tractable. |
| **SRE** | Prune bug = production workload deletion. Blast radius is total. |

**Resolution:** LoopZero generates exactly Deployment, Service, ConfigMap, IngressRoute (+ cert-manager Certificate). Prune for 5 known types is NOT "rebuilding ArgoCD's prune." BUT prune edge cases (rollout in progress, finalizer-blocked pod, foreground deletion ordering) are real. **The risk is manageable with scoped implementation + exhaustive envtest, not with 6-12 months of generic prune engineering.**

### Confrontation 3: Scale Relevance

| Agent | Position |
|-------|----------|
| **Architect** | CNOE benchmark is irrelevant. YAGNI. |
| **GitOps** | Agrees. Scale is not the problem. |

**Resolution:** UNANIMOUS — scale is not the deciding factor. The decision is about operational complexity vs engineering effort.

### Confrontation 4: Orchestrator Challenge — What About Flux?

None of the 5 agents discussed Flux CD as an alternative. This is a blind spot.

**Flux advantages for LoopZero:**
- Lighter than ArgoCD (no UI, no server, no Redis)
- Kustomize controller handles apply + prune + health natively
- Multi-tenancy via Flux tenancy model
- Notification controller for push-based events
- HelmRelease and Kustomization CRDs are declarative

**Flux risks:** Different ecosystem, different community, different operational knowledge. Migration from ArgoCD to Flux is still a migration.

**Resolution:** Flux is noted as a viable alternative in the ADR but NOT evaluated in depth. If the team decides to remove ArgoCD, both direct-apply AND Flux should be evaluated as replacements.

## Stage 4 — Decision Synthesis

### Chosen Approach

**PHASE 0 (now): Fix critical bugs. PHASE 1 (next sprint): Evaluate ArgoCD removal in dedicated T3 sprint with POC.**

This is NOT a decision to keep or remove ArgoCD. This is a decision to:
1. Fix the bugs found in this meeting IMMEDIATELY
2. Run a time-boxed POC (2 weeks) to measure the actual engineering effort of direct apply
3. Make the final keep/remove decision based on POC evidence, not projections

### Rationale

The meeting revealed a genuine 2-2-1 split. The arguments on both sides are technically valid:
- Architect and SRE are correct that ArgoCD with manual sync provides diminished value for its operational cost
- GitOps and K8s Controller are correct that prune/health are non-trivial to replace
- DistSys is correct that this is a T3 decision requiring more evidence

A decision made today without a POC would be based on projections, not evidence. The user explicitly requested "99% confidence with real evidence." We do not have that for either direction yet.

### Immediate Actions (APPROVED unconditionally)

**Action 1: Fix SetGitCommit bug (P0, same day)**
`container_delivery.go:258-260` treats `SetGitCommit` failure as non-fatal. This bypasses the revision guard in `SyncCallbackActivator`, allowing wrong-version activation. Fix: make `SetGitCommit` failure fatal OR treat empty `GitCommit` in the callback as "do not activate, let convergence loop handle."

**Action 2: Fix syncRetriggers memory leak**
`ReleaseConvergenceLoop.syncRetriggers` map entries are never cleaned up. Add cleanup when release exits PENDING state.

**Action 3: Update ADR-0007 with new Option D (Flux CD)**
Add Flux as a fourth option in the evaluation matrix. Not evaluated in depth, but documented for completeness.

### POC Specification (APPROVED — time-boxed 2 weeks)

**Goal:** Build a minimal `WorkloadReconciler` controller that replaces ArgoCD for LoopZero's specific use case. Measure: lines of code, test coverage for prune edge cases, deploy latency, and operational complexity.

**Scope:** Apply + Prune + Health for 5 resource types (Deployment, Service, ConfigMap, IngressRoute, Certificate). Server-side apply. Label-based ownership for prune. Deployment rollout health check.

**NOT in scope:** Drift detection (defer), multi-source (LoopZero doesn't need), Helm/Kustomize (LoopZero uses raw YAML).

**Success criteria:**
- Deploy E2E: API → controller → pod Running (measure latency vs current ArgoCD path)
- Prune E2E: delete project → resources removed from cluster (verify correctness)
- Health E2E: deploy broken image → controller reports Degraded (verify detection)
- At least 15 envtest cases covering prune edge cases
- Lines of code < 1000 (excluding tests) — if it exceeds this, the "don't reinvent" argument wins

**After POC:** Reconvene meeting with POC results. Make final decision based on measured evidence.

### Alternatives Rejected

| Alternative | Why Rejected |
|-------------|-------------|
| Decide to remove ArgoCD today | 2-2 split. No POC evidence. Prune risk is real but unmeasured. |
| Decide to keep ArgoCD forever | Manual sync negates core value. 5 compensation mechanisms. Technical debt grows. |
| Migrate to ApplicationSets now | YAGNI. 1 tenant in production. ApplicationSet controller is SPOF. |
| Migrate to Flux CD now | Untested alternative. Same migration effort, different ecosystem. |

### Trade-offs Accepted

1. The POC costs 2 weeks of engineering time. If the conclusion is "keep ArgoCD," the POC code is discarded. This is an acceptable cost for a T3 decision.
2. The SetGitCommit fix and memory leak fix are done regardless of the ArgoCD decision.
3. ADR-0007 remains in PROPOSED status until the POC completes.

### Risks Accepted

| Severity | Risk | Mitigation | Owner |
|----------|------|------------|-------|
| HIGH | POC may reveal prune is harder than Architect estimates | If > 1000 LOC or > 15 edge cases unresolvable, keep ArgoCD | POC Owner |
| MEDIUM | 2-week POC delays other sprint work | Time-boxed. If no conclusion in 2 weeks, keep ArgoCD as default. | Engineering Lead |
| LOW | Flux evaluation deferred | Not blocking. Documented in ADR-0007 as future option. | — |

### Risks NOT Accepted (Blockers)

| Severity | Risk | Required Action | Owner |
|----------|------|-----------------|-------|
| CRITICAL | SetGitCommit non-fatal → wrong-version activation | Fix BEFORE any other work. Make SetGitCommit fatal or invert revision guard. | API Engineer |

### Vetoes

None. No agent exercised veto power. The SRE noted operational concerns but did not veto — the bugs are being fixed and the POC is time-boxed.

### Dissents

| Agent | Position | Accepted? |
|-------|----------|-----------|
| **Principal Architect** | Should decide to remove ArgoCD now, not defer to POC | No — insufficient evidence for 99% confidence. POC provides the evidence. |
| **GitOps Engineer** | "Removing ArgoCD violates Don't Reinvent the Wheel" | Partially — the POC will measure whether replacement is truly "reinventing" or "scoped implementation" |
| **K8s Controller** | "Prune will have bugs" — requests 25+ envtest cases if removal proceeds | Accepted as POC requirement |
