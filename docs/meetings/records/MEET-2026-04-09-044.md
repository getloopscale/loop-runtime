## Stage 2 — Analyses

### Principal Architect

CTO verdict is accurate. The release improves production for real. All 7 points are correctly calibrated risks, not rejections.

**Assessment by point:**
1. Auto-deploy — gaps are real and compound. Advisory lock catches concurrent submits but only after wasted S3/download work. Superseded-push is the most serious sub-gap.
2. Custom Domains — CF API calls without timeout are the first fix needed; periodic reconciliation is the second.
3. Manifest gate — this is a mitigation note. Per-project ArgoCD Applications is architectural debt for P2/P3.
4. Build GC — single-class retention works at current scale. Class differentiation is sound operations but not urgent.
5. PG failover — code fixes unproven. P0 until empirical test passes.
6. Revision mismatch — three counters are small implementation. Fix exists, observability missing.
7. Framework drift — "Mirrors — kept in sync" is a broken promise waiting to happen. Three-way drift (CLI, routes, build_plan) will cause user-visible failures.

**Risks not accepted:** PG failover untested (P0), CF API no timeout (P0).

### SRE Engineer

Focus: production observability, failover reliability, runbook completeness.

Point 5 is the most critical operationally. Worst-case failover gap: ~75s where no leader exists (keepalive detection + heartbeat timeout + re-election). This is acceptable IF proven. The auto-deploy + PG failover combination creates a data-loss scenario (not duplication): webhook fires, build transaction rolls back on failover, deploy is silently lost. Always-200 response means no GitHub retry; the deploy is gone.

Point 6: three specific counters needed — loopzero_argocd_revision_mismatch_total, loopzero_argocd_resync_triggered_total, loopzero_argocd_resync_failure_total.

Point 2: CF API calls (CreateZone, ScanDNS, CreateRecord) need per-call timeout (5-10s) + exponential backoff. A single hanging CF API call can block the domain provisioner goroutine indefinitely.

Runbook gaps identified:
1. No runbook for PG failover (detection time, re-election time, when to escalate)
2. No runbook for CF zone stuck-provisioning recovery

### Distributed Systems Engineer

Point 1c (superseded-push) is the most serious gap and should be P0, not P1. The failure mode: three rapid pushes, first push gets the advisory lock, second and third are rejected with 409. First push's commit deploys. The LATEST commit does NOT deploy. User pushed a fix, gets old code. This is directly backwards from the Vercel model the product promises.

Current advisory lock provides correctness (no double-release) but not intended behavior (latest-commit-deploys). Correct fix: queue-with-supersede. When new push arrives and build is running, cancel running build and start new one.

Point 5 + auto-deploy cross-risk: webhook fires → goroutine starts download+S3 → calls withEnvironmentLock → PG failover rolls back transaction → build not in DB → deploy silently lost. Delivery_id persistence enables replay recovery.

Point 7: three independent lists = three-way drift. User adds framework to CLI → validator approves → API resolveLanguageStrategy returns "custom" → Dockerfile required → build fails with confusing error.

### DX Engineer

Point 7 is the primary DX concern. Concrete drift scenario: developer adds framework to CLI detection/ → validator approves → API routes/builds.go isUnknownFramework is OK (if list was updated) → resolveLanguageStrategy returns "custom" → user gets "Dockerfile required" error for a known framework. Or: developer updates build_plan.go but not routes/builds.go → 422 error for a supported framework.

Recommended fix: single struct/map in build_plan.go (framework → strategy); isUnknownFramework in routes/builds.go delegates to build_plan package; CLI uses generated or bundled list with lint check (CLI list must be a superset of API list).

Point 1 dead-letter: the higher-priority fix is commit status set to "failure" on all error paths in HandlePush. Currently, commit status is only set to "pending" after successful submission. S3 upload failure, build submitter failure — user sees nothing. A GitHub commit status "failure" with description is the user-visible signal.

Point 2: domain status UX for stuck states. When `loopzero domain add` leaves user at pending_ns for hours, is there actionable guidance? This is a user-facing gap distinct from the operator-facing dashboard.

## Stage 3 — Confrontation

### Conflict 1: Superseded-push priority (Point 1c)

| Agent | Position |
|-------|----------|
| Principal Architect | P1 — lock prevents correctness failure; auto-deploy is not the only deploy path |
| Distributed Systems | P0 — first push deploys, not latest; directly contradicts Vercel model promise |

**Resolution:** Distributed Systems is correct. The failure is user-visible: user pushes a fix commit immediately after a broken commit; broken commit deploys because it got the lock first. This is not capacity waste — it is incorrect behavior. **Superseded-push deduplication: P0.**

Caveat: full queue-with-supersede requires a build cancellation path. Minimum viable fix: when new push arrives for same env and a build is QUEUED (not yet RUNNING), cancel the QUEUED build before submitting new one. Builds already RUNNING complete. This is the minimum that prevents the backwards-deploy scenario for rapid pushes.

### Conflict 2: Dead-letter priority (Point 1d)

| Agent | Position |
|-------|----------|
| Principal Architect | P2 — logging covers diagnostics |
| SRE | P1 — silent drops invisible in production |
| Distributed Systems | P1 (elevated) — PG failover creates silent data loss, not just diagnostic gap |
| DX Engineer | Commit status on failure path is higher DX value than dead-letter table |

**Resolution:** Two separate issues collapsed into "dead-letter":
1. Commit status "failure" on error paths (P1) — user-visible, small change in HandlePush
2. Dead-letter/persistence table (P2) — operational recovery, GitHub dashboard covers near-term

**Dead-letter table: P2. Commit status on failure paths: P1.**

### Consensus Challenge

All four agents agree on PG failover as P0. Challenge: is the failover test sufficient, or do we need an automated chaos test in CI? Conclusion: a one-time controlled test on staging with documented results is the right bar for pre-launch. Automated chaos in CI is Sprint 8 scope. The test must produce a written result: detection_time, re-election_time, duplicate_builds_count.

## Stage 4 — Decision

**Chosen:** Full agreement with CTO's 7 points. All risks are real and correctly identified. Priority calibration adjusted from CTO's framing on superseded-push (P0, not implicit P1).

**Rejected alternatives:**
- Superseded-push as P1: rejected — first-push-wins is a correctness failure for the product promise
- Dead-letter before commit status: rejected — commit status uses existing GitHub App integration, faster user value
- Per-project ArgoCD Applications as near-term: deferred to P2/P3 — architectural cost not justified before 100 tenants

**Trade-offs consciously accepted:**
- Dead-letter table (P2): GitHub delivery dashboard covers operator diagnostics at early scale
- Domain funnel Grafana dashboard (P2): raw Prometheus metrics queryable; no urgency before 10 tenants
- Build GC class differentiation (P2): single 30d policy prevents unbounded growth; optimization deferred
- Delivery_id idempotency (P1): mitigated by always-200 response; risk is manual operator replay only

**Risks Accepted:**
- 75s worst-case leader gap during PG failover: acceptable IF proven by controlled test (P0)
- No revision mismatch metrics: acceptable short-term, logging provides diagnostic trail (P1 action)

**Risks NOT Accepted (block until resolved):**
- PG failover behavior unproven empirically
- CF API calls without per-call timeout (goroutine hang risk)
- Superseded-push: first-push-wins instead of latest-push-wins

**Mandatory Actions:**

1. [P0] Add per-call timeout (5-10s) + exponential backoff (3 attempts) to cfzone HTTP client for all zone operations (CreateZone, ScanDNS, CreateRecord, DeleteZone, DeleteRecord). Owner: api-engineer.

2. [P0] Run controlled PG failover test on staging. Kill PG primary, measure: detection_time, re-election_time, duplicate_builds, silent_lost_deploys. Document results. Pass criteria: detection ≤ 60s, re-election ≤ 90s, zero duplicates. Owner: sre-engineer (infra-engineer for infrastructure kill; api-engineer for result verification).

3. [P0] Implement superseded-push minimum viable fix: when new webhook push arrives for (tenant, project, env) and a QUEUED build exists for that env, cancel the QUEUED build before submitting new one. Builds in RUNNING state are not cancelled (acceptable trade-off). Owner: api-engineer.

4. [P1] Set GitHub commit status to "failure" (with descriptive message) on all error paths in HandlePush: S3 upload failure, build submitter failure, loopzero.yaml parse error for linked repos. Owner: api-engineer.

5. [P1] Add three Prometheus counters for ArgoCD revision mismatch: loopzero_argocd_revision_mismatch_total, loopzero_argocd_resync_triggered_total, loopzero_argocd_resync_failure_total. Emit from release_convergence_loop.go. Owner: api-engineer.

6. [P1] Consolidate framework mapping: isUnknownFramework() in routes/builds.go must delegate to a shared function/map in build_plan.go package instead of duplicating the list. Remove the "Mirrors — kept in sync" comment. Add a CI lint check (or test) that verifies the two Go lists are identical. Owner: api-engineer.

7. [P1] Extend framework synchronization to CLI: add a test or script that asserts CLI's supported framework list (cli/src/detection/) is a superset of the API's resolveLanguageStrategy map. Fails CI if drift detected. Owner: cli-engineer.

8. [P1] Implement periodic CF zone state reconciliation loop: background goroutine that, for each domain in state ns_active or provisioning, calls CF API to verify zone status matches DB state. On divergence: log + emit DomainCFZoneErrors metric + set domain to error state for re-provisioning. Interval: 15 minutes. Owner: api-engineer.

9. [P1] Store GitHub webhook delivery_id in a github_webhook_deliveries table (delivery_id UNIQUE, received_at, status, error). Check on receipt; skip processing if already seen. Owner: api-engineer (T1 — migration + store method + handler check).

10. [P2] Define differentiated GC retention: builds metadata (90d), build_events (14d). Update BuildGC config and document Loki retention as separate concern. Owner: api-engineer.

11. [P2] Add domain provisioning funnel Grafana dashboard: panels for domains by state (pending_ns / ns_active / provisioning / active / error), NS propagation duration histogram, CF zone error rate. Owner: sre-engineer.

12. [P2] Implement webhook dead-letter: persist GitHub push events before dispatch; mark failed events for operator replay. Owner: api-engineer.

13. [P3 roadmap] Per-project ArgoCD Applications: architectural migration away from single-Application-per-tenant. Track as spec §6 architectural debt item. No action before 100 tenants.
