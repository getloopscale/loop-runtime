**Problem:** Cross-validation between LoopZero PaaS and Epinio PaaS revealed critical architectural and operational problems. The original analysis identified 3 CRITICAL, 4 HIGH, and 3 MEDIUM issues. **Decision Required:** Which corrections to approve, in what order, with what test strategy.

**Constraints:**

## Stage 2 — Agent Analyses

### 2.1 Principal Platform Architect

**Assessment:**
- Triple state (PG + CRDs + ArgoCD) is a justified trade-off, not a flaw. Each store owns a distinct concern: PG for transactional workflow state, CRDs for declarative infrastructure intent, ArgoCD for sync/health.
- The gap is post-activation health reconciliation — once a release is ACTIVE, nobody verifies ArgoCD stays healthy.
- CRITICAL-2 as stated is WRONG: it is 1 Application per environment, not per tenant.
- CRITICAL-3 is NOT a flaw: manifest generation in API is architecturally correct (build plane should not write to GitOps repo).
- HIGH-3 is INCORRECT: ArgoCD does not block API startup.
- Drain-on-shutdown is a confirmed bug.

**Recommendation:** P0: drain-on-shutdown. P1: extend ReleaseConvergenceLoop to monitor ACTIVE releases + per-project notification scoping. Reject manifest-gen-in-workflow and per-project ArgoCD Applications.

**Risks:** [CRITICAL] Post-activation health drift. [HIGH] Drain-on-shutdown race. [HIGH] Cross-project blast radius within environment.

### 2.2 Staff Distributed Systems Engineer

**Assessment:**
- System converges correctly for build-to-deploy path but has a convergence gap post-activation.
- Discovered NEW P0 bug: `ActivateReleaseKernel` can be called concurrently by SyncCallbackActivator and ReleaseConvergenceLoop. Second call panics on invalid state machine transition (ACTIVE has no SyncCompleted event). SyncCallbackActivator HTTP handler has NO panic recovery.
- Single ArgoCD Application per environment IS structurally broken — must change to per-project.
- RELEASING state machine + reconcile loop retry is well-designed crash recovery (CRITICAL-3 is overstated).
- Advisory lock prevents DB-level races but not duplicate activation race.

**Recommendation:** P0: fix duplicate activation race (5-line idempotency guard in ActivateReleaseKernel). P1: per-project ArgoCD Applications. P2: post-activation health monitoring. P3: drain-on-shutdown.

**Risks:** [CRITICAL] Duplicate activation panic in production. [CRITICAL] Per-environment blast radius. [HIGH] No drain-on-shutdown.

### 2.3 Staff SRE / Production Readiness Engineer

**Assessment:**
- **VETO** on going to production without addressing silent state divergence.
- Discovered phantom alert: `loopzero_drift_detected` referenced in PrometheusRules but metric never emitted. This is the most dangerous class of false green.
- `LoopZeroOrphanBuild` alert referenced in code comments but PrometheusRule does not exist.
- HIGH-3 already mitigated by circuit breaker pattern.
- Missing critical metrics: reconcile loop latency, gitops operation duration, releases pending gauge, state divergence count.

**Recommendation:** P0: emit `loopzero_drift_detected` metric or remove phantom alert, add `LoopZeroOrphanBuild` PrometheusRule, implement state divergence detection, add `loopzero_releases_pending` gauge. P1: drain-on-shutdown, reconcile loop heartbeat, gitops latency histogram.

**Risks:** [CRITICAL] Phantom alert gives false confidence. [CRITICAL] Silent state divergence undetected. [HIGH] Missing orphan build alert.

### 2.4 Staff GitOps / Delivery Engineer

**Assessment:**
- GitOps model is architecturally sound: Gitea is genuine source of truth, API is sole writer, audit trail is complete.
- Discovered convergence loop gap: `ReleaseConvergenceLoop` polls ArgoCD status but NEVER triggers sync. With manual sync policy, if initial `TriggerSync` fails after git push, release stuck in PENDING forever.
- Discovered notification callback gap: `SyncCallbackActivator` activates ALL pending releases for a tenant-environment without verifying the synced revision matches the expected git commit. Rapid sequential deploys could activate wrong version.
- Git CLI subprocess is fragile (exec.Command, string parsing, no rate limiting).
- ArgoCD startup dependency (ValidateToken) should be background health check.

**Recommendation:** P1: convergence loop must retry sync triggers. P2: revision verification on notification callback. P3: decouple API startup from ArgoCD. P4: per-project ArgoCD Applications. P5: go-git migration.

**Risks:** [HIGH] Stuck releases when TriggerSync fails. [HIGH] Wrong version activation via callback. [MEDIUM] Partial state between git push and ArgoCD sync.

### 2.5 Staff API / Domain Architect

**Assessment:**
- "The LoopZero API is an operator wearing an API costume." 6 background goroutines running controller-like reconciliation loops.
- API cannot scale horizontally: 2 replicas = duplicate reconcile processing, wasted work, potential races.
- BuildReconcileLoop is a Kubernetes controller that does not use controller-runtime (no leader election, no watch-based triggers, no backoff queues).
- Manifest generation couples API to Kubernetes resource schemas.
- ActivateReleaseKernel as single source of truth for activation is the ONE well-designed decision.

**Recommendation:** Phase 0 (now): document single-replica constraint, add leader election guard. Phase 1 (before HA): extract reconcile loops to standalone binary/operator. Phase 2 (before scale): move manifest gen. Phase 3 (optional): convert reapers to CronJob.

**Risks:** [CRITICAL] Horizontal scaling impossible. [CRITICAL] API crash kills all reconciliation. [HIGH] Manifest gen couples API to K8s schemas.

### 2.6 Staff Test & Verification Architect

**Assessment:**
- Verification maturity is moderate for existing system, absent for proposed corrections.
- Every cross-validation finding has zero test coverage.
- Rollback tests use only fakes — hide real bugs (supersede bug was found in production, not tests).
- E2E failure scenarios are all `PIt` (Pending).
- Integration test pattern exists (concurrent builds test is gold standard) but not applied to rollback or state divergence.

**Recommendation:** Conditional approval. Each correction MUST follow TDD. Rollback integration test is highest-leverage item. State divergence monitor test second.

**Conditions:** No correction merges without its corresponding test passing.

## Stage 3 — Confrontations

### Confrontation 1: Per-Project ArgoCD Applications vs Notification Scoping

| Agent | Position |
|-------|----------|
| **Principal Architect** | AGAINST per-project. Notification scoping at resource level is sufficient. Per-project multiplies Application count (150 vs 30 for 10 tenants × 3 envs × 5 projects). Operational overhead not justified. |
| **Distributed Systems** | FOR per-project. Blast radius is unbounded. Notification scoping doesn't fix the convergence loop which also checks per-Application health. |
| **GitOps** | FOR per-project but acknowledges it's T3. Per-resource health check mitigates polling path but NOT notification path. |
| **SRE** | Neutral. Blast radius is real but scoped to environment. Document as known limitation with migration plan. |

**Resolution:** DIVERGENCE — Principal Architect vs Distributed Systems. Per governance Rule 4, this triggers a **mandatory ADR**. The ADR must evaluate both approaches (notification scoping vs per-project Applications) with concrete blast radius analysis. Decision deferred to ADR. In the interim, document the limitation and implement per-resource health filtering in the convergence loop as a partial mitigation.

### Confrontation 2: Manifest Generation Location

| Agent | Position |
|-------|----------|
| **Principal Architect** | KEEP in API. Build plane should not have GitOps write access or deployment topology knowledge. |
| **Distributed Systems** | KEEP in API. Moving to workflow reintroduces the C-02 problem already fixed. |
| **GitOps** | KEEP in API. LOW priority, YAGNI. |
| **API Domain** | MOVE to workflow or controller. It's control plane logic in developer plane. |

**Resolution:** REJECTED (4 vs 1). Manifest generation stays in the API/control plane. The build plane produces artifacts only. The API Domain Architect's concern is noted for the Phase 1 extraction plan (when reconcile loops move to operator, manifest gen goes with them).

### Confrontation 3: SRE Veto on State Divergence

| Agent | Position |
|-------|----------|
| **SRE** | VETO — cannot go to production without state divergence detection. Phantom alert makes it worse. |
| **Principal Architect** | Agrees gap exists but frames as monitoring problem, not architecture problem. Extend existing convergence loop. |

**Resolution:** SRE VETO STANDS (absolute veto per governance Rule 3). State divergence detection is a P0 blocker for production. Implementation approach: extend `ReleaseConvergenceLoop` to also poll ACTIVE releases (Architect's recommendation), emit metrics (SRE's requirement), and fix the phantom alert.

### Confrontation 4: API as Operator — Extract Now or Later?

| Agent | Position |
|-------|----------|
| **API Domain** | Architectural debt. Document single-replica constraint NOW. Extract before HA. |
| **Principal Architect** | Not addressed directly. |
| **SRE** | Not a production readiness concern for single-replica. |

**Resolution:** ACCEPTED as known technical debt. Document single-replica constraint in operational runbooks. Add leader election advisory lock as startup guard. Extract reconcile loops in Phase 1 (before HA/scaling). This is NOT a blocker for first external user.

### Confrontation 5: Orchestrator Challenge — What Are We Not Seeing?

All agents converged on similar findings. I challenge: **what happens if the PostgreSQL connection pool exhausts during a burst of concurrent deploys?**

- Advisory locks hold connections. Each deploy holds a connection for the duration of `withEnvironmentLock`.
- `BuildReconcileLoop` uses its own connections for polling.
- `ReleaseConvergenceLoop` uses its own connections.
- SSE streaming holds connections for the duration of the stream.

With default pool size and 20+ concurrent deploys + streams, pool exhaustion could cascade: locks timeout, reconcile loops fail, SSE streams drop. No agent addressed this.

**Resolution:** Noted as a scaling concern for the ADR on per-project ArgoCD Applications. Not a P0 for single-tenant pre-release. Add `loopzero_db_pool_exhaustion` metric to P1.

**Tier 0 — P0 Fixes (same-day, blocks everything):**

| # | Fix | Owner | Justification |
|---|-----|-------|---------------|

| 2 | **Fix phantom `loopzero_drift_detected` alert** — either emit the metric or remove the PrometheusRule | Infra Engineer | False green. Operators believe drift detection exists when it doesn't. |

| # | Fix | Owner | Justification |
|---|-----|-------|---------------|

### Corrections Rejected

| Proposal | Rejected Because | By |
|----------|------------------|----|
| Move manifest generation into Argo Workflow | Build plane must not have GitOps write access. Violates build/release separation. Current RELEASING retry is adequate. | Architect, DistSys, GitOps, SRE (4/6) |
| Fix "ArgoCD blocks API startup" | Finding is factually incorrect. Code does not do fatal ArgoCD connectivity check at boot. Circuit breaker already handles this. | Architect, SRE (code review) |
| New "State Divergence Monitor" daemon | Wrong approach. Extend existing `ReleaseConvergenceLoop` instead of creating new daemon. | Architect |
| Extract reconcile loops to operator NOW | YAGNI for single-replica pre-release. Document and plan, don't execute yet. | SRE, Architect |

### Alternatives Rejected

| Alternative | Why Rejected |
|-------------|--------------|
| Eliminate PostgreSQL, go Kubernetes-native like Epinio | Loses ACID guarantees on concurrent mutations, advisory locks, queryable build history. Different trade-off, not superior. |
| Remove GitOps entirely, do imperative Helm install like Epinio | Loses auditability, drift detection, rollback via git history. Regression in architecture. |
| Create reconciliation between all 3 state stores (PG, CRDs, ArgoCD) | Overengineered. The gap is only post-activation health, not full state reconciliation. |

### Trade-offs Accepted

1. Triple state (PG + CRDs + ArgoCD) remains — justified by distinct ownership per store. Monitoring closes the gap.
2. API runs as single replica until reconcile loops are extracted — acceptable for pre-release.
3. ArgoCD Application model (per-environment) remains until ADR resolves the debate — partial mitigation via per-resource health filtering.
4. Manifest generation stays in API — build/release separation preserved at cost of API/K8s schema coupling.

| MEDIUM | Git CLI subprocess fragility | go-git migration in P2, pinned git version in Dockerfile as interim | Infra Engineer |
