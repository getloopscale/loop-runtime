## Stage 2 — Analyses

### Principal Architect

**Assessment:**

The root cause is architectural: a single Pulumi stack managing resources with three distinct lifecycles. Strategy A (fix in place) does not address this. Strategy C (full rewrite) is correct long-term but cannot be delivered today.

Strategy B (2 stacks) is the right intermediate step. However, the cert-manager timing issue is independent of the stack split — it exists because of a fundamental mismatch between Kubernetes readiness probes (HTTP liveness) and webhook TLS readiness (self-signed cert generation). This is a well-known cert-manager issue.

The current code in `bootstrap-shared.ts` already has two layers of defense: (1) `Deployment.get()` on the webhook, (2) `customTimeouts: { create: "5m" }`. The problem is that `customTimeouts` only controls how long Pulumi waits for the resource to become ready AFTER creation — but the Pulumi K8s provider treats webhook validation errors as immediate failures, not as "not ready yet." The provider does NOT retry on `InternalError` from webhook validation failures.

**Risks identified:**
1. `customTimeouts` does not retry on webhook validation failures — it only extends the readiness wait
2. `Deployment.get()` confirms replicas are ready, but NOT that the webhook TLS cert is serving
3. The cert-manager `startupapicheck` Job validates CRD installation, NOT webhook TLS readiness
4. `waitForJobs: true` waits for startupapicheck, which completes before TLS is ready

**Recommendation:** Strategy A for TODAY (but with a proper readiness gate, not sleep). Strategy B as migration target for next sprint. The cert-manager fix is a `command.local.Command` resource that runs a retry loop validating webhook TLS, placed between cert-manager Helm release and ClusterIssuer.

**Conditions for approval:**
1. The cert-manager readiness gate must be a Pulumi resource (not CI shell), so it works in both CI and manual `pulumi up`
2. Strategy B migration plan must be documented as an ADR

**Impact if ignored:** Continued pipeline failures on every destroy+recreate. Developer velocity blocked.

### SRE Engineer

**Assessment:**

The pipeline is in a state where `sleep 90` is the only reliable mechanism for cert-manager webhook readiness. This is unacceptable for production. I have examined the failure mode:

1. cert-manager Helm chart deploys: webhook Deployment created
2. `waitForJobs: true` waits for `startupapicheck` Job — this Job verifies CRDs are installed, NOT that the webhook is serving TLS
3. `Deployment.get()` confirms webhook pods are `Ready` — but K8s `Ready` means the readiness probe passed (HTTP), not that the self-signed TLS cert has been generated and loaded
4. ClusterIssuer creation hits the webhook — webhook returns `HTTP response to HTTPS client` or `connection refused` because TLS cert is not yet loaded
5. Pulumi K8s provider treats this as a creation failure (not a timeout) and does NOT retry

The gap is between pod Ready (HTTP probe) and TLS serving (cert generated + loaded). This gap is typically 10-30 seconds but can be up to 60 seconds on slow clusters (DO nodes with limited CPU).

**Risks identified:**
1. Strategy A alone does not address the 6 CRITICAL findings from MEET-026
2. Even with a proper readiness gate, the single-stack architecture means any Pulumi state corruption affects the entire platform
3. The bootstrap shell (270 lines) with `continue-on-error: true` can still produce a "green pipeline, broken platform"

**Recommendation:**

For TODAY: Strategy A with a `command.local.Command` resource that uses sleep as a Pulumi resource (not CI shell). Combined with removing `continue-on-error: true` from bootstrap.

For NEXT SPRINT: Strategy B (2 stacks), but also fix CRIT-01 through CRIT-04 from MEET-026 in the current pipeline immediately.

**Conditions for approval:**
1. `continue-on-error: true` must be removed from Bootstrap and Health Validation steps (CRIT-01) in the same commit
2. The readiness gate must be a Pulumi resource, not CI shell

**Impact if ignored:** Pipeline continues to fail ~50% of destroy+recreate attempts. Development velocity drops to zero when failures cascade.

### Pipeline Reviewer (Helena Duarte)

**Assessment:**

I have reviewed all three strategies against my five criteria: determinism, build/release separation, scale, observability, recovery.

**Strategy A (fix in place):**
- Determinism: FAILS. Sleep replaced by Pulumi resource, but the 3-step dance (up -> build -> up) is inherently non-deterministic.
- Build/release separation: FAILS. Images built between two `pulumi up` runs.
- Scale: N/A (single-tenant dev pipeline).
- Observability: POOR. 103x `2>/dev/null` + 43x `|| true` remain.
- Recovery: FAILS. No rollback mechanism.

**Strategy B (2 stacks):**
- Determinism: IMPROVED. Stack 1 runs to completion before images are built.
- Build/release separation: IMPROVED. Images built after infra exists, before apps deploy.
- Observability: IMPROVED only if stacks are separate jobs.
- Recovery: IMPROVED. Stacks can be rolled back independently.

**Strategy C (full rewrite):**
- All criteria: PASS. But estimated 1-2 weeks.

**Objections:**

1. The `command.local.Command` approach requires careful consideration: `sleep` is available everywhere, but smarter checks (curl, openssl) require the webhook ClusterIP to be reachable from the runner. It is not — the runner is external to the cluster.

2. A `command.local.Command` with `sleep 60` as a Pulumi resource is honest, deterministic, trackable in state, and solves the problem. It is different from `sleep 90` in CI shell because it is a typed dependency, idempotent, and visible in `pulumi preview`.

**Recommendation:** `command.local.Command` with `sleep 60` for TODAY. Strategy B for next sprint. Document the sleep as TEMPORARY with a TODO for upstream Pulumi K8s provider retry-on-webhook-failure.

**Conditions for approval:**
1. Sleep gate must be documented as TEMPORARY
2. Image tags must be immutable (CRIT-05) before Strategy B migration begins

**Impact if ignored:** Pipeline remains a coin flip on destroy+recreate.

## Stage 3 — Confrontation

### Conflict 1: cert-manager readiness gate mechanism

| Agent | Position |
|-------|----------|
| Principal Architect | `command.local.Command` with curl/openssl retry loop |
| SRE Engineer | Poll-based check with exponential backoff |
| Pipeline Reviewer | `command.local.Command` with simple `sleep 60` |

**Resolution:** The `command.local.Command` with `sleep 60` is the correct immediate fix. Smart checks (curl, openssl) require cluster-internal access (webhook is ClusterIP). The Pulumi runner is external. Port-forwarding in a `command.local.Command` is fragile. The sleep is honest, deterministic, and tracked in Pulumi state. TODO to replace when Pulumi K8s provider adds retry-on-webhook-failure.

### Conflict 2: Strategy for TODAY vs TARGET

| Agent | Position |
|-------|----------|
| Principal Architect | Strategy A today, Strategy B next sprint |
| SRE Engineer | Strategy A + CRIT-01 fixes today, Strategy B next sprint |
| Pipeline Reviewer | Strategy A is debt-compounding; Strategy B should start this week |

**Resolution:** Strategy A + CRIT-01 fix TODAY (remove `continue-on-error: true`). CRIT-03/04 next session. Strategy B starts next sprint with documented ADR. The Pipeline Reviewer's urgency is acknowledged but Strategy B requires multi-day effort.

### Conflict 3: Sleep duration (45s vs 60s)

| Agent | Position |
|-------|----------|
| SRE Engineer | 60 seconds — DO nodes are slow |
| Pipeline Reviewer | 45 seconds — CI retry catches the rest |

**Resolution:** 60 seconds. Cost of extra 15 seconds is negligible. Cost of retry failure is 20-45 minutes. SRE's production experience with DO node performance is authoritative.
