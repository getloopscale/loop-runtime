## Problema

Imagens quebradas (crash loop, OOM, deadlock) consumindo recursos do cluster sem servir trafico. Em ambiente multi-tenant, um app quebrado de um tenant degrada todos os tenants.

## Decisao

Aprovar plano de 12 items em 4 fases com as condicoes abaixo.

---

## Fase 1 — APPROVED (items 1.1-1.6)

Manifests robustos + alerting. Nativo K8s, zero dependencias novas.

### Condicoes obrigatorias Fase 1

**F1-C1: progressDeadlineSeconds = 210s (nao 180s)**
Rationale: 150s startup + 10s readiness + 10s minReady = 170s. Com 180s, margem de 10s e insuficiente. Com 210s, margem de 40s cobre variacoes reais.

**F1-C2: Workers DEVEM receber PDB**
PDB com `unhealthyPodEvictionPolicy: AlwaysAllow` para TODOS os workloads de tenant (server e worker). Nenhum workload de tenant deve bloquear node drain.

**F1-C3: Documentar contrato do `/health` endpoint**
Adicionar ao spec (docs/technical.md) que `/health` e responsabilidade do usuario. LoopZero gera probes apontando para `/health`, usuario deve implementar. Liveness e readiness no mesmo path e aceitavel para Fase 1. Nota: liveness NUNCA deve checar deps externas (DB, cache).

**F1-C4: Ajustar thresholds dos alertas**
- `LoopZeroAppCrashLoop`: reduzir `for` de 10m para 5m
- `LoopZeroAppReplicaMismatch`: reduzir `for` de 15m para 5m

**F1-C5: Adicionar alerta ProgressDeadlineExceeded**
Novo alerta warning: `kube_deployment_status_condition{condition="Progressing",status="false"}` filtrado por namespace de tenant. Firing quando Deployment atinge progressDeadlineSeconds.

**F1-C6: Adicionar alerta critico para CrashLoop prolongado**
`LoopZeroAppCrashLoopCritical`: CrashLoopBackOff persistindo > 30 minutos. Severity critical.

**F1-C7: Testes devem usar parsing estrutural**
Novos testes de manifest DEVEM parsear YAML em structs tipadas (nao `strings.Contains`). Adicionar:
- `TestRender_BackwardCompat_NoNewConfig` (gate W3)
- `TestRender_PDB_IncrementsDocumentCount`
- `TestRender_KubeconformValid` (kubeconform programatico)
- `TestPromQLSyntax_WarningRules` (via `promql.ParseExpr`)

**F1-C8: Integrar progressDeadlineSeconds com ReleaseConvergenceLoop**
Quando ArgoCD reporta `Synced + Degraded` (Deployment falhou progressDeadline), o convergence loop DEVE transicionar a release para estado terminal FAILED. Sem isso, releases ficam orphaned em estado nao-terminal.

## Fase 2 — APPROVED_WITH_CHANGES

### Mudanca: ValidatingAdmissionPolicy ao inves de Kyverno

Kyverno e YAGNI para 3 policies simples de validacao. K8s 1.32 (DOKS) suporta `ValidatingAdmissionPolicy` (GA desde 1.30) com CEL expressions nativamente. Zero webhook, zero HA replicas, zero deps novas.

**Kyverno sera instalado apenas na Fase 4** quando `verifyImages` (cosign) for necessario. Ate la, VAP cobre registry restriction, no-latest, e require-limits.

### Condicoes Fase 2

**F2-C1: Policies VAP devem cobrir initContainers e ephemeralContainers**
Nao apenas `containers`. CEL expression deve iterar sobre todos os tipos de container.

**F2-C2: Adicionar VAP protegendo NetworkPolicies de plataforma**
Bloquear delecao de NetworkPolicies com label `loopzero.io/managed-by=environment-controller` em namespaces de tenant. Mitigacao para RISK-3 (Enterprise RBAC grants `networkpolicies` delete).

**F2-C3: Testes via kyverno test CLI ou equivalente VAP**
Fixture resources + expected results. Minimo 4 cenarios: valid, wrong-registry, latest-tag, no-limits.

## Fase 3 — CONDITIONALLY APPROVED

### Condicoes bloqueantes Fase 3

**F3-C1: Design concreto para `checkReleaseHealth`**
Mecanismo escolhido: **LoopZeroApplicationStatus no CRD (mgmt cluster)**.
- ApplicationController ja reconcilia health do workload cluster
- Estender `LoopZeroApplicationStatus` com `HealthSummary` (Healthy/Degraded/CrashLoop/ImagePullFailed)
- API le CRD status no mgmt cluster — zero cross-plane queries
- Se CRD status nao disponivel: ALLOW deploy (fail-open, nao fail-closed)
- Usar condition `ApplicationHealthy` com `lastTransitionTime` para "unhealthy since"

Rationale (Principal Architect): "O API existe no Developer/Control plane. Deve ler health do source of truth que ja existe: LoopZeroApplicationStatus no CRD do mgmt cluster."

**F3-C2: Remover exit code 1 do FailJob**
Apenas exit code 137 (OOM/SIGKILL) mapeia para FailJob. Exit code 1 continua retryable. Transient DNS/npm/registry failures exitam com 1 e sao recuperaveis.

**F3-C3: Spike de compatibilidade Argo Workflows + Pod Failure Policy**
Verificar ANTES de implementar se Argo Workflows WorkflowSpec aceita `podFailurePolicy`. Se nao, usar `activeDeadlineSeconds` como fallback (ja usado em cwt-cache-save).

**F3-C4: Definir comportamento quando health check falha**
Se CRD nao disponivel ou status stale: ALLOW deploy com warning log. Deploy circuit breaker e fail-open, NUNCA fail-closed. Um Prometheus/CRD indisponivel nao pode bloquear deploys.

**F3-C5: Audit event para --force**
Adicionar evento de auditoria estruturado quando `--force` e usado. Incluir: tenant, project, environment, health status anterior, usuario.

**F3-C6: Testes de failure modes**
- `TestCheckReleaseHealth_CRDUnavailable` → allow deploy
- `TestCheckReleaseHealth_NoPods_FirstDeploy` → allow deploy
- `TestCheckReleaseHealth_ConcurrentDeploys` → advisory lock serializa
- `TestDeployCircuitBreaker_RollbackNeverBlocked` → rollback bypassa

## Fase 4 — DEFERRED (requer design docs separados)

### Gate obrigatorio

Cada item da Fase 4 requer:
1. Design doc proprio
2. Reuniao tecnica separada (MEET-XXX)
3. Aprovacao antes de implementacao

### Condicoes pre-design doc

**F4-C1: Reaper DEVE ser controller separado**
Nao embeber no ApplicationController. Motivos:
- SRP: ApplicationController gerencia hostname/route/health. Reaper gerencia lifecycle destructivo.
- Deps diferentes: Reaper precisa de Gitea client. ApplicationController nao.
- Timing diferente: Reaper e time-based. ApplicationController e event-based.
- Nome sugerido: `UnhealthyWorkloadReaperController`

**F4-C2: Reaper deve fazer rollback, nao scale-to-zero**
Scale-to-zero cria estado estavel quebrado que requer intervencao humana (viola self-healing). O reaper deve fazer rollback automatico para a ultima release SUCCEEDED. Se nenhuma release saudavel existe, entao scale-to-zero como ultimo recurso + notificacao ao usuario.

**F4-C3: Reaper deve coordenar com advisory lock**
Race condition entre reaper gitops-push e deploy gitops-push. Reaper DEVE usar o mesmo mecanismo de lock (ou chamar a API para solicitar scale-down/rollback).

**F4-C4: Usar condition `lastTransitionTime` ao inves de `UnhealthySince`**
Condition `type: Unhealthy` com `lastTransitionTime` e mais idiomatico que campo custom. Nao adicionar campos de status desnecessarios ao CRD.

**F4-C5: Argo Rollouts requer design doc + meeting T3**
Conversao Deployment→Rollout muda health checks, rollback mechanics, e resource tracking do ArgoCD. E T3 por si so.

## Riscos aceitos

| Risco | Severidade | Mitigacao | Owner |
|-------|-----------|-----------|-------|
| Startup probe 150s insuficiente para JVM/ML pesado | Medium | progressDeadline 210s da margem. Futuro: override via loopzero.yaml | API Engineer |
| PDB com 1 replica e no-op para disruption protection | Low | PDB se torna efetivo com replicas > 1. Documentar | API Engineer |
| Alertas dependem de Prometheus estar up | Low | Probes e progressDeadline sao hard guarantees; alertas sao notificacao | Infra Engineer |
| Same `/health` path para liveness e readiness | Low | Documentar contrato. Separar paths e futuro enhancement | API Engineer |
| preStop hook ausente (rolling update race) | Low | Aceito para Fase 1. Backlog item para `sleep 5` preStop | API Engineer |

## Riscos NAO aceitos (blockers)

| Risco | Severidade | Acao requerida |
|-------|-----------|----------------|
| API query workload cluster diretamente (3.1) | High | Usar CRD status no mgmt cluster (F3-C1) |
| Exit code 1 como FailJob (3.2) | High | Remover, manter apenas 137 (F3-C2) |
| Reaper no ApplicationController (4.3) | High | Controller separado (F4-C1) |
| Kyverno policy nao cobre initContainers | High | Cobrir todos os tipos (F2-C1) |
| Enterprise RBAC permite delete NetworkPolicy | High | VAP protegendo policies de plataforma (F2-C2) |

## Alternativas rejeitadas

| Alternativa | Motivo da rejeicao |
|-------------|-------------------|
| Kyverno na Fase 2 | YAGNI — K8s 1.32 suporta VAP nativamente. 3 policies simples nao justificam webhook externo. Kyverno so quando verifyImages for necessario (Fase 4) |
| API query Prometheus para health check | Cross-plane coupling. API ganha dependencia de Prometheus/workload cluster. CRD status no mgmt e o source of truth correto |
| API query K8s API do workload cluster | Mesmo problema + latencia + blast radius. Se workload cluster down, deploys bloqueados |
| Scale-to-zero como acao do reaper | Cria estado estavel quebrado sem self-healing. Rollback automatico e preferivel |
| String-based test assertions | Fragil para 15+ campos numericos em 3 probes. Parsing estrutural e obrigatorio |
