## Stage 1 — Context

**Problem:** Phase 4 of the Workload Protection plan contains three items that were DEFERRED in MEET-021 pending individual design review: (1) Argo Rollouts for progressive delivery, (2) cosign image signing with Kyverno verification, (3) a custom Reaper controller for automatic rollback of crash-looping workloads. Each item introduces new infrastructure components and has non-trivial interaction with existing systems (ArgoCD, advisory locks, build pipeline).

**Decision Required:** For each item: approve, reject, or defer. Define sequencing, pre-conditions, and execution contracts. Determine whether Argo Rollouts is justified given the single-replica PaaS model.

**Constraints:**
- Pre-conditions F4-C1 through F4-C5 from MEET-021 are binding
- Phases 1-3 must be complete before Phase 4 implementation begins
- Single-replica is the default (and only supported) deployment model
- ArgoCD manages all workload cluster resources via manual sync
- Advisory lock (`pg_advisory_xact_lock`) is the serialization mechanism for all mutations
- Controller runs on mgmt cluster, workloads run on workload cluster
- Pre-release: backward compatibility not required, clean design preferred

**Known Context:**
- `LoopZeroApplicationStatus` already has `ApplicationHealthy` condition with `lastTransitionTime` (conditions/types.go)
- `ApplicationReconciler` already sets `ApplicationHealthy` based on phase (Reachable/Serving = healthy)
- Advisory lock lives in `api/internal/lock/environment_lock.go` — requires pgx pool, runs in API process
- Build pipeline uses Argo Workflows + BuildKit, images pushed to DO Container Registry
- GitHub Actions `build-images.yml` builds platform images (API, operator) — separate from user app builds
- ArgoCD 2.13.3 deployed, supports Rollout CRD natively
- Traefik 28.3.0 as ingress controller
- DOKS K8s 1.32

**Proposal:** Evaluate each item independently per F4-C5 requirement.

## Stage 2 — Analyses

### Principal Architect

**Assessment:**

Item 4.1 (Argo Rollouts): This is YAGNI for a single-replica PaaS. Canary deployment requires splitting traffic between stable and canary pods. With 1 replica, you either have 0% or 100% on canary — there is no meaningful progressive rollout. The AnalysisTemplate with Prometheus metrics presupposes measurable traffic on the canary, which does not exist with 1 replica. Additionally, converting Deployment to Rollout CRD changes the fundamental resource type that ArgoCD tracks, health-checks, and reports on. This is a T3 change to the entire deploy flow for zero practical benefit at current scale.

Item 4.2 (cosign): Architecturally clean. Keyless signing via GitHub Actions OIDC is the correct approach — no key management. Kyverno is justified here because `verifyImages` has no native K8s equivalent (unlike the Phase 2 policies where VAP sufficed). The signing happens in the platform build pipeline (GitHub Actions), not in the user build pipeline (Argo Workflows), which keeps the user flow unchanged.

Item 4.3 (Reaper): The pre-conditions from MEET-021 are sound. A separate controller watching LoopZeroApplication CRDs and triggering rollback via API call is the correct architecture. The controller should NOT directly push to Gitea — it should call the API rollback endpoint, which already handles advisory locking, gitops push, and release state transitions. This preserves the existing source of truth hierarchy.

**Risks:**
- [critical] Argo Rollouts with 1 replica provides false progressive delivery — canary analysis measures nothing meaningful
- [high] Rollout CRD conversion changes ArgoCD health detection, sync status reporting, and rollback mechanics
- [medium] Reaper calling API introduces a dependency from controller plane to developer plane (mgmt cluster controller → API)
- [low] cosign keyless relies on Sigstore public infrastructure (Fulcio, Rekor)

**Objections:**
- Argo Rollouts is complexity without benefit at current scale. Reject.
- Reaper must NOT have its own Gitea client (F4-C1 rationale says "Reaper needs Gitea client" — this is wrong. Reaper should call API.)

**Recommendation:** Reject 4.1. Approve 4.2 and 4.3 with conditions.

**Conditions for approval:**
- 4.1: Only reconsider when `replicas > 1` is supported in loopzero.yaml
- 4.2: Kyverno installed only on workload cluster (not mgmt) for verifyImages. Dev/staging in Audit mode
- 4.3: Reaper triggers rollback via API HTTP call, not via direct Gitea push

**Impact if ignored:** Installing Argo Rollouts for 1-replica apps creates operational complexity (new CRD, new controller, Traefik integration) without observable improvement in deployment safety. The AnalysisTemplate will either always pass (no canary traffic to fail) or be meaningless.

### K8s Controller Engineer

**Assessment:**

Item 4.1 (Argo Rollouts): Technically feasible but semantically wrong for 1 replica. The Rollout CRD replaces Deployment, which means every existing piece of code that generates or inspects Deployment manifests must change. The `renderer.go:buildDeployment()` function generates Deployment YAML — converting to Rollout changes the entire manifest contract. ArgoCD health checks for Rollout differ from Deployment. The blast radius is too large for the benefit.

Item 4.2 (cosign): No controller impact. Signing happens in GitHub Actions. Verification happens in Kyverno admission webhook. Controllers are not involved.

Item 4.3 (Reaper): Strong opinion on the design:
1. Separate controller (`UnhealthyWorkloadReaperController`) — correct per F4-C1
2. Watches LoopZeroApplication CRDs on mgmt cluster — uses existing `ApplicationHealthy` condition
3. Uses `lastTransitionTime` on condition `ApplicationHealthy` (status=False) to determine "unhealthy since" — correct per F4-C4
4. Does NOT need a custom `UnhealthySince` field — the condition already tracks this via `lastTransitionTime`
5. Must be idempotent: if rollback already triggered, reconcile is a no-op
6. Must have a requeue interval (e.g., 60s) to periodically re-check unhealthy apps

**CRD changes needed:** None. The existing `LoopZeroApplicationStatus.Conditions` with `ApplicationHealthy` condition already provides the signal. No new CRD fields required.

**Risks:**
- [high] Reaper reconcile loop must not fight with ApplicationController reconcile — they operate on different concerns but the same CRD status. Reaper reads status, ApplicationController writes status.
- [medium] If Reaper triggers rollback while a deploy is in progress, the advisory lock must serialize them. Reaper calling the API ensures this.
- [low] Reaper needs API credentials (service account token or internal auth)

**Objections:**
- The plan says "Reaper needs Gitea client" (item 4.3 in workload-protection.md). This is wrong. Reaper must NOT interact with Gitea. It calls the rollback API endpoint.
- The plan suggests "scale to 0 via ArgoCD" as primary action. MEET-021 already corrected this to "rollback first, scale-to-zero only as last resort" (F4-C2). The design doc must enforce this.

**Recommendation:** Reject 4.1. Approve 4.3 with strict conditions on controller design.

**Conditions for approval:**
- Reaper controller is read-only on LoopZeroApplication CRD (reads conditions, never writes status)
- Reaper triggers rollback via API HTTP call (uses existing lock + state machine)
- Reaper has configurable threshold (default 5 minutes unhealthy before action)
- Reaper reconcile uses `requeueAfter: 60s` for periodic polling, not event-driven (avoids hot loop on flapping apps)

**Impact if ignored:** If Reaper writes directly to Gitea, it bypasses advisory lock, release state machine, and audit trail. Concurrent rollback from Reaper and deploy from user creates split-brain in gitops repo.

### Distributed Systems Engineer

**Assessment:**

Item 4.1 (Argo Rollouts): The fundamental issue is statistical. Canary analysis requires enough traffic to produce meaningful signal. With 1 replica and canary weight at 20%, the canary gets 20% of traffic. For low-traffic apps (common in PaaS), this may be single-digit requests per minute. The AnalysisTemplate's `sum(rate(...[2m]))` query over 2-minute windows on single-digit requests produces noisy, unreliable results. The success rate metric `>= 0.95` can flip from 100% to 0% on a single failed request. This is not progressive delivery — it is coin-flip delivery.

Item 4.2 (cosign): The trust chain is external (Fulcio CA, Rekor transparency log). If Sigstore infrastructure is down, signing fails. Mitigations: (a) signing is in GitHub Actions, not in user-facing flow, so retry is acceptable; (b) Kyverno verifyImages in `Audit` mode means verification failure does not block deploys in dev/staging; (c) Fulcio/Rekor have >99.9% availability. The failure mode is acceptable.

Concern: verification latency. Kyverno verifyImages fetches the signature from the registry and verifies against Rekor. This adds 200-500ms to pod admission. Acceptable for PaaS deploys but must be monitored.

Item 4.3 (Reaper): The critical race condition is: user starts `loopzero deploy` (acquires lock, starts build) → build takes 5 minutes → meanwhile Reaper detects unhealthy state from previous release → Reaper calls rollback API → rollback tries to acquire lock → timeout (build holds lock) → rollback fails.

This is actually CORRECT behavior. The advisory lock serializes mutations. The deploy in progress will either succeed (replacing the unhealthy release) or fail (in which case Reaper retries on next reconcile). The Reaper must handle lock timeout gracefully — not as an error, but as "mutation in progress, requeue".

Another race: app flaps between healthy and unhealthy. The `lastTransitionTime` on the `ApplicationHealthy` condition handles this — the 5-minute threshold resets on every transition. But the Reaper must check that the condition has been continuously False for 5 minutes, not just that `lastTransitionTime` is > 5 minutes ago. Nuance: `lastTransitionTime` records when the condition LAST CHANGED. If it changed to False 6 minutes ago, and has been False since, that is 6 minutes of unhealthy. Correct. But if it flapped to True at minute 3 and back to False at minute 4, `lastTransitionTime` is 4 minutes ago — Reaper correctly waits. The K8s condition semantics are correct for this use case.

**Risks:**
- [high] Argo Rollouts canary analysis on low-traffic apps produces statistically meaningless results
- [medium] Reaper lock timeout on concurrent deploy is expected behavior but must not log as error (confusing)
- [medium] cosign verification latency adds to pod startup time (stacks with startup probe 150s window)
- [low] Reaper flapping detection depends on correct ApplicationController condition updates

**Objections:**
- Argo Rollouts is statistically invalid for single-replica, low-traffic apps

**Recommendation:** Reject 4.1. Approve 4.2 and 4.3.

**Conditions for approval:**
- 4.3: Reaper must treat lock timeout as "mutation in progress, requeue in 30s" — not as error
- 4.3: Reaper must verify `ApplicationHealthy` condition status is False AND `lastTransitionTime` is older than threshold
- 4.2: Monitor Kyverno verifyImages webhook latency — alert if p99 > 1s

**Impact if ignored:** Deploying Argo Rollouts with meaningless canary analysis creates false confidence. Operators see "canary passed" when the analysis had insufficient data to be meaningful.

### SRE / Production Readiness

**Assessment:**

Item 4.1 (Argo Rollouts): In production, I want progressive delivery. But not at the cost of false confidence. With 1 replica, Argo Rollouts adds operational burden (new controller, new CRD, Traefik integration for traffic splitting) without adding real safety. The existing Deployment + readiness probe + progressDeadlineSeconds (210s from Phase 1) already provides the safety net: if the new pod does not become ready, the Deployment does not progress, and the old pod stays running (maxUnavailable: 0). This IS progressive delivery for single-replica apps — just binary (old pod stays until new pod is ready) rather than percentage-based.

Item 4.2 (cosign): Good for supply chain security. Must be Audit-only initially, even in prod. Move to Enforce after 2 weeks of clean audit logs. Concern: if the build pipeline fails to sign an image (transient Fulcio failure), the user's deploy succeeds but the image is unsigned. When Kyverno switches to Enforce later, pods from that unsigned image would fail admission on restart/reschedule. Mitigation: the build pipeline must retry signing, and signing failure must be a build failure (not silent).

Item 4.3 (Reaper): This is the highest-value item in Phase 4. Automatic rollback of crash-looping apps is the number one operational pain point. The 5-minute threshold is correct — long enough to avoid false positives from transient startup failures, short enough to limit resource waste. The fallback to scale-to-zero when no healthy release exists is acceptable but must generate a CRITICAL alert (not just warning).

Operability concerns for Reaper:
- Must emit Kubernetes events on the LoopZeroApplication CR when triggering rollback
- Must have a Prometheus metric: `loopzero_reaper_rollback_total{tenant, project, environment}`
- Must log structured event with correlation ID
- `loopzero status` must show "Automatically rolled back due to prolonged crash loop" — in product language

**Risks:**
- [high] cosign signing failure in pipeline produces unsigned image — time bomb for future Enforce
- [medium] Reaper scale-to-zero without alert leaves tenant with invisible outage
- [low] Reaper metric cardinality — bounded by number of (tenant, project, env) tuples

**Objections:**
- None for rejection of 4.1
- cosign signing failure MUST fail the build, not silently skip

**Recommendation:** Reject 4.1. Approve 4.2 and 4.3.

**Conditions for approval:**
- 4.2: Signing failure in build pipeline = build failure. No silent skip.
- 4.2: Start in Audit mode everywhere (including prod). Move to Enforce after 2 weeks of clean logs.
- 4.3: Reaper emits K8s Event on LoopZeroApplication when triggering rollback
- 4.3: Reaper emits Prometheus metric `loopzero_reaper_rollback_total`
- 4.3: Scale-to-zero (last resort) generates severity=critical alert
- 4.3: `loopzero status` shows rollback reason in product language

**Impact if ignored:** Without the Reaper, crash-looping apps consume resources indefinitely until a human notices and runs `loopzero rollback`. In multi-tenant, this steals resources from healthy tenants.

### GitOps / Delivery Engineer

**Assessment:**

Item 4.1 (Argo Rollouts): Converting from Deployment to Rollout changes the gitops contract. The manifests pushed to Gitea would contain `kind: Rollout` instead of `kind: Deployment`. ArgoCD Application's `spec.source` does not need to change (ArgoCD discovers resource types automatically), but the health check logic differs. ArgoCD uses Rollout-specific health checks from the `argo-rollouts` resource customization. If Argo Rollouts controller is down, ArgoCD reports the Rollout as `Unknown` health. This adds a single point of failure to the delivery pipeline.

Item 4.2 (cosign): Signing happens in GitHub Actions (platform images) but user app images are built by Argo Workflows on the build cluster. For user app images, cosign signing must be added as a step in the Argo Workflow template (or as a post-build step in the callback). This is a pipeline change that touches `api/internal/argo/workflow_builder.go`. The cosign binary must be available in the build cluster (either in the BuildKit image or as a separate container step).

Correction: User app images are what Kyverno verifyImages checks on the workload cluster. Platform images (API, operator) are not checked by Kyverno because they run on mgmt/build clusters, not workload. So cosign must sign USER app images, not just platform images. This means the Argo Workflow must include a signing step after image push.

Item 4.3 (Reaper): The Reaper triggering rollback via API call means the rollback follows the standard gitops flow: API updates release state → generates rollback manifests → pushes to Gitea → ArgoCD syncs. This preserves the gitops contract. The Reaper is essentially an automated operator for `loopzero rollback`, which is the correct abstraction.

Concern: the Reaper needs to know WHICH release to rollback to. The API rollback endpoint already handles this (finds the last SUCCEEDED release). The Reaper just needs to call `POST /api/v1/projects/{project}/rollback` with the environment and a "reaper" context.

**Risks:**
- [high] Item 4.1 introduces Argo Rollouts controller as SPOF for delivery health reporting
- [high] Item 4.2 requires cosign in Argo Workflow — changes the build pipeline (T3)
- [medium] Reaper needs API authentication (service account or internal token)

**Objections:**
- 4.1: Adding Argo Rollouts controller as SPOF is unacceptable for the delivery pipeline
- 4.2: Must clarify scope — is this platform images only (GitHub Actions) or user images too (Argo Workflows)?

**Recommendation:** Reject 4.1. Approve 4.2 with scope clarification. Approve 4.3.

**Conditions for approval:**
- 4.2: Phase 4.2 scope is platform images ONLY (GitHub Actions). User app image signing is a separate design doc (Phase 5 scope)
- 4.2: Kyverno verifyImages for user apps is DEFERRED until user image signing pipeline is designed
- 4.3: Reaper uses internal API authentication (service account token, not user token)
- 4.3: Reaper rollback calls include `X-Triggered-By: reaper-controller` header for audit trail

**Impact if ignored:** If user image signing is conflated with platform image signing, the build pipeline change is much larger and riskier. Separating scopes allows incremental delivery.

### Conflict 4: What happens when no healthy release exists for rollback?

| Agent | Position |
|-------|----------|
| SRE | Scale-to-zero as last resort + CRITICAL alert. Tenant gets notified. |
| K8s Controller Engineer | Agree — but scale-to-zero must also go through the API (not direct manifest edit). API should have a "scale-to-zero" endpoint or the rollback endpoint should handle "no healthy release" gracefully. |
| Distributed Systems Engineer | The Reaper should NOT scale-to-zero itself. It should request rollback from API. **Resolution:** Reaper does NOT scale-to-zero. ### Challenge from Meeting Orchestrator

"All agents agree on rejecting 4.1 and the Reaper design for 4.3. What are we NOT seeing? What could go wrong with a Reaper that auto-rollbacks?"

Responses:
- **SRE:** "A buggy health check in ApplicationController could cause false unhealthy signals, triggering unnecessary rollbacks. Mitigation: the 5-minute threshold, and the Reaper should only trigger rollback ONCE per release (not repeatedly)."
- **Distributed Systems:** "If the rollback release is also unhealthy (regression in previous version), the Reaper would detect unhealthy again after rollback, trigger another rollback to an even older release, cascading backwards. Mitigation: Reaper should only attempt rollback ONCE per unhealthy episode. After triggering rollback, it waits for the ApplicationHealthy condition to change (either to True or to a new lastTransitionTime indicating re-evaluation)."
- **K8s Controller Engineer:** "Annotation-based guard: after triggering rollback, Reaper annotates the LoopZeroApplication with `loopzero.io/reaper-rollback-requested: <release-id>`. On next reconcile, if the annotation matches the current active release, Reaper skips — rollback already requested for this unhealthy episode."

**Resolution:** Added as mandatory condition — Reaper must have cascade protection. Single rollback attempt per unhealthy episode, tracked via annotation.

## Stage 4 — Decision

### Item 4.1 — Argo Rollouts with canary + AnalysisTemplate

**Verdict: REJECTED**

**Justification:** Single-replica deployment model makes canary analysis statistically meaningless. Traffic splitting with 1 replica is binary (0% or 100%), not progressive. The existing Deployment with `maxUnavailable: 0` + `maxSurge: 1` + `progressDeadlineSeconds: 210s` already provides binary progressive delivery (old pod stays until new pod is ready). Argo Rollouts adds a new CRD, a new controller, Traefik traffic splitting configuration, and changes the manifest contract (Deployment to Rollout) — all for zero practical benefit at current scale.

**Alternatives rejected:**
- "Install Argo Rollouts now, use later" — rejected because installing a CRD and controller that is unused creates operational burden (monitoring, upgrades, resource consumption) with no benefit
- "Use Argo Rollouts without canary (just blue-green)" — rejected because blue-green with 1 replica is equivalent to the current rolling update with maxUnavailable:0

**Reconsideration gate:** Argo Rollouts should be reconsidered when:
1. `replicas` field in loopzero.yaml is configurable and tenants can set replicas > 1
2. Traffic volume per tenant is sufficient for meaningful canary analysis (>100 RPM)
3. Both conditions must be met simultaneously

### Item 4.2 — Image signing with cosign + Kyverno verifyImages

**Verdict: APPROVED_WITH_CONDITIONS**

**Scope reduction:** Phase 4.2 covers PLATFORM images only (API, operator — built in GitHub Actions). User app image signing (Argo Workflows) is deferred to a separate design doc.

**Chosen approach:**
1. Add cosign keyless signing step to `build-images.yml` GitHub Actions workflow
2. Install Kyverno on workload cluster (this is the Kyverno install point — not Phase 2)
3. Create `verifyImages` ClusterPolicy in Audit mode for all images from `registry.digitalocean.com/loopzero-infra-registry/*`
4. Enforce mode is BLOCKED until both platform AND user image signing pipelines are operational

**Trade-offs accepted:**
- Audit mode provides visibility but not enforcement — unsigned images can still run
- Kyverno adds webhook latency (200-500ms) to pod admission on workload cluster
- External dependency on Sigstore public infrastructure (Fulcio, Rekor)

### Item 4.3 — Unhealthy Workload Reaper Controller

**Verdict: APPROVED_WITH_CONDITIONS**

**Chosen approach:**
1. New controller: `UnhealthyWorkloadReaperController` in `operators/internal/controller/`
2. Watches: `LoopZeroApplication` CRDs on mgmt cluster
3. Detection: reads `ApplicationHealthy` condition — if status=False and `lastTransitionTime` > threshold (default 5 minutes)
4. Action: calls API rollback endpoint via HTTP (`POST /api/v1/projects/{project}/environments/{env}/rollback`)
5. Coordination: advisory lock handled by API, not by Reaper
6. Cascade protection: annotation `loopzero.io/reaper-rollback-requested: <release-id>` prevents repeated rollback
7. No Gitea dependency. No direct manifest manipulation.
8. If rollback fails (no healthy release): emit K8s Event, set condition, do NOT scale-to-zero

**Alternatives rejected:**
- Embed in ApplicationController — rejected per F4-C1 (SRP violation, different concerns, different timing)
- Direct Gitea push — rejected because it bypasses advisory lock, release state machine, and audit trail
- Scale-to-zero as primary action — rejected per F4-C2 (creates stable broken state requiring human intervention)
- CronJob with kubectl — rejected as fragile, no leader election, no structured status reporting

**Trade-offs accepted:**
- Reaper adds a dependency from controller plane to API (HTTP call). If API is down, Reaper cannot trigger rollback. Mitigation: Reaper retries on next reconcile (60s), and API downtime is already a P1 incident.
- Reaper is polling-based (requeueAfter: 60s), not event-driven. This means up to 60s delay between detection and action. Acceptable for a 5-minute threshold.
- Single rollback attempt per unhealthy episode means Reaper cannot cascade through multiple previous releases automatically. This is intentional — cascading rollback is dangerous and should require human decision.

**Risks Accepted:**

| Risk | Severity | Mitigation | Owner |
|------|----------|------------|-------|
| Reaper false positive from buggy health check | Medium | 5-minute threshold + single rollback per episode + annotation guard | Operator Engineer |
| cosign Fulcio/Rekor downtime blocks platform image signing | Low | Retry in GitHub Actions (3 attempts, 30s backoff). Fulcio >99.9% SLA | Infra Engineer |
| Kyverno webhook latency on workload cluster | Low | Monitor p99 webhook latency. Alert if >1s. Audit mode means no blocking. | Infra Engineer |

| Reaper directly modifying Gitea | High | Reaper must use API rollback endpoint. This is non-negotiable. |
| cosign signing failure silently skipped in pipeline | High | Signing failure MUST fail the build job. No silent skip. |
| Kyverno verifyImages in Enforce mode before user signing pipeline | High | Enforce mode blocked until both platform and user signing operational |
