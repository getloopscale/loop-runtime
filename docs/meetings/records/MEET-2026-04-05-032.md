## Stage 1 — Context

**Problem:** The dashboard login flow has a persistent redirect loop. The architecture combines two incompatible patterns: the dashboard is simultaneously a PKCE initiator (redirecting to Hydra) AND a Kratos self-service UI renderer (receiving Kratos flow redirects). When Kratos redirects to `dashboard.dev.loopzero.example/login?flow=xxx`, the dashboard attempts a cross-origin fetch to `accounts.dev.loopzero.example/self-service/login/flows?id=xxx`. This fetch fails (CORS/cookies), the flow object is null, buttons render without flow context, user clicks a button, `startPKCELogin()` fires again, redirecting back to Hydra, which loops.

**Decision Required:** Which architecture resolves the redirect loop definitively? Four options proposed (A through D).

**Constraints:**
- Must work now — no multi-week redesigns
- Pre-release — can break things and redesign cleanly
- Already deployed: Hydra, Kratos, cloud service, dashboard on DigitalOcean
- CLI login (Device Code Flow) must remain unaffected
- Cookie domain is `.dev.loopzero.example` (shared across subdomains)

**Known Context:**
- Kratos `login.ui_url` = `https://dashboard.dev.loopzero.example/login` (mgmt-bootstrap.ts line 576)
- Kratos cookie domain = `.dev.loopzero.example` (line 565)
- Consent handler `kratosPublicURL` = `https://accounts.dev.loopzero.example` (line 1085)
- Consent handler redirects to `kratosPublicURL/self-service/login/browser?return_to=/auth/login/complete?login_challenge=...` (handler.go line 73-75)
- Kratos initiates browser login flow, then redirects to `login.ui_url` (dashboard) with `?flow=xxx`
- Dashboard's `getFlow()` fetches from `ACCOUNTS_URL/self-service/login/flows?id=xxx` — cross-origin
- Hydra login URL = `https://api.dev.loopzero.example/auth/login` (line 689)
- Hydra consent URL = `https://api.dev.loopzero.example/auth/consent` (line 690)

## Stage 2 — Analyses

### Principal Platform Architect

**Assessment:** The root cause is an architectural confusion of responsibilities. The dashboard is trying to be two things: (1) an OAuth2 client that initiates PKCE flows, and (2) a Kratos self-service UI that renders login forms. These are fundamentally different roles. A PKCE client redirects to the authorization server and receives a callback. A Kratos UI is the authorization server's login page. Combining both in one application on a different origin than Kratos is architecturally incoherent.

**Risks:**
- [medium] Moving login UI to a separate domain creates visual discontinuity. Mitigation: consistent branding.
- [low] Additional deployment (Kratos self-service UI). Mitigation: Ory provides a maintained Node.js UI.

**Objections:** Strong objection to Option B (proxy) and Option D (path routing) — both add complexity to solve what is fundamentally a misplaced responsibility.

**Recommendation:** Option C with Option A's deployment model. Deploy Ory's self-service UI at `accounts.dev.loopzero.example`. Dashboard only handles PKCE callback.

**Conditions for approval:** Clean separation enforced — dashboard code must not import Kratos flow types.

**Impact if ignored:** Redirect loop persists. Every patch attempt will produce fragile workarounds.

### Platform Security Engineer

**Assessment:** Multiple security concerns beyond the redirect loop:

1. **Cross-origin session leakage:** Dashboard fetches Kratos flows cross-origin with `credentials: 'include'`. If CORS were added, XSS on the dashboard could read Kratos session data.
2. **CSRF token confusion:** Login page constructs forms with Kratos CSRF tokens from a different origin. This is exactly the pattern CSRF protection prevents.
3. **return_to parameter injection:** The consent handler constructs `return_to` URLs that need strict validation.

**Risks:**
- [high] Cross-origin CSRF token submission is fundamentally broken and insecure. This is a security defect, not just a UX bug.
- [medium] Shared cookie domain (`.dev.loopzero.example`) — compromise of any subdomain allows session cookie theft.

**Objections:** **VETO on Option B and Option D.** Option B proxies sensitive identity flows through additional layer. Option D collapses identity into the API domain, violating isolation.

**Recommendation:** Option A/C hybrid. Identity UI must be same-origin with identity API.

**Conditions for approval:**
1. CSRF tokens must be same-origin only
2. Cloud service's `/auth/login/complete` must validate `return_to` strictly

**Impact if ignored:** Cross-origin CSRF vulnerability. Potential session fixation if CORS is loosened.

### DX/Tooling Engineer

**Assessment:** Current flow is catastrophically broken — users cannot log in. Option C (redirect-only) provides the simplest mental model: click "Log in", end up on accounts page with LoopZero branding, authenticate, come back. This is the industry standard pattern.

**Risks:**
- [medium] Visual inconsistency between dashboard and accounts UI. Mitigation: shared theme.
- [low] User confusion about separate domain. Mitigation: standard pattern, users understand it.

**Objections:** Would object to any solution that does not also fix registration, recovery, and account pages — they have the same cross-origin bug.

**Recommendation:** Option A/C hybrid. Remove ALL Kratos flow rendering code from dashboard.

**Conditions for approval:**
1. All identity pages served from accounts domain
2. Dashboard stripped of all Kratos flow rendering code
3. Consistent visual theme

**Impact if ignored:** Users cannot log in. Registration, recovery, and account pages will also fail.

### API/Domain Architect

**Assessment:** The consent handler architecture is sound. The cloud service correctly acts as Hydra's login/consent provider. The problem is purely in the Kratos UI layer.

The consent handler's `kratosPublicURL` is set to browser-accessible `https://accounts.dev.loopzero.example`, but `getKratosSessionSubject()` (line 111) makes a server-to-server call to this URL — going out through the load balancer unnecessarily. This is a latent bug.

**Risks:**
- [medium] `getKratosSessionSubject` uses public URL for server-to-server call. Should use internal URL.
- [low] `return_to` parameter is relative URL — should be absolute for clarity.

**Objections:** None to Option A/C. Consent handler requires no changes for the login fix itself.

**Recommendation:** Option A/C hybrid. Fix `kratosPublicURL` usage as follow-up.

**Conditions for approval:** Consent handler internal URL fix tracked as follow-up action.

**Impact if ignored:** Login remains broken. Latent server-to-server routing issue increases latency.

## Stage 3 — Confrontation

### Conflict 1: Cookie domain scope

| Agent | Position |
|-------|----------|
| Platform Security Engineer | Kratos session cookies MUST be scoped to `accounts.dev.loopzero.example` only |
| Principal Platform Architect | Agreed in principle, but may break consent handler flow |
| API Domain Architect | Cloud service at `api.*` needs Kratos session cookie forwarded from browser to validate identity |

**Resolution:** Shared cookie domain (`.dev.loopzero.example`) must remain because the consent handler at `api.dev.loopzero.example/auth/login/complete` reads Kratos session cookies from the browser request. Scoping cookies to `accounts.*` would prevent the browser from sending them on the redirect to `api.*`. Security Engineer concedes but registers dissent — future improvement should co-locate consent handler with Kratos.

### Conflict 2: Scope — login only vs. all identity pages

| Agent | Position |
|-------|----------|
| DX Engineer | ALL identity pages must move in this change |
| Principal Architect | Login fix is urgent; other pages can be fast follow-up |
| DX Engineer | They ALL have the same cross-origin bug — register still fails |

**Resolution:** DX Engineer is correct. Fix is sequenced: Phase 1 deploys Kratos UI and fixes login. Phase 2 updates all `ui_url` values (same Pulumi change). Both are part of one deliverable.

### Consensus Challenge

All agents agree on Option A/C hybrid. Orchestrator challenged: "What could go wrong?"

- **Deployment complexity:** Manageable — accounts subdomain routing already exists.
- **Ory UI version compatibility:** Must verify against deployed Kratos version.
- **OIDC callbacks:** Should work since `base_redirect_uri` already points to `accounts.*`.
- **Custom branding:** Cosmetic, not blocking.

None are blocking. **Consensus holds.**

## Stage 4 — Decision

**Chosen:** Option A/C Hybrid — Deploy a Kratos Self-Service UI at `accounts.dev.loopzero.example`. Dashboard becomes a pure OAuth2 PKCE client (initiates flow, receives callback, exchanges code). All identity forms (login, registration, recovery, verification, account settings) rendered by the Kratos UI on the same origin as Kratos.

**Alternatives rejected:**
| Alternative | Reason |
|-------------|--------|
| Option B — Proxy Kratos through API | Fragile proxy for sensitive identity operations; must perfectly preserve CSRF/session semantics; Security VETO |
| Option D — Path routing under one domain | Collapses identity trust boundary into API domain; Security VETO |
| Dashboard patches (CORS/cookie tweaks) | Fundamental architecture is wrong; loosening security controls creates vulnerabilities |

**Trade-offs accepted:**
- Additional deployment (Kratos UI container) adds operational surface area
- Visual discontinuity until theme is unified
- Shared cookie domain remains necessary for consent flow

**Risks accepted:**
- [medium] Visual inconsistency — Mitigation: apply LoopZero branding to Kratos UI — Owner: DX Engineer
- [medium] Consent handler uses public URL for server-to-server call — Mitigation: fix to use internal URL — Owner: API Engineer
- [low] Ory UI version compatibility — Mitigation: test before deploying — Owner: Infra Engineer

**Risks NOT accepted:** None blocking.

**Mandatory actions:**
1. Deploy Ory Kratos Self-Service UI at `accounts.dev.loopzero.example` — Owner: Infra Engineer
2. Update ALL Kratos `ui_url` fields to `accounts.dev.loopzero.example/*` — Owner: Infra Engineer
3. Remove Kratos flow rendering from dashboard (kratos.ts, flow logic in all pages) — Owner: Frontend Engineer
4. Simplify dashboard login page to PKCE-only — Owner: Frontend Engineer
5. Fix consent handler `getKratosSessionSubject` to use internal Kratos URL — Owner: API Engineer
6. Verify `return_to` in consent handler works with new Kratos UI URLs — Owner: API Engineer
7. End-to-end test of complete flow on DigitalOcean — Owner: Test Engineer

**Dissent:**
- Platform Security Engineer: shared cookie domain is suboptimal. Registered as future improvement.

  │ 5. Redirects to login.ui_url = accounts.dev.loopzero.example/login
  │
  ▼

  │
  │ 6. User authenticates (GitHub OIDC / email+password)
  │ 7. Kratos creates session → redirect to return_to
  │
  ▼

  │
  │ 8. Validates Kratos session cookie → accepts Hydra login
  │
  ▼

  │
  │ 9. Redirect to dashboard callback with authorization code
  │
  ▼

  │
  │ 10. Exchange code for tokens → authenticated!
