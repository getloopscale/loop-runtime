# MEET-2026-03-26-008 — Release Activation Recovery (RELEASING State)

**Data:** 2026-03-26
**Tipo:** architecture + distributed-systems
**Status:** APPROVED_WITH_CONDITIONS
**Sponsor:** Distributed Systems Engineer
**Challenger:** SRE (operational risk) + Principal Architect (convergence model)
**Owner:** API Engineer (build_orchestrator.go, build_reconcile_loop.go, statemachine)

---

## Contexto

O deploy flow tem duas fases (design DA-17):
- **Phase 1** (inside advisory lock): Build RUNNING → SUCCEEDED. Commits independentemente.
- **Phase 2** (outside lock): activateRelease (create release → gitops push → ArgoCD sync → health → ACTIVE).

Se o pod da API morre entre Phase 1 commit e Phase 2 completion, o build fica SUCCEEDED no banco mas nenhuma release e criada. O sistema nao tem recovery path:
- `FindActiveBuilds` query: `WHERE status IN ('QUEUED', 'RUNNING')` — SUCCEEDED e invisivel
- `OnBuildCompleted` fast path: `IsBuildTerminal → return nil` — impede retry
- `BuildReaper` e `StartupReconciler` tambem ignoram SUCCEEDED
- A app nunca chega ao workload cluster. Nenhum alerta dispara.

**Blast radius:** Todo deploy onde Phase 2 falha ou e interrompido (rollout, crash, Gitea down, ArgoCD unavailable) resulta em build SUCCEEDED sem deployment. Silencioso.

## Decisao

**Adotar Proposta B — Estado intermediario RELEASING no state machine de build.**

### Nova transicao:

```
QUEUED → RUNNING → RELEASING → SUCCEEDED
                 ↘ FAILED      ↘ FAILED (release activation timeout/permanent failure)
```

- `RELEASING`: build de imagem concluido, ativacao de release em andamento
- `SUCCEEDED`: deploy completo (release ACTIVE, app no workload cluster)
- `IsBuildTerminal(RELEASING) = false` — reconcile loop ve e retenta

### Como funciona:

1. `OnBuildCompleted` Phase 1: transiciona para **RELEASING** (nao SUCCEEDED)
2. Phase 2 (`activateRelease`) executa inline no happy path (zero latency regression)
3. Phase 2 sucesso: transiciona RELEASING → SUCCEEDED
4. Phase 2 falha (ou crash): build fica em RELEASING
5. `BuildReconcileLoop` ve RELEASING no proximo tick, reconstroi dados e retenta Phase 2
6. `BuildReaper` enforce timeout de 10min em RELEASING → FAILED

### Propostas Rejeitadas

| Proposta | Motivo |
|----------|--------|
| **(A) Orphan Build Detector** | Adiciona loop separado para compensar modelo quebrado. Duplica logica de activateRelease. Deteccao por ausencia de release e anti-pattern (estado implicito). |
| **(C) Reconcile loop com JOIN** | Mesma deteccao por ausencia de release. "O sistema deve saber o estado de um build olhando o build, nao fazendo JOIN contra releases" (Architect + DistSys). |

### Trade-offs Aceitos

1. **State machine change e forward-only.** RELEASING e um novo valor em `GET /builds/:id`. Consumidores que checam `status == 'SUCCEEDED'` veem RELEASING durante Phase 2. Aceito porque: RELEASING e mais informativo (deploy em progresso), e SUCCEEDED agora significa "totalmente deployado".
2. **Todos os call sites de IsBuildTerminal precisam ser auditados.** Aceito porque: sao poucos (build_orchestrator, reconcile_loop, reaper) e o compilador nao pega mudancas semanticas.

### Riscos Aceitos

| Risco | Severidade | Mitigacao | Owner |
|-------|-----------|-----------|-------|
| IsBuildTerminal call sites nao atualizados | HIGH | Grep todos os usos antes de merge | API Engineer |
| RELEASING build stuck sem release (retry falha) | HIGH | BuildReaper timeout 10min + max 3 retries | API Engineer |
| Latencia do reconcile loop (10s poll) no retry path | MEDIUM | Happy path executa inline, retry path paga 10s max | N/A |

### Riscos NAO Aceitos (Blockers — SRE Veto)

| Risco | Condicao para Desbloqueio |
|-------|---------------------------|
| Nenhuma metrica detecta orphan builds | Criar gauge `loopzero_orphan_builds` antes do merge |
| Nenhum alerta existe | Criar alerta `LoopZeroOrphanBuild` (critical, 5min) |
| `emitActivationFailure` e unico sinal e nao sobrevive crash | Persistir falha no DB, nao apenas SSE |

## Acoes Obrigatorias

### State Machine (`pkg/statemachine/build.go`)
1. Adicionar `BuildReleasing State = "RELEASING"`
2. Adicionar eventos `BuildReleaseStarted`, `BuildReleaseCompleted`, `BuildReleaseTimeout`
3. Transicoes: RUNNING → RELEASING, RELEASING → SUCCEEDED, RELEASING → FAILED
4. `IsBuildTerminal(RELEASING) = false`

### Build Store (`api/internal/db/build_store.go`)
5. `FindActiveBuilds` query: `WHERE status IN ('QUEUED', 'RUNNING', 'RELEASING')`

### Build Orchestrator (`api/internal/services/build_orchestrator.go`)
6. `OnBuildCompleted` Phase 1: transicionar para RELEASING (nao SUCCEEDED)
7. Phase 2 sucesso: transicionar RELEASING → SUCCEEDED
8. Phase 2 falha: deixar em RELEASING (reconcile loop retenta)
9. Remover fast path `IsBuildTerminal` para RELEASING (ou ajustar para pular apenas SUCCEEDED/FAILED/CANCELLED)

### Reconcile Loop (`api/internal/services/build_reconcile_loop.go`)
10. `reconcileBuild`: quando build.Status == RELEASING, verificar estado da release associada:
    - Sem release: chamar activateRelease (reconstruir BuildCallbackRequest de apps_spec)
    - Release em GIT_MIRROR_FAILED: chamar RetryRelease
    - Release em ACTIVE: transicionar build RELEASING → SUCCEEDED
11. Adicionar retry counter (`release_attempts`) com max 3

### Build Reaper (`api/internal/services/build_reaper.go`)
12. Adicionar timeout para RELEASING (10 minutos) → FAILED

### Observabilidade
13. Gauge `loopzero_orphan_builds`: builds em RELEASING > 2min
14. Alerta `LoopZeroOrphanBuild`: critical se `loopzero_orphan_builds > 0` por 5min
15. Log structured quando reconcile loop retenta Phase 2

### Testes
16. Unit: RUNNING → RELEASING → SUCCEEDED (happy path)
17. Unit: RELEASING sem release → reconcile loop cria release → SUCCEEDED
18. Unit: RELEASING com release GIT_MIRROR_FAILED → reconcile retenta → SUCCEEDED
19. Unit: RELEASING > 10min → BuildReaper → FAILED
20. Unit: OnBuildCompleted em build RELEASING com release ACTIVE → SUCCEEDED
21. Integration: API crash durante Phase 2, build fica RELEASING, recovery no restart
