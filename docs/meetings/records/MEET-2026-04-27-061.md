### GitOps Engineer

**Assessment.** Phase 2 changes the topology that ArgoCD operates on. Gitea moving from 1 → 2 replicas with NFS shared storage is a non-trivial concurrency story — git's lock files (`HEAD.lock`, `refs/heads/.lock`) are filesystem-local and rely on POSIX `O_EXCL`. NFSv4 supports `O_EXCL`; NFSv3 does not. The DO Volume + nfs-subdir-external-provisioner combination must be NFSv4. Concurrent push from two API replicas to the same Gitea repo via two replicas on RWX must be load-tested *with* the 200-concurrent-clone target *while* a tenant is provisioning (write under read pressure).

Harbor HA with Redis externalization is operationally simpler — Harbor was built for this.

MinIO standalone → distributed migration affects the API's `s3` client (build artifact upload) and Argo Workflows' build-side push. Any in-flight build during cutover will fail. This argues for a maintenance window with `loopzero deploy` paused (env-lock at API level) for the migration duration.

**Risks.**
1. NFSv3 vs NFSv4 mode mismatch on DO Volumes can produce silent corruption of git refs under concurrent push. Pre-cutover validation: `mount | grep nfs` shows `vers=4`.
2. ArgoCD `notifications.notifiers` (CLAUDE.md known issue: `services` silently ignored) is a watch-item across Phase 6 — when alert manifests change, validate that notifiers stay configured.
3. T2.3 cutover sequence must explicitly drain Argo Workflows queue before MinIO endpoint flips. Without that, in-flight builds reference the old endpoint and 503.
4. The "single ArgoCD Application per tenant per env" (CLAUDE.md) means any Degraded resource blocks ALL notifications — chaos injection in Phase 5 must not leave half-Degraded apps for >2min, otherwise alert noise contaminates Phase 6 baseline.

**Recommendation.** **Option B.** Three reasons specific to gitops:
1. CHG-002a Gitea HA needs its own validation matrix (concurrent-clone p95, concurrent-push success, NFS mode verify). Co-mingled with chaos in one CHG, those checks get truncated.
2. T2.3 MinIO migration deserves a dedicated cutover runbook published *before* CHG-002a opens; the runbook is the contract for "blue/green safe."
3. Phase 5 chaos must run *after* shared-service HA stabilizes for >24h — separation of concerns enforces that gap.

**Conditions for CHG-002a.**
- T2.1: NFSv4 explicit, pre-cutover validate-mount.
- T2.3: Maintenance window with env-lock; published runbook (`docs/runbooks/minio-distributed-migration.md`); Argo queue drain step explicit; rollback path defined (keep old MinIO running for 48h post-cutover, blue/green endpoint alias).
- ArgoCD notifier sanity check (`kubectl -n argocd get cm argocd-notifications-cm -o yaml | grep -c notifiers`) added to CHG-002a validation matrix.

**Impact if ignored.** Concurrent-push corruption is silent and only surfaces under load — exactly the L3 conditions of CHG-002b. Bug attribution will be "L3 unstable" rather than "Gitea NFS mode wrong."

### Platform Security Engineer (VETO HOLDER)

**Assessment.** CHG-002 mutates four security surfaces:
1. **Redis externalization (Harbor HA, T2.2):** DO managed Redis is a new credential primitive. Connection string carries password; must be in K8s Secret + ESO, never in Helm values literal.
2. **NFS RWX surface (T2.1):** NFSv4 export from a DO Volume is a new shared-filesystem trust boundary. nfs-subdir-external-provisioner runs with elevated privileges. Multi-tenant Gitea on shared NFS is acceptable only if ALL access goes through Gitea's auth layer — direct PVC mount by other workloads must be denied (NetworkPolicy + RBAC).
3. **Chaos Mesh CRDs + privileged operations (T0.3, T5.1):** Chaos Mesh requires `cap_sys_admin` for some experiments (network partition) and access to `/proc` for stress-chaos. Default install is NOT secure; Helm values must enforce: `controllerManager.serviceAccount.create: true`, RBAC scoped to `chaos-mesh` namespace and target-allowed namespaces only, dashboard disabled (no UI), webhook validation enabled.
4. **MinIO migration (T2.3):** Per-tenant STS credentials (ADR-0010 commitment) must survive the migration. New MinIO root credentials must be issued; old credentials revoked post-cutover; ESO refresh of consumer namespaces required.

Telemetry-derived: `lokiPushUrl: http://10.20.0.26:30100` is plaintext — Loki authentication is TODO. If we leave it as `http://`, log push is unauthenticated within the VPC. Acceptable today; flag as Phase 6 follow-up.

**Risks.**
1. **VETO TARGET:** Chaos Mesh installed cluster-wide with default RBAC = ability to crash any pod in any namespace. Bundled with active workloads + supply chain (Sprint 6 policy-controller in Audit), an over-broad chaos policy can mask Deny-flip readiness.
2. **VETO TARGET:** MinIO endpoint cutover without atomic credential rotation = window during which stale tokens reach new MinIO with wrong credentials, generating 403s indistinguishable from auth attack.
3. **VETO TARGET:** NFS PVC mounted RWX by anything other than Gitea pods is a horizontal escape vector. Must be enforced with `volumeAttachments.spec.allowedTopologies` or namespace-scoped StorageClass.
4. The 4 `mgmt-*.ts` components without PSA compliance audit may run as `restricted` already (DO does that by default for new namespaces) but must be verified pre-T2.1.

**Objections.** I VETO Option A. Bundling chaos with HA migration and MinIO cutover means the security-review attention budget is split three ways under one approval. Option B isolates each surface.

**Recommendation.** **Option B with security gates per CHG.**

**Conditions for CHG-002a (mandatory, all four):**
1. Harbor Redis password via ESO (DO managed Redis secret) — never in Helm `values.yaml`. New `redis-credentials` ExternalSecret resource.
2. NFS StorageClass scoped to `gitea` namespace via `allowedTopologies` or `csi.storage.k8s.io/provisioner-secret-namespace`. NetworkPolicy on `gitea` namespace: ingress only from `argocd`, `loopzero-api`, internal `gitea` pods. No other workload can mount the PVC.
3. Chaos Mesh Helm values: `dashboard.enabled: false`, `controllerManager.replicaCount: 1` (cluster-singleton), RBAC scoped to `chaos-mesh` namespace + explicit allowed-target namespaces (`gitea`, `harbor`, `argocd`, `loopzero-api`, `loopzero-system`, `minio`). NO `cluster-admin` ClusterRoleBinding.
4. MinIO migration runbook (T2.3) MUST include atomic credential rotation: issue new root credentials BEFORE flipping endpoint; revoke old credentials AFTER ESO consumer namespaces refresh; document the 5-second blackout window.

**Conditions for CHG-002c:**
- T5.1 chaos manifests must declare `spec.selector.namespaces` explicitly. Cluster-wide selectors banned.
- T5.1 must run AFTER Sprint 6 policy-controller Deny-flip observation window closes (or with policy-controller temporarily set to dry-run for chaos-test namespaces — operator-supervised).

**Impact if ignored.** Auditable security regression. NFS escape and chaos blast scope are exactly the failure modes a security review is supposed to catch before they happen.

### SRE Engineer (VETO HOLDER, Challenger)

**Assessment.** This is the hardest CHG of the year. Three live infrastructure mutations (PG resize, mgmt rolling upgrade, MinIO migration), one new high-privilege operator (Chaos Mesh), and an iterative diagnostic loop that may discover BuildKit/ArgoCD architectural bugs. Big-bang means one validation gate for all of it.

**Risks (severity-ordered).**
1. **HIGH — T0.1 PG resize 5-min downtime.** DO managed PG resize is failover (synchronous replica promotion). The API's PG connection pool will see EOF for ~5 min. The advisory-lock semantics survive failover (locks are session-scoped and die with the session — connections reconnect; mid-flight transactions roll back). However: any in-flight `loopzero deploy` during resize will hit `pg_advisory_xact_lock` failure and the API's `withEnvironmentLock` returns 503. Without `loopzero` global maintenance flag, users see deploy failures. Mitigation: env-lock at API level + customer comm window.
2. **HIGH — T2.3 MinIO migration data integrity.** `mc mirror` is best-effort eventual consistency. If a build artifact lands on old MinIO mid-mirror, it may not migrate. Blue/green with read-from-both-during-transition is the only safe pattern. Plan v3.2 references `docs/plans/minio-distributed-migration.md` which DOES NOT EXIST. Blocker.
3. **HIGH — T0.2 mgmt rolling upgrade 15min duration.** During the upgrade, 3 nodes cycle one-by-one; pods reschedule. ArgoCD, Gitea, Harbor, MinIO controllers all live in mgmt — each will be restarted. PR webhooks during this window may fail. Mitigation: pre-announce window; validate `kubectl wait --for=condition=Available` per Helm release post-upgrade.
4. **HIGH — T5.1 chaos kill recovery <2min SLA.** Gate 2a requires this. If Phase 2 HA is not deeply validated before Phase 5, chaos surfaces config gaps as "test failures" — confusing failure mode (was it chaos or was it HA?). Phase 2 must stabilize >24h before Phase 5 runs.
5. **MEDIUM — L3 100-tenant test cost.** Each L3 run consumes registry pulls, S3 puts, builder CPU. Five consecutive runs = 500 builds = real DO billing. SRE sign-off required on cost.
6. **MEDIUM — Cell-2 still inactive after CHG-002.** ADR-0010 Gate 2b is Sprint 9. Investor narrative should not conflate "Gate 2a passed" with "cell-2 live."
7. **MEDIUM — `lokiPushUrl: 10.20.0.26:30100` brittle.** First time cluster IPs shift, log push silently dies. Service DNS fixes this.
8. **LOW — k8s version drift staging vs prod.** `1.32.13-do.2` reaches DO end-of-life sooner than `1.33.9-do.3`. Bumping staging/prod must happen in CHG-002a or Phase -1 housekeeping is wasted.

**Objections.** I VETO Option A on the same grounds I vetoed CHG-001's Option A: epic-CHG with three live-data mutations under one approval is unbounded blast radius. I additionally VETO any CHG-002 that does not include a published `docs/runbooks/minio-distributed-migration.md` BEFORE T2.3 executes — referencing a missing document is the exact pattern that caused this round of state-zombie debt.

### Production Design Reviewer
