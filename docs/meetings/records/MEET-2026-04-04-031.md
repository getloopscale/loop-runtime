## Stage 2 — Analyses

### Principal Architect

**Assessment:**
The proposed architecture has a fundamental tension: the dashboard currently authenticates via Hydra PKCE (getting JWT access tokens), but Kratos selfservice flows (verification, recovery, settings) operate via Kratos sessions (cookies). These are two separate session mechanisms. The plan must address how the dashboard handles both.

The current flow is: Dashboard -> Hydra PKCE -> consent handler redirects to Kratos -> Kratos authenticates user -> consent handler accepts login -> Hydra issues JWT. Selfservice flows like verification and recovery do NOT go through Hydra — they are Kratos-native. This means the dashboard needs to call Kratos public API directly for these flows, independent of the Hydra/PKCE flow.

The proposed approach of having the dashboard call Kratos `/self-service/*` endpoints directly is correct. These flows do not require an active session — they are initiated by URL (email link) or form submission. Verification and recovery are anonymous flows. Settings requires an active Kratos session (not a Hydra JWT).

**Risks:**
1. Settings page requires a Kratos session cookie. If the user logged in via Hydra PKCE, they may not have a Kratos session cookie accessible to the dashboard (different domains or cookie scope).
2. URL naming collision: `/settings` in the dashboard is currently the team settings page. Account/profile settings needs a different path.
3. The selfservice URL overrides must use the dashboard domain, but the dashboard is an SPA — Kratos will redirect to `dashboard.dev.loopzero.example/verification?flow=<id>`, and the SPA must handle that route and call Kratos API to fetch/submit the flow.

**Objections:**
- The plan conflates team settings (`/settings`) with account settings. The existing `/settings` page is team configuration (danger zone, CLI commands). Account settings (password change, linked accounts) is a different concern.

**Recommendation:**
- Use `/account` or `/account/settings` for Kratos selfservice settings to avoid collision with the existing team `/settings` page.
- For verification and recovery: these are anonymous flows, no session conflict. The dashboard page fetches the flow via `?flow=<id>` query param and renders it. Straightforward.
- For account settings: the user needs a Kratos session. Since the consent handler already interacts with Kratos during login, the Kratos session cookie should exist if the cookie domain is set correctly (same parent domain). Verify cookie scope.
- Do NOT introduce a separate accounts service. The SPA can handle all 5 pages. Adding another service increases operational cost for zero benefit at this scale.

**Conditions for approval:**
1. Resolve the `/settings` path collision before implementation.
2. Verify Kratos session cookie is accessible to the dashboard domain.
3. Kratos `serve.public.cors` must allow the dashboard origin.

**Impact if ignored:** Users will hit broken routes or see team settings when they expect profile settings. Session mismatches will cause 401s on the settings page.

### Platform Security Engineer

**Assessment:**
Six security concerns require attention:

1. **Email enumeration:** Kratos recovery and registration flows can leak whether an email is registered. Kratos 1.3.x has built-in anti-enumeration (it always shows "check your email" regardless of whether the email exists), but this must be verified in the configuration — `selfservice.flows.recovery.notify_unknown_recipients` should be `true` (default in 1.3+).

2. **Rate limiting:** The plan has ZERO mention of rate limiting. Recovery and verification endpoints are prime abuse targets. An attacker can trigger unlimited emails to any address. Kratos has no built-in rate limiting — it must be applied at the ingress layer (Traefik) or via middleware.

3. **CSRF protection:** Kratos selfservice flows use CSRF tokens in flow objects. The dashboard MUST render and submit the `csrf_token` field from the flow response. This is non-negotiable — without it, CSRF attacks can trigger password resets and account changes.

4. **SMTP credentials:** The Resend API key will be stored as a Pulumi secret (`pulumi config set --secret smtpConnectionUri`). This is correct — it follows the existing pattern for sensitive values. However, the SMTP connection string contains the API key in cleartext in the URI. Ensure Kratos does not log the connection URI at startup.

5. **Email link security:** Verification and recovery links contain flow IDs and codes. These are single-use and time-limited by Kratos. The default expiration is 1 hour for recovery and 24 hours for verification. These defaults are acceptable.

6. **SPF/DKIM/DMARC:** Sending email from `noreply@loopzero.example` via Resend requires DNS records (SPF, DKIM) for deliverability. Without them, emails will land in spam. This is an infrastructure prerequisite that the plan does not mention.

**Risks:**
1. HIGH: No rate limiting on email-sending flows (recovery, registration) — abuse vector for email bombing.
2. MEDIUM: SPF/DKIM not configured — emails may go to spam, breaking the entire flow.
3. LOW: `leak_sensitive_values: false` is set in Kratos config, which is correct. But verify it is not overridden by Pulumi.

**Objections:**
- The plan MUST include rate limiting before going live. Even pre-release, an exposed endpoint that sends emails to arbitrary addresses is a liability.
- The plan MUST include SPF/DKIM DNS setup or email delivery will fail silently (spam folder).

**Recommendation:**
1. Add Traefik rate limiting on Kratos public endpoints: `accounts.dev.loopzero.example` should have a rate limit of 5 requests/minute per IP for `/self-service/recovery` and `/self-service/verification`.
2. Add SPF and DKIM DNS records for `loopzero.example` via Resend's domain verification.
3. Verify `leak_sensitive_values: false` is not overridden.
4. Set verification flow lifespan to 24h, recovery to 1h (Kratos defaults — confirm they are active).
5. Custom email templates should include a "you did not request this" footer with an ignore instruction.

**Conditions for approval:**
1. MANDATORY: Rate limiting on recovery/verification/registration endpoints before deployment.
2. MANDATORY: SPF/DKIM DNS records configured in Resend + DigitalOcean DNS (or Cloudflare if DNS is delegated).
3. Verify `leak_sensitive_values: false` is preserved in production config.

**Impact if ignored:** Email bombing of arbitrary addresses using your domain. Emails landing in spam. Potential domain reputation damage. CSRF attacks on account settings.

### DX/Tooling Engineer

**Assessment:**
The user experience of auth flows is critical — these are the first touchpoints for new users. The proposed plan covers the mechanics but needs DX polish.

1. **Custom pages vs. @ory/elements:** Custom pages are the right choice. @ory/elements adds a dependency, has its own design system that would clash with the existing Tailwind + Radix UI + framer-motion aesthetic, and abstracts away control over error messages (Rule 3 compliance). The existing login page is a good template — consistent design language, motion animations, branded.

2. **Error messages:** Kratos returns structured error objects with `messages` arrays. These MUST be translated to product language. Example: Kratos may return `"The identity's credentials do not exist"` which must become `"Incorrect email or password"`. Similarly, `"The recovery token is invalid or has expired"` should become `"This recovery link has expired. Request a new one."`. A mapping layer is needed.

3. **Flow UX patterns:**
   - Registration: should offer social login (GitHub, Google) prominently, with email+password as secondary. The current login page has this layout — maintain it.
   - Verification: should be a single-purpose page. User lands from email, sees "Verifying your email..." then success or failure. Minimal UI.
   - Recovery: two-step — (1) enter email, (2) after clicking link, enter new password. Each step is a different state of the same flow.
   - Account settings: tabbed or sectioned — profile info, change password, linked accounts.
   - Error: generic error page with human-readable message and "Go to dashboard" CTA.

4. **Internal terms (Rule 3):** The pages MUST NOT expose: Kratos, Hydra, Ory, CSRF, flow ID, identity schema, traits, or any JSON error detail. All error rendering must go through a sanitization layer.

5. **Redirect behavior:** After verification success, redirect to login (if not logged in) or dashboard (if logged in). After recovery (password reset), redirect to login. After settings change, show success toast and stay on page.

**Risks:**
1. Kratos error messages leaking internal terms into the UI.
2. Complex flow state management if the Kratos API returns unexpected states.

**Objections:** None on approach. The plan is sound for DX.

**Recommendation:**
- Build a `kratosFlowRenderer` utility that takes a Kratos flow response, extracts UI nodes, maps messages to product language, and renders form fields. This is reusable across all 5 pages.
- Use the existing design system (Card, Button, motion variants from login page).
- Add a `kratosMessageMap` that translates known Kratos message IDs to user-friendly strings.

**Conditions for approval:**
1. All 5 pages must pass Rule 3 audit (no internal terms).
2. Error messages must suggest next action (consistent with CLI error philosophy).
3. Loading and error states must be handled gracefully (skeleton/spinner on flow fetch, clear error on failure).

**Impact if ignored:** Users see cryptic error messages, internal terms, or broken flows. First impression of the product is damaged.

### SRE/Production Engineer

**Assessment:**
The operational concerns are focused on email deliverability, monitoring, and DNS.

1. **Resend as provider:** Resend is acceptable for pre-release. Free tier (100 emails/day) is sufficient for pre-release volume. The `smtps://resend:re_XXXX@smtp.resend.com:465` connection format is standard SMTP-over-TLS. Resend has 99.9% uptime SLA on paid plans; free tier has no SLA but historically reliable.

2. **DNS requirements for email:** To send from `noreply@loopzero.example`:
   - SPF record: `v=spf1 include:_spf.resend.dev ~all` (TXT record on `loopzero.example`)
   - DKIM: Resend provides CNAME records to add to DNS
   - DMARC: `v=DMARC1; p=none; rua=mailto:dmarc@loopzero.example` (start with `p=none` for monitoring)
   - These DNS records must be added to the domain (DigitalOcean DNS or Cloudflare, depending on where the domain is managed).

3. **Monitoring:** Add alerting for:
   - Kratos courier queue depth (emails pending send) — metric: `kratos_courier_message_total` and `kratos_courier_message_status`
   - SMTP connection failures (Kratos logs)
   - Resend dashboard for bounce/complaint rates

4. **Rollback plan:** If Resend has issues, the only fallback is reverting `smtpConnectionUri` to empty (disabling email) or switching to another provider. The Pulumi config makes this a single `pulumi config set` + deploy.

5. **Kratos pod restart:** Changing the Helm values (SMTP, selfservice URLs) requires a Kratos pod restart. Pulumi handles this via Helm upgrade. The Kratos automigration initContainer will run but should be a no-op since the schema is already current.

**Risks:**
1. MEDIUM: DNS record propagation may take up to 48 hours. SPF/DKIM should be configured BEFORE sending production emails, or they will bounce/spam.
2. LOW: Resend free tier has no SLA. Acceptable for pre-release.
3. LOW: Kratos courier runs as a sidecar/goroutine. If email sending fails, it retries with backoff. No email loss, but delivery delay.

**Objections:**
- SPF/DKIM MUST be set up before Phase 1 is declared done. Sending emails without proper DNS records will damage the domain reputation even during pre-release.

**Recommendation:**
1. Add SPF/DKIM/DMARC as Phase 0 (DNS prerequisite) before Phase 1.
2. Verify Resend domain in Resend dashboard before configuring SMTP.
3. Test email delivery to multiple providers (Gmail, Outlook, ProtonMail) to verify no spam filtering.

**Conditions for approval:**
1. MANDATORY: SPF + DKIM DNS records configured and verified BEFORE first email is sent.
2. DMARC record added in monitoring mode (`p=none`).
3. Resend domain verification completed.

**Impact if ignored:** Emails go to spam. Domain reputation damaged. Recovery and verification flows appear broken to users even though they technically work.

## Stage 4 — Decision

**Chosen approach:**

1. **Resend as SMTP provider** — APPROVED. Pulumi config path already exists. Wire `LOOPZERO_SMTP_CONNECTION_URI` as environment variable for CI/CD, or use `pulumi config set --secret` directly.

2. **Custom dashboard pages (NOT @ory/elements)** — APPROVED. Build 5 pages using existing design system (React + Tailwind + Radix + framer-motion). Create a shared `kratosFlowRenderer` utility for form rendering and message translation.

3. **Dashboard SPA handles all selfservice URLs (NOT a separate service)** — APPROVED. No new service. The SPA renders verification, recovery, registration, account settings, and error pages.

4. **Session model: Redirect-based Kratos session for /account** — APPROVED. Verification and recovery are anonymous flows (no session needed). The `/account` page uses redirect to Kratos to initiate settings flow, avoiding cross-domain cookie issues.

5. **Custom email templates** — APPROVED, mandatory if defaults contain internal terms. Branded "LoopZero" templates.

6. **Rate limiting via Traefik middleware** — APPROVED, mandatory before deployment.

7. **Path: `/account` for profile/password/linked accounts** — APPROVED. `/settings` remains team settings.

**Rejected alternatives:**
- @ory/elements library: Adds dependency, clashes with design system, reduces control over Rule 3 compliance.
- Separate accounts service: Unnecessary operational overhead. SPA can handle the flows directly.
- Hydra-only session model: Kratos selfservice flows require Kratos sessions. Cannot avoid this.
- Deferring rate limiting: Security veto — email-sending endpoints without rate limits are an abuse vector.

**Trade-offs consciously accepted:**
- The dashboard must call Kratos public API directly for selfservice flows. This adds coupling to Kratos API, but is the intended integration pattern.
- Custom email templates require maintenance when Kratos is upgraded (template variables may change). Acceptable.
- Redirect-based settings flow adds one extra redirect. Acceptable UX cost for avoiding cross-domain cookie complexity.

**Risks accepted:**
| Risk | Mitigation | Owner |
|------|-----------|-------|
| Resend free tier has no SLA | Acceptable for pre-release. Upgrade to paid when needed. Monitor delivery. | SRE |
| DNS propagation delay for SPF/DKIM | Configure DNS records first (Phase 0). Wait for verification before sending. | SRE |
| Kratos API changes on upgrade | Pin Kratos version. Test flow rendering after upgrades. | Infra Engineer |

**Risks NOT accepted (blocking):** None. All risks have mitigations.

**Mandatory actions before implementation:**

1. **[SRE]** Configure SPF, DKIM, and DMARC DNS records for `loopzero.example` via Resend domain verification. This is Phase 0 — must complete before any email is sent.
2. **[Infra]** Add Traefik rate limiting middleware on `accounts.dev.loopzero.example` IngressRoute: 5 req/min per IP on `/self-service/recovery/*` and `/self-service/verification/*` paths.
3. **[Infra]** Check default Kratos email templates for internal terms (Ory, Kratos). If present, create custom templates with LoopZero branding.
4. **[Infra]** Update selfservice URL overrides in `mgmt-bootstrap.ts` to use `/account` instead of `/settings` for the settings flow.
5. **[Dashboard]** Rename the plan: `/settings` -> `/account` for Kratos selfservice settings throughout.
6. **[Dashboard]** Create `kratosMessageMap` utility to translate Kratos error/info messages to product language (Rule 3).
7. **[Security]** Verify `leak_sensitive_values: false` is not overridden in any Pulumi config path.
