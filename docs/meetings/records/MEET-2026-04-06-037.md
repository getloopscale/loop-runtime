## Stage 1 — Context

**Problem:** When a user authenticates via Google or GitHub OIDC, Kratos creates the identity with `verifiable_addresses: [{ value: "email@example.com", verified: false }]`. This happens because the identity schema (`identity.default.schema.json`) has `"verification": { "via": "email" }` on the email trait, which applies uniformly to ALL authentication methods — password and OIDC alike. The OIDC Jsonnet mappers only map `identity.traits` (email, name) and do not propagate the provider's `email_verified` claim.

The dashboard's `isEmailVerified()` function checks `verifiable_addresses` — it currently assumes OIDC users have NO `verifiable_addresses` (empty array = pre-verified). But Kratos DOES populate `verifiable_addresses` for OIDC users when the schema has `verification.via`, so `isEmailVerified()` returns `false`, triggering the verification banner. When the user clicks "Verify now," the verification flow fails with a 403 CSRF violation because the CSRF cookie from the OIDC redirect chain does not match the new verification flow context.

**Decision Required:**
1. Which approach to fix OIDC email verification: dashboard-side detection (Option A), Kratos admin API webhook (Option B), or both (Option C)?
2. Is trusting OIDC provider email verification secure for pre-release?
3. What verification does `isEmailVerified()` need to remain correct across auth methods?

**Constraints:**
- Kratos v1.3.1 — OIDC mappers can only write to `identity.traits`, not `verifiable_addresses`
- Single identity schema — Kratos does not support per-method schemas
- Pre-release: backward compatibility not required; cleanest design preferred
- Cookie domain `.dev.loopzero.example` with SameSite=Lax
- Production on DigitalOcean, Kratos in `platform-system` namespace
- CSRF token mismatch is inherent to the OIDC-then-verification flow transition

**Known Context:**
- `infra/helm/ory-kratos/values.yaml` lines 156-187: identity schema with `verification: { via: "email" }`
- `infra/helm/ory-kratos/values.yaml` lines 51, 59: OIDC mapper Jsonnet (base64) — maps only traits
- `cloud/dashboard/src/lib/auth.ts` lines 33-36: `isEmailVerified()` function
- `cloud/dashboard/src/app.tsx` line 30: verification check in DashboardLayout
- `cloud/dashboard/src/components/verification-banner.tsx`: the banner shown to unverified users
- MEET-036: established Kratos HTTP courier for email delivery via Resend

**Proposal:** Four options under evaluation:
- **Option A:** Dashboard-side detection — check `session.authentication_methods` for `oidc` type
- **Option B:** Kratos after-registration webhook — call Kratos Admin API to mark email verified
- **Option C:** Both A (immediate) + B (follow-up)
- **Option D:** Schema change or dual schemas — rejected upfront (Kratos limitation)

## Stage 2 — Analyses

### Platform Security Engineer

**Assessment:** The core question is whether trusting Google and GitHub's email verification claim is acceptable. Both providers verify email ownership as part of their account creation process: Google requires phone/email verification, GitHub requires email confirmation before granting `user:email` scope access. For these two specific providers, the email verification is strictly stronger than Kratos's own code-by-email verification — the user already proved ownership to a major identity provider with robust anti-fraud systems.

However, blindly trusting ANY OIDC provider is dangerous. The trust must be explicitly scoped to known providers (Google, GitHub) and not extended to arbitrary future OIDC integrations without review.

**Risks identified:**
1. (low) Google/GitHub email verification trust — these are tier-1 identity providers with verified email guarantees
2. (medium) Future OIDC providers added without verification review — could auto-trust an unverified provider
3. (low) Email address change after OIDC registration — user changes email in provider, Kratos still has old verified address

**Objections:**
- Option A alone leaves inconsistent state in Kratos DB (`verified: false` for actually-verified emails). This is a data integrity issue. If any future system component queries Kratos directly for verification status, it will get the wrong answer.

**Recommendation:** Option C (A + B). Option A provides immediate UX fix. Option B provides data correctness. Both are needed.

**Conditions for approval:**
1. Dashboard detection MUST check specific provider IDs (github, google), NOT generic "is oidc" — future providers need explicit allowlisting
2. Webhook must validate the provider before marking verified
3. Document the trust model: which providers are trusted for email verification and why

**Impact if ignored:** OIDC users see perpetual verification banner they cannot dismiss. CSRF error on verification attempt. Broken first-login experience for 2 of 3 auth methods.

### Principal Architect

**Assessment:** Architecturally, Option B (Kratos Admin API webhook) is the correct long-term solution. The source of truth for identity state is Kratos. If the dashboard works around bad Kratos state, we are building a lie into the UI layer that must be maintained everywhere Kratos data is consumed.

However, Option B has significant implementation complexity:
- New webhook endpoint in the cloud Go service
- Kratos `after.oidc.hooks` configuration (must be ordered BEFORE the `session` hook, or the webhook fires after redirect)
- Kratos Admin API authentication (internal service-to-service, no public exposure)
- Error handling: what if the webhook fails? Does registration fail? Does the user get stuck?

For pre-release, Option A is pragmatic and sufficient. Option B should follow as a data-correctness improvement but should NOT block the fix.

**Risks identified:**
1. (medium) Webhook ordering — if webhook fires after session hook, the redirect happens before the admin API call, creating a race with the dashboard
2. (low) Webhook failure — must be non-blocking (registration should not fail if email marking fails)
3. (low) Admin API exposure — must be cluster-internal only

**Objections:** None to Option C. Would object to Option B alone (too slow for a UX-blocking bug).

**Recommendation:** Option C. Deploy Option A immediately. Build Option B as a tracked follow-up.

**Conditions for approval:**
1. Option A must be deployed within the current session
2. Option B must be tracked as a concrete task, not deferred indefinitely

**Impact if ignored:** Dashboard UX broken for majority of users (social login is the primary onboarding path).

### DX/Tooling Engineer

**Assessment:** This is a critical first-login experience bug. Social login is the primary path for new users — Google and GitHub buttons are prominently displayed. A user who signs up via Google, lands on the dashboard, sees "Verify your email" immediately, clicks it, and gets a CSRF error will lose trust in the product. This is a P0 UX issue.

The current `isEmailVerified()` function has a faulty assumption documented in its own comment: "OIDC users (GitHub/Google) don't have verifiable_addresses." This is wrong — Kratos DOES populate `verifiable_addresses` when the schema includes `verification.via`. The function was written based on an incorrect mental model.

Option A fix should check `session.authentication_methods` for the `oidc` method type. The Kratos session object includes `authentication_methods: [{ method: "oidc", aal: "aal1", completed_at: "..." }]`. This is a reliable signal.

**Risks identified:**
1. (low) `authentication_methods` might not be populated in all Kratos versions — must verify against v1.3.1
2. (low) User registers with password, later links OIDC — `authentication_methods` reflects the current session's auth method, not the identity's registration method

**Objections:** None to Option C.

**Recommendation:** Option A implemented as: check if `session.authentication_methods` includes any entry with `method === "oidc"` AND `provider_id` is in the trusted set `["github", "google"]`. If so, treat as verified regardless of `verifiable_addresses`.

**Conditions for approval:**
1. Fix must not break password-registered users who genuinely need verification
2. The verification banner must still work correctly for password users

**Impact if ignored:** Broken onboarding for social login users. Product credibility damage at first touch.

### SRE/Production Engineer

**Assessment:** From an operational perspective, Option A is a client-side code change with zero infrastructure risk. Option B introduces a new webhook call in the registration critical path. For pre-release, Option A is the correct priority.

Regarding Option B: the after-registration webhook should be configured as `non-blocking` if Kratos supports it. If the Kratos Admin API call to mark the email verified fails, registration must NOT fail. The user gets a degraded experience (sees the banner) but is not locked out. This matches the existing behavior.

**Risks identified:**
1. (low) Option A: pure frontend change, no infra risk
2. (medium) Option B: webhook in registration path — if misconfigured, could block all OIDC registrations
3. (low) Monitoring: no current alerting for verification flow failures — but this is pre-existing, not new

**Objections:** Would object if Option B were deployed without a non-blocking/graceful-degradation design.

**Recommendation:** Option C. Option A immediately. Option B only when webhook can be proven non-blocking.

**Conditions for approval:**
1. Option B webhook MUST be non-blocking — registration succeeds even if webhook fails
2. No new infrastructure dependencies for Option A

**Impact if ignored:** Every OIDC user sees a broken verification flow. Support burden increases.

### Verification Architect

**Assessment:** The current `isEmailVerified()` has no test coverage for the OIDC case. The comment says "OIDC users don't have verifiable_addresses" but this is factually incorrect when `verification.via` is in the schema. This is a documentation-as-test failure — the comment became the test, and it was wrong.

**Risks identified:**
1. (high) No test for OIDC verification path — the bug exists because there is no test
2. (medium) No integration test for the full OIDC login -> dashboard -> verification flow

**Objections:** Would block if Option A is deployed without unit tests covering all three scenarios: (1) password user with unverified email, (2) OIDC user with provider in trusted set, (3) OIDC user with provider NOT in trusted set.

**Recommendation:** Option C with mandatory tests before deployment.

**Conditions for approval:**
1. Unit test: `isEmailVerified()` returns `false` for password user with `verified: false`
2. Unit test: `isEmailVerified()` returns `true` for OIDC user (github/google) regardless of `verifiable_addresses`
3. Unit test: `isEmailVerified()` returns `false` for hypothetical OIDC user with untrusted provider
4. Comment in `isEmailVerified()` corrected to match actual Kratos behavior

**Impact if ignored:** Regression risk — future changes to the function could re-break OIDC or break password verification.

| Agent | Position |

### Consensus challenge (Orchestrator)

All agents agree on Option C. Challenging the consensus: "What could go wrong?"

1. **What if `authentication_methods` is not in the session object for Kratos v1.3.1?** The Kratos session `whoami` endpoint returns `authentication_methods` since v0.10+. Kratos v1.3.1 definitely includes it. Low risk, but the implementation should handle the field being absent gracefully (fall back to current behavior).

2. **What if a user registers with password, then links Google?** The `authentication_methods` in the session reflects the CURRENT login method, not the registration method. If they logged in with password, they should still verify. If they logged in with Google, they are verified for that session. This is correct behavior — the email was verified by Google when they used Google.

3. **What if Google/GitHub returns a different email than what is in `verifiable_addresses`?** This would be a Kratos mapper issue. The mapper sets `traits.email` from the OIDC claim, and Kratos creates `verifiable_addresses` from traits. They should match. Low risk.

No additional risks identified. Consensus stands.

## Stage 4 — Decision

**Chosen:** Option C — Both dashboard-side detection (A) + Kratos admin API webhook (B)

Option A deployed immediately: modify `isEmailVerified()` to check `session.authentication_methods` for trusted OIDC providers (github, google). If the session was authenticated via a trusted OIDC provider, treat email as verified regardless of `verifiable_addresses` state.

Option B tracked as follow-up: add `after.oidc.hooks` webhook that calls Kratos Admin API to set `verifiable_addresses[].verified = true` for OIDC registrations from trusted providers.

**Rejected:**
- **Option A alone:** Rejected because it leaves inconsistent data in Kratos. Every system that queries Kratos directly would get wrong verification status.
- **Option B alone:** Rejected because it requires infrastructure changes (webhook, admin API auth, Helm config, Pulumi updates) and cannot be deployed fast enough to fix the current UX-blocking bug.
- **Option D (schema change / dual schemas):** Rejected because Kratos does not support per-method schemas. Removing `verification.via` would disable verification for password users.

**Trade-offs consciously accepted:**
1. Option A introduces a temporary inconsistency: Kratos DB says `verified: false`, dashboard says "verified." This is acceptable for pre-release and will be resolved by Option B.
2. The trusted provider list is hardcoded in the dashboard. Adding a new OIDC provider requires a code change. This is acceptable and preferred over automatic trust.

**Risks Accepted:**
| Risk | Severity | Mitigation | Owner |
|------|----------|------------|-------|
| `authentication_methods` absent in edge case | Low | Graceful fallback to current behavior (check `verifiable_addresses` only) | Infrastructure Engineer |
| Future OIDC provider added without email trust review | Medium | Trusted provider list is explicit; adding a provider requires code change + review | Platform Security Engineer |
| Kratos DB inconsistency until Option B | Low | Pre-release only; no external systems query Kratos verification status directly | Principal Architect |

**Risks Blocked:** None. No vetoes from Security or SRE.

**Mandatory Actions:**
1. **(Owner: Infrastructure Engineer)** Implement Option A: modify `isEmailVerified()` with trusted OIDC provider check. TDD: write tests first.
2. **(Owner: Infrastructure Engineer)** Fix the incorrect comment in `isEmailVerified()` — Kratos DOES populate `verifiable_addresses` for OIDC users.
3. **(Owner: Infrastructure Engineer)** Write unit tests: (a) password user unverified, (b) OIDC github verified, (c) OIDC google verified, (d) OIDC untrusted provider unverified, (e) missing `authentication_methods` field.
4. **(Owner: Infrastructure Engineer — follow-up)** Track Option B as a task: Kratos after-registration webhook to mark OIDC emails verified via Admin API. Must be non-blocking.
