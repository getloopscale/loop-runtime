## Stage 1 — Context

### Decision Required

1. Approve or reject Sprint 8 v3.1 for implementation under pre-release governance.
2. Choose Option A (big-bang) vs B (bootstrap-only first) vs C (redesign).

## Stage 2 — Analyses

### Principal Architect

**Assessment.** ADR-0010 is the load-bearing decision: cell-2 is gated on 7 deliverables, none of which can be observed without infrastructure that does not exist. The plan correctly identifies Phase -1 as a mandatory predecessor. However, the plan conflates two qualitatively different problems: (a) provisioning the platform from scratch (one-shot, externally observable, recoverable via `pulumi destroy && pulumi up`), and (b) iterative hardening of running services (multi-week, observability-driven, requires telemetry to even validate completion). Bundling them obscures the dependency: there is no path to validate T0.1 (PG bump) or T2.1 (Gitea HA) without a successful T-1.3.

**Risks.**
1. Big-bang scope means a Phase -1 failure cascades into rejection of unrelated Phase 6 (observability) edits. Inverse blast radius.
2. The registry name mismatch (`loopzero-infra-registry` vs `loopzero-system`) is a live drift that must be resolved BEFORE preview succeeds. Two paths exist (rename in Pulumi vs adopt-or-create); choosing one without explicit ADR is silent precedent for future drifts.
3. ADR-0008/0010 explicitly preserve runtime-2 wiring; abandoning it (Option C) wastes a green-field commitment without compensating gain.

**Objections.** Option C is wrong: the `runtimeCluster2` wiring in `infra.ts:164` is the single concrete artifact that makes ADR-0008 cellular at the IaC layer. Removing it for "application sharding" rewinds 8 months of architectural work. Reject C.

**Recommendation.** **Option B.** Phase -1 is a discrete deliverable with a clear acceptance test (`pulumi stack output execution` all-true, smoke E2E green). Phases 0-6 should be a separate CHG once the platform is observable. Force two ADRs: this one (bootstrap + adopt-or-create policy for registry) and a later one for hardening tradeoffs.

**Conditions.** (1) Resolve registry naming via adopt-or-create (preserve `loopzero-system`), not rename. (2) Document rollback path explicitly. (3) ADR must cite ADR-0010 and reaffirm that runtime-2 stays wired.

**Impact if ignored.** Big-bang produces unreviewable diffs; rollback requires `pulumi destroy` of services that the team has not yet operated.

### Platform Architect (Sponsor)

**Assessment.** The plan's reading of `index.ts` is correct: `pulumi up --stack dev` is the canonical LoopZero Cloud bootstrap. `loopzero platform install` is for self-hosting customers (confirmed in `cli/src/installer/profiles/example-values.yaml`). The Pulumi.dev.yaml secrets are intact and decryptable via `.env` `PULUMI_CONFIG_PASSPHRASE`. `adopt-or-create.ts` handles VPC + CF orphans; the VPC will be adopted cleanly. Container registry adoption is a missing primitive.

**Risks.**
1. The 45-90min `pulumi up` is an externally-observable atomic operation; mid-flight failure leaves partial DOKS. `pulumi up` is idempotent and resumable, but operators unfamiliar with the path can panic and `destroy` mid-run, losing state.
2. Pulumi.dev.yaml `lokiPushUrl: http://10.20.0.26:30100` is stale (CIDR-internal IP from prior bootstrap). Will need post-bootstrap update OR will silently fail to ship logs. Not a blocker for Phase -1 acceptance, but a Phase 6 follow-up.

**Recommendation.** **Option B.** Approve a narrow CHG-001 for Phase -1 (T-1.0a → T-1.5). Approved files: `docs/plans/sprint8-hardening-chaos-plan.md` (plan maintenance), `infra/pulumi/src/components/infra.ts` (registry adopt-or-create), `infra/pulumi/src/core/adopt-or-create.ts` (new lookup helper for DOCR). All Phase 0-6 work goes to CHG-002 after T-1.5 passes.

**Conditions.** Add T-1.0c sub-task: implement `lookupExistingRegistry(name)` in `core/adopt-or-create.ts` mirroring the VPC pattern; `infra.ts:282` consumes the import ID. Renaming the live DOCR is out of scope (would require image republish across all Helm charts).

**Impact if ignored.** Iterative debug via SSH/manual kubectl will accumulate undocumented divergence between code and infra (the same zombie state that put us here).

### GitOps Engineer

No Argo Applications exist yet; `bootstrapCluster` will install ArgoCD into mgmt and seed it with manifest sources from Gitea (which itself is bootstrapped in the same run). This is a chicken-and-egg pattern Pulumi resolves correctly via `apply` chains. T-1.5 smoke E2E is the integrity check.

**Impact if ignored.** Phase 0 starts with a stale Application that will trigger `Degraded` on first ArgoCD reconcile and block Sprint 8 dashboards.

### Platform Security Engineer (VETO HOLDER)

**Assessment.** Phase -1 touches secrets, registry naming, and network surface. I have three concerns.

**Risk 1 — Registry rename vs adopt.** If we rename DOCR to `loopzero-infra-registry` (matching code), every Helm chart pulling `registry.digitalocean.com/loopzero-system/...` breaks. If we leave DOCR as `loopzero-system` and adopt, we must NOT change the registry endpoint string baked into running images or Helm values. Adoption is the safer path.

**Risk 2 — Secrets exposure during bootstrap.** `pulumi up` materializes 5 secrets via `pulumi.secret()` outputs. Stack export (T-1.3 task 1: `pulumi stack export > /tmp/state-pre-bootstrap.json`) writes secrets in cleartext to `/tmp`. `/tmp` is world-readable on shared machines. T-1.3 task 6 (`pulumi stack output --stack dev --json > /tmp/stack-outputs.json`) has the same problem.

**Risk 3 — `kubectl config get-contexts` writing kubeconfigs to `~/.kube/config` after T-1.3 task 5.** Four cluster contexts (mgmt, build, runtime, runtime-2) with admin-equivalent credentials in a single file. If the operator's home is compromised, all four cells are. Production policy elsewhere requires per-cluster kubeconfig with `chmod 600`.

**Objections.** Two of three risks are P0 for Phase -1.

**Recommendation.** **Option B with security gates.** I VETO Phase -1 as currently specified. To unblock:
1. T-1.3 task 1 redirected to `${HOME}/.loopzero/state-pre-bootstrap-$(date +%s).json` with `chmod 600` on creation. NOT `/tmp`.
2. T-1.3 task 6 same treatment, OR just `pulumi stack output execution` (non-secret) for validation.
3. Adopt registry, do not rename. Add T-1.0c (Platform Architect's proposal) to CHG-001.
4. T-1.3 task 5: kubeconfigs saved to `${HOME}/.kube/loopzero-${cluster}.yaml` with `chmod 600`, not merged into default `~/.kube/config`. Operator manually exports `KUBECONFIG` per session.

**Conditions for approval.** All four mitigations land in the plan before T-1.3 executes.

**Impact if ignored.** Auditable secret leak. Pre-release governance is meaningless if secrets bypass it.

### SRE Engineer (VETO HOLDER, Challenger)

**Assessment.** Bootstrapping 4 DOKS + managed PG + Helm-orchestrating ~30 releases in a single 45-90min run is the riskiest unattended operation this project has ever performed. Pulumi's idempotency is real but not omnipotent — partial failures (DOKS quota, transient DO API 5xx, Helm CRD race conditions) require operator judgment.

**Risks.**
1. **Blast radius of T-1.3 partial failure.** If cluster mgmt comes up but Helm install of ArgoCD fails (CRD apply race), `pulumi up` errors halfway. Re-running may succeed — or may stall on a misconfigured Helm release (CLAUDE.md "Helm uninstall blocked" warning). Operator without a runbook will be tempted to `helm uninstall`.
2. **No rollback policy documented.** The plan says "if T-1.3 fails: `pulumi refresh && pulumi up`" — that's optimism, not a runbook.
3. **DO quota.** 4 DOKS clusters at minimum 2 nodes each = 8 droplets minimum. PG managed = 1 droplet equivalent. Build cluster medium = 2-5 nodes. Default DO project quota is often 10 droplets. The plan does not include a `doctl account get` quota check.
4. **Recovery from zombie state.** If Pulumi state corrupts mid-up (unlikely but real), recovery requires `pulumi stack import` from the pre-up backup. Per Risk 1 from Security, that backup will live in `/tmp` (deletable on reboot).
5. **L3 instability is the real bloqueador.** Even after a perfect Phase -1, Gate #1 (L3 ≥95/100 ten times consecutive) is a multi-sprint diagnostic problem. Big-bang scope hides this fact behind hardening tasks that are also Sprint 8.

**Objections.** I VETO Option A. Big-bang under a single CHG produces a multi-headed change with no clear acceptance test for partial completion. Option B narrows blast radius to a single externally-observable acceptance: `pulumi up` exits 0 + smoke E2E green.

**Recommendation.** **Option B, mandatory.** And:
1. Pre-flight quota check (T-1.0d) before T-1.3: `doctl account get` confirms droplet limit ≥ 12.
2. Runbook draft (`docs/runbooks/sprint8-bootstrap.md`) BEFORE T-1.3 starts, covering: DO quota exhaustion, DOKS create timeout, Helm CRD race, Pulumi state lock, partial-up resumption, full destroy + retry decision tree.
3. Operator must keep `pulumi up` in foreground (not background); 45-90min unattended is unsafe.
4. Backup state file (T-1.3 task 1) lives in `${HOME}/.loopzero/backups/` with retention until Phase -1 declared green.

**Conditions.** All four. SRE veto holds until they are committed to the plan.

**Impact if ignored.** First production bootstrap with no runbook = guaranteed support pages.

### Production Design Reviewer

**Assessment.** From production fitness lens: the question is "does Phase -1 produce a system that an operator can run, debug, and recover?" Today's plan answers yes for `pulumi up` happy path, partially for failure paths. The bigger production fitness question — does Phase 0-6 produce a 5k-app cell? — is exactly the question Option B defers.

**Risks.**
1. The plan's success metric (Gate 2a Exit) is multi-week. Bundling it under one CHG creates an "epic-CHG" anti-pattern that prior meetings (MEET-051) explicitly rejected for Phase 2 itself.
2. Registry adoption sets a precedent: when names drift, we adopt rather than recreate. That's correct policy for stateful primitives but should be in an ADR, not implicit in a one-line code change.

**Recommendation.** **Option B.** Make CHG-001 = Phase -1 (bootstrap + adopt-or-create primitive + registry import). Make CHG-002 = Phase 0-6 (with its own meeting after Phase -1 telemetry exists). Reject Option A (epic-CHG anti-pattern) and Option C (rewinds ADR-0008).

**Conditions.** ADR must explicitly establish "adopt-or-create is the default policy for live stateful resources at re-bootstrap" — referenceable for future drifts.

**Impact if ignored.** Sprint 8 becomes a 6-week unobservable mega-PR.

## Stage 4 — Decision

### Chosen Approach

**Option B — Bootstrap-only CHG-001 covering Phase -1 (T-1.0a → T-1.5).** Phases 0-6 deferred to CHG-002, which requires a new meeting after Phase -1 acceptance.

### Alternatives Rejected

| Option | Rejection Reason |
|---|---|
| A (big-bang) | SRE VETO: epic-CHG anti-pattern, blast radius unbounded, unobservable failure surface; rejected unanimously by 9 reviewers on merit |
| C (redesign to app-sharding) | Architect rejection: discards `runtimeCluster2` wiring (8 months of work since ADR-0008); cost of redesign > cost of activation; no reviewer endorsed |

### Trade-offs Consciously Accepted

1. Two-CHG ceremony adds ~1 day of approval lead time. Accepted in exchange for narrow blast radius.
2. Phase -1 success does not mean Gate 2a is closer in calendar terms — it means we can finally measure how far we are. Accepted as the honest narrative.
3. Adopt-or-create for registry sets a precedent that may be misapplied to non-stateful resources; mitigated via explicit policy in ADR-0015.

### Risks Accepted (with mitigation and owner)

| Severity | Risk | Mitigation | Owner |
|---|---|---|---|
| HIGH | `pulumi up` partial failure mid-T-1.3 | Runbook (`docs/runbooks/sprint8-bootstrap.md`) drafted before T-1.3 executes | SRE |
| HIGH | DO quota exhaustion blocks T-1.3 | T-1.0d pre-flight check (`doctl account get` confirms ≥12 droplet headroom) | Infra Engineer |
| MEDIUM | Pulumi state corruption mid-up | `pulumi stack export` to `~/.loopzero/backups/` with chmod 600 retention until Phase -1 green | SRE |
| MEDIUM | Kubeconfig admin keys aggregated in default file | Per-cluster file at `~/.kube/loopzero-${cluster}.yaml` chmod 600; KUBECONFIG export per session | Security |
| MEDIUM | Stale `lokiPushUrl` IP in Pulumi.dev.yaml | Track as Phase 6 follow-up in CHG-002, not blocking Phase -1 | SRE |
| LOW | Smoke project residue blocks Phase 0 dashboards | T-1.5 acceptance includes `loopzero project delete --force` + Gitea repo verify | GitOps |

### Risks NOT Accepted (Blockers)

- Secrets/state files in `/tmp` — Security VETO, absolute.
- Kubeconfigs merged into `~/.kube/config` — Security VETO, absolute.
- Renaming live DOCR `loopzero-system` — Security + Production Design VETO (breaks running images).
- Executing T-1.3 without runbook — SRE VETO, absolute.
- Executing T-1.3 without DO quota check — SRE VETO, absolute.
- Operating `pulumi up` in background — SRE VETO (45-90min unattended is unsafe).
