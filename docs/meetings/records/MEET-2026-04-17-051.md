## Stage 1 — Context

**Problem:** Deleting tenants in bulk (160 tenants for L3 load test cleanup) causes a retry storm. Each tenant's finalizer runs independently, making N×(Harbor+ArgoCD+MinIO+Gitea+Build) API calls with no backpressure. When Gitea saturates (Bug #44), all 160 finalizers enter requeue-loop (5s fixed interval), amplifying congestion. No circuit breaker, no per-step visibility, no bulk ops, no TTL/reaper. Force-null (removing finalizer manually) is used 2x in L3 cleanup, orphaning external resources.

**Decision Required:** Should we approve the proposed TenantReaper architecture with worker pool, circuit breakers, tombstone audit, and phased execution?

**Constraints:**
- Pre-release: can break things, prefer clean design
- Production on DigitalOcean (3 DOKS clusters)
- pg_advisory_xact_lock only (never session-scoped) — Rule 7
- Gitea is most fragile dep (Bug #44 — CPU saturation)
- Must not orphan ArgoCD apps or Gitea repos
- State machine: Deleting is terminal (no restore from Deleting)

**Known Context:**
- Current code: `operators/internal/controller/tenant_controller.go` lines 223-374
- State machine: `pkg/statemachine/tenant.go`
- Existing project deletion: `api/internal/services/project_deleter.go`
- Existing reapers: `api/internal/services/build_reaper.go`, `release_reaper.go` (goroutines in API, operate on DB only)
- Existing circuit breaker: `api/internal/services/pg_circuit_breaker.go`

## Stage 2 — Agent Analyses

### Principal Platform Architect

**Assessment:** The proposal is architecturally incoherent — it creates a second control plane (TenantReaper) in the API plane that crosses into the Control plane boundary. Three sources of truth for deletion state (PG pending table, K8s DeletionTimestamp, PG tombstone) guarantee inconsistency during partial failures.

**Key Objections:**
1. TenantReaper is a controller in disguise, placed in the wrong plane
2. PostgreSQL as K8s workqueue is a worse abstraction than controller-runtime's native workqueue
3. Soft-delete with restore contradicts Deleting as terminal state — needs new `PendingDeletion` state
4. Phase 0 (kubectl from CLI) contradicts Design Principle #1 on the same document

**Recommendation:** REJECT. Redesign with controller as sole owner of deletion execution.

### Staff K8s Controller Engineer

**Assessment:** The diagnosis is correct but the solution is over-engineered. The retry storm is a controller configuration issue, not a missing-orchestrator issue. `MaxConcurrentReconciles=5` is one line of code that achieves the same backpressure as a 4-day TenantReaper build.

**Key Objections:**
1. TenantReaper is YAGNI — native controller-runtime primitives solve the problem
2. Circuit-breaker-via-annotations is an anti-pattern (controller should decide based on reality)
3. 5 per-step conditions on a dying resource adds complexity for no consumer — use Prometheus metrics
4. `DeleteApplications` is NOT idempotent (doesn't handle NotFound per app) — this is the actual bug

**Recommendation:** MODIFY — fix controller-level bugs first, add throttling via controller-runtime.

### Staff Distributed Systems Engineer

**Assessment:** The dual-orchestrator architecture (Reaper + Controller) creates coordination problems more severe than the retry storm it solves. Circuit breaker lives in the Reaper but actual calls happen in the Controller — the backpressure solution is architecturally disconnected.

**Key Risks:**
1. CRITICAL: Orphaned lease deadlock — no TTL, no automated reclamation
2. CRITICAL: Circuit breaker gap — CB in Reaper, calls in Controller
3. HIGH: Race between soft-delete and in-flight mutations (no fence in WithEnvironmentLock)
4. HIGH: Wrong primitive for leader election (pg_advisory_xact_lock is transaction-scoped)

**Recommendation:** MODIFY — single orchestrator (controller as executor, Reaper reduced to observer).

### Staff Platform Security Engineer

**Assessment:** Most sensitive administrative capability in LoopZero. Current RBAC (owner/admin/member) is tenant-scoped — no platform admin role exists. Force-delete and bulk-evict endpoints have no viable authorization mechanism.

**Vetoes:**
1. **ABSOLUTE VETO:** Bulk-evict without dry-run and two-step confirmation
2. **ABSOLUTE VETO:** Force-delete and bulk-evict without platform-admin auth mechanism
3. **ABSOLUTE VETO:** Phase 0 via kubectl without audit trail

**Key Requirements:**
- Platform admin auth (LOOPZERO_ADMIN_API_KEY for pre-release)
- Credential revocation before resource cleanup (reorder: MinIO → Harbor → ArgoCD → Build NS → Gitea)
- LISTEN/NOTIFY as wake-up only (never trust payload)
- Worker lease TTL (5-10 min)
- Tombstone PII retention policy (anonymize after 2 years)
- Audit actions for every deletion lifecycle transition

### Staff SRE / Production Readiness Engineer

**Assessment:** Architecture is sound in shape but has zero operability. 10+ new failure modes with zero PrometheusRules. No health endpoint for Reaper, no deletion SLO, no stuck tenant detection, no rollback plan, no MTTR estimate.

**Key Requirements:**
1. Alert definitions for ALL new failure modes (concrete PromQL)
2. Reaper health endpoint + heartbeat metric
3. Leader election via existing `api/internal/leader/` pattern, not new pg_advisory_xact_lock
4. Reaper as goroutine in API process (like BuildReaper), not separate binary
5. Worker pool default 2 (not 5) until Gitea capacity data exists
6. REAPER_PAUSED config flag for rollback
7. Remove "saga with compensation" language — it's forward-only idempotent teardown
8. Deletion SLO: 95% complete within 1h of grace expiry

### Staff API / Domain Architect

**Assessment:** Intent-capture via API is correct. But `/force` calling kubectl is execution, not intent. `/admin/` namespace breaks existing convention (everything under `/api/v1/`). Bulk evict has the least design rigor for the most dangerous endpoint.

**Key Objections:**
1. `/force` as separate route — should be request body `{"force": true}` on single endpoint
2. `/admin/` namespace breaks convention — use `/api/v1/` with admin middleware
3. Missing idempotency contract on all new endpoints
4. Missing restore endpoint design (race with reaper)
5. Missing deletion-status observation (polling/SSE)
6. Missing `--json` schemas for all new CLI commands
7. Missing LoopZeroError codes for all failure paths

## Stage 3 — Confrontations

### Confrontation 1: TenantReaper as separate service vs Controller-native throttling

| Agent | Position |
|-------|----------|
| Principal Architect | REJECT Reaper — second control plane in wrong plane |
| K8s Controller | REJECT Reaper — `MaxConcurrentReconciles=5` is one line |
| Distributed Systems | MODIFY — single orchestrator, Reaper reduced to observer |
| SRE | CONDITIONAL — goroutine in API, not separate binary |
| Security | CONDITIONAL — acceptable if admin auth solved |
| API Domain | MODIFY — force path through reaper, not kubectl |

**Resolution:** TenantReaper as separate service is **REJECTED** (4/6 agents). Controller-native throttling via `MaxConcurrentReconciles=5` + circuit breaker in controller + exponential backoff. Grace period monitoring as goroutine in API (like BuildReaper).

### Confrontation 2: State machine — PendingDeletion vs Deleting with grace

| Agent | Position |
|-------|----------|
| Principal Architect | MANDATORY: new `PendingDeletion` state, `Deleting` stays terminal |
| Distributed Systems | Agrees — restore requires reversible state |
| API Domain | Agrees — restore endpoint needs atomic guard |

**Resolution:** New `PendingDeletion` state added. Transitions: `Active/Suspended → PendingDeletion` (delete request), `PendingDeletion → Active` (restore), `PendingDeletion → Deleting` (grace expired or force).

### Confrontation 3: Circuit breaker placement

| Agent | Position |
|-------|----------|
| Distributed Systems | CB co-located with caller (controller) |
| K8s Controller | CB via annotations is anti-pattern |
| SRE | CB defaults: 3 failures, 60s cooldown |

**Resolution:** Circuit breaker inside TenantController as reconciler field. No annotation-based communication.

### Confrontation 4: Bulk evict guardrails

| Agent | Position |
|-------|----------|
| Security | ABSOLUTE VETO without dry-run + confirmation |
| API Domain | Under `/api/v1/`, max batch 50, typed confirmation token |
| SRE | Start with worker pool 2, not 5 |

**Resolution:** Two-step protocol mandatory. Under `/api/v1/tenants/bulk-delete`.

### Confrontation 5: `tenants_pending_deletion` table necessity

| Agent | Position |
|-------|----------|
| Principal Architect | UNNECESSARY — K8s DeletionTimestamp is the queue |
| K8s Controller | Agrees — reimplementation of K8s workqueue |
| API Domain | NECESSARY — for grace period, restore, audit |
| SRE | NECESSARY — for tombstone/audit |

**Resolution:** Table kept for grace/restore/audit, NOT as workqueue. Flow: API inserts (intent) → grace expires → API deletes CR → Controller executes → Controller writes tombstone via callback.

### Confrontation 6: Credential cleanup ordering

| Agent | Position |
|-------|----------|
| Security | Credentials revoked FIRST, then resources cleaned |

**Resolution:** Reorder to: MinIO creds → Harbor access → ArgoCD apps → Build NS → Gitea archive.

## Stage 4 — Decision

### Chosen Approach

**Controller-native deletion with API intent gateway.** The controller owns all execution. The API captures intent (soft-delete, grace period) and monitors grace expiry. No separate TenantReaper service.

### Architecture

```
CLI: loopzero team delete
    │
    ▼
API: DELETE /api/v1/tenants/:id
    │ INSERT tenants_pending_deletion (grace_until, force, reason)
    │ UPDATE tenant status → PendingDeletion
    │ 202 Accepted
    │
    ├── if force=true or grace expired:
    │     DELETE Tenant CR via K8s API
    │
    ▼
TenantController (MaxConcurrentReconciles=5):
    │ reconcileDelete with:
    │   - Circuit breaker per dep (3 failures → open, 60s cooldown)
    │   - Exponential backoff (error return, not RequeueAfter)
    │   - Per-step progress tracking (condition + metrics)
    │   - Skip completed steps on requeue
    │   - Credential-first cleanup ordering
    │
    ▼ on finalizer removed:
    │
API callback: POST /internal/tenants/:id/deletion-complete
    │ INSERT tenant_tombstones
    │ DELETE tenants_pending_deletion
    │ Emit audit event
```

### Alternatives Rejected

| Alternative | Reason |
|------------|--------|
| TenantReaper as separate service in `api/cmd/tenant-reaper/` | Two orchestrators, two retry loops, circuit breaker disconnected from caller, crosses plane boundary, reimplements K8s workqueue in PostgreSQL |
| Circuit breaker via annotations on Tenant CR | Anti-pattern: controller decides based on reality, not side-channel opinions |
| `/admin/` namespace for admin endpoints | Breaks existing convention (everything under `/api/v1/`), creates dual API surfaces |
| `DELETE /tenants/:id/force` as separate route | Not a sub-resource, duplicates middleware, ambiguous idempotency |
| Phase 0 with kubectl from CLI | Violates Design Principle #1, no audit trail |
| `pg_advisory_xact_lock` for leader election | Transaction-scoped lock inappropriate for long-lived leadership |

### Trade-offs Accepted

1. Force-delete has ~5-30s latency (via grace expiry goroutine polling) instead of instant kubectl
2. Controller complexity increases ~100 lines (circuit breaker + per-step tracking + backoff)
3. Grace period monitoring uses polling (30s interval) — acceptable for 24h grace windows

### Risks Accepted

| Severity | Risk | Mitigation | Owner |
|----------|------|------------|-------|
| MEDIUM | CB thresholds without production data | Conservative defaults (3/60s), adjust with data | Operator Engineer |
| MEDIUM | Tombstone PII without automated anonymization at launch | `anonymized_at` column, anonymization job as future task | API Engineer |
| LOW | LISTEN/NOTIFY non-durable for grace expiry | Polling as primary mechanism | API Engineer |

### Risks NOT Accepted (Blockers)

| Severity | Risk | Blocker | Condition to Unblock |
|----------|------|---------|---------------------|
| CRITICAL | No platform admin auth for destructive endpoints | Security VETO | Implement `LOOPZERO_ADMIN_API_KEY` middleware |
| CRITICAL | Bulk delete without dry-run/confirmation | Security VETO | Two-step protocol with confirmation token |
| CRITICAL | `DeleteApplications` not idempotent (no NotFound handling) | K8s Controller | Fix per-application NotFound handling |
| HIGH | Zero alerts for new failure modes | SRE VETO | PrometheusRules for stuck tenant, CB open, grace expired |

### Mandatory Actions

1. Fix `DeleteApplications` idempotency — handle NotFound per application in `real_provisioner.go`
2. Add `MaxConcurrentReconciles: 5` to `SetupTenantController` in `tenant_controller.go`
3. Change cleanup failures from `RequeueAfter` to `error` return — activates native exponential backoff
4. Add `PendingDeletion` state to tenant state machine in `pkg/statemachine/tenant.go`
5. Implement `LOOPZERO_ADMIN_API_KEY` middleware for admin-level endpoints
6. Define `DELETE /api/v1/tenants/:id` (force via request body `{"force": true}`)
7. Define `POST /api/v1/tenants/bulk-delete` with mandatory dry-run and confirmation token
8. Define `POST /api/v1/tenants/:id/restore` with atomic guard (`worker_leased_by IS NULL`)
9. Define `GET /api/v1/tenants/:id/deletion-status` or SSE for progress observation
10. Circuit breaker per dep in TenantController (3 failures, 60s cooldown, 2 successes to close)
11. Per-step Prometheus metrics (`loopzero_tenant_deletion_step_duration_seconds`, `loopzero_tenant_deletion_step_errors_total`)
12. `DeletionProgress` condition with structured message
13. Skip completed steps on requeue (condition marks step done)
14. PrometheusRules: tenant stuck >1h (warning), >6h (critical), CB open >10min (warning)
15. Reorder cleanup: MinIO creds → Harbor → ArgoCD → Build NS → Gitea
16. Define `--json` schemas for all new CLI commands
17. LoopZeroError codes: `TENANT_NOT_FOUND`, `TENANT_ALREADY_PENDING_DELETION`, `TENANT_DELETION_IN_PROGRESS`, `TENANT_NOT_PENDING_DELETION`, `BULK_DELETE_LIMIT_EXCEEDED`, `BULK_DELETE_CONFIRMATION_REQUIRED`
18. Audit actions: `tenant.deletion_requested`, `tenant.deletion_started`, `tenant.deletion_completed`, `tenant.deletion_failed`, `tenant.force_deleted`, `tenant.bulk_evict_requested`, `tenant.restored`
19. Grace expiry goroutine in API (like BuildReaper) — polls every 30s
20. ADR documenting controller-native vs reaper-separate decision
21. Remove "saga with compensation" language — replace with "forward-only idempotent teardown with circuit-breaker backpressure"
