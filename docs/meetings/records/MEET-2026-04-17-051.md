## Stage 1 — Context

**Problem:** ADR-0008 approved cell-based architecture (2026-03-31). Phase 0 deployed (cell_id, PlacementEngine, DynamicRouter), Phase 1 ~75% code-ready (CRD + controller + Pulumi cell.ts scaffold), but **zero `ClusterCredential` CRs registered** and single workload cluster in production. Paulo authorized DO quota + $400-800/mo for 2nd cell. Urgency framed as "investor-facing scalability proof — first question VCs ask."

**Decision Required:** Approve/Reject/Rescope ADR-0010 Phase 2 activation covering (1) 2nd cell provisioning, (2) cross-cell DNS routing, (3) PlacementEngine at 2+ cells, (4) tenant migration, (5) cross-cell observability, (6) failure modes.

**Constraints:**
- Pre-release phase — backward compatibility not required, clean redesign preferred
- Single cell NOT yet stable — Gate #1 open (best L3 = 75/100, target ≥95/100)
- DO droplet quota ticket open (T-08)
- Central shared services: Gitea, Harbor, MinIO, PG (single managed), mgmt cluster

**Orchestrator's Proposal (now rejected):**
CF Worker + KV cross-cell routing extending existing `loopzero-static-delivery` Worker; sticky placement; central ArgoCD; single mgmt cluster.

## Stage 2 — Agent Analyses (Summary)

### Principal Architect — REJECT CF Worker design, propose API data-path proxy

**Core argument:** "Cells are a declarative workload-plane unit, not a runtime concern." Three candidate owners for tenant→cell binding (Pulumi, CRD, PG) is already two too many. Routing is a **derived fact** from placement, not an independent control surface.

**Key finding:** CF Worker + KV creates a **second control plane** with its own state, deploy cycle, failure mode outside the cluster. Debuggability collapses (3am 503 now requires tailing Worker logs in 3rd-party dashboard).

**Alternative design:** per-cell Traefik + tenant-aware edge Traefik in mgmt cluster that reads `tenants.cell_id` from Postgres (30s cache). Keeps routing state in PG (single source). Cell failover = SQL UPDATE.

**Veto conditions:**
- `ClusterCredential` CR is the ONLY source for cell topology
- PG `tenants.cell_id` is operational (not declarative)
- Routing degrades to last-known-good on mgmt outage
- State machine `Provisioning → Active → Draining → Retired` in `pkg/statemachine/`

### Distributed Systems — VETO KV-as-authority + VETO RoundRobin without lock

**Core argument:** Split-brain between 3 authorities (PG, KV, ArgoCD). CF KV is eventually consistent (60s+ propagation p99); stitching CP authority to AP cache without fallback = user-facing 404 on first-request-after-create.

**Named failure scenarios:**
- **Day 2, 15:32 UTC:** Tenant created → PG commit → KV write queued → user's `loopzero deploy` at 15:32:04 hits FRA edge with KV miss → 404. Retry at 15:32:08 hits IAD (KV hit) → works. User reports "flaky deploys." Unfixable without PG fallback.
- **Day 14, 03:17 UTC:** cell-1 at 98/100 capacity. 10 concurrent tenant creations. RoundRobin TOCTOU → 7 assigned to cell-1 → 105/100 → ResourceQuota rejects 5 → tenants stuck `Provisioning`.

**Mandatory invariants:**
- PG is authority; KV is cache with TTL; Worker has PG fallback on miss
- `pg_advisory_xact_lock(hash('placement'), hash(cell_id))` wraps capacity-check + assignment
- Cell health probe ≤10s + 3-strike failure threshold + `Draining` status
- KV reconciliation cron job (5min) — PG → KV convergence
- Kubeconfig rotation automated with grace period

### SRE — **ABSOLUTE VETO** until 7 conditions met

**Core argument:** Moving 1 cell → 2 cells = 3x failure domains (cells + routing + placement), but observability/alerts/chaos are still sized for 1 cell. Phase 0 deployed ≠ Phase 2 safe.

**Alert storm risk:** cell-2 down with N tenants = N alerts without aggregation. First real incident = on-call burns out, misses signal.

**Rollback SPOF amplification:** `loopzero rollback` depends on central Gitea. 2 cells = 2x blast radius when Gitea hiccups.

**Veto conditions (1, 2, 4, 6 non-negotiable):**
1. Per-cell synthetic probe emitting `synthetic_deploy_success{cell}`
2. `cell:degraded` Alertmanager aggregation + inhibit rules
3. Cell health controller (not just CRD) evaluating formal contract
4. Gitea SPOF mitigation (HA replica OR DB-backed degraded rollback)
5. Runbooks for 6 failure modes
6. All 6 chaos scenarios executed with MTTR recorded
7. On-call rotation updated with paging deduplication

**30-day impact if ignored:** 2-3 SEV-1s, on-call attrition, lost customer trust pre-launch.

### Platform Security — **VETO kubeconfig-in-CRD + VETO shared MinIO credential**

**Core argument:** Multi-cell done right contracts blast radius 100% → 1/N. Done wrong amplifies: compromised mgmt = all cells gone + N new attack surfaces.

**Critical credentials without TTL/rotation today:** ClusterCredential kubeconfig, CF API token, MinIO/Spaces key, Harbor robot, PG connection string.

**Attack paths named:**
- **Kubeconfig leak** (PG backup/logs/mgmt API exfil) → full workload admin across all cells → rebuild all clusters to recover
- **CF KV poisoning** → rewrite `tenant-stripe.loopzero.example → cell-attacker` → capture all deploy webhooks + production traffic
- **Central MinIO + cell-1 RCE** → exfiltrate all tenants' source bundles → supply-chain injection

**8 veto conditions:**
1. Kubeconfig TTL ≤1h OR Secret-stored with ≤24h rotation (NEVER in CRD spec)
2. Per-tenant STS credentials for MinIO/Spaces
3. CF API token scoped to single KV namespace, 30d rotation, PG-first write-through
4. Cosign signature verification at each cell's admission controller
5. Per-cell ESO with scoped SA (no mgmt-proxy pattern)
6. NetworkPolicy default-deny cross-cluster
7. Audit queries include `cell_id`; regression test tenant-A/cell-B returns empty
8. Threat model document for each new attack surface

### GitOps Engineer — Central ArgoCD OK for Phase 2, VETO per-cell Gitea + auto-sync

**Reversal from MEET-2026-03-31-024:** previously defended central ArgoCD against removal. Still rejects removal, but also rejects central ArgoCD beyond Phase 2. CNOE benchmark + Akuity evidence confirm per-cell ArgoCD is the documented scale pattern.

**Concrete scale ceiling:**
- Central ArgoCD survives Phase 2 (≤2 cells, ≤500 tenants)
- NOT Phase 3 (500+) without per-cell ArgoCD
- ApplicationSet single-threaded (GH #19113 unresolved in 2.13) → cap 500 apps/AppSet

**Vetoes:**
- Per-cell Gitea replicas (creates dual-write + split-brain)
- Auto-sync on any cell (violates ADR-0007 manual sync)

**Recommendations:**
- Central Gitea with Gitea 1.22 HA (PG backend + shared object storage)
- One AppSet per cell, path-level cell encoding `gitops/cells/{cell-id}/...`
- Migration state machine `ACTIVE → PREPARING → DUAL → DRAINING → ACTIVE` with finalizers

### Production Design Reviewer — **HARDEST VETO: Phase 2 as framed is "cell-ready, not cell-production"**

**Brutal diagnosis:** "Claiming 2 cells = blast radius isolated with Gitea/Harbor/MinIO/PG/mgmt as single instances is **architecturally false**. ADR-0008's promise is undeliverable in Phase 2 as proposed. Investor demo would be false advertising if we can't show independent failure."

**Reality checks:**
- Single cell not stable: L3 best 75/100, v14 = 62/100, Gate #1 unmet
- PG already 72% connection-saturated at idle (36/50 used)
- mgmt at 74% memory on one node at idle
- "N dashboards, N kubeconfigs, N ArgoCDs at a moment when single cell hasn't passed stability gate"

**Recommendation: RESCOPE to Phase 2a + Phase 2b**

- **Phase 2a — Shared-Service Hardening (prerequisite):** Close Gate #1 + Gitea HA + Harbor HA + MinIO distributed + PG bump + mgmt memory headroom
- **Phase 2b — Cell-2 Activation (only after 2a):** with federation, unified dashboard, chaos proof Day 1

**Required for investor demo:** chaos test VIDEO (cell-1 down, cell-2 serving 200 for 10 min, reverse validated). NOT a topology slide.

## Stage 3 — Technical Confrontation

### Conflict #1: Proceed vs Rescope

| Position | Agents |
|---|---|
| Proceed with design changes | Architect, DistSys, GitOps (conditional), Security (conditional) |
| Rescope to 2a/2b | **Production Design Reviewer, SRE** |

**Resolution:** Rescope wins. SRE has veto power + Production Design's diagnosis is unrebutted: "2 cells sharing 1 Gitea is an architecture diagram, not a cell." The others' conditions (Architect's SoT, Security's credential controls, DistSys's consistency invariants) become Phase 2b gates.

### Conflict #2: Routing authority — CF KV vs PG direct

| Position | Agents |
|---|---|
| PG as authority, KV cache with fallback | DistSys |
| API data-path proxy reading PG directly, CF Worker out of dynamic path | **Architect** |
| (Orchestrator's original: CF KV authority) | — all 6 rejected |

**Resolution:** Architect's design wins. PG is single source, API proxy reads with cache, CF Worker stays for static delivery only. Simpler, one authority, debuggable with standard tooling. DistSys's consistency invariants still apply (advisory lock on placement, health probe + Draining state).

### Conflict #3: ArgoCD topology

**Unanimous:** central for Phase 2b (≤2 cells), per-cell for Phase 3+. Path-level cell encoding in Gitea (`gitops/cells/{cell-id}/...`).

### Conflict #4: Migration scope

**Unanimous:** defer to Phase 3 explicitly. Phase 2b new tenants go to cell-2 (capacity-aware sticky), existing 100 stay on `cell-default`. No movement.

### Challenge to consensus

Orchestrator asked: "Is anyone OK with shipping Phase 2 without shared-service hardening to hit investor deadline?" **No agent endorsed this.** All 6 signaled that false scalability proof is worse than no proof.

## Stage 4 — Decision Synthesis

### Verdict: **DEFERRED → RESCOPED**

Phase 2 as originally framed (1 monolithic phase) is rejected. Split into **Phase 2a (prerequisite)** and **Phase 2b (cell-2 activation)**.

### Phase 2a — Shared-Service Hardening (MUST PRECEDE 2b)

| Deliverable | Owner | Trigger Gate |
|---|---|---|
| Close Gate #1: L3 10× ≥95/100 consecutive | Infra + API | T-08 runtime bump OR LOOPZERO_LEAN_RESOURCES |
| PG bump: `max_connections ≥ 100` (db-s-2vcpu-4gb minimum) | Infra | Phase 2a |
| Gitea HA (already started — bfbe818 Redis; complete with shared storage + HA replica) | Infra | Phase 2a |
| Harbor HA (2+ core replicas, Redis HA, S3 shared) | Infra | Phase 2a |
| MinIO distributed (plan exists: `minio-distributed-migration.md`) | Infra | Phase 2a |
| mgmt cluster memory headroom (currently 74% at idle) | Infra | Phase 2a |
| `tenant-health` Grafana dashboard: single panel `tenant_id → cell_id, status per stage` | Observability | Phase 2a |

### Phase 2b — Cell-2 Activation (after 2a)

| Component | Design | Owner |
|---|---|---|
| **Cell SoT** | `ClusterCredential` CR — Pulumi produces, controller reconciles, API reads | Architect |
| **Routing** | API data-path proxy reading `tenants.cell_id` from PG (30s cache). CF Worker stays for static delivery only. | Architect |
| **Placement** | Sticky-at-creation + capacity-gated + `pg_advisory_xact_lock('placement', cell_id)` | DistSys |
| **Cell health** | Controller evaluates formal contract every 60s (probe synthetic deploy + all platform components). `healthy \| degraded \| unhealthy \| draining` | SRE |
| **Kubeconfig** | Secret-stored with ≤24h rotation. NEVER in CRD spec/status. Controllers watch + hot-reload. | Security |
| **MinIO credentials** | Per-tenant STS (15-min TTL) at build submission | Security |
| **CF API token** | KV-namespace scoped, 30d rotation, PG-first write-through with reconciler cron | Security + DistSys |
| **ArgoCD** | Central (Phase 2b scope). Path-level cell encoding in Gitea `gitops/cells/{cell-id}/...`. One AppSet per cell. | GitOps |
| **Migration** | Explicitly out of scope. New tenants → cell-2 (capacity-aware). Existing 100 stay on `cell-default`. Migration = Phase 3. | All |
| **Observability** | Per-cell Prometheus with remote-write to central (Thanos or long-retention Prom). Alertmanager `group_by: [cell]` + `cell:degraded` inhibit rules. | SRE |
| **Cosign verification** | Enforced at each cell's admission controller. Per-cell pull-only Harbor robot. | Security |
| **Per-cell ESO** | Scoped SA per cell. No mgmt-proxy pattern. | Security |
| **NetworkPolicy** | Default-deny cross-cluster (no inter-cell pod traffic) | Security |

### Absolute Veto Conditions for Phase 2b Activation

**SRE (non-negotiable items 1, 2, 4, 6):**
1. Per-cell synthetic probe with `synthetic_deploy_success{cell}` SLI
2. `cell:degraded` Alertmanager aggregation + inhibit rules tested via injected failure
3. Cell health controller IMPLEMENTED evaluating formal contract
4. Gitea SPOF mitigation: HA OR DB-backed degraded rollback path documented
5. Runbooks merged for all 6 failure modes with tested recovery
6. All 6 chaos scenarios executed in staging-equivalent with MTTR recorded
7. On-call rotation updated with cell-boundary paging deduplication

**Security (all 8 are absolute):**
1. Kubeconfig TTL ≤1h OR Secret-stored ≤24h rotation, NEVER in CRD spec
2. Per-tenant or per-cell storage credential isolation for MinIO/Spaces
3. CF API token scoped to single KV namespace, ≤30d rotation, PG-first write-through
4. Cosign verification + per-cell pull-only Harbor robot
5. Per-cell ESO, no mgmt-proxy
6. NetworkPolicy default-deny cross-cluster
7. Audit queries include `cell_id`; regression test passes
8. Threat model doc for each new attack surface

**DistSys (all 8 are mandatory):**
1. PG is authority; Worker fallback to PG on KV miss
2. `pg_advisory_xact_lock` on placement capacity
3. Cell health probe ≤10s + 3-strike + Draining state
4. KV reconciliation job (5min cron)
5. Kubeconfig rotation automated with grace period
6. Chaos test: cell-2 down → cell-1 unaffected; cell-2 tenants return 503 (not 502, not hang)
7. Chaos test: KV propagation delay 60s → PG fallback <2s
8. Placement race test with 10 concurrent creations

**Architect (must be designed-in):**
1. `ClusterCredential` CR is only read-source for cell topology
2. PG `tenants.cell_id` is operational (not declarative)
3. Routing degrades to last-known-good on mgmt outage
4. Cell lifecycle state machine: `Provisioning → Active → Draining → Retired`

**Production Design (absolute):**
1. Gate #1 closed on single cell BEFORE Phase 2b
2. PG `max_connections ≥ 100` with headroom for cell-2 processes
3. Shared services HA deployed and load-tested BEFORE cell-2
4. Chaos video: kill cell-2 → cell-1 apps serve 200 for 10min, reverse validated
5. Grafana `tenant-health` dashboard single-panel
6. Runbook "cell-2 down at 3am" rehearsed in <5min

### Alternatives Rejected

- **Proceed as originally framed** — rejected unanimously. All 6 vetoes stand.
- **CF Worker + KV as routing authority** — rejected by Architect + DistSys. KV is AP, binding is CP.
- **Per-cell Gitea replicas** — rejected by GitOps. Dual-write split-brain.
- **Auto-sync on any cell** — rejected by GitOps. Violates ADR-0007.
- **Include migration in Phase 2** — rejected unanimously. Migration = Phase 3.
- **Proceed without chaos proof** — rejected by SRE + Production Design. "Diagram ≠ product."

### Risks Accepted with Mitigation

| Severity | Risk | Mitigation | Owner |
|---|---|---|---|
| HIGH | Central Gitea even with HA remains a choke point | Phase 2a HA + Phase 3 evaluation for per-cell clustering | GitOps |
| HIGH | Central PG is shared DB across cells | Phase 2a bump to db-s-2vcpu-4gb; Phase 3+ evaluate read replica per cell | SRE + DistSys |
| MEDIUM | Central Harbor is supply-chain SPOF | Cosign verification per cell; multi-region Harbor evaluated at Phase 4 | Security |
| MEDIUM | Shared mgmt cluster as control plane for all cells | Phase 3+ evaluate mgmt HA | Architect |

### Risks NOT Accepted (Blockers for Phase 2b)

- Kubeconfig in CRD spec (Security)
- KV without PG fallback (DistSys)
- RoundRobin placement without capacity lock (DistSys)
- No chaos proof (Production Design + SRE)
- Migration in Phase 2 scope (unanimous)

## Stage 5 — Execution Contract

### Phase 2a Deliverables (blocking Phase 2b)

1. Gate #1 closed (10× L3 ≥95/100) — plan reference: T-09 in `docs/plans/50k-immediate-focus.md`
2. PG bumped to db-s-2vcpu-4gb minimum (requires Pulumi preview + drift-safe apply)

- 5 consecutive L3 runs ≥ 98/100
- Chaos: each shared service (Gitea / Harbor / MinIO / PG) killed individually, platform recovers within 2min
