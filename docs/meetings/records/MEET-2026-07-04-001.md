# MEET-2026-07-04-001 — J-16 slice 3: `build.failed` / `deploy.failed` outbox emit

- **Date:** 2026-07-04
- **Type:** api-boundaries + database (T2 — event contract + build-failure paths)
- **Verdict:** **APPROVED_WITH_CONDITIONS**
- **Milestone:** M1 — Settings (J-16 Webhooks). Completes the emit side after the `deploy.succeeded` emit (loopzero#176). `deploy.succeeded` is 100% wired; this ratifies the **failure-event** emit.
- **Depends on:** loopzero#175 (`deploy_events` outbox) + loopzero#176 (emit pattern) merging.

## Context

The J-16 delivery pipeline emits `deploy.succeeded` transactionally from the single
release-activation SoT (`ActivateReleaseKernel`, loopzero#176). Customers can also subscribe
to `deploy.failed` / `build.failed`. The question: **from where, and for which failures,
does the engine emit the failure event on the outbox — given build→FAILED is reached from
several code paths with heterogeneous transaction semantics?**

## Findings (evidence)

Unlike `deploy.succeeded` (one documented SoT choke point), build→FAILED is reached from
**four** independent sites with **different** tx semantics:

| Path | Site | Tx in scope? |
|---|---|---|
| Build workflow reported failed | `build_orchestrator_complete.go:76` — `UpdateStatus(tx, BPEventFailed)` | ✅ inside lock tx |
| Build stuck / errored in reconcile | `build_reconcile_retry.go:213-222` — `UpdateStatus(tx, …)` inside `WithLock` | ✅ tx |
| Stale build timed out | `build_reaper.go:245` — `UpdateStatus(tx, …)` inside `WithLock` | ✅ tx |
| **Workflow submission failed** | `build_orchestrator_submit.go:342` — `UpdateStatusIfCurrent(…)` **CAS, no tx** | ❌ **intentionally lock-free** |

The submit path (`failQueuedBuild`) runs the lock-free CAS variant **deliberately**, per
**ADR 2026-07-03-m9-5b** (REVIEW-BLOCKER-1): to unblock the environment immediately on a
submit failure. Wrapping it in a tx to emit transactionally would **reverse that ADR**
(re-introduce lock contention on the submit-failure path).

## Decision (design ratified WITH conditions)

- **Emit `deploy.failed` transactionally at the THREE build-EXECUTION-failure paths**
  (complete / reconcile-retry / reaper) — each already has the `tx` in scope, so the emit
  mirrors the `deploy.succeeded` pattern (loopzero#176): `deployEventStore.AppendDeployEvent`
  on the SAME tx as the FAILED transition, fresh `transition_id` per entry, customer-safe
  payload (`event=deploy.failed`, `deploy_id`, `project`, `environment`, `status=failed`,
  `occurred_at` — Rule 3, no internal terms).
- **Do NOT emit for the submit-failure path** (`failQueuedBuild`). This is a **semantic
  boundary, not a gap**: a workflow-*submission* failure is a **platform infrastructure
  error** — the customer's build never ran — which is a distinct class from `deploy.failed`
  (the customer's build ran and failed). A customer webhook on `deploy.failed` should not
  fire on a LoopZero-side submission hiccup; that is a platform incident surfaced via ops
  alerting, not a deploy-outcome event. Respecting ADR 2026-07-03-m9-5b (submit stays
  lock-free) is the design, not a compromise.
- **Wiring:** `deployEventStore` (nilable, mirroring the `onReleaseActivated` convention)
  threaded into `BuildOrchestrator` (complete), `BuildReconcileLoop` (reconcile-retry), and
  `BuildReaper` (reaper); production-wired in the composition root; nil in unit paths.
- **Runtime metric:** `deploy.failed` emits increment the same enqueue/delivery pipeline
  the `deploy.succeeded` events do; the `loopzero_workspace_webhook_delivery_total{result}`
  counter already covers delivery outcomes for both event types (loopzero-cloud#151).

## Conditions for approval (BLOCKING — before merge)

1. The three execution-failure emits are on the SAME tx as their FAILED transition; a
   rolled-back FAILED transition emits 0 events (tested, mirroring loopzero#176's rollback→0).
2. The submit-failure exclusion is documented at the call site (`failQueuedBuild`) with the
   ADR 2026-07-03-m9-5b + semantic rationale, so a future reader does not "fix" it into a
   silent-partial or an ADR-reversing tx wrap.
3. Payload carries ZERO internal terms (Rule 3), asserted by a no-internal-terms test.
4. `transition_id` is a fresh UUID per entry (not `build.ID`), consistent with loopzero#176.
5. Security + SRE guardian sign-off (per MEET-2026-07-03-005, which governs the delivery
   pipeline this feeds).

## Alternatives rejected

- **Refactor submit into a tx to emit there** — reverses ADR 2026-07-03-m9-5b (re-introduces
  lock contention on submit failure). Rejected.
- **Emit non-transactionally at submit (best-effort)** — reintroduces the at-most-once loss
  the transactional outbox exists to prevent (rejected by the distsys/security review in
  MEET-2026-07-03-005). Rejected.
- **A single build-failed choke point** (route all four paths through one tx helper) — would
  force the submit path into a tx (same ADR reversal). The three-of-four transactional emit
  + documented submit exclusion is simpler and does not touch the ratified lock-free path.

## Impact if ignored

Emitting from a single naive choke point would reverse ADR 2026-07-03-m9-5b and re-introduce
lock contention on submit failure. Emitting non-transactionally would silently lose failure
events on crash. Emitting from only some paths WITHOUT documenting the boundary would read as
a bug to the next maintainer.

## Actions

1. Implement the three transactional `deploy.failed` emits + submit-exclusion doc — loopzero repo,
   mirrors loopzero#176 (T2, gated on #175/#176 merging).
2. Tests: rollback→0 per path (real PG) + payload hygiene + emit-called hermetic.
3. Guardian sign-off before merge.
