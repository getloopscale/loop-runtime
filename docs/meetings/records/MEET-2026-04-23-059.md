## Stage 1 — Context

### Problem

B15: CLI validator emits a false warning `Unknown field 'apps.<name>.replicas' -- ignored` (and same for `autoscaling`), because the allowlist in `cli/src/adapters/validate-config.ts:174-176` is missing the two fields. The fields are already:

- Typed in `cli/src/adapters/loopzero-yaml.ts:14-32` (LoopZeroYamlAutoscaling, LoopZeroYamlApp.replicas/autoscaling).
- Parsed in `parseLoopZeroYaml` (`cli/src/adapters/loopzero-yaml.ts:102-142`) — bounds-checked (min≥1, max≥min, CPU 1-100).
- Normalized in `cli/src/adapters/app-unit.ts:95-116` (AppUnit.replicas/autoscaling).
- Understood by the API renderer (`api/internal/manifests/renderer.go:43-58`, `renderer_deployment.go:95-106`, `renderer_scaling_test.go` passing).
- Persisted by the DB layer (`api/internal/db/build_store.go:50-64` — `BuildAppSpec.Replicas/Autoscaling`).
- Used by the orchestrator (`api/internal/services/build_orchestrator_submit.go:87-104`).
- Flowed through the manifest builder (`api/internal/services/manifest_builder.go:64-74`).

### The actual gaps (investigation evidence)

1. **CLI `AppInput` DTO** (`cli/src/commands/deploy-types.ts:12-22`) does not include `replicas` or `autoscaling`.
2. **CLI deploy payload** (`cli/src/commands/deploy.ts:301-312`) maps AppUnit → AppInput explicitly and silently drops the two fields.
3. **API `AppInput` DTO** (`api/internal/routes/builds.go:28-37`) is missing `Replicas int` and `Autoscaling *AppAutoscalingSpec` JSON fields. Server-side `services.AppSpec` has them (`build_orchestrator.go:50-72`), but the route-local `AppInput` is the actual wire contract — values are dropped at HTTP boundary.
4. **Route → orchestrator copy** (`builds.go:291-300`): `Apps: req.Apps` passes the stripped struct directly; unknown fields never reach the DB or renderer.
5. **CLI validator allowlist** (`validate-config.ts:174-176`): `replicas`, `autoscaling` missing — B15 symptom.
6. **Plan-limit enforcement**: no `max_replicas_per_service` (or equivalent) row in `plan_limits` (per migration `000023_update_plan_limits_tiers.up.sql`). Existing enforcement middleware (`pkg/enforcement/middleware.go`) cannot inspect request body — it counts DB rows. An in-handler cap is required.
7. **Ambiguity**: both `replicas` and `autoscaling` can be set simultaneously. Renderer silently prefers `autoscaling.minReplicas` when both are present (`renderer_deployment.go:98-107`). The CLI accepts both without warning. No ADR records this precedence.

### Constraints

- Pre-release phase. Aggressive cleanup permitted. No backward-compat burden.
- Rule 3 (no internal terms) — error messages must be user-facing.
- Rule 4 (exit codes permanent) — validator error uses exit 1 (usage), API rejection uses 422 (existing pattern).
- Rule 5 (JSON contract stability) — adding fields is permitted; semantics must be deterministic.
- Rule 6 (environment lock) — payload change does not alter locking; existing `withEnvironmentLock` path unchanged.
- Spec alignment: MEET-2026-03-29-016 caps 1 server + 1 worker per project; CLAUDE.md pricing table states "Starter, 1 project, … max 2 pods" (via monorepo validator). This meeting adds a **replicas-per-service** dimension absent from that cap.

### Proposal (to evaluate)

**Three-layer wiring + hard cap per plan tier:**

1. CLI: add `replicas`, `autoscaling` to `AppInput` and to allowlist; map from AppUnit during payload build.
2. API: add `Replicas` and `Autoscaling` fields to route `AppInput`; copy through to orchestrator.
3. API: add in-handler check in `BuildHandler.Create` that rejects payloads exceeding `max_replicas_per_service` for the tenant's plan.
4. Add plan_limits rows: starter=2, pro=5, team=10, enterprise=NULL (unlimited).
5. Resolve `replicas` vs `autoscaling` ambiguity by making them mutually exclusive at validation time (fail-fast over silent precedence).

## Stage 2 — Analyses

### Principal Architect

**Assessment:** The feature exists end-to-end except at the two boundary DTOs. This is "correct code in wrong place" pattern (see CLAUDE.md Known Systemic Patterns). Root cause: when the renderer+orchestrator+DB were wired (prior work), nobody updated the two wire-format structs because the CLI validator didn't complain about unknown fields — it merely warned. Silent data loss across a contract is exactly the failure mode Rule 5 exists to prevent.

**Risks identified:**
- Fixing in pieces (CLI-only, API-only) would leave inconsistent behavior. Must be atomic.
- Introducing a `max_replicas_per_service` row without an enforcement site leaves dead data and developer confusion.
- Not resolving the `replicas` vs `autoscaling` precedence leads to surprise in production when users set both.

**Objections:** None to the direction. Strong preference for mutual exclusion over silent precedence (KISS + fail-fast).

**Recommendation:** APPROVE as a single atomic change. Require ADR because ambiguity precedence is a permanent semantic decision.

**Conditions:** (1) All 6 files land together. (2) ADR documents "autoscaling wins when both set OR validation rejects — choose rejection." (3) `services_per_project` pre-existing metric is unaffected — this meeting adds a new metric, not renames one.

**Impact if ignored:** Scaling is documented as supported (FB-3 in MEET-057), but is actually a no-op. Users cannot scale. GA-blocker unresolved.

### API/Domain Architect (Sponsor)

**Assessment:** `loopzero.yaml` is the user-facing contract. Today it accepts `replicas`/`autoscaling` silently and does nothing with them at deploy time — a bait-and-switch violating the Vercel-DX promise. The fix is straightforward: extend the POST /api/v1/builds request schema, extend the `--json` output contract to include the echoed scaling config (for CI visibility), and make the semantic precedence explicit.

**Risks identified:**
- Changing route `AppInput` is a T2 contract change (adding fields is compatible, but semantics must be locked now).
- If we ever support `scale` out-of-band (the `loopzero scale` CLI exists at `cli/src/commands/scale.ts`), we must decide whether runtime-set replicas override loopzero.yaml on next deploy. The existing `scale` command is not covered by this meeting; out of scope.

**Recommendation:** APPROVE. Add fields as optional, strip `omitempty` where zero-value is meaningful (i.e., `Replicas` stays `omitempty` because 1 is default; `Autoscaling` is a pointer).

**Conditions:** (1) Route DTO field names match CLI JSON keys: `replicas` (int, `omitempty`), `autoscaling` (object, `omitempty`). (2) `--json` deploy output does NOT need to echo scaling config (not in spec §0.3 schema); leave unchanged to avoid Rule 5 surface growth without necessity.

### DX Engineer

**Assessment:** The current warning "Unknown field 'apps.<name>.replicas' -- ignored" actively misleads users: they think they have to remove the field, then they remove it, then they can't scale. DX harm is direct. Warning messages are also a user-facing contract. Beyond fixing the allowlist, two UX improvements matter:

1. **Mutual exclusion messaging**: if the user sets both, the error must be specific and suggest a fix.
2. **Plan-limit error**: the error must name the plan, cite the cap, and suggest `loopzero billing upgrade` (or the upgrade URL). Existing `FormatLimitError` pattern (`pkg/enforcement/limiter.go:162-172`) is reusable.

**Risks identified:**
- Adding fields to the validator allowlist without validating their VALUES leaves silent acceptance of e.g. `replicas: -5` at the CLI (parser clamps to `undefined`, but user sees no error). The parser at `loopzero-yaml.ts:104` silently drops invalid values; CLI validator should reject explicitly.
- No internal terms (Rule 3). Error messages must say "replicas" and "autoscaling" (user-provided field names — safe). Never "HPA", "K8s", "Deployment", "reconcile".

**Recommendation:** APPROVE with explicit value validation in the CLI validator (fail-fast, exit 1).

**Conditions:**
- CLI validator rejects `replicas < 1` or `replicas > plan-cap-guess` with user-friendly error.
- CLI validator rejects both `replicas` and `autoscaling` set simultaneously (mutual exclusion).
- CLI validator rejects `autoscaling.max < autoscaling.min` (parser drops silently today).
- Plan-limit 402 response uses existing `FormatLimitError` — same UX as other limits.

### Platform Security Engineer (Challenger)

**Assessment:** This is where silent data loss becomes an **abuse-prevention hole**. Without a cap, a Starter tenant can set `replicas: 10000` in loopzero.yaml; today nothing stops them at the API layer. The NetworkPolicy, ResourceQuota, and LimitRange CRs from H7 hardening would throttle them eventually at K8s admission, but (a) that's defense-in-depth, not a primary gate, and (b) the Deployment spec IS accepted by the API and committed to the gitops repo — the user has already consumed build minutes and DB rows. Primary gate must be at HTTP boundary.

**Absolute veto conditions (MUST be satisfied before APPROVED stands):**

1. **Plan-limit enforcement lives IN-HANDLER, not as middleware.** The enforcement middleware pattern (`pkg/enforcement/middleware.go:20-52`) only inspects request metadata + DB counts. It cannot see request body. A new in-handler call `planLimiter.CheckLimit(tenantID, "max_replicas_per_service", app.Replicas)` is required per app in `req.Apps`.
2. **Request body is authoritative.** The check must use `app.Replicas` (and `autoscaling.MaxReplicas` when autoscaling is set), not any DB-derived number. This is an intent check, not a row count.
3. **HTTP response is 422 (not 402).** `ErrPlanLimit` returns 402 (`Payment Required`). Here we are rejecting malformed intent (too-high replicas for plan). 422 `Unprocessable Entity` is consistent with `ErrFrontendMustBeStatic` and `ErrPodLimitExceeded` (`pkg/errors/errors.go:217-231`). Users on Starter can upgrade → 402 is meaningful for quota exhaustion (projects, builds/month). For intent rejection, 422 is the right code.
4. **Fallback plan = starter.** The `getTenantPlan` logic (`limiter.go:123-138`) falls back to "starter" when subscription row is missing. Acceptable; this is strictest cap, fail-safe.
5. **No way to bypass.** Both `deploy` and any future auto-deploy webhook (`api/internal/github/autodeploy.go`) must pass through the same check. Since both converge on `BuildOrchestrator.SubmitBuild`, the check must live either in the route handler OR inside `SubmitBuild` (preferred — closer to truth, covers webhooks automatically).
6. **Audit log entry when rejected.** Plan-limit violations are security-relevant signals (abuse attempts). Existing audit middleware covers HTTP handler path. If we move the check into the orchestrator, we must emit an audit event there.

**Risks identified:**
- Placing the check in the route handler covers only CLI-originated builds. GitHub App auto-deploy also calls `SubmitBuild`. If we do not place the check inside the orchestrator, auto-deploy can silently bypass the cap (since webhook sets replicas from loopzero.yaml read from GitHub).
- If `services_per_project` already caps service count, and `max_replicas_per_service` caps replicas, the total pod cap is the product. For Starter (services_per_project=3, max_replicas_per_service=2) that's 6 pods — within the existing ResourceQuota (MEET-2026-03-29-016 stated "max 2 pods" is stale; the monorepo validator enforces 1 server + 1 worker = 2 pods at service-count level). **This meeting does NOT relax that cap** — 1 server + 1 worker × N replicas each. On Starter: 1 server × 2 replicas + 1 worker × 2 replicas = 4 pods total. This must be explicitly validated against H7 ResourceQuota values; SRE will confirm.

**Recommendation:** APPROVE subject to the 6 veto-conditions above. Prefer check inside `BuildOrchestrator.SubmitBuild` over route-handler check for uniform coverage.

**Conditions:** See veto conditions 1-6.

### SRE/Production Engineer

**Assessment:** The operational impact is real — `replicas` is what customers scale with when traffic spikes. Current behavior (always 1 replica) is a reliability bug: a Pro-plan customer cannot absorb load without HPA, and HPA is also silently disabled. This is why MEET-057 flagged FB-3 as a BLOCKER. But wiring the plumbing without validating the ResourceQuota interaction is irresponsible.

**Absolute veto conditions:**

1. **Resource-quota interaction MUST be documented.** When Starter is capped at 2 replicas per service and the workload namespace has a ResourceQuota of N pods / M CPU, we must confirm `max_replicas_per_service × services_per_project × (CPU request per pod) ≤ quota`. If not, deploys succeed at API layer but fail at K8s admission — the exact failure mode H7 was supposed to prevent. This must be a pre-implementation calculation, documented in the ADR or gate file.
2. **HPA default behavior**: if the user sets `autoscaling` with only `min` (no `max`), the parser defaults max=3 (per `loopzero-yaml.ts:16`). This default is NOT visible to the user and may exceed plan caps. ADR must specify: if `autoscaling.max > plan_cap`, reject (not clamp). The parser silently-drops behavior for invalid values becomes fail-fast at validator.
3. **Observability**: emit metric `loopzero_plan_limit_violation_total{metric="max_replicas_per_service", plan="..."}` (reuse existing plan-limit counter if present). Must be visible in Grafana to detect abuse patterns.
4. **Rollback path**: if the change is bad, reverting requires (a) removing new DTO fields (OK — additive), (b) removing the in-handler check (OK — single code site), (c) leaving `plan_limits` rows (OK — unused rows are safe). Additive changes permit clean rollback.

**Risks identified:**
- If autoscaling is silently preferred over replicas (current renderer behavior), a user setting `replicas: 5` and forgetting `autoscaling` still-set from a prior revision gets 1-2 replicas with no warning. Operations-blind for the customer.

**Recommendation:** APPROVE subject to vetoes. Strong support for mutual exclusion (fail-fast).

**Conditions:** See 1-4. Quota math documented in ADR or gate.

**Plan-limit test** (`pkg/enforcement/limiter_test.go`):

**Risk identified:**
- Existing `CheckLimit` uses `currentCount >= hardLimit` to reject (`limiter.go:84`). For replicas, the semantics differ: we are checking `requested_replicas > plan_cap`. **Recommendation:** APPROVE with a dedicated `CheckValue` method OR passing `currentCount = requestedReplicas - 1` (the current API treats limit as strict `<` — `if current >= hard then deny`, i.e. `if requested-1 >= hard then deny` ≡ `if requested > hard then deny`, correct). The cleaner approach is a new `CheckValue` method; fallback is the arithmetic adapter.

**Conditions:** All 7 test contracts above must be written FIRST (red), then implementation (green). No implementation without a failing test — Rule 1.

## Stage 3 — Confrontation

### Conflict 1: `replicas` vs `autoscaling` precedence

| Agent | Position |
|-------|----------|
| Principal Architect | Mutual exclusion, fail-fast at validator (no silent precedence) |
| API/Domain Architect | Mutual exclusion (contract clarity) |
| DX Engineer | Mutual exclusion with specific error message |
| Platform Security Engineer | Mutual exclusion (reduces surface) |
| SRE | Mutual exclusion (fail-fast operability) |
| Verification Architect | Both positions testable; mutual exclusion has fewer edge cases |
| Pipeline Reviewer | Not opinionated |

**Resolution:** UNANIMOUS — mutual exclusion. If both `replicas` and `autoscaling` are set in loopzero.yaml, the CLI validator REJECTS with exit 1. Defense-in-depth: the API also rejects with 422 `SCALING_AMBIGUOUS` (so auto-deploy from GitHub App cannot bypass CLI validation). The renderer's current silent-precedence behavior (`renderer_deployment.go:98-107`) becomes unreachable on the happy path but is preserved as a safety net for prior payloads already persisted — no backward-compat burden since pre-release.

### Conflict 2: Enforcement location — route handler vs orchestrator

| Agent | Position |
|-------|----------|
| Platform Security | Orchestrator (covers auto-deploy path) |
| API/Domain Architect | Route handler (keeps HTTP concerns in HTTP layer) |
| Principal Architect | Orchestrator wins — uniform coverage > layer purity |
| SRE | Orchestrator (fewer bypass paths) |
| Verification | Either testable; orchestrator has fewer duplications |

**Resolution:** Orchestrator-level enforcement. Check lives in `BuildOrchestrator.SubmitBuild` BEFORE the transaction starts. Reasons: (a) covers CLI, GitHub App webhook, and any future entry points; (b) single test surface; (c) failure returns a typed `LoopZeroError` that the route handler maps to 422 via existing `mapBuildError`. Route handler keeps the existing syntactic validation (app name, path) unchanged.

### Conflict 3: `services_per_project` vs `max_replicas_per_service` cap semantics

No disagreement. `services_per_project` (existing, pre-populated for all plans) caps the number of distinct apps. `max_replicas_per_service` (new) caps replicas per app. They compose multiplicatively. Quota math must be documented in ADR or gate.

### Self-challenge (per orchestration rules): What could go wrong that nobody surfaced?

1. **The CLI parser silently drops invalid `autoscaling.max < min`** (`loopzero-yaml.ts:118`). After this change, validator rejects — but the parser behavior creates a subtle inconsistency: the parsed object loses `max`, the validator runs against `autoscaling` as `{min: X}`, which looks valid in isolation. Fix: validator must read BOTH the parsed object AND the raw yaml, OR the parser must preserve invalid values for the validator to reject. Cleanest: change parser to preserve values and let validator reject. Assigned as mandatory action #3.
2. **Pro plan HPA max default = 3** (parser default). If Pro plan cap is 5, this never conflicts. If Pro plan cap is 3, silent max=3 may conflict with user intent (they expected more). Document defaults explicitly in plan limits migration comment and in loopzero.yaml docs (out of scope here; flag to docs).
3. **`scale` command out-of-band mutation** (`cli/src/commands/scale.ts`). The existing `loopzero scale` command updates replicas imperatively. It is NOT covered by this meeting. Future deploys from loopzero.yaml could silently overwrite scale-command changes. Out of scope — noted for follow-up.

## Stage 4 — Decision

### Chosen approach

**Atomic B15 change with 6 coordinated edits:**

1. **CLI validator allowlist** — add `replicas`, `autoscaling` to `knownFields` set; B15 warning disappears.
2. **CLI validator semantic rules** — reject: `replicas < 1 || replicas > 100`, `autoscaling.max < autoscaling.min`, `autoscaling.targetCPU` outside 1-100, both `replicas` AND `autoscaling` set. Errors (not warnings), exit code 1.
3. **CLI parser** — stop silently dropping invalid autoscaling values; preserve raw numbers so the validator can reject them explicitly. (`loopzero-yaml.ts:102-128`)
4. **CLI payload** — add `replicas?: number` and `autoscaling?: { min, max, targetCPU }` to `AppInput`; map from AppUnit in `deploy.ts:301-312`.
5. **API route DTO** — add `Replicas int` + `Autoscaling *AppAutoscalingInput` to `routes.AppInput`. New local type `AppAutoscalingInput{Min, Max, TargetCPU int}`.
6. **API orchestrator** — `SubmitBuild` copies request `Replicas`/`Autoscaling` into `services.AppSpec` (already has the fields). Before creating the build, call `planLimiter.CheckLimit(tenantID, "max_replicas_per_service", max(replicas, autoscaling.max))` per app. On denial, return new typed error `ErrReplicasExceedPlan` (HTTP 422). On mutual-set (defense-in-depth), return new typed error `ErrScalingAmbiguous` (HTTP 422).
7. **Migration** — add `000032_plan_limits_max_replicas.up.sql` inserting `(plan, 'max_replicas_per_service', hard_limit)` rows: starter=2, pro=5, team=10, enterprise=NULL.
8. **Enforcement semantics** — add `PlanLimiter.CheckValue(tenantID, metric, requestedValue) LimitResult` method (or verify the existing `CheckLimit` arithmetic works for intent-check). Decision: add `CheckValue` for clarity — `CheckLimit`'s row-count semantics leak.

### Alternatives rejected

- **Fix CLI-only (allowlist)**: rejected — leaves scaling silently broken end-to-end. Makes B15 appear "fixed" while masking the real bug (fields dropped at API boundary).
- **Let renderer silently prefer autoscaling over replicas when both set**: rejected — violates fail-fast, causes surprise in production.
- **Enforce plan limits at route middleware**: rejected — middleware cannot read body; would require body buffering + re-injection; also bypassed by auto-deploy.
- **Add pod cap via NetworkPolicy/ResourceQuota only (defense-in-depth alone)**: rejected — primary gate belongs at API; K8s admission is secondary.
- **Clamp replicas silently to plan cap (instead of rejecting)**: rejected — "silent clamp" is a footgun. User asked for 10, got 2, wonders why traffic drops. Explicit rejection + upgrade prompt is correct DX.

### Trade-offs consciously accepted

- **Validator now has stricter rules**: existing loopzero.yaml files with malformed autoscaling values will start failing validation. Pre-release acceptable (no production customers).
- **`CheckValue` new method**: adds surface to `PlanLimiter`. Justified by semantic clarity (row-count vs intent-check).
- **Mutual exclusion between replicas and autoscaling**: users who want "start at 2 replicas and autoscale up to 5" must express this as `autoscaling: {min: 2, max: 5}`. Document in loopzero.yaml docs.

### Risks accepted with mitigation

| Risk | Mitigation | Owner |
|------|-----------|-------|
| Plan-limit row missing in DB → fallback denies | `getLimits` returns hardLimit=0 when row missing → CheckLimit denies. Migration MUST ship in same PR. | api-engineer |
| Quota math wrong (2 replicas × 3 services on Starter > ResourceQuota) | Pre-implementation calculation documented in ADR; update H7 quota if needed. | sre-engineer (async review) |
| Auto-deploy path not covered if check is in route handler | Check lives in `SubmitBuild` (orchestrator), verified by integration test triggering via mock webhook. | api-engineer + test-engineer |
| `loopzero scale` command diverges from loopzero.yaml | Out of scope; follow-up ticket. | tracked as follow-up |

### Risks NOT accepted (blockers until mitigated)

None that block approval. All Security/SRE vetoes are addressed by the chosen approach.
