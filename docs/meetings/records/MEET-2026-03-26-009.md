# MEET-2026-03-26-009 — Frontend Static Asset Delivery Architecture

**Data:** 2026-03-26
**Tipo:** architecture
**Status:** APPROVED_WITH_CONDITIONS (+ Staff Review 8 critical points incorporated)
**Sponsor:** Principal Architect
**Challenger:** SRE (operational parity) + API Architect (refactoring prerequisite)
**Owner:** Orchestrator (multi-component)

---

## Contexto

LoopZero deploya frontends estaticos (Vite, CRA, Vue, Svelte, Astro, Next.js export) como pods Kubernetes 24/7 — identico a backend servers. Um processo Node.js/nginx serve arquivos estaticos permanentemente. Isso é desperdiço de compute, latência sub-otima, e arquiteturalmente incorreto para um PaaS que promete "Vercel-quality DX".

## Decisao

**Adotar delivery em 3 fases com prerequisito de refatoração.**

### Fase 0: Prerequisito — DeliveryActivator Interface (1 sprint)

Refatorar `activateRelease` em uma interface `DeliveryActivator` com duas implementações: `ContainerDeliveryActivator` (fluxo existente Gitea+ArgoCD) e `StaticDeliveryActivator` (novo fluxo S3+Traefik). Esta refatoração é obrigatória ANTES de adicionar qualquer lógica CDN.

**Motivo (API Architect):** Sem a interface, cada modelo de delivery adiciona branches `if/else` a um método de 300+ linhas. O `activateRelease` atual já é um orquestrador de control plane mascarado como lógica de API. CDN o torna insustentável.

### Fase 1: Static Asset Delivery via S3 + Traefik (1-2 sprints)

Build produz asset bundle → upload para DO Spaces → Traefik IngressRoute + Middleware proxy para S3 origin → ArgoCD sincroniza.

**O que resolve:** elimina pod permanente para frontends estaticos (economia de compute).
**O que NÃO resolve:** latência (trafego ainda passa pelo cluster). Isso e v2.

```
┌──────────┐     ┌──────────────────┐     ┌──────────────┐
│ Browser  │────→│ Traefik (workload)│────→│ DO Spaces    │
│          │←────│  Cache-Control    │←────│  S3 origin   │
└──────────┘     │  headers          │     └──────────────┘
                 └──────────────────┘
Assets com hash no filename: Cache-Control: max-age=31536000
index.html: Cache-Control: no-cache, must-revalidate
```

### Fase 2: CDN Edge Layer (futuro, quando trafego justificar)

Cloudflare ou DO CDN na frente do Traefik. Zero mudança no app — apenas DNS + proxy config.

### Modelo de Detecção (v1: explícito, v2: auto-detect)

```yaml
# loopzero.yaml v2
apps:
  dashboard:
    type: frontend
    framework: vite
    render: static        # NOVO: "static" | "server" (default: "server" para backward compat)
    path: apps/dashboard
```

- `render: static` → build produz assets, upload S3, Traefik proxy
- `render: server` (default) → comportamento atual (container image, pod)
- Se `render` omitido + `type: frontend` → default `server` (NUNCA mudar silenciosamente para CDN)

### Propostas Rejeitadas

| Proposta | Motivo |
|----------|--------|
| Edge Functions (Cloudflare Workers) | DO não tem edge compute. Dependência em provider externo viola boundary. YAGNI. |
| Full CDN na v1 | Sobre-engenharia. Traefik+S3 resolve o problema (eliminar pod) sem nova infra. |
| Auto-detect static vs SSR na v1 | Risco de classificar errado (Next.js com SSR detectado como static). Explícito e seguro. |
| CDN sem refatoração | `activateRelease` vira god method. API Architect veto. |

### Trade-offs Aceitos

1. **v1 não melhora latência.** Traefik→S3 ainda é single-region. Aceito porque: o problema principal é custo de compute, não latência. v2 resolve latência.
2. **Dois caminhos de delivery.** Aumenta complexidade do reconcile loop e rollback. Aceito porque: mitigado pela DeliveryActivator interface.
3. **Prerequisito de refatoração atrasa valor.** ~1 sprint antes de qualquer frontend ir para S3. Aceito porque: sem a interface, o tech debt é insustentavel em 2 sprints.

### Riscos Aceitos + Mitigação

| Risco | Sev. | Mitigação |
|-------|------|-----------|
| S3 origin latency (~50-100ms cache miss) | HIGH | Cache-Control agressivo em assets com hash. Somente index.html hit S3 a cada request. |
| SPA routing (client-side routes → 404) | HIGH | Traefik middleware: error page serve index.html on 404. Padrão conhecido. |
| Deploy parcial (upload incompleto) | HIGH | Upload para path versionado `/{release-id}/`. Só trocar pointer após upload completo + health probe. |
| Deploy race condition | MEDIUM | Mesma `withEnvironmentLock` do fluxo container. |
| Asset cleanup (S3 acumulação) | LOW | S3 lifecycle policy: 30 dias prod, 7 dias preview. |

### Riscos NÃO Aceitos (SRE Blockers)

| Risco | Condição para Desbloqueio |
|-------|---------------------------|
| Deploy sem health probe | Post-deploy HTTP GET no CDN URL para index.html. Deploy NÃO é ACTIVE até probe passar. |
| Rollback inexistente | `loopzero rollback` DEVE funcionar para CDN apps. Implementação: switch pointer S3 + IngressRoute update. |
| Deploy atomicity | Assets em path versionado. Pointer switch só após upload completo. NUNCA servir upload parcial. |
| Zero alerting | Mínimo: blackbox-exporter probe periódico nas URLs de frontends estaticos. |

## Decisões Arquiteturais

| Decisão | Justificativa |
|---------|---------------|
| **Traefik+S3 (não CDN puro) na v1** | Usa infra existente. Elimina pod waste sem nova infra. CDN e v2. |
| **`render` field explícito, não auto-detect** | Evita classificação errada (SSR como static). Default `server` é backward compat. |
| **DeliveryActivator interface como prerequisito** | Impede god method em activateRelease. Cada delivery model e uma implementação. |
| **Versioned S3 paths `/{release-id}/`** | Rollback instantâneo (pointer swap). Deploy atômico (upload completo antes de switch). |
| **ArgoCD ainda sincroniza IngressRoute** | CDN routing config e K8s resource (IngressRoute+Middleware). Fonte de verdade permanece Gitea. |
| **Release record existe para CDN deploys** | Unifica rollback, status, e source of truth. `environment_targets` funciona igual. |
