## Stage 1 — Context

**Problem:** SRE Guardian Report (iteration 2, post-deploy ce8b29f) detected 5 anomalies:
1. ArgoCD callback 401 — token mismatch (hardcoded vs dynamic per deploy)
2. Grafana PVC deadlock — RollingUpdate + RWO = stuck 112+ min
3. gitea-bootstrap CrashLoop — ArgoCD secret not ready when Job starts
4. Leader election status=0 — possibly sampling bias
5. metrics-server absent — `kubectl top` fails on all 3 DOKS clusters

**Decision Required:** Validate remediation approach for each anomaly.

**Uncertainties:**
- Is leader election a real issue or sampling bias from `kubectl exec deploy/`?
- What's the correct approach for callback token (security)?
- Is the wait-for-secret pattern robust enough for bootstrap?

## Stage 2 — Analyses

### SRE Engineer

Priority: Callback 401 (P0) > Grafana PVC (P1) > gitea-bootstrap (P2) > metrics-server (P3) > leader (P4 — verify first).

Leader election is almost certainly sampling bias. `kubectl exec deploy/` hits a random pod. Verify via `sum(loopzero_api_leader_status)` in Prometheus or query each pod individually.

Callback token must use Pulumi-managed secret (RandomPassword or config secret), not hardcoded constant. Grafana Recreate is the only valid fix for RWO PVC.

### Platform Security Engineer

**VETO** options (a) config secret and (b) constant string — manual distribution and plaintext in code respectively.

**APPROVE** option (c) `@pulumi/random.RandomPassword`: length >= 32, special: false (URL-safe). Single source of truth, encrypted in Pulumi state (DO Spaces backend), no human touches the value.

Minimum posture for pre-release: random token via Pulumi state is sufficient given same-namespace, NetworkPolicy enforced, single-purpose endpoint. mTLS is correct long-term but premature now.

### Distributed Systems Engineer

Leader election is **sampling bias with 95% confidence**. Absence of leader-related logs (no heartbeat failures, no re-election attempts) is reassuring — a real failure would produce 60s-interval re-election logs.

**Critical finding:** The `pg_advisory_unlock` stale-lock cleanup (lines 554-559) is **dangerous**. If pod B starts on a PG connection that was previously used by pod A (connection pool reuse), the unlock releases pod A's active lock. Creates a window where NEITHER pod holds the lock. Recommendation: **remove the unlock entirely** — PG cleans dead sessions automatically.

Increase retry from 6→12 (60s) is harmless but addresses a likely non-problem. More important: expose per-pod metrics properly (ServiceMonitor with pod labels).

### Principal Architect

gitea-bootstrap is the most architecturally significant issue. A bash Job orchestrating critical bootstrap is an anti-pattern accumulating ordering assumptions.

Wait-for-secret loop (option a) is acceptable ONLY as tactical bridge. The destination is PlatformBootstrapController (CRD already exists with state machine: Pending → ConfiguringGitea → ConfiguringArgoCD → WaitingForAPI → Complete).

Options (b) Pulumi reading K8s secrets and (c) Command provider are worse — they mix IaC declaration with runtime orchestration.

Callback token: single source of truth is the only acceptable pattern.

## Stage 3 — Confrontation

### Resolved Conflicts

| Topic | Resolution |
|-------|-----------|
| Callback token approach | Unanimous: `@pulumi/random.RandomPassword`. Security vetoed alternatives. |
| Bootstrap: wait loop vs redesign | Both: tactical wait loop now + tracking item for PlatformBootstrapController |
| Leader election: fix vs verify | Verify first (query each pod). Remove `pg_advisory_unlock` regardless. Increase retry defensively. |
| Priority ordering | All in same deploy — ordering is moot. |

### Unresolved: `pg_advisory_unlock` removal

DistSys identified a correctness risk in the stale-lock cleanup. However, the unlock was added intentionally (MEET-043 P1) to handle crashed pods. Removing it could mean a dead pod's lock persists until PG timeout (~90s).

**Resolution:** Remove the unlock. PG handles dead session cleanup via TCP keepalive (15s × 3 missed probes = 45s). The 60s retry window covers this. The correctness risk of the unlock (releasing another pod's lock) outweighs the latency benefit.

## Stage 4 — Decision

### Fix 1: ArgoCD Callback Token — `@pulumi/random.RandomPassword`

- Install `@pulumi/random` package
- Create `RandomPassword` resource (length=32, special=false)
- Reference in ArgoCD notifications ConfigMap AND API Secret
- Delete hardcoded `cb-loopzero-dev-2026`
- **File:** `infra/pulumi/src/components/mgmt-bootstrap.ts` lines 287, 1358

### Fix 2: Grafana Strategy: Recreate

- Add `strategy: { type: "Recreate" }` to Grafana Helm values
- **File:** `infra/pulumi/src/components/mgmt-observability.ts` after line 202

### Fix 3: gitea-bootstrap Wait-for-Secret

- Add `kubectl wait --for=jsonpath` or explicit loop before reading ArgoCD admin secret
- Bounded retries: 60 × 5s = 5min max
- Exit non-zero on timeout (not infinite loop)
- **File:** `infra/pulumi/src/components/mgmt-bootstrap.ts` bootstrap script (~line 1009)

### Fix 4: Leader Election — Verify + Defensive Hardening

- **FIRST:** Verify via `kubectl exec` on each pod individually
- Remove `pg_advisory_unlock` stale-lock cleanup (lines 554-559) — correctness risk
- Increase retry from 6→12 (60s total)
- Add startup log `"starting leader election"`
- **File:** `api/cmd/main.go` lines 549-573

### Fix 5: metrics-server on All Clusters

- Add `installMetricsServer()` to `bootstrap-shared.ts`
- Call from mgmt, build, and runtime bootstrap functions
- Helm chart: `metrics-server` v3.12.1 with `--kubelet-insecure-tls` (DOKS requirement)
- **Files:** `bootstrap-shared.ts`, `mgmt-bootstrap.ts`, `build-bootstrap.ts`, `runtime-bootstrap.ts`
