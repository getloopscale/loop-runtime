## Stage 1 — Context

**Problem:** The current tenant deletion system has two disconnected paths: API-level `ProjectDeleter` and operator-level `TenantController.reconcileDelete`. When bulk-deleting tenants (160 load-test tenants), all finalizers run concurrently without rate limiting, causing retry storms that saturate Gitea, Harbor, MinIO, and ArgoCD. There is no circuit breaker, no per-step visibility, no tombstone audit trail, and force-null finalizer removal is used as a recurring hack.

**Decision Required:** Should we approve the proposed 5-component architecture (API soft-delete, DB tables, TenantReaper service, refactored TenantController, CLI admin commands)?

**Constraints:**
- Pre-release phase — can break backward compat
- Production on DigitalOcean (3 DOKS clusters)
- Existing in-memory circuit breaker pattern (`pg_circuit_breaker.go`)
- TenantController runs serial cleanup: Harbor → ArgoCD → Build NS → MinIO → Gitea
- `pg_advisory_xact_lock` only (transaction-scoped)
- Four Planes architecture (Developer, Control, Build, Workload)
- Spec §5 defines tenant state machine: Provisioning → Active → Suspended → Deleting

**Known Context:**
- MEET-2026-04-17-051 already reviewed this topic (referenced by SRE)
- Bug #44 (Gitea CPU saturation under load)
- Existing `BuildReaper` pattern (polling-based, timeout-per-state)
- Existing `ProjectDeleter` (synchronous orchestrator — known anti-pattern)

## Stage 2 — Agent Analyses (Summary)

### SRE / Production Readiness

- **Assessment:** Problem diagnosis is correct. Architecture direction sound but 4 critical operability gaps.
- **Key Risks:** (1) `DeleteApplications` not idempotent (NotFound not handled → infinite requeue). (2) No grace expiry goroutine heartbeat metric. (3) No tombstone delivery guarantee. (4) `MaxConcurrentReconciles=5` blocks tenant provisioning during bulk delete.
- **Recommendation:** APPROVE WITH CONDITIONS. Fix `DeleteApplications` idempotency as literal first commit. Add 10+ PrometheusRules for all failure modes. Define deletion SLO: 95% within 60min.

### Platform Security

- **Assessment:** Most security-sensitive admin capability in LoopZero. Three ABSOLUTE VETOs.
- **VETO 1:** No platform-admin auth mechanism exists. Force-delete/bulk-delete require cross-tenant authority that no current role provides. Implement `LOOPZERO_ADMIN_API_KEY` with dual-key rotation.
- **VETO 2:** Bulk-delete without two-step cryptographic confirmation. Confirmation token must be HMAC-SHA256 signed, time-bound (5min), single-use, scope-bound.
- **VETO 3:** Deletion callback must be authenticated (use existing `ServiceAuthSecret` pattern).
- **Additional:** IDOR protection on `DELETE /api/v1/tenants/:id`. Tombstone PII anonymization policy (2-year TTL). Audit every lifecycle transition.
- **Recommendation:** APPROVED WITH CONDITIONS (3 absolute vetoes must be resolved first).

### Distributed Systems

- **Assessment:** Hybrid control loop (API Reaper orchestrating K8s Controller) creates crash-recovery gaps, dual-leader-election incoherence, and unbounded waits.
- **Key Risks:** (1) Crash between CR deletion and tombstone write. (2) Finalizer hangs indefinitely — no timeout. (3) Circuit breakers at wrong layer (Reaper vs Controller). (4) LISTEN/NOTIFY at-most-once without polling fallback. (5) Lease without TTL. (6) No max attempts/backoff.
- **Critical Finding:** Circuit breakers in the Reaper are useless — actual calls happen in the Controller. Retry storm reduced from 160x to 5x, not eliminated.
- **Recommendation:** CONDITIONAL APPROVAL with 7 mandatory corrections.

### K8s Controller Engineer

- **Assessment:** Existing `reconcileDelete` is sound for single-tenant. Problem is concurrency, not logic.
- **Critical Objection:** The TenantReaper solves a controller problem outside the controller. `MaxConcurrentReconciles` is the Kubernetes-native answer. Annotation-based circuit breaker is condition-gated reconciliation through the back door.
- **Counter-proposal:** (1) Set `MaxConcurrentReconciles=5`. (2) Exponential backoff replacing fixed 5s requeue. (3) Circuit breakers in provisioner HTTP clients. (4) Metrics for observability, not conditions. (5) Hard deadline via annotation.
- **Recommendation:** CONDITIONAL APPROVAL — Reaper scope must be limited to queue management + tombstone writing. No annotation-based controller behavior modification.

### Principal Architect

- **Assessment:** **REJECT the TenantReaper architecture.** Dual source of truth (PG + K8s), boundary violation (API driving Control Plane), circuit breakers in wrong process, PG as hand-rolled work queue.
- **Counter-proposal:** Option A (minimal): `MaxConcurrentReconciles` + client-side circuit breakers. Option B (if bulk needed): `TenantDeletionRequest` CRD watched by a dedicated controller.
- **Warning:** If Reaper ships, API becomes shadow control plane. Every future lifecycle op will follow the same pattern. Four Planes becomes fiction.
- **Recommendation:** REJECT Reaper. Approve problem statement. Redesign controller-native.

### API Domain Architect

- **Assessment:** API surface has 7 design issues. Intent/execution separation is correct direction.
- **Key Issues:** (1) `DELETE /force` is REST anti-pattern → use `?force=true`. (2) `/admin/` namespace → move to `/api/v1/` with RBAC. (3) Missing idempotency on all mutating endpoints. (4) No status observation endpoint. (5) No LoopZeroError codes defined. (6) 202 response body undefined. (7) Phase 0 kubectl bypass must be explicitly temporary.
- **Recommendation:** CONDITIONAL APPROVAL with 7 API design corrections.

## Stage 3 — Technical Confrontation

### Confrontation 1: TenantReaper vs Controller-Native

| Agent | Position |
|-------|----------|
| Principal Architect | REJECT Reaper. Violates Four Planes. API becomes shadow control plane. |
| K8s Controller | REJECT Reaper as orchestrator. `MaxConcurrentReconciles=5` solves primary problem. |
| Distributed Systems | Conditional on Reaper. Circuit breakers at wrong layer. 7 gaps. |
| SRE | References MEET-051 which already rejected Reaper in favor of controller-native. |
| API Domain | Accepts intent/execution separation but requires Reaper as separate process. |

**Resolution:** TenantReaper as designed is **REJECTED**. The API-side orchestrator violates the Four Planes architecture, puts circuit breakers in the wrong process, creates dual source of truth, and reimplements K8s work queue primitives in PostgreSQL.

**Approved approach:** Controller-native with API intent gateway.

### Confrontation 2: Circuit Breaker Location

| Agent | Position |
|-------|----------|
| All 4 technical agents | Unanimous: circuit breakers in provisioner HTTP clients |

**Resolution:** Circuit breakers in `gitea.RealProvisioner`, `argocd.RealProvisioner`, `harbor.Client`, `minio.AdminProvisioner`. Benefits ALL controller paths, not just deletion.

### Confrontation 3: Per-Step Deletion Conditions

| Agent | Position |
|-------|----------|
| K8s Controller | REJECT. Conditions on dying objects are ephemeral lies. Use metrics. |
| SRE | Agrees metrics are correct vehicle. |
| Principal Architect | Conditions for deletion observability are pattern abuse. |

**Resolution:** No per-step deletion conditions on Tenant CR. Use `tenant_deletion_step_duration_seconds{step,tenant,result}` metric and structured logs.

### Confrontation 4: Source of Truth

| Agent | Position |
|-------|----------|
| Principal Architect | Tenant CR is sole source of truth. PG deletion queue is duplication. |
| API Domain | PG is acceptable for intent storage (same as build requests). |
| K8s Controller | PG queue reimplements K8s work queue. Unnecessary. |

**Resolution:** Compromise. PG stores **intent** (soft-delete request, grace period) and **audit** (tombstone). Tenant CR remains source of truth for lifecycle state. API sets annotation `loopzero.io/deletion-requested` + writes PG row for audit. Grace expiry goroutine (leader-elected) calls `kubectl delete tenant` when grace expires. Controller executes cleanup autonomously.

### Confrontation 5: Orchestrator Challenge

**Challenge:** If `MaxConcurrentReconciles=5` and 5 tenants trigger panics, throughput drops to zero.

**Resolution:** Exponential backoff (5s → 5min cap) + hard max attempts (10) + `DeletionStuck` alert. At max attempts, controller stops requeuing and emits critical alert. Manual intervention required (acceptable for pre-release).

## Stage 4 — Decision

### Chosen Approach

**Controller-native deletion with API intent gateway.** Three components instead of five:

```
┌─────────────────────────────────────────────────────────────────┐
│  1. API: DELETE /api/v1/tenants/:id                              │
│     - Writes intent to PG (tenants_pending_deletion)             │
│     - Sets annotation loopzero.io/deletion-requested on Tenant CR    │
│     - Returns 202 with deletion record                           │
│     - Grace expiry goroutine (leader-elected, heartbeat metric)  │
│       calls kubectl delete tenant when grace_until < NOW()       │
│     - POST /api/v1/tenants/:id/restore within grace window       │
│     - POST /api/v1/tenants/bulk-delete (admin, two-step HMAC)    │
└────────────┬────────────────────────────────────────────────────┘
             │ kubectl delete tenant (rate-limited by grace expiry goroutine)
             ▼
┌─────────────────────────────────────────────────────────────────┐
│  2. TenantController.reconcileDelete (refactored)                │
│     - MaxConcurrentReconciles = 5 (configurable)                 │
│     - Exponential backoff (5s base, 5min cap, max 10 attempts)   │
│     - Circuit breakers in provisioner HTTP clients                │
│     - Per-step metrics (not conditions)                          │
│     - Callback to API on completion (authenticated)              │
│     - Hard deadline: stop requeue after 10 attempts, emit alert  │
└────────────┬────────────────────────────────────────────────────┘
             │ on finalizer removed (or max attempts)
             ▼
┌─────────────────────────────────────────────────────────────────┐
│  3. API writes tombstone to PG + emits audit event               │
│     - tenant_tombstones table (permanent, PII anonymized at 2y)  │
│     - Reconciliation job detects missing tombstones              │
└─────────────────────────────────────────────────────────────────┘
```

### Alternatives Rejected

| Alternative | Rejected Because |
|-------------|-----------------|
| TenantReaper as API-side service | Violates Four Planes. API becomes shadow control plane. Circuit breakers in wrong process. PG as hand-rolled work queue reimplements K8s primitives. Dual source of truth. |
| DeletionRequest CRD | YAGNI for pre-release. `MaxConcurrentReconciles` + API intent is sufficient. Can be added later if bulk orchestration needs grow. |
| Annotation-based circuit breaker | Secondary control channel. Stale annotations create persistent lies. Controller behavior must depend on observed reality, not external annotations. |
| Per-step deletion conditions | Ephemeral on dying objects. Metrics are the correct observability vehicle. |
| Separate `/admin/` namespace | Fragments API surface. RBAC handles authorization, not URL structure. |

### Trade-offs Accepted

1. `MaxConcurrentReconciles=5` throttles ALL tenant reconciles, not just deletions. New tenant provisioning is slowed during bulk delete. **Acceptable for pre-release.** If this becomes a problem post-release, separate deletion into a dedicated controller.
2. Grace expiry goroutine adds a background process to the API. Requires leader election and heartbeat monitoring. **Acceptable — follows BuildReaper pattern.**
3. Circuit breakers in provisioner clients add complexity to 4 packages. **Worth it — benefits all controller paths, not just deletion.**
4. Tombstone delivery is not guaranteed if controller callback fails. **Mitigated by reconciliation job that detects missing tombstones.**

### Risks Accepted

| Severity | Risk | Mitigation | Owner |
|----------|------|------------|-------|
| HIGH | `MaxConcurrentReconciles=5` blocks provisioning during bulk delete | Document trade-off. Monitor `tenant_provisioning_queue_depth`. Post-release: split into dedicated deletion controller if needed. | Operator Engineer |
| HIGH | Tombstone callback failure leaves no audit record | Reconciliation job compares `tenants_pending_deletion` against K8s state. Runs every 5 minutes. | API Engineer |
| MEDIUM | Circuit breaker defaults (5 failures, 120s cooldown) are guesses | Start conservative. Add `loopzero_tenant_cb_state{dep}` gauge. Tune based on production data. | Operator Engineer |
| MEDIUM | Grace expiry goroutine silent crash | Heartbeat metric + PrometheusRule (`stale >120s`). Copy `LoopZeroReconcileLoopStale` pattern. | API Engineer |
| LOW | Dual leader election (PG for grace goroutine, K8s Lease for controller) | Independent concerns. PG leader owns intent processing. K8s leader owns reconciliation. No interaction needed. | N/A |

### Risks NOT Accepted (Blockers)

| Severity | Risk | Required Action |
|----------|------|-----------------|
| **CRITICAL** | No platform-admin auth mechanism (Security VETO) | Implement `LOOPZERO_ADMIN_API_KEY` with dual-key rotation before any destructive endpoint ships |
| **CRITICAL** | Bulk-delete without cryptographic confirmation (Security VETO) | Two-step HMAC-SHA256 confirmation, 5min TTL, single-use, scope-bound |
| **CRITICAL** | Deletion callback without authentication (Security VETO) | Authenticate with `X-Service-Auth` using existing `ServiceAuthSecret` pattern |
| **CRITICAL** | `DeleteApplications` NotFound not handled (SRE finding) | Add `errors.IsNotFound(err)` guard. Fix as literal first commit. |
| **HIGH** | IDOR on `DELETE /api/v1/tenants/:id` | Enforce `uc.TenantID == :id` for non-admin callers |
| **HIGH** | No idempotency on mutating endpoints | DELETE naturally idempotent. Restore + bulk-delete require Idempotency-Key. |

### Mandatory Actions

1. **Fix `DeleteApplications` NotFound handling** — 3-line fix in `argocd/real_provisioner.go`. Ship independently before any architectural work.
2. **Implement `LOOPZERO_ADMIN_API_KEY` middleware** — dual-key rotation, applied to force-delete, bulk-delete, restore admin ops.
3. **Set `MaxConcurrentReconciles=5`** for TenantController (configurable via env var).
4. **Replace fixed 5s requeue with exponential backoff** — 5s base, 5min cap, tracked via annotation `loopzero.io/deletion-retry-count`. Max 10 attempts → emit alert, stop requeuing.
5. **Add circuit breakers to provisioner HTTP clients** — `gitea.RealProvisioner`, `argocd.RealProvisioner`, `harbor.Client`, `minio.AdminProvisioner`. Extract generic circuit breaker from existing `pg_circuit_breaker.go` pattern.
6. **Implement `DELETE /api/v1/tenants/:id`** — writes to `tenants_pending_deletion`, sets annotation, returns 202 with defined schema. `?force=true` for immediate (admin only).
7. **Implement `POST /api/v1/tenants/:id/restore`** — cancels within grace window. Idempotency-Key required.
8. **Implement `POST /api/v1/tenants/bulk-delete`** — under `/api/v1/`, admin RBAC, two-step HMAC confirmation, max batch 50.
9. **Grace expiry goroutine** — leader-elected (PG advisory lock), polls every 30s, heartbeat metric, calls `kubectl delete tenant` for expired grace periods.
10. **Tombstone table + reconciliation job** — `tenant_tombstones` with PII anonymization at 2 years. Reconciliation job every 5 minutes compares PG pending vs K8s state.
11. **Per-step deletion metrics** — `tenant_deletion_step_duration_seconds{step,tenant,result}`, `tenant_deletion_stuck_total{step}`. No conditions on the CR.
12. **PrometheusRules** — 10 rules covering all failure modes (see SRE analysis table). Not 3, all 10.
13. **Define LoopZeroError codes** — `TENANT_NOT_FOUND`, `TENANT_DELETION_PENDING`, `GRACE_PERIOD_EXPIRED`, `NO_PENDING_DELETION`, `INVALID_SELECTOR`, `FORBIDDEN`.
14. **202 response schema** — `{ deletion_id, tenant_id, grace_until, status, requested_at }`. Stability contract per spec §0.3.
15. **Augment `GET /api/v1/tenants/:id`** with `deletion` object when tenant is pending deletion.
16. **IDOR protection** — enforce `uc.TenantID == :id` for non-admin callers on DELETE endpoint.
17. **Audit events** — `tenant.deletion_requested`, `tenant.deletion_cancelled`, `tenant.deletion_started`, `tenant.deletion_step_completed`, `tenant.deletion_completed`, `tenant.deletion_failed`, `tenant.force_deleted`, `tenant.bulk_delete_requested`, `tenant.bulk_delete_executed`.
18. **Authenticate deletion callback** — `POST /internal/tenants/:id/deletion-complete` with `X-Service-Auth`.
19. **Update `docs/plans/tenant-lifecycle-deletion.md`** to reflect approved architecture (controller-native, not TenantReaper). Must happen before implementation.
20. **Document Phase 0 as temporary** — deprecated upon Phase 1 delivery.
21. **Add `PendingDeletion` state to tenant state machine** — `Active → PendingDeletion → Deleting`. `PendingDeletion` is the grace period state. Requires spec §5 update.

### Open Decisions Resolved

| # | Question | Decision | Rationale |
|---|----------|----------|-----------|
| 1 | Grace period default | 24h self-service, 0 for force/admin | Industry standard. Configurable per plan in future. |
| 2 | GDPR tombstone anonymization | Hash `requested_by` after 2 years. Add `anonymized_at` column. | Tombstone record never deleted (audit). PII within it is anonymized. |
| 3 | TenantReaper deployment | **REJECTED as separate service.** Grace expiry goroutine runs in API process (leader-elected). Controller handles cleanup natively. | Four Planes architecture. Controller-native is correct. |
| 4 | Bulk evict authn/authz | `LOOPZERO_ADMIN_API_KEY` with dual-key rotation | No current RBAC role covers cross-tenant operations. API key is simplest secure mechanism for pre-release. |
| 5 | Worker pool size | N/A — replaced by `MaxConcurrentReconciles=5` (configurable) | Kubernetes-native backpressure. No custom worker pool needed. |
