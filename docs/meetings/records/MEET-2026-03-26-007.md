## Contexto

O pipeline de build Argo Workflows usa um sidecar pattern para BuildKit: buildkitd daemon (sidecar com Daemon=true) + buildctl client (main container). Quando o build sucede e buildctl sai com exit 0, Argo mata o sidecar via SIGTERM. RootlessKit (wrapper do buildkitd) retorna exit code 1 no SIGTERM. Argo atribui esse exit code ao template e marca como Failed — mesmo com imagem construida e pushed com sucesso ao registry DO.

A API tem `allMainContainersSucceeded()` em `workflow_submitter.go:172` que detecta e corrige false failures no reconcile loop. Mas:
1. Argo retries 3x antes de declarar Failed (~6 min desperdicio)
2. Usuario ve status FAILED temporariamente
3. Metricas `loopzero_builds_total{status="failed"}` infladas
4. `allMainContainersSucceeded` e heuristica fragil sobre estrutura nao-tipada do Argo

## Decisao

**Adotar Proposta A — Single Container Pattern.**

Eliminar o sidecar. Rodar buildkitd + buildctl no mesmo container usando `rootlesskit sh -c <entrypoint-script> -- buildctl <args>`.

### Propostas Rejeitadas

| Proposta | Motivo da Rejeicao |
|----------|-------------------|
| **(B) ContainerSet** | forge SDK `ContainerNode` nao tem SecurityContext, per-container VolumeMounts, Daemon flag, Annotations. Seria necessario deformar o SDK para um caso de uso que ContainerSet nao suporta nativamente (daemon de longa duracao). Viola KISS e YAGNI. |
| **(C) preStop Hook** | Nao resolve a causa raiz. RootlessKit e PID 1 do container — preStop nao controla seu exit code. Mascarar sintoma sem beneficio arquitetural. |

### Trade-offs Aceitos

1. **Escopo de seccomp/AppArmor expandido.** No sidecar pattern, apenas buildkitd tinha Unconfined. No single container, buildctl tambem roda com Unconfined. Aceito porque: args do buildctl nao sao user-injectable, rootlesskit user namespace provê containment equivalente, NetworkPolicy restringe egress.
2. **Script de entrypoint como single point of failure.** Bug no script = 100% build failure. Aceito porque: mitigado por 12 testes unitarios + validacao DOKS + retry strategy funcional para falhas reais.
3. **Recursos combinados em um container.** buildkitd + buildctl compartilham limites. Aceito porque: buildctl e lightweight (gRPC client), buildkitd domina o uso de recursos. Limites do single container = limites do buildkitd anterior.

### Riscos Aceitos

| Risco | Severidade | Mitigacao | Owner |
|-------|-----------|-----------|-------|
| Exit code masking no script | CRITICAL | `set -e`, captura explicita de `$?`, teste de propagacao | API Engineer |
| Buildkitd fail-to-start causa hang | CRITICAL | Timeout 60s no wait loop, teste de timeout | API Engineer |
| Zombie buildkitd process | HIGH | `trap 'kill $PID' EXIT` no script, teste de cleanup | API Engineer |
| Seccomp/AppArmor no container errado | HIGH | PodSpecPatch target `main`, teste unitario + DOKS validation | API Engineer |
| Resource limits insuficientes | HIGH | Limits >= buildkitd anterior (2000m/4Gi), teste unitario | API Engineer |

### Riscos NAO Aceitos (Blockers)

| Risco | Condicao para Desbloqueio |
|-------|---------------------------|
| Image tag mutavel (`v0.18.2-rootless` sem digest) | Pinar por digest antes de production: `moby/buildkit:v0.18.2-rootless@sha256:<digest>` |
| Validacao apenas local (k3d) | Build real DEVE completar com sucesso no DOKS antes de merge |

## Acoes Obrigatorias

1. Implementar `buildkitEntrypointScript()` com: buildkitd background, wait-for-socket com timeout 60s, `"$@"` para buildctl, `trap` para cleanup, `set -e`, exit code propagation
2. Remover `Sidecars` de ambos `buildkitTemplateForApp` e `buildkitTemplateFromPlan`
3. Mudar image para `moby/buildkit:v0.18.2-rootless`
4. Command: `["rootlesskit", "sh", "-c", script, "--"]`, Args: `["buildctl", ...buildctlArgs]`
5. Remover volume `buildkit-socket` de `buildVolumes()` e dos VolumeMounts
6. PodSpecPatch seccomp target `main` (nao sidecar name)
7. AppArmor annotation target `main` (nao sidecar name)
8. Resources: requests 500m/512Mi, limits 2000m/4Gi
9. Manter `allMainContainersSucceeded()` permanentemente com comment atualizado. Adicionar log.Info quando fires.
10. Pinar image por digest antes de production
11. Validar build completo no DOKS
12. Atualizar 16 testes existentes + escrever 12 novos testes
