## Reason for Reassessment

The orchestrator identified three errors in MEET-047:

1. **Tenant isolation was treated as a future requirement.** At 100k tenants with YAGNI suspended, it is a present requirement. Security's CRITICAL finding was registered but not weighted in the decision.
2. **Harbor's operational cost was overestimated.** Minimal deployment is 6-7 pods (not 15-20). Online GC in 2.9+ removes the blocking concern.
3. **The cost of building tenant isolation on zot was underestimated.** 2-3 sprints of custom security-critical code that violates the "Don't Reinvent the Wheel" principle.

## Stage 2 — Agent Re-Assessments

### SRE — VETO LIFTED

Previous position: Vetoed Harbor (15-20 pods, GC blocking).
New position: **Approves Harbor with conditions.**

Key quote: "6-7 pods using existing managed PG is incremental. LoopZero already runs 40+ pods across 3 clusters. The SRE calculation is simple: which option generates fewer pages? Harbor with conditions wins."

Conditions: Minimal deployment only (no Trivy/Notary/Portal), separate PG database, synthetic health probe (push+pull every 60s), GC monitored, rollback plan documented, resource limits on all pods, staging-first for upgrades.

### Security — HARBOR RECOMMENDED

Previous position: Recommended R2 for bucket-scoped keys. Flagged tenant isolation as CRITICAL.
New position: **Recommends Harbor. VETO on any solution without per-tenant image access enforcement.**

Key quote: "Custom authz proxy is exactly the category where 'don't reinvent the wheel' applies most strongly. Custom authz proxies are where vulnerabilities live."

Conditions: One Harbor project per tenant, robot account TTL ≤ 24h with automatic rotation, build pods get tenant-scoped push/pull token, workload pods get tenant-scoped pull-only token, Harbor admin API restricted via NetworkPolicy, audit log to Loki, disable unused features.

### Distributed Systems — MAINTAINS HARBOR

Previous position: Recommended Harbor, filed dissent against zot.
New position: **Withdraws dissent, formally recommends Harbor.**

Key quote: "PG-based metadata with online GC provides deterministic convergence. zot requires building 2-3 sprints of infrastructure without convergence proof."

Conditions: Harbor PG pool capped at 10 connections, liveness probe on jobservice with 30s timeout, `pg_stat_activity` alert if combined connections exceed 80% of managed PG limit, blob storage on DO Spaces.

New risk identified: **PG connection pool exhaustion.** If Harbor exhausts the connection pool, LoopZero's `withEnvironmentLock` fails to acquire connections, causing 5s timeouts on ALL deploys. Unbounded blast radius. **Mandatory mitigation: cap Harbor pool at 10 connections.**

### Production Design — MAINTAINS ZOT (MINORITY)

Previous position: Recommended zot + Spegel.
New position: **Maintains zot recommendation but acknowledges Harbor is "legitimate at 100k."**

Key quote: "Harbor's PG dependency creates an irrecoverable failure domain. zot's BoltDB is reconstructible from S3 by design. Eliminating a failure domain is worth more than native multi-tenancy features."

Counter-position accepted: Acknowledges tenant isolation must be mandatory (upgrades from "nice to have" to "required before 100k"). Proposes phased approach: zot now, auth proxy at Phase 2, Harbor at Phase 3 if needed.

## Stage 3 — Technical Confrontation

### Confrontation 1: Tenant isolation — present or future?

| Agent | Position |
|-------|----------|
| Security | PRESENT. "The moment you accept Tenant B's money, you have an implicit contract." VETO without isolation. |
| SRE | PRESENT. "Custom isolation code is code I page for at 3 AM." |
| Distributed Systems | PRESENT. "Every line of custom auth code is a line without convergence proof." |
| Production Design | Future (phased). "Build auth proxy at Phase 2, before Team tier." |

**Resolution:** PRESENT. 3-1 consensus. Security VETO is absolute. Building custom tenant isolation on zot violates "Don't Reinvent the Wheel" (Princípio Inquebável #9) in a security-critical context. Harbor resolves this natively.

### Confrontation 2: PG as failure domain

| Agent | Position |
|-------|----------|
| Production Design | Harbor PG corruption = irrecoverable without PITR. zot BoltDB = reconstructible from S3. |
| Distributed Systems | Managed PG failover is seconds. zot BoltDB rescan of 150 TB is hours. |
| SRE | PG backup is operational standard. Rollback plan: PG snapshot + S3 versioning. |

**Resolution:** Distributed Systems and SRE prevail. DO managed PG has automated failover + daily backups + PITR. Harbor PG recovery (failover: seconds, PITR: minutes) is faster than zot BoltDB rescan (hours at 150 TB). Production Design concern is valid in loopzerory but weaker in practice with managed PG.

### Confrontation 3: Perpetual operational cost

| Agent | Position |
|-------|----------|
| Production Design | 6-7 pods + PG dependency + upgrade cycles = perpetual tax. |
| SRE | "6-7 managed pods with battle-tested tenant isolation vs 2-3 sprints of custom isolation code I maintain indefinitely." |

**Resolution:** SRE prevails. Both options have perpetual cost. Harbor's perpetual cost is operational (monitor, upgrade, maintain 6-7 pods). zot's perpetual cost is engineering (maintain custom auth proxy, credential controller, quota enforcement, audit, retention). For a small team, operational cost of a proven system is preferable to engineering cost of a custom system.

### Orchestrator Challenge to New Consensus

Three risks in the new consensus:
1. **PG connection pool exhaustion** — Harbor + LoopZero share managed PG instance. If Harbor exhausts pool, all deploys fail. Mitigated by cap at 10 connections + monitoring. MANDATORY.
2. **Harbor upgrade complexity** — historical destructive migrations. Mitigated by staging-first. MANDATORY.
3. **Harbor long-term dependency** — CNCF graduated, 300+ contributors, low risk. Mitigated by OCI compliance (images portable).

None sufficient to reverse the consensus.

## Stage 4 — Decision

**Chosen:** Harbor (minimal deployment) + DO Spaces as storage backend

**Supersedes:** MEET-2026-04-11-047 decision (zot + Spaces is revoked)

### Justification for Reversal

1. **Tenant isolation is a present requirement.** Security VETO is absolute. Building isolation on zot = reinventing the wheel in a security-critical context (violates Princípio #9). Harbor resolves natively.
2. **Harbor operational cost was overestimated in MEET-047.** 6-7 pods (not 15-20), online GC (not stop-the-world), existing PG (not new). Delta: ~5 additional pods, ~3.5 GB additional RAM.
3. **zot engineering cost was underestimated in MEET-047.** 2-3 sprints of custom security-critical code maintained indefinitely > operational cost of proven system.

### Alternatives Rejected

| Alternative | Reason |
|-------------|--------|
| zot + Spaces (MEET-047 decision) | Security VETO: no native tenant isolation. Building equivalent = 2-3 sprints custom security code, violates "Don't Reinvent the Wheel" |
| zot + Spaces + custom auth proxy | Same engineering cost as Harbor, without maturity. "Custom authz proxies are where vulnerabilities live" |
| Cloudflare R2 + any registry | SRE VETO from MEET-047 stands: correlated blast radius with CF Tunnel |
| DO Container Registry | 100 GB cap. Mathematically infeasible. |

### Trade-offs Accepted

1. PG as failure domain for registry — DO managed PG has automated failover + backups
2. 6-7 additional pods in mgmt cluster — incremental, not transformative
3. Harbor upgrade complexity — staging-first mandatory
4. Online GC unproven at 1M images — PG-based mark is O(n) rows, monitoring + off-peak scheduling

### Risks Accepted

| Risk | Severity | Mitigation | Owner |
|------|----------|------------|-------|
| PG connection pool exhaustion | HIGH | Cap Harbor PG pool at 10 connections. Alert on `pg_stat_activity` >80% | Infra Engineer |
| Harbor upgrade destructive | MEDIUM | Staging-first mandatory. Rollback: PG snapshot + S3 versioning | Infra Engineer |
| Online GC slow at 1M images | MEDIUM | GC scheduled off-peak. Monitor: duration, blobs deleted, errors | Infra Engineer |
| Harbor project changes direction | LOW | CNCF graduated, 300+ contributors. OCI compliance = images portable | — |

### Risks NOT Accepted (Blockers — maintained from MEET-047)

| Risk | Condition to Lift |
|------|-------------------|
| DO Spaces account-scoped keys | Validate bucket-scoped keys OR separate DO account |
| DO API Token as registry auth | Eliminate — dedicated credential only |
| Zero registry monitoring | Deploy monitoring package BEFORE migration |
| No dual-push during migration | Dual-push mandatory with rollback test |

### Mandatory Actions

1. **[GATE] Validate DO Spaces bucket-scoped access keys** — if unavailable, create separate DO account
2. **[GATE] Eliminate DO API Token as registry auth** — pre-existing CRITICAL finding
3. Deploy Harbor minimal: core×2, registry×2, jobservice×1, Redis×1. Trivy/Notary/Chartmuseum/Portal DISABLED
4. Separate PG database (`harbor_db`) on existing managed instance. Connection pool capped at 10
5. One Harbor project per tenant. Robot accounts scoped per project, TTL ≤ 24h, automatic rotation by TenantController
6. Workload pods receive pull-only token scoped to tenant project
7. Harbor admin API restricted via NetworkPolicy to operator namespace
8. Audit log enabled, forwarded to Loki
9. Registry monitoring package before migration (canary push/pull 60s, alerts, dashboard, `pg_stat_activity`)
10. Dual-push during migration + rollback tested (PG snapshot + S3 versioning)
11. Migration runbook + rollback runbook
12. Immutable tags per project
13. Spegel P2P cache on workload cluster (Phase 2, before 10k apps)
14. VAP admission policy updated + migrate Audit → Deny
15. ADR: `docs/adr/ADR-XXX-registry-migration-harbor-spaces.md`
16. Staging-first for every Harbor upgrade
17. Liveness probe on jobservice with 30s timeout
