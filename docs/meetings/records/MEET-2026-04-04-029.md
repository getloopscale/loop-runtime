## Stage 2 — Analyses

### Principal Architect

**Assessment:** The async release activation model (MEET-015) is architecturally sound — three independent activation paths (callback, convergence loop, reaper) provide defense-in-depth. The problem is NOT the architecture; it is incomplete implementation of the architecture. All three paths have defects that prevent them from functioning.

**Risks identified:**
1. **All three activation paths are broken simultaneously** — callback returns 401, convergence loop may not run (leader election), reaper timeout is a race with convergence loop at identical 5min thresholds
2. **No single fix resolves the issue** — it requires fixing all three paths
3. **The system has no visibility into WHY a release failed** — SYNC_FAILED is the terminal state whether the cause was auth failure, timeout, or genuine health problem

**Objections:**
- The convergence loop SyncTimeout (300s) and reaper PendingTimeout (5min/300s) are identical. This means they race to fail the release. The reaper should be strictly AFTER the convergence loop has given up.

**Recommendation:** Fix in priority order: RC-2 (callback auth) first (highest impact, lowest effort), then RC-5 (leader election), then RC-3 (timeout alignment), then the rest.

**Conditions for approval:**
- Each fix must have an independent test
- Timeout hierarchy must be documented: convergence SyncTimeout < reaper PendingTimeout, always

**Impact if ignored:** Every deploy on DigitalOcean has a high probability of failing with SYNC_FAILED, making the platform unusable for its core purpose.

### K8s Controller Engineer

**Assessment:** The TenantController creates ArgoCD Application CRs during tenant provisioning (`reconcileArgoCDApp` in `tenant_gitops.go`). The code is correct — it creates one Application per environment. However, there is a timing issue: the first deploy for a new project can arrive BEFORE the TenantController has finished reconciling the Tenant CR.

**Risks identified:**
1. **RC-1 (Application CR not yet created):** If the API receives a deploy before TenantController creates the ArgoCD Application, `TriggerSync` returns 404 (`argocd sync: application "tn-xxx-dev" not found`). The current code treats this as a fatal error and transitions to SYNC_FAILED immediately via `phaseEFinalize`.
2. **No readiness gate between tenant provisioning and first deploy:** The API does not verify that the ArgoCD Application exists before attempting to sync.

**Objections:**
- Adding a readiness check to the API (e.g., verify Application CR exists before TriggerSync) adds coupling between the API and operator planes. Prefer making the sync trigger failure recoverable instead.

**Recommendation:**
- Make 404 from TriggerSync a recoverable error (do NOT call phaseEFinalize). Let the release stay PENDING and let the convergence loop retry TriggerSync via `retriggerSyncIfNeeded`.
- This is a 5-line change in `container_delivery.go:106-116`.

**Conditions for approval:**
- Test: deploy for a tenant where ArgoCD Application does not yet exist should NOT result in SYNC_FAILED immediately
- The convergence loop retrigger must eventually succeed once the Application CR is created

**Impact if ignored:** First deploy for any new tenant/project will always fail with SYNC_FAILED on production.

### Distributed Systems Engineer

**Assessment:** The leader election mechanism is fundamentally flawed. The code uses `pg_try_advisory_lock` (session-scoped) on a connection acquired from a pool. While the code correctly uses `pool.Acquire()` to hold a dedicated connection, the comment at line 473 acknowledges the fragility. More critically, the observed behavior — "both API pods logged 'another instance holds the leader lock'" — means NEITHER pod acquired the lock, so ALL background loops (convergence, reaper, reconcile) were NOT running.

**Risks identified:**
1. **RC-5 (Leader election total failure):** If both pods fail to acquire the lock, zero background loops run. PENDING releases have no convergence mechanism. They will sit in PENDING until the reaper runs — but the reaper is also a background loop that requires the leader.
2. **Race condition between convergence loop and reaper:** Both use `created_at` to determine timeout. Both have 300s/5min thresholds. The reaper runs every 30s, the convergence loop every 10s. There is no ordering guarantee — the reaper might reap a release that the convergence loop is actively verifying.
3. **`pg_try_advisory_lock` vs `pg_advisory_xact_lock`:** The leader lock uses SESSION-scoped advisory lock (Rule 7 says never use session-scoped). While the code intentionally uses session-scope here (to persist across transactions), it violates the project's own rule. The risk is that if the connection is dropped and re-established by pgx, the lock is silently lost.

**Objections:**
- The "both pods see false" scenario suggests a pgx connection pool behavior issue. When `pool.Acquire()` returns a connection that already holds the lock from a previous process (connection reuse), `pg_try_advisory_lock` returns false for the new process because the lock is already held on that connection by the previous session. This is a pgx connection reuse bug.
- Session-scoped locks are correct for leader election (they must survive transactions), but the connection must be verified as "fresh" (not reused from a pool with a stale lock).

**Recommendation:**
1. Add `pool.Config().AfterConnect` hook to release any stale advisory locks on new connections
2. After `pg_try_advisory_lock`, verify with `SELECT pg_advisory_unlock($1)` + re-acquire if the lock was stale
3. Add a heartbeat: periodically verify the lock is still held (`SELECT pg_try_advisory_lock($1)` returns true for the holder)
4. Increase reaper PendingTimeout to 600s (10min) to create a clear separation from convergence loop SyncTimeout (300s)

**Conditions for approval:**
- Leader election must have a health check endpoint that reports whether this instance is the leader
- If leader lock is lost, the instance must either re-acquire or crash (fail loud)

**Impact if ignored:** Background loops silently stop running, PENDING releases accumulate indefinitely with no visibility.

### SRE/Production Engineer

**Assessment:** The operational impact is severe. SYNC_FAILED is the most common deploy failure mode and has no automated recovery. The user sees "sync_failed" and has no recourse except `loopzero deploy` again (which may hit the same bug). The timeout configuration is the most immediately dangerous issue.

**Risks identified:**
1. **RC-3 (Timeout race):** Convergence loop SyncTimeout (300s) equals reaper PendingTimeout (300s from `statemachine.ReleasePendingTimeout = 5 * time.Minute`). Wait — actually the statemachine defines `ReleasePendingTimeout = 5 * time.Minute` and the convergence loop config uses `SyncTimeout: 300 * time.Second` (5min). These are IDENTICAL. The reaper runs every 30s and the convergence loop runs every 10s. Whichever fires first wins. If the reaper fires first, it transitions to SYNC_FAILED even if the convergence loop was about to activate the release.
2. **No structured error context:** When a release transitions to SYNC_FAILED, the reason is either "Sync timeout: service did not become healthy within the time limit" (convergence loop) or "Release timed out waiting for sync to complete (2 min limit)" (reaper, but the message says 2min despite the actual timeout being 5min — **stale error message**).
3. **`releaseReaperReason` returns hardcoded "2 min limit"** at line 128 of `release_reaper.go`, but the actual `ReleasePendingTimeout` is 5 minutes. This misleading message was never updated when the timeout was changed.

**Objections:**
- **SRE VETO on current timeout configuration.** The convergence loop and reaper MUST have different timeout thresholds. The reaper must be the LAST resort, with a timeout strictly greater than the convergence loop. Proposed: convergence SyncTimeout = 300s, reaper PendingTimeout = 600s.

**Recommendation:**
1. Fix the stale error message in `releaseReaperReason` (line 128)
2. Change `ReleasePendingTimeout` to 10 minutes (600s) — double the convergence SyncTimeout
3. Add a `/healthz/leader` endpoint that reports leader status
4. Add a Prometheus metric `loopzero_api_leader_status` (gauge, 0 or 1)

**Conditions for approval:**
- Timeout hierarchy documented and enforced: convergence SyncTimeout (300s) < reaper PendingTimeout (600s)
- Leader status must be observable via metrics and health endpoint
- Error messages must reflect actual configured timeouts, not hardcoded strings

**Impact if ignored:** Deploys will continue to fail unpredictably. Operators cannot diagnose root cause from logs because error messages are wrong.

### GitOps/Delivery Engineer

**Assessment:** RC-2 (ArgoCD Notifications callback returning 401) is the highest-impact, lowest-effort fix. The root cause is definitively identified by code inspection:

The ArgoCD Notifications webhook configuration (`infra/helm/argocd/values.yaml:148-152` and `infra/pulumi/src/components/mgmt-bootstrap.ts:255-258`) sends requests with only a `Content-Type: application/json` header. It does NOT include an `Authorization: Bearer <secret>` header.

The API handler (`api/internal/routes/argocd_callback.go:57-63`) validates `Authorization: Bearer <secret>` using `LOOPZERO_ARGO_CALLBACK_SECRET` (default: `loopzero-dev-callback-secret`, production: `cb-loopzero-dev-2026` per `mgmt-bootstrap.ts:848`).

**Result:** Every callback from ArgoCD is rejected with 401. The fast activation path (seconds instead of minutes) has NEVER worked on production. All activations have been handled by the convergence loop (10s poll) or the reaper timeout.

**Risks identified:**
1. **RC-2 is a configuration bug, not a code bug.** The fix is adding the `Authorization` header to the ArgoCD Notifications webhook service configuration.
2. **The callback secret value must match between Helm/Pulumi config and the API env var.** Currently the Pulumi config sets `LOOPZERO_ARGO_CALLBACK_SECRET: "cb-loopzero-dev-2026"` but the webhook has no auth header at all.

**Objections:** None. This is an unambiguous bug.

**Recommendation:**
Fix the webhook service configuration in both locations:
1. `infra/helm/argocd/values.yaml` — add `Authorization: Bearer <secret>` header
2. `infra/pulumi/src/components/mgmt-bootstrap.ts` — add matching header

The secret should reference the same value as `LOOPZERO_ARGO_CALLBACK_SECRET`.

**Conditions for approval:**
- After fix, deploy a test project and verify the callback is received with 200 (not 401) in API logs
- Verify the release is activated via callback path (log message: "sync callback: releases activated")

**Impact if ignored:** The fast activation path remains permanently broken. All deploys take 10-300s longer than necessary, and the system relies entirely on the convergence loop (which itself depends on leader election working).

If all 3 retriggers fail with 404, the convergence SyncTimeout (300s) will eventually fail the release with a clear message: "Application not found — tenant provisioning may not be complete."

### Conflict 2: Leader election — fix or replace?

| Agent | Position |
|-------|----------|
| Distributed Systems Engineer | Replace with proper mechanism: Kubernetes Lease-based leader election or a heartbeat loop that re-acquires lost locks. |
| Principal Architect | Fix the current mechanism. Pre-release, but adding k8s Lease dependency is scope creep. The pgx pool.Acquire() approach is sound if we add stale lock detection. |
| SRE | Fix current + add observability (metric + health endpoint). Replace in Sprint 7 if needed. |

| GitOps Engineer | Agrees. The reaper should only fire when everything else has failed. |

**Resolution:** CONSENSUS. Change `ReleasePendingTimeout` from 5min to 10min (600s). Update `pkg/statemachine/release.go`. This creates a clear hierarchy: convergence loop gives up at 300s, reaper cleans up at 600s. The reaper is the safety net for the safety net.

### Consensus Challenge (Orchestrator)

All agents agree on the overall approach. Challenging the consensus: **What could go wrong?**

1. **Fix ordering risk:** If we fix the callback auth (RC-2) but NOT the leader election (RC-5), we still depend on the callback handler running (which it does — it is an HTTP handler, not a background loop, so it works regardless of leader status). This is actually fine — RC-2 fix is independent of RC-5.

2. **Convergence loop revision check:** The convergence loop (`checkSync`) does NOT verify the git revision matches the release's GitCommit. It only checks `synced + healthy`. This means if two rapid deploys occur, the convergence loop might activate Release A when ArgoCD has actually synced Release B's manifests. The callback activator has revision verification (line 109 of `sync_callback_activator.go`), but the convergence loop does not.

**This is a NEW issue (RC-7)** not previously identified. The convergence loop should verify `app.Status.Sync.Revision == release.GitCommit` before activating.

| Agent | Position on RC-7 |
|-------|----------|
| Distributed Systems Engineer | Critical. Without revision check, rapid sequential deploys can activate the wrong release. |
| Principal Architect | Agrees. Must be included in this fix batch. |
| GitOps Engineer | The callback path already has this check. Convergence loop must match. |

**Resolution:** Add revision verification to the convergence loop's `verifyRelease` method. If the synced revision does not match `release.GitCommit`, do NOT activate. Log a warning. This prevents wrong-version activation on rapid sequential deploys.

## Appendix A — Root Cause Evidence

### RC-2 Evidence (Callback Auth)

ArgoCD Notifications webhook config (`infra/helm/argocd/values.yaml:148-151`):
```yaml
headers:
- name: Content-Type
  value: application/json
# NOTE: No Authorization header — this is the bug
```

API handler expects (`api/internal/routes/argocd_callback.go:57-63`):
```go
if h.secret != "" {
    auth := r.Header.Get("Authorization")
    if !strings.HasPrefix(auth, "Bearer ") || ... {
        h.logger.Warn("argocd callback: unauthorized request")
        w.WriteHeader(http.StatusUnauthorized)
        return
    }
}
```

**Fix:** Add to webhook headers:
```yaml
- name: Authorization
  value: "Bearer cb-loopzero-dev-2026"
```

### RC-3 Evidence (Timeout Race)

- `pkg/statemachine/release.go:14`: `ReleasePendingTimeout = 5 * time.Minute`
- `api/cmd/main.go:448`: convergence `SyncTimeout: 300 * time.Second` (5min)
- Both = 300 seconds. Race condition.
- `release_reaper.go:128`: says "2 min limit" but actual timeout is 5 minutes.

### RC-5 Evidence (Leader Election)

- `api/cmd/main.go:492`: `pg_try_advisory_lock` on pooled connection
- Production logs: both pods logged "another API instance holds the leader lock"
- Result: zero background loops running, all PENDING releases stuck

### RC-7 Evidence (New — Convergence Loop Missing Revision Check)

- `sync_callback_activator.go:108-114`: HAS revision check (`release.GitCommit != revision`)
- `release_convergence_loop.go:229`: activates on `synced + healthy` only, NO revision check
- Risk: rapid sequential deploys can activate wrong release version via convergence path
