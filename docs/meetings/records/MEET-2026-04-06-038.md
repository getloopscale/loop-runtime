## Stage 1 — Context

**Problem:** The LoopZero platform has ~70% of Stripe billing code written and tested in isolation but only ~30% wired to the runtime cloud service. This is the classic "Implemented but not wired" pattern documented in CLAUDE.md. The cloud service `main.go` has zero references to billing, enforcement, or metering packages. The CLI `billing` command exists but is not registered in the CLI program. The dashboard has a billing page with hard-coded limits.

**Decision Required:** A phased execution plan with concrete Definition of Done for each phase, ordering, risk assessment, and clear ownership.

**Constraints:**
- Pre-release (can break things, prefer clean design over backward compatibility)
- Stripe test-mode keys available in Pulumi config
- Cloud service is Go + chi, no database connection yet (auth-only service today)
- TDD required (Rule 1)
- No internal terms in user-facing output (Rule 3 — "Stripe", "subscription", "webhook" must never appear in CLI/dashboard error messages)
- Cloud service currently has no `*sql.DB` — adding one is a prerequisite

**Known Context:**
- `cloud/internal/billing/stripe.go` — StripeClient (tested)
- `cloud/internal/billing/webhook.go` — WebhookHandler with HMAC-SHA256 (tested)
- `cloud/internal/routes/billing.go` — BillingHandler (tested)
- `cloud/internal/enforcement/limiter.go` — PlanLimiter (tested)
- `cloud/internal/enforcement/middleware.go` — 402 middleware (tested)
- `cloud/internal/metering/tracker.go` — usage tracker (tested)
- `cloud/internal/metering/reporter.go` — Stripe usage reporter (tested)
- `cloud/internal/metering/reconciler.go` — drift reconciler (tested)
- `api/internal/db/migrations/000013_billing_tables.up.sql` — schema exists
- `cloud/dashboard/src/pages/billing.tsx` — UI exists with hard-coded limits
- `cli/src/commands/billing.ts` — BillingCommand class exists, NOT registered in index.ts
- All existing tests use nil-DB pattern (graceful degradation)
- `cloud/cmd/main.go` has NO database connection, NO billing handler registration
- `cloud/internal/config/config.go` already has StripeAPIKey + StripeWebhookSecret fields

**Proposal:** Wire in 6 phases ordered by dependency: (1) DB connection in cloud service, (2) main.go route wiring, (3) Stripe customer creation on signup, (4) background job scheduler, (5) CLI wiring, (6) dashboard completion.

## Stage 2 — Analyses

### API/Domain Architect (Sponsor)

**Assessment:** The code quality is high — all packages follow clean separation (billing, enforcement, metering), have proper nil-DB guards, and are independently tested. The wiring gap is purely integration: `main.go` needs a DB connection and must instantiate + register handlers. The phase ordering should follow dependency: DB first (everything depends on it), then routes (unblocks CLI/dashboard), then signup flow, then background jobs.

**Risks identified:**
1. Adding `*sql.DB` to the cloud service creates a new operational dependency — the cloud service currently starts even without PostgreSQL
2. The `subscriptions` table references `tenants(id)` via FK — the cloud service's DB must be the SAME database as the API's, not a separate one
3. `BillingHandler.GetBilling` currently returns `PlanDisplayName(claims.TenantID)` which is wrong — it treats tenant ID as a plan name
4. The `Reporter.ReportPending` query joins `subscriptions` and `usage_records` — requires subscription to exist before usage can be reported to Stripe

**Objections:**
- Free tier (starter) should NOT create a Stripe subscription. Creating subscriptions for free users means Stripe API calls for every signup, $0 subscriptions cluttering the Stripe dashboard, and payment_behavior=default_incomplete will fail without a payment method. Free users should exist in our DB only.

**Recommendation:** 6 phases, DB-first. Free tier = DB-only, no Stripe subscription. Stripe customer creation deferred to first paid action (lazy creation).

**Conditions for approval:**
- Phase ordering must be strictly sequential (each phase's DoD gates the next)
- Free tier must not touch Stripe API
- Integration test with Stripe test keys required before production wiring

**Impact if ignored:** Dead code in production, billing page returns fake data, enforcement never activates.

### Principal Platform Architect

**Assessment:** The billing system architecture is sound — it follows the platform pattern of "code exists, needs wiring" that was already documented. The separation into billing/enforcement/metering packages is correct. However, there is a structural question: should the cloud service own its own DB connection or proxy through the engine API?

**Risks identified:**
1. Two services (API + cloud) sharing the same database creates coupling — if the API migrates schemas, the cloud service sees them immediately
2. The migration `000013` is in `api/internal/db/migrations/` — this means the API owns the schema, but the cloud service reads/writes it. This is acceptable in pre-release but should be tracked.
3. No circuit breaker or retry on Stripe API calls — `StripeClient.post()` fails hard on HTTP errors

**Objections:**
- The cloud service opening its own DB connection is acceptable for pre-release, but the migration ownership must remain with the API (single migration runner). The cloud service is a READ-HEAVY consumer + webhook writer.

**Recommendation:** Proceed with direct DB connection in cloud service. Document that API owns migrations. Add a health check that verifies DB connectivity.

**Conditions for approval:**
- Cloud service must use the same `DATABASE_URL` as the API
- Cloud service must NOT run migrations — only the API does
- DB health check must be added to `/health` endpoint

**Impact if ignored:** Schema drift, migration conflicts, cloud service silently fails with no DB.

### Platform Security Engineer (Challenger)

**Assessment:** Several security concerns with the current implementation:

**Risks identified:**
1. **Webhook endpoint MUST bypass JWT auth.** The current Traefik IngressRoute must ensure `/v1/webhooks/stripe` is publicly accessible. If JWT middleware is applied globally, Stripe cannot call us.
2. **Stripe webhook signature tolerance is 5 seconds** (`time.Since > 5*time.Second` in `VerifySignature`). This is extremely tight — Stripe documentation recommends 300 seconds (5 minutes). Network latency, clock skew, or Stripe retry delays will cause legitimate events to be rejected.
3. **`StripeAPIKey` is loaded from env but never validated on startup.** If empty in production, all Stripe calls fail silently with 401 errors. The `Validate()` function does not check Stripe keys.
4. **Webhook secret rotation:** No dual-secret support. Stripe sends events signed with the old secret during rotation. The current `VerifySignature` checks only one secret.
5. **`metadata[tenant_id]` in Stripe customer creation** — if a tenant ID is sensitive, it should not be stored in Stripe metadata where Stripe support can see it.

**Objections:**
- **VETO CONDITION:** The 5-second timestamp tolerance in `VerifySignature` MUST be increased to 300 seconds before any webhook is wired. This will cause production incidents.
- The `Validate()` function must require `StripeAPIKey` and `StripeWebhookSecret` in production.

**Recommendation:** Fix timestamp tolerance, add production validation for Stripe keys, document webhook routing requires auth bypass. Tenant ID in Stripe metadata is acceptable for pre-release (it is an internal identifier, not PII).

**Conditions for approval:**
- Timestamp tolerance increased from 5s to 300s (Stripe recommendation)
- `Config.Validate()` must require Stripe keys when `Environment == "prod"`
- Webhook route must be documented as auth-exempt
- Dual-secret support for rotation is P1 but does not block this phase

**Impact if ignored:** Legitimate Stripe webhooks rejected in production, subscription state never updates, billing is broken.

### SRE / Production Readiness Engineer

**Assessment:** The metering and reporting subsystem needs a background scheduler. The current code has `Reporter.ReportPending()` and `Reconciler.ReconcileBuilds()` but no runner.

**Risks identified:**
1. **No graceful shutdown for background goroutines.** If the cloud service adds ticker-based goroutines, they must respect context cancellation and the existing `signal.Notify` shutdown.
2. **Hourly reporter + weekly reconciler.** These are lightweight operations. A simple `time.Ticker` goroutine with context cancellation is sufficient. A full cron library (robfig/cron) is unnecessary complexity.
3. **No Prometheus metrics for billing operations.** Build count, billing API latency, webhook processing time, and enforcement rejections should be metered.
4. **Reporter uses `LIMIT 100` per run.** If drift causes 1000+ unreported records, it takes 10 hours to catch up. This should be configurable or run in a loop until drained.
5. **Dashboard hard-codes `limit: 100`** for all usage metrics. This creates a false ceiling display.

**Objections:**
- Background jobs must be wired into the existing graceful shutdown (context-based). No orphaned goroutines.
- Metrics can be P2 but must be on the backlog.

**Recommendation:** Use `time.Ticker` with context, not a cron library. Wire into existing shutdown. The reporter `LIMIT 100` is fine for initial wiring — the hourly cadence means it catches up over time.

**Conditions for approval:**
- Background goroutines must use `context.Context` with cancellation
- Graceful shutdown must wait for in-progress reporting to finish (bounded timeout)
- `/health` must reflect background job health (last-run timestamp or similar)

**Impact if ignored:** Orphaned goroutines on shutdown, usage data never reaches Stripe, billing is decorative.

### DX/Tooling Engineer

**Assessment:** The CLI `billing` command is well-implemented but completely disconnected. It exists at `cli/src/commands/billing.ts` but is not registered in `cli/src/index.ts`. The dashboard billing page works but shows hard-coded limits.

**Risks identified:**
1. **CLI `billing` not wired** — `loopzero billing` will show "unknown command". Users who discover billing through docs will hit a wall.
2. **Dashboard usage response shape mismatch** — The dashboard expects `usage: Record<string, number>` but `BillingHandler.GetBilling` returns `usage: {}` (empty). The dashboard code then maps `Object.entries(billing.usage)` which will render nothing.
3. **Dashboard hard-codes `limit: 100`** — Line 29 of billing.tsx: `limit: 100`. This should come from the API response (plan_limits table).
4. **No `loopzero billing upgrade` command** — Users on the free tier have no CLI path to upgrade. They must use the portal.
5. **Error messages are correct** — no internal terms detected in existing billing code. `FormatLimitError` says "Plan limit reached" which is clean.

**Objections:**
- **BLOCKS DELIVERY:** The API response shape for `/v1/billing` must include `limits` alongside `usage` so the dashboard can show accurate progress bars. Current shape is: `{plan, team, usage: {}, message}`. Required shape: `{plan, team, usage: {metric: {used, limit}}, message}`.

**Recommendation:** The `/v1/billing` response must be redesigned to include structured usage with limits. The dashboard should never hard-code limits.

**Conditions for approval:**
- `/v1/billing` response must include per-metric `{used, limit}` pairs
- CLI `billing` command must be registered in index.ts
- `loopzero billing portal` must open real Stripe portal URL (not placeholder)

**Impact if ignored:** Dashboard shows fake limits, CLI command unreachable, billing is a Potemkin village.

### Consensus Challenge (Orchestrator)

All agents agreed on most points. Challenging: **What are we not seeing?**

1. **Stripe API idempotency** — `CreateCustomer` and `CreateSubscription` are NOT idempotent. If the cloud service crashes between creating the Stripe customer and writing to the DB, we get an orphaned Stripe customer. Mitigation: use Stripe's `Idempotency-Key` header on all mutating API calls. This was NOT in the current `stripe.go`.

2. **Migration 000013 FK constraint** — `subscriptions.tenant_id REFERENCES tenants(id)` means we cannot insert a subscription for a Kratos user who does not yet have a tenant record in the API's `tenants` table. The signup flow must ensure the tenant exists before creating a subscription row. Currently LoopZero creates tenants via `loopzero init`, not on registration. This means the subscription row cannot be created until the user runs `loopzero init`.

3. **Clock skew in multi-cluster** — The webhook timestamp check relies on `time.Now()`. If the cloud service pod has clock skew relative to Stripe, events may be rejected even with 300s tolerance. Mitigation: NTP is standard on DO, 300s is generous. Acceptable risk.

**These findings are incorporated into the execution plan below.**

## Stage 4 — Decision

**Chosen:** 6-phase execution plan with strict phase gating. Each phase has a concrete Definition of Done that must be met before proceeding to the next phase.

**Rejected:**
1. *Single big-bang wiring PR* — Rejected because it would be too large to review, too risky to deploy, and violates TDD workflow.
2. *Proxy billing through engine API* — Rejected because it adds an unnecessary hop. The cloud service should talk to the DB directly for billing reads.
3. *robfig/cron for background jobs* — Rejected per YAGNI. Two ticker-based jobs do not justify a dependency.
4. *Stripe subscription for free tier* — Rejected per unanimous agreement. DB-only for starter plan.

**Trade-offs consciously accepted:**
- Two services (API + cloud) share the same PostgreSQL database. This is acceptable in pre-release. Migration ownership stays with the API.
- Eager Stripe customer creation on registration may create orphaned Stripe customers if the webhook handler crashes. Mitigated by Idempotency-Key headers.
- The subscription row requires a tenant to exist (`tenants(id)` FK). Users who register but never run `loopzero init` will not have a subscription row. The `/v1/billing` endpoint must handle this gracefully (return starter plan defaults).

**Risks Accepted:**
1. Two services sharing DB — mitigated by API owning all migrations, cloud service is read-heavy
2. Orphaned Stripe customers on crash — mitigated by Idempotency-Key + manual cleanup
3. No dual-secret rotation support — mitigated by rapid secret swap during maintenance window. P1 follow-up.

**Risks NOT Accepted (block until resolved):**
- NONE. All vetoes are resolved in the plan.

**Mandatory Actions:**

1. **[Security]** Fix `VerifySignature` timestamp tolerance from 5s to 300s — Owner: api-engineer — BLOCKS Phase 2
2. **[Security]** Add Stripe key validation in `Config.Validate()` for production — Owner: api-engineer — BLOCKS Phase 2
3. **[API]** Add `Idempotency-Key` header support to `StripeClient.post()` — Owner: api-engineer — BLOCKS Phase 3
4. **[API]** Redesign `/v1/billing` response shape to include `{used, limit}` per metric — Owner: api-engineer — BLOCKS Phase 6
5. **[DX]** Register `billing` command in CLI index.ts — Owner: cli-engineer — BLOCKS Phase 5
