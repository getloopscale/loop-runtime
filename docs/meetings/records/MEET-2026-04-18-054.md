## Decisao

**Verdict:** APPROVED_WITH_CONDITIONS

**Key Decision:** Multi-cloud = Helm-based "Bring Your Own Infrastructure" (BYOI), NOT Crossplane or Pulumi provisioning of customer resources. Crossplane rejected unanimously. Pulumi stays for LoopZero-hosted SaaS only. Customer installs LoopZero via Helm chart + 5 config values.

## Contexto

O founder decidiu que LoopZero deve ser instalavel na infra do cliente (AWS, DO, Azure, GCP). A pergunta original era "Crossplane vs Pulumi para provisionar infra multi-cloud." Os 4 agentes redefiniram o problema: o cliente ja TEM infra — nao precisa que LoopZero provisione.

## Opcoes Avaliadas

### Opcao A: Pulumi multi-provider (AWS stub → full impl)
**Rejeitada.** Enterprises nao permitem que PaaS terceiro rode `pulumi up` contra sua conta AWS. Compete com o IaC existente do cliente. 2 semanas de esforco para o persona errado.

### Opcao B: Crossplane para infra de celulas
**Rejeitada unanimemente.** Crossplane resolve provisioning, mas o cliente ja tem infra provisionada. Dois sources of truth (Crossplane + cliente's Terraform) e arquiteturalmente fatal. 4-6 semanas de esforco com zero valor para o caso de uso principal.

### Opcao C: Crossplane + CAPI
**Rejeitada.** Overkill. CAPI providers tem maturidade variavel. 6-8 semanas.

### Opcao D: Hibrido Pulumi + Crossplane
**Rejeitada.** Dois tools com escopo overlapping. Boundary "bootstrap vs day-2" nao e enforceable.

### Opcao E: Helm-based BYOI + PlatformConfig CRD (APROVADA)
**Aprovada com condicoes.** O cliente fornece K8s cluster, PG, S3, registry, dominio. LoopZero instala via Helm chart. Pulumi permanece para LoopZero-hosted SaaS.

## Findings

### SRE VETO (BLOCKER)

**Alertmanager routes para `/dev/null`.** 50+ alertas, 7 PrometheusRule manifests, zero entrega a humanos. `localhost:9093/dev-null` como receiver. Isso invalida toda a postura de monitoramento — nao apenas para multi-cloud, mas para producao atual no DO.

**Arquivo:** `infra/helm/monitoring/values.yaml` L155-160
**Impacto:** Incidents so sao descobertos por reclamacao de usuarios, nao por alertas.
**Resolucao obrigatoria:** Wire Alertmanager a PagerDuty/Opsgenie/Slack ANTES de qualquer trabalho multi-cloud.

### DX CONDITIONAL VETO (blocks delivery)

**3 clusters e deal-breaker para adocao.** Custo minimo AWS: ~$600/mês para 3 EKS clusters. 90% dos clientes potenciais vao desistir. Single-cluster mode e mandatory para self-hosted.

**Resolucao:** `loopzero platform install --mode single-cluster` como default para BYOI.

| Lock-in | Arquivo | Severidade |
|---------|---------|:----------:|

### Advisory Lock Latency (DistSys)

O timeout de 5s para `pg_advisory_xact_lock` foi desenhado para latencia same-VPC (<1ms). Cross-cloud (50-200ms RTT), cada lock acquisition + queries dentro do lock consomem latencia. Uma secao critica que leva 4.5s localmente vai timeout a 5s com overhead cross-cloud.

**Impacto:** Blocker para cells em clouds diferentes com PG compartilhado.
**Resolucao:** Analise formal de latency budget antes de habilitar cross-cloud cells.

## Trade-offs Aceitos

1. **Crossplane rejeitado** — perde reconciliacao continua de infra, mas evita complexidade operacional e conflito com IaC do cliente.
2. **AWS Pulumi provider adiado** — nao atende "LoopZero provisiona tudo no AWS", mas BYOI cobre 90% dos clientes sem escrever codigo cloud-specific.
3. **Single-cluster como default** — perde isolamento de blast radius, mas desbloqueia adocao. Multi-cluster e upgrade path, nao prerequisito.
4. **PG central com latencia cross-cloud** — aceito para Phase 2-3. PG por regiao e Phase 4.
