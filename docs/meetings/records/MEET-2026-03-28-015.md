## Stage 2 — Analyses

### Principal Platform Architect

**Assessment:** All three changes are architectural cleanup that should have been done before production. The convergence loop + callback pattern is strictly superior to synchronous Phase D polling. TokenProvider is the correct abstraction for any credential-bearing client. Loki is a prerequisite for `loopzero logs` to function.

**Risks identified:**
- [medium] Removing Phase D means the deploy.completed SSE event is ONLY emitted by async paths. If both callback and convergence loop fail, the CLI hangs forever.
- [low] TokenProvider adds a new abstraction layer — but the design is already sketched and tested in MEET-014.

**Objections:** None. Pre-production is exactly when these changes should be made.

**Recommendation:** Approve all three. Phase D removal is the highest priority — it is the root cause of false DEPLOY_FAILED errors.

**Conditions for approval:**
1. Phase D removal must preserve the deploy.completed event contract — async paths must emit deploy.completed with the same schema.
2. CLI must have a timeout (not wait forever) even with async activation.

**Impact if ignored:** False deploy failures continue, token rotation remains manual restart, build logs remain empty.

### Staff Distributed Systems Engineer

**Assessment:**

**D1 (Phase D removal):** Phase D WaitForSync is a synchronous redundancy that actively harms correctness. The system now has TWO async activation paths:
- **Fast path:** ArgoCD Notification callback (push, ~seconds latency)
- **Safety net:** ReleaseConvergenceLoop (poll every 10s, 180s timeout)

Phase D is a THIRD path doing the same thing synchronously. Three paths activating the same release creates a race condition — Phase D and the callback can both try to transition PENDING to ACTIVE simultaneously. The advisory lock prevents data corruption, but the duplicate work is wasteful and the 600s timeout causes false failures.

**D2 (TokenProvider):** The interface is clean. `StaticTokenProvider` for dev, `FileWatchTokenProvider` for production. The concern from MEET-014 about "undefined reload trigger" is resolved: the trigger is `fsnotify` on the mounted Secret file. K8s Secret mount propagation is well-understood (~60s).

**D3 (Loki):** No distributed systems concern. Straightforward deployment.

**Risks identified:**
- [high] After Phase D removal, if ArgoCD Notifications are not configured on the production cluster, AND the convergence loop has a bug, releases stay PENDING forever. Both async paths must be verified.
- [medium] `ParseArgoAppName` in `sync_callback_activator.go` uses `LastIndex("-")` — if tenant ID contains hyphens (all tenant IDs start with "tn-"), parsing is wrong. Example: `tn-loopzero-production` parses as tenant=`tn-loopzero`, env=`production` — this happens to be correct for the current naming convention but is fragile.

**Objections:**
- Phase D removal requires verifying that the convergence loop emits deploy.completed with the FULL schema (including `apps`, `duration_seconds`, `deploy_id`). Currently, the convergence loop only emits deploy.live — it does NOT emit deploy.completed. This is a gap.

**Recommendation:** Approve D1 with the condition that the convergence loop is enhanced to emit deploy.completed with the same schema as Phase E.

**Conditions for approval:**
1. Convergence loop must emit deploy.completed (not just deploy.live)
2. ArgoCD Notifications must be verified deployed on DigitalOcean
3. Add a PENDING timeout alert: if any release stays PENDING > 5 minutes, alert fires

**Impact if ignored:** False deploy failures, CLI shows timeout when deploy actually succeeded.

### Staff SRE / Production Readiness

**Assessment:**

**D1 (Phase D removal):** I agree with removal. Phase D WaitForSync with 600s timeout is the single biggest contributor to false deploy failures. The async model is correct. But I need observable proof that the async paths work.

**D2 (TokenProvider):** The current static token works. But implementing TokenProvider now avoids a future incident during any ArgoCD maintenance. In pre-production, the cost is low and the protection is permanent.

**D3 (Loki):** Build logs being empty is an operational blind spot. Without Loki, `loopzero logs` returns nothing, and debugging build failures requires `kubectl` on the build cluster — which violates Rule 3. This is a hard blocker for operability.

**Risks identified:**
- [high] Loki endpoint is currently a placeholder (`http://pending-loki-ip:30100`). The `infra-deploy.yml` pipeline step "Configure cross-cluster Loki" must actually resolve the build cluster node IP and patch the API. This pipeline step may not exist or may be broken.
- [medium] Loki on build cluster needs sufficient storage. Build log volume can spike during concurrent builds.
- [low] Promtail must filter to only capture Argo Workflow pods (not all pods).

**Objections:**
- D3 (Loki): I need to see the `infra-deploy.yml` pipeline step that resolves the Loki endpoint. If it doesn't exist, Loki deployment is incomplete even if Helm charts are installed.

**Recommendation:** Approve all three. D3 is the most urgent from operability perspective — empty build logs is unacceptable.

**Conditions for approval:**
1. D1: Add Prometheus metric `loopzero_release_pending_duration_seconds` histogram to track time releases spend in PENDING state
2. D1: Add alert `LoopZeroReleasePendingTooLong` if any release is PENDING > 5 minutes
3. D3: Verify or create the pipeline step that resolves Loki cross-cluster endpoint
4. D3: Validate `loopzero logs` returns real build output on DigitalOcean

**Impact if ignored:** False failures erode trust in `loopzero deploy`, empty build logs make debugging impossible, manual token restart during ArgoCD maintenance.

### Staff Platform Security Engineer

**Assessment:**

**D2 (TokenProvider):** The MEET-014 deferral was based on YAGNI. The owner has overridden YAGNI. From a security perspective, TokenProvider is strictly better than a static string:
- Enables credential rotation without pod restart
- Reduces blast radius window (old token becomes invalid immediately on rotation)
- Establishes a pattern for ALL credential-bearing clients (Gitea client should follow later)

The `FileWatchTokenProvider` using `fsnotify` on a mounted K8s Secret is the standard pattern (used by cert-manager, external-secrets-operator, etc.). Well-understood, battle-tested.

**Risks identified:**
- [low] fsnotify can miss events on certain filesystems. Mitigation: add a periodic re-read (every 5 minutes) as belt-and-suspenders.
- [low] Concurrent goroutines reading atomic.Value during rotation is safe (atomic operations are lock-free).

**Objections:** None. This is the correct pattern.

**Recommendation:** Approve D2 unconditionally.

**Conditions for approval:**
1. `FileWatchTokenProvider` must validate the new token before accepting it (call ValidateToken)
2. If validation fails, keep old token and log error (don't swap to invalid token)
3. Emit `loopzero_argocd_token_rotated_total` counter on successful rotation
4. Emit `loopzero_argocd_token_rotation_errors_total` counter on failed rotation

**Impact if ignored:** ArgoCD maintenance requires API pod restart. Risk of missed rotation window.

## Stage 3 — Confrontation

### Conflict 1: Does removing Phase D create a "release stuck forever" scenario?

| Agent | Position |
|-------|----------|
| Distributed Systems Engineer | Yes, if BOTH async paths fail (callback misconfigured + convergence loop bug), releases are stuck PENDING. Need a third safety mechanism. |
| Principal Architect | The convergence loop IS the safety mechanism. If it has a bug, fix the bug — don't keep Phase D as a crutch. The RELEASE_PENDING_TIMEOUT (10m) in the ReleaseReaper already handles this: it transitions stale PENDING releases to TIMED_OUT. |
| SRE | Agrees with Architect. The ReleaseReaper is the ultimate safety net. But we need an ALERT (not just timeout) so operators know. |

**Resolution:** The system already has three layers of defense:
1. **Fast path:** ArgoCD Notification callback (~seconds)
2. **Safety net:** ReleaseConvergenceLoop (polls every 10s, 180s timeout, transitions to SYNC_FAILED)
3. **Reaper:** ReleaseReaper (10m timeout, transitions PENDING to TIMED_OUT)

Phase D was a fourth layer doing the same thing less well (synchronous, blocking, 600s timeout). Removing it is correct. The missing piece is the deploy.completed SSE event in the async paths — this MUST be added.

**Action:** Convergence loop and callback activator must emit deploy.completed with the full schema (`deploy_id`, `status`, `duration_seconds`, `apps`). Currently they only emit deploy.live.

### Conflict 2: Is the MEET-014 YAGNI override justified?

| Agent | Position |
|-------|----------|
| Principal Architect | YAGNI was correct at the time. Owner has now explicitly overridden it based on operational experience. Pre-production is the right time. |
| Distributed Systems Engineer | Agrees. TokenProvider is ~100 lines of code. The abstraction is clean and well-designed. No YAGNI violation when the owner mandates it. |
| Security Engineer | Agrees. The pattern is not speculative — it's standard infrastructure practice. |

**Resolution:** Unanimous. Owner override of YAGNI is accepted. TokenProvider is approved.

### Conflict 3: Is Loki deployment complete if the endpoint is a placeholder?

| Agent | Position |
|-------|----------|
| SRE | No. Deploying Helm charts without resolving the cross-cluster endpoint is theater. `loopzero logs` will still return empty. |
| Principal Architect | Agrees. The endpoint resolution must be part of the deliverable, not a manual step. |

**Resolution:** D3 deliverable includes: (1) Helm install via Pulumi, (2) endpoint resolution in `infra-deploy.yml`, (3) validation that `loopzero logs` returns real output on DigitalOcean. If any of these three is missing, D3 is not done.

### Orchestrator Challenge: "What could go wrong that nobody mentioned?"

**Challenge 1:** The convergence loop uses `FindPendingReleases(ctx)` which queries ALL pending releases across ALL tenants. At scale (100+ concurrent deploys), this query returns 100+ rows every 10 seconds. Is this a problem?

**Resolution from Distributed Systems:** At current scale (single tenant, <10 concurrent deploys), this is fine. At 100+, add a `WHERE created_at > NOW() - INTERVAL '30 minutes'` filter and an index on `(status, created_at)`. Not a blocker for now, but document as a known scale limitation.

**Challenge 2:** `ParseArgoAppName` uses `LastIndex("-")`. Tenant ID `tn-loopzero` contains a hyphen. App name `tn-loopzero-production` parses as tenant=`tn-loopzero`, env=`production`. What about `tn-loopzero-staging-preview-42`?

**Resolution from Distributed Systems:** Environment names in LoopZero are constrained to `production`, `staging`, `preview`. No hyphens in environment names. The current parsing is correct for all valid inputs. Add a validation comment documenting this assumption.

## Stage 4 — Decision

### Decision 1: Remove Phase D WaitForSync — APPROVED

**Chosen:** Remove Phase D (phaseDVerify) and Phase E (phaseEFinalize) from `ContainerDeliveryActivator.Activate()`. After Phase C records PENDING status and emits deploy.delivering, the Activate method returns. Release activation is handled by:
1. ArgoCD Notification callback (fast path, ~seconds)
2. ReleaseConvergenceLoop (safety net, polls every 10s)
3. ReleaseReaper (ultimate safety net, 10m timeout)

**Alternatives rejected:**
- Keep Phase D with reduced timeout (120s) — rejected because it still blocks the goroutine and can still produce false failures
- Make Phase D optional via config — rejected because two code paths means two bug surfaces

**Trade-offs accepted:**
- Deploy success is now eventually consistent — CLI may show "deploying" for a few extra seconds before the async path fires deploy.completed
- The convergence loop and callback must be reliable — no fallback to synchronous polling

**Risks accepted:**
| Risk | Severity | Mitigation | Owner |
|------|----------|------------|-------|
| Both async paths fail simultaneously | Low | ReleaseReaper (10m) + alert | SRE |
| CLI shows "deploying" longer than before | Low | Callback fires in ~seconds; UX impact is minimal | DX |

### Decision 2: Implement TokenProvider — APPROVED (overrides MEET-014)

**Chosen:** Implement Option B from MEET-013/014:
- `TokenProvider` interface: `Token() string`, `Refresh(ctx) error`
- `StaticTokenProvider`: wraps a string, Refresh is no-op. For tests and local dev.
- `FileWatchTokenProvider`: reads token from file path, watches with fsnotify, validates before swap, periodic re-read every 5 minutes.
- `SyncClient` uses `TokenProvider` instead of `string` field.

**Alternatives rejected:**
- Keep static string (MEET-014 decision) — rejected by owner override. Pre-production is the time.
- SecretWatchTokenProvider using K8s API — rejected in favor of file-based (simpler, no RBAC needed for API watch)

**Trade-offs accepted:**
- Adds ~150 lines of code and a new dependency (fsnotify)
- Slightly more complex SyncClient initialization

**Risks accepted:**
| Risk | Severity | Mitigation | Owner |
|------|----------|------------|-------|
| fsnotify misses file change event | Low | Periodic re-read every 5 minutes as fallback | API Engineer |
| New token is invalid | Low | Validate before swap, keep old token on failure | API Engineer |

### Decision 3: Deploy Loki + Promtail — APPROVED

**Chosen:** Deploy Loki + Promtail to build cluster via Pulumi bootstrap. Resolve cross-cluster Loki endpoint in `infra-deploy.yml`. Validate `loopzero logs` returns real output.

**Alternatives rejected:**
- Deploy only on next sprint — rejected by owner mandate. Build logs being empty is an operability failure.
- Use CloudWatch/DO monitoring instead of Loki — rejected because Loki stack is already designed, Helm values exist, API client exists.

**Trade-offs accepted:**
- Additional infrastructure cost (Loki pod on build cluster)
- Cross-cluster networking complexity (NodePort 30100)

**Risks accepted:**
| Risk | Severity | Mitigation | Owner |
|------|----------|------------|-------|
| Loki storage fills up | Medium | Retention config in Helm values (168h default) | Infra Engineer |
| Cross-cluster endpoint breaks on node replacement | Medium | Pipeline resolves endpoint on each deploy | Infra Engineer |
