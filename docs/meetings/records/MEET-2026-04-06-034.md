## Stage 1 — Context

**Problem:** Custom Domains feature (MEET-033) has full API/CLI/infra/dashboard implemented, but the critical provisioning path is a stub. `DomainProvisioner.provisionDomain()` logs "manifest integration pending" and returns. `removeDomain()` deletes the DB row without cleaning up the gitops repo. No code transitions domains from `provisioning` to `active`. Domains are stuck forever in `provisioning` status.

**Decision Required:** Approve the implementation approach for 3 code blocks:
1. `provisionDomain()` — manifest re-render + gitops push flow
2. `provisioning → active` transition mechanism
3. `removeDomain()` with proper gitops cleanup

Five specific technical questions require resolution:
- Q1: gitops.Push inside or outside the environment lock?
- Q2: How to handle "no active release" on provision and remove?
- Q3: Option A/B/C for provisioning → active transition?
- Q4: Re-render ALL apps' manifests or only add/remove custom domain resources?
- Q5: Race condition between deploy and domain provisioner gitops push?

**Constraints:**
- The existing deploy flow (ContainerDeliveryActivator) does gitops.Push OUTSIDE the lock (Phase B)
- Both deploy and domain provisioner write to the same gitops path: `{projectID}/{environment}/manifests.yaml`
- `withEnvironmentLock` uses `pg_advisory_xact_lock` with 5s timeout (Rule 7)
- DomainProvisioner runs in the API process, not in the operator
- The provisioner needs `releaseStore`, `buildStore`, `baseDomain`, `registryURL` — currently not available on the struct
- `manifests.Render()` produces a FULL manifest document for all apps — it is not additive/incremental
- Gitea git push is not atomic — non-fast-forward errors possible on concurrent pushes
- Pre-release: clean design preferred over backward compatibility

**Known Context:**
- Design doc: `docs/plans/custom-domains-design.md` (sections 7-8)
- Prior meeting: MEET-2026-04-05-033 (approved with conditions)
- ContainerDeliveryActivator Phase B: push outside lock (`container_delivery.go:226-238`)
- Build reconcile loop: renders full manifests with `manifests.Render()` + `RenderInput` (`build_reconcile_loop.go:476-484`)
- `ListActiveByApp()` already exists in DomainStore — returns active/provisioning domains for an app
- `GetActiveByEnvTx()` returns nil (not error) when no active release exists
- Manifest renderer already supports `CustomDomains` field on `AppManifestInput`
- Known Systemic Pattern: "Single ArgoCD Application per tenant" — if ANY resource is Degraded, ALL notifications are blocked

**Proposal:** As described in the meeting request — 3 code blocks with specific implementation patterns.

## Stage 2 — Analyses

### Distributed Systems Engineer

**Assessment:** The core challenge is that domain provisioning and deploy write to the same gitops file (`{project}/{env}/manifests.yaml`) and the existing deploy flow deliberately pushes OUTSIDE the lock. This creates a real race condition: two concurrent git commits to the same file path, one of which will get a non-fast-forward rejection.

The existing pattern in `ContainerDeliveryActivator` is: Phase A (lock) creates release, Phase B (no lock) pushes to gitops, Phase C (lock) records result. This was designed so the lock is not held during the slow gitops network call.

**Risks:**
1. [HIGH] **Concurrent deploy + domain provision race.** Both push to `{project}/{env}/manifests.yaml`. If deploy wins, domain provision gets non-fast-forward. If domain provision wins, deploy gets non-fast-forward.
2. [HIGH] **Full re-render with stale data.** DomainProvisioner re-renders based on the active release's build apps. If a deploy is in progress, the provisioner uses old release data. The subsequent deploy then overwrites WITHOUT custom domains.
3. [MEDIUM] **No active release edge case.** `GetActiveByEnvTx()` returns nil. The provisioner cannot render manifests without app specs.

**Objections:**
- Option A (cert-manager status check) requires K8s API access from the API process to the runtime cluster. The API process does NOT have runtime cluster credentials. Architecturally wrong.
- Holding the lock during gitops push contradicts the established pattern. Need consistency.

**Recommendation:** Approve with mandatory build reconcile loop fix. The deploy flow must also query custom domains when rendering manifests. This is the only correct fix.

**Conditions for approval:**
1. Build reconcile loop MUST query `ListActiveByApp()` and populate `CustomDomains` on `AppManifestInput`.
2. gitops.Push for domain provisioning follows SAME pattern as deploy: push outside lock, record result inside lock.
3. "No active release" is a documented, graceful no-op.

**Impact if ignored:** Every deploy after domain provisioning silently removes the custom domain IngressRoute and Certificate.

### GitOps/Delivery Engineer

**Assessment:** The critical insight is that `manifests.Render()` produces the COMPLETE manifest for `{project}/{env}/manifests.yaml`. It is not incremental. Whoever pushes last wins — and the loser's changes are silently overwritten.

**Risks:**
1. [CRITICAL] **Deploy overwrites custom domain manifests.** The build reconcile loop builds `manifestApps` WITHOUT custom domains. The gitops push replaces the entire `manifests.yaml`. Custom domain resources vanish.
2. [HIGH] **Non-fast-forward on concurrent push.** Gitea rejects pushes that are not fast-forward. The deploy flow fails the release to `GIT_MIRROR_FAILED`.
3. [MEDIUM] **ArgoCD prune timing.** Domain removal pushes manifests without the IngressRoute; ArgoCD prune deletes the Certificate CR even if cert-manager is still issuing.

**Objections:**
- Q4 answer is definitively "re-render ALL apps' manifests". The renderer produces a single YAML file. No incremental mechanism exists.

**Recommendation:** Approve ONLY if the deploy flow is updated simultaneously.

**Conditions for approval:**
1. [BLOCKER] Build reconcile loop must populate `CustomDomains` on `AppManifestInput` from `ListActiveByApp()`.
2. Domain provisioner must retry on non-fast-forward.
3. `removeDomain()` must re-render full manifests without the removed domain.

**Impact if ignored:** Custom domains work exactly once, then break on the next deploy.

**Risks:**

3. [MEDIUM] **Missing metrics.** Provisioning duration metric not implemented.
4. [LOW] **Lock contention with many domains.** 5s timeout may not be enough.

**Objections:**
- Option B (optimistic "active" after push) is dangerous. User sees "active" but cert may never issue. Prefer Option C.

**Recommendation:** Approve with Option C and clear "no active release" handling.

**Conditions for approval:**
1. "No active release": domain stays in `provisioning`, log warning, skip. Next deploy includes it.
2. Option C for active transition.
3. Add `loopzero_domain_provisioning_duration_seconds` histogram.
4. Provisioner must NOT panic on any error.

**Impact if ignored:** Stuck domains with no recovery. Silent cert failures. No operational visibility.

| Agent | Position |
|-------|----------|

**Resolution:** UNANIMOUS — gitops.Push OUTSIDE the lock. Pattern: (1) Lock: fetch data + render, (2) Unlock, (3) Push, (4) Lock: record result.

| Agent | Position |

### Consensus Challenge: Is Build Reconcile Loop Fix Really Needed?

Orchestrator challenged: "Could we avoid modifying the build reconcile loop and instead have the domain provisioner always run AFTER every deploy?"

All agents REJECTED:
- **Distributed Systems:** Deploy flow does not notify domain provisioner. No event hook.
- **GitOps:** Deploy's gitops push has ALREADY overwritten custom domain resources. Damage is done.
- **SRE:** Custom domains would disappear for up to 30s after every deploy.

**Resolution:** Build reconcile loop fix is MANDATORY. Only correct solution.

## Stage 4 — Decision

**Chosen:** Approve implementation of all 3 code blocks with the approach below.

**Block 0 (CRITICAL PREREQUISITE) — Build Reconcile Loop Fix:**
Both `onWorkflowSucceeded` and `retryReleasingBuild` in `build_reconcile_loop.go` must query `ListActiveByApp()` for each app and populate `CustomDomains` on `AppManifestInput`. Without this, every deploy silently removes custom domain IngressRoutes.

**Block 1 — `provisionDomain()`:**
1. Pre-check: `releaseStore.GetActiveByEnv()` (no lock). If nil, log warning, skip.
2. Lock: fetch release via `GetActiveByEnvTx()`, get build apps, query `ListActiveByApp()` for all apps, build `AppManifestInput[]` with `CustomDomains`, render manifests.
3. Unlock.
4. Push to gitops (outside lock).
5. Lock: on success, set domain status `active`. On failure, set `failed` with reason.
6. On non-fast-forward: retry on next tick.

**Block 2 — Active Transition:**
Option C. Set `active` after gitops push. TLS tracked via `tls_status`. DomainHealthChecker monitors cert issuance.

**Block 3 — `removeDomain()`:**
1. Pre-check: `releaseStore.GetActiveByEnv()`. If nil, delete DB row directly.
2. Lock: fetch release, build apps, query remaining custom domains (excluding removed one), render manifests.
3. Unlock.
4. Push to gitops.
5. On success: delete DB row.
6. On failure: leave in `removing`, retry next tick.

**Alternatives rejected:**
- gitops.Push inside lock — holds advisory lock during network I/O (up to 60s), violates 5s timeout design
- Option A (cert-manager check) — API process has no runtime cluster credentials
- Option B (optimistic active) — confusing; Option C with separate TLS tracking achieves same UX
- Incremental manifest changes — renderer produces complete YAML by design
- Domain provisioner as sole custom domain renderer — deploys would overwrite custom domain resources

**Trade-offs consciously accepted:**
- Full re-render on domain operations: rendering bug could affect all apps (mitigated by existing tests)
- Non-fast-forward between concurrent deploy + domain provision (mitigated by retry)
- "No active release" means domain stuck until first deploy (mitigated by 1-hour timeout)

**Risks accepted:**

| Severity | Risk | Mitigation | Owner |
|----------|------|------------|-------|
| HIGH | Full re-render bug takes down all apps | Existing renderer tests; add re-render test with domains | API Engineer |
| MEDIUM | Provisioner and deploy race on gitops push | Non-fast-forward retry; deploy uses convergence loop | API Engineer |
| MEDIUM | 1-hour timeout confuses users | Clear error message suggesting `loopzero deploy` first | API Engineer |
| LOW | Lock contention with many domains | Batch limit of 50, `SKIP LOCKED` for HA | API Engineer |

**Risks NOT accepted (blocking):**

| Risk | Blocker For | Resolution Required |
|------|-------------|---------------------|
| Build reconcile loop does not include custom domains | ALL 3 blocks | MUST fix to populate `CustomDomains` on `AppManifestInput` |

**Mandatory actions:**

1. [BLOCKER] Fix build reconcile loop: query `ListActiveByApp()`, populate `CustomDomains` on `AppManifestInput`. Both code paths. **Owner:** API Engineer.
2. Expand `DomainProvisioner` struct with `releaseStore`, `buildStore`, `domainStore`, `baseDomain`, `registryURL`. **Owner:** API Engineer.
3. Extract shared manifest rendering function for both build reconcile loop and domain provisioner. **Owner:** API Engineer.
4. Add provisioning timeout (1 hour) to DomainHealthChecker. **Owner:** API Engineer.
5. Add `loopzero_domain_provisioning_duration_seconds` histogram metric. **Owner:** API Engineer.
6. Add test: `TestProvisionDomain_NoActiveRelease_SkipsGracefully`. **Owner:** API Engineer.
