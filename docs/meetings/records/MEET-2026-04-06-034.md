## Stage 1 — Context

**Problem:** Login and registration are completely broken. The Kratos selfservice `ui_url` values are inconsistent — some point to `accounts.{domain}` (which routes to the deleted `kratos-ui` service) and others point to `cloud.{domain}` (which has NO IngressRoute at all). Meanwhile, the dashboard now renders Kratos flows directly but fetches from `api.{domain}/self-service/*` (baked via `VITE_API_URL`), which falls through to `loopzero-api:8080` (404 — not Kratos).

**Current broken state:**
| Flow | ui_url | Status |
|------|--------|--------|
| login | `accounts.{domain}/login` | DEAD — kratos-ui deleted |
| registration | `accounts.{domain}/registration` | DEAD — kratos-ui deleted |
| verification | `cloud.{domain}/self-service/verification` | DEAD — no IngressRoute for cloud.{domain} |
| recovery | `cloud.{domain}/self-service/recovery` | DEAD — no IngressRoute for cloud.{domain} |
| settings | `accounts.{domain}/settings` | DEAD — kratos-ui deleted |
| error | `accounts.{domain}/error` | DEAD — no kratos-ui |

**Three compounding problems:**
1. Kratos `ui_url` values point to dead endpoints
2. Dashboard makes Kratos API calls to `api.{domain}/self-service/*` which routes to loopzero-api, not Kratos
3. OIDC `base_redirect_uri` points to `accounts.{domain}` (dead)

**Decision Required:** What should all `ui_url` values be, and how should the dashboard reach the Kratos API?

**Constraints:**
- `kratos-ui` is deleted and should not be redeployed (MEET-032 approach abandoned in practice)
- Dashboard already has working pages: login.tsx, register.tsx, recovery.tsx, error.tsx, settings.tsx
- `VITE_API_URL` is baked at build time — all dashboard Kratos calls go to `api.{domain}`
- The api-gateway IngressRoute has no `/self-service/*` route
- Pre-release — clean redesign is preferred over patches
- The dashboard is served at `dashboard.{domain}` via its own IngressRoute

**Known Context:**
- MEET-032 decided Option A/C (deploy kratos-ui at accounts.{domain}), but implementation diverged
- Dashboard now renders Kratos flows directly (the pattern MEET-032 explicitly rejected)
- However, the dashboard pages ARE same-origin with Kratos IF we route `/self-service/*` through the same domain
- `PLATFORM_INGRESS_ROUTES` includes `accounts` → `kratos-ui:3000` (dead service)
- `api-gateway` IngressRoute has paths: `/v1/auth/*`, `/v1/billing/*`, `/v1/webhooks/*`, `/auth/*` → loopzero-cloud, `/*` → loopzero-api

**Proposal:** Add `/self-service/*` route to dashboard IngressRoute pointing to ory-kratos-public, update all `ui_url` to `dashboard.{domain}/*`, update OIDC `base_redirect_uri` to `dashboard.{domain}`.

## Stage 2 — Analyses

### Principal Platform Architect

**Assessment:** The implementation deviated from MEET-032's decision. Instead of deploying a separate kratos-ui at `accounts.{domain}`, the team built Kratos flow rendering into the dashboard. This is a valid alternative approach — but it only works if the dashboard and Kratos API are on the same origin (for CSRF tokens and cookies). Currently they are not: dashboard is at `dashboard.{domain}`, Kratos API has no browser-accessible endpoint.

Two viable architectures exist:

**Architecture 1 — Dashboard as Kratos UI (path-routing):** Add `/self-service/*` route on `dashboard.{domain}` IngressRoute pointing to `ory-kratos-public`. Dashboard fetches Kratos flows from same origin. All `ui_url` values point to `dashboard.{domain}`. This is the simplest fix given what already exists.

**Architecture 2 — Dedicated cloud domain:** Create `cloud.{domain}` IngressRoute with path-routing: `/self-service/*` → ory-kratos-public, `/*` → loopzero-dashboard. Move dashboard from `dashboard.{domain}` to `cloud.{domain}`. All ui_urls point to `cloud.{domain}`. This provides a unified "cloud console" URL.

Architecture 1 is simpler and works immediately. Architecture 2 is cleaner long-term but requires rebuilding the dashboard image with updated URLs and creating a new IngressRoute.

**Risks:**
- [medium] Path-routing identity API under dashboard domain creates shared trust boundary
- [low] CSRF token same-origin requirement is satisfied by either architecture

**Recommendation:** Architecture 1 — add `/self-service/*` to `dashboard.{domain}` IngressRoute. Minimum change, maximum impact.

**Conditions for approval:** OIDC `base_redirect_uri` must also be updated (currently points to dead `accounts.{domain}`).

**Impact if ignored:** All identity flows remain broken. No login, no registration, no recovery.

### Platform Security Engineer

**Assessment:** Multiple security issues in the current state:

1. **Broken state is a security issue itself** — users cannot authenticate
2. **CSRF same-origin:** Dashboard at `dashboard.{domain}` fetching Kratos API at `api.{domain}/self-service/*` is cross-origin. CSRF tokens generated by Kratos for `api.{domain}` will not match browser expectations for `dashboard.{domain}`. This is WHY login is broken even if the route existed.
3. **OIDC redirect:** `base_redirect_uri` at `accounts.{domain}` means social login callbacks go to a dead service

For path-routing Kratos under dashboard domain: this works for CSRF because browser and API share the same origin. The Kratos session cookie domain is `.dev.loopzero.example` (shared), so cookies flow correctly.

**Risks:**
- [medium] Kratos admin endpoints must NOT be exposed via this route — only public endpoints
- [low] Path collision: `/self-service/*` is well-namespaced, no risk of collision with dashboard routes

**Objections:** None to Architecture 1. The same-origin model is correct and matches how Kratos is designed to work (browser flow expects same-origin UI).

**Recommendation:** Architecture 1. Ensure only `ory-kratos-public` (not `ory-kratos-admin`) is exposed.

**Conditions for approval:**
1. Only `ory-kratos-public` port 80 is routed, NOT admin port
2. `base_redirect_uri` updated to `dashboard.{domain}`
3. `allowed_return_urls` updated to include `dashboard.{domain}`
4. Remove dead `accounts` IngressRoute entry from `PLATFORM_INGRESS_ROUTES`

**Impact if ignored:** Login remains broken. Social login callbacks go to dead endpoint.

### DX/Tooling Engineer

**Assessment:** The dashboard already has high-quality pages for all Kratos flows (login, register, recovery, error, settings). The work is done. The only problem is plumbing: the Kratos API is unreachable from the dashboard's origin.

Architecture 1 is the correct fix — it makes the existing dashboard pages work by routing `/self-service/*` to Kratos on the same domain.

The `VITE_API_URL` being set to `api.{domain}` is wrong for Kratos calls. The dashboard should call Kratos at its own origin (relative URL or `dashboard.{domain}`). However, since `VITE_API_URL` is baked at build time, changing it requires rebuilding the image. An alternative: the Kratos calls in the dashboard should use a relative URL (just `/self-service/*`) instead of `VITE_API_URL`.

**Risks:**
- [high] Dashboard code uses `VITE_API_URL` for Kratos calls — must be changed to relative URLs or a separate `VITE_KRATOS_URL` env var
- [medium] Recovery page uses `ACCOUNTS_URL` (resolves to `api.{domain}`) for flow initiation redirect

**Objections:** If we only fix Pulumi `ui_url` but not the dashboard's Kratos API base URL, the dashboard will still fail to fetch flows.

**Recommendation:** Architecture 1 + dashboard code fix: change all Kratos API calls to use relative URLs (`/self-service/*`) instead of `VITE_API_URL`. This way the dashboard always calls Kratos on its own origin, which is correct by design.

**Conditions for approval:**
1. Dashboard Kratos calls use relative URLs (no `VITE_API_URL` for self-service)
2. All `ui_url` values point to `dashboard.{domain}/*` routes
3. All existing dashboard pages (login, register, recovery, error) must work after the fix

**Impact if ignored:** Dashboard pages render but Kratos API calls fail. Users see forms but form submission goes to wrong endpoint.

### API/Domain Architect

**Assessment:** The api-gateway IngressRoute currently routes `/auth/*` to loopzero-cloud for the consent handler. Adding `/self-service/*` to the api-gateway would be wrong — it mixes identity API with the platform API domain.

Architecture 1 (path-routing on dashboard domain) is architecturally clean: the dashboard is the identity UI, Kratos is the identity API, both on the same origin.

The `cloud.{domain}` concept was introduced but never materialized (no IngressRoute exists). References to `cloud.{domain}` in the codebase should be cleaned up to avoid confusion.

The `logout` flow's `default_browser_return_url` points to `dashboard.{domain}/login` — this is correct and should remain as-is.

**Risks:**
- [low] loopzero-cloud env var `KRATOS_PUBLIC_URL` set to `cloud.{domain}` (dead) — needs updating

**Recommendation:** Architecture 1. Clean up all `cloud.{domain}` references. Update loopzero-cloud's `KRATOS_PUBLIC_URL` to the internal URL (it's server-to-server, not browser-facing).

**Conditions for approval:** loopzero-cloud `KRATOS_PUBLIC_URL` must use internal URL for server-to-server calls, not a public URL.

**Impact if ignored:** loopzero-cloud's consent handler may fail if it tries to reach `cloud.{domain}` (which does not resolve).

## Stage 3 — Confrontation

### Conflict 1: Dashboard renders Kratos flows — contradicts MEET-032

| Agent | Position |
|-------|----------|
| Principal Architect | MEET-032 decided dashboard should be PKCE-only. Implementation diverged. |
| DX Engineer | The diverged implementation is better — custom-branded pages with LoopZero look and feel. The kratos-ui was a generic Node.js app that crashed. Dashboard pages are production-quality. |
| Security Engineer | MEET-032's concern was cross-origin CSRF. If same-origin is achieved via path-routing, the security concern is resolved. The implementation approach is acceptable. |

**Resolution:** MEET-032's decision is SUPERSEDED. The security concern (cross-origin CSRF) is resolved by Architecture 1 (same-origin path routing). The dashboard rendering Kratos flows is the superior approach for DX (branded, consistent, already built). Formal supersession documented.

### Conflict 2: VITE_API_URL vs relative URLs

| Agent | Position |
|-------|----------|
| DX Engineer | Dashboard must use relative URLs for Kratos — baked env vars are fragile |
| API Domain Architect | Relative URLs are correct only if Kratos is always on the same domain as dashboard |
| Principal Architect | With Architecture 1, Kratos IS always on dashboard domain. Relative URLs are correct. |

**Resolution:** Unanimous. Dashboard Kratos calls must use relative URLs (`/self-service/*`). The `VITE_API_URL` is for the LoopZero platform API only. A dedicated constant (e.g., empty string or `''`) should be used for Kratos base URL.

### Conflict 3: Clean up cloud.{domain} references or keep for future?

| Agent | Position |
|-------|----------|
| Principal Architect | Remove all `cloud.{domain}` references — dead code confuses future work |
| API Domain Architect | Agreed. loopzero-cloud's `KRATOS_PUBLIC_URL` should use internal URL |

**Resolution:** Unanimous. All `cloud.{domain}` references in Pulumi should be replaced. loopzero-cloud `KRATOS_PUBLIC_URL` should use the internal cluster URL (it's server-to-server).

### Consensus Challenge

All agents agree on Architecture 1. Orchestrator challenge: "What could go wrong?"

1. **Priority ordering:** If `/self-service/*` priority is lower than dashboard catch-all, Kratos calls would hit nginx (SPA) instead of Kratos. **Mitigation:** `/self-service/*` route must have higher priority than dashboard catch-all.
2. **Kratos admin exposure:** If wrong service/port is used, admin endpoints could be exposed. **Mitigation:** Explicitly route to `ory-kratos-public:80` only.
3. **Cookie domain collision:** Dashboard session cookie and Kratos session cookie on same domain. **Not an issue:** They use different cookie names.
4. **Image rebuild required:** Dashboard code changes (relative URLs) require rebuilding the container image. **Accepted:** This is a code change, not just config.

None are blocking. **Consensus holds.**

## Stage 4 — Decision

**Chosen:** Architecture 1 — Path-route `/self-service/*` under `dashboard.{domain}` to `ory-kratos-public`. Dashboard renders all identity flows. All `ui_url` values point to `dashboard.{domain}`. Dashboard code uses relative URLs for Kratos API calls.

**MEET-032 is formally SUPERSEDED** for the identity UI approach. The security requirement (same-origin CSRF) is satisfied by path-routing.

**Rejected alternatives:**

| Alternative | Reason |
|-------------|--------|
| Redeploy kratos-ui at accounts.{domain} (MEET-032 original) | kratos-ui crashed, generic UI, dashboard pages are superior. Superseded. |
| Create cloud.{domain} IngressRoute | New domain, new TLS cert, requires dashboard URL change everywhere. Over-engineering. |
| Route /self-service/* through api-gateway | Mixes identity and platform API domains. Security boundary violation. |

**Trade-offs accepted:**
- Dashboard and Kratos share the same origin — acceptable because Kratos public API is read-only for flows and submit-only for credentials
- Dashboard code needs modification (relative URLs) — requires image rebuild

  ├── /v1/billing/*       → loopzero-cloud:13002
  ├── /v1/webhooks/*      → loopzero-cloud:13002

  └── *                   → ory-hydra-public:4444

Kratos Flow (browser):
  1. User visits dashboard.dev.loopzero.example/login
  2. Dashboard JS calls /self-service/login/browser (same origin → ory-kratos-public)

  4. User submits form → POST to flow.ui.action (Kratos endpoint, same origin)
  5. Kratos authenticates → session created → redirect to dashboard
