# T2.7 Stripe Portal SDK Integration — Change Governor Diagnostic Package

**Date prepared:** 2026-05-27 (Ralph iter 11)
**Plan reference:** T2.7 of `docs/plans/2026-05-26-maturity-3-62-to-4-0-roadmap-plan.md`
**Status:** **AWAITING SPONSOR REVIEW** — diagnostic pre-populated

## 1. Problem Statement

`POST /api/v1/billing/portal` em `api/internal/routes/billing.go:180-215` returns hardcoded Stripe global dashboard URL with placeholder comment "Sprint 11 — wire CreatePortalSession SDK call". User clicks "Manage Billing" em dashboard, opens generic `https://dashboard.stripe.com` and must navigate manually to find their account — poor UX.

Sprint 11 (Auth + Billing) is COMPLETE per CLAUDE.md sprint plan, but this single endpoint was deferred. M10 audit (2026-05-26) flagged as MEDIUM gap because:
- Pro tier customers expect Customer Portal (industry standard)
- Without portal, customers must email support to change payment method / cancel subscription / download invoices
- Pricing decisions (MEET-2026-05-12 D4) committed Pro tier as "public at GA" — Portal is implicit in that commitment

## 2. Decision Required

**APPROVE Stripe SDK integration** for `POST /api/v1/billing/portal` to return real customer-scoped Portal URL, replacing placeholder.

## 3. Tier Classification

**T2** — API contract change + billing flow. Per `.claude/rules/pre-release-governance.md`, T2 requires:
- Change Governor meeting (smaller than T3)
- Sponsor sign-off NOT mandatory; ADR recommended

**Why sponsor IS requested:** Stripe **production API key** access requires sponsor authorization (financial commitment per MEET-2026-05-12 — Pro tier billing live).

## 4. Alternatives Evaluated

### Option A — Stripe BillingPortalSession SDK (RECOMMENDED — plan default)

Replace placeholder with `stripeClient.BillingPortalSession.New()` SDK call.

**Pros:**
- Industry-standard Stripe pattern (used by Vercel, Linear, Heroku, etc.)
- Stripe-managed UI (no maintenance burden)
- Auto-localized to customer's locale + currency
- Supports all Pro tier features (cancel, update payment, download invoice)
- Idempotency via Redis cache key `portal:<customer-id>:<hourBucket>` (EC-13 absorbed)

**Cons:**
- External dependency on Stripe SDK + Stripe API uptime
- Requires Stripe prod restricted key with scopes `subscriptions:read + billing_portal:write`
- Network round-trip per call (mitigated by 1h cache)

**Effort:** 4h engineering + Stripe test mode validation

### Option B — Custom in-LoopZero billing UI

Build LoopZero-native billing UI (no Stripe Portal).

**Pros:**
- No external dependency
- Custom branding
- No Stripe API quota concerns

**Cons:**
- **20+h engineering** (subscription state, invoice rendering, payment method mgmt UI)
- Must replicate Stripe webhook handlers for all events
- PCI compliance considerations (even with Stripe Elements)
- Ongoing maintenance burden (Stripe API version bumps)
- M10 score won't lift (Stripe Portal IS the industry standard)

**Verdict:** REJECTED — re-inventing wheel per CLAUDE.md design-principles "Don't Reinvent the Wheel".

### Option C — Continue placeholder (defer to v1.x)

Keep hardcoded URL; promise Portal "coming soon" em docs.

**Pros:**
- Zero engineering this iter

**Cons:**
- Pro tier launch promise un-delivered
- Support burden (manual customer requests for invoices, payment changes, cancellations)
- Signals immaturity to enterprise customers (T11 SOC 2 prep)

**Verdict:** REJECTED unless explicit MEET-ASYNC-AMENDMENT defers Pro tier billing-portal feature.

## 5. Trade-offs (Option A)

| Dimension | Trade-off |
|-----------|-----------|
| Cost | $0 marginal (Stripe Customer Portal is free; included em Stripe transaction fees) |
| Engineering effort | 4h |
| Operational complexity | +1 SDK dependency to track (stripe-go) |
| Customer UX | Industry-standard, auto-localized |
| Support burden | Reduced (customer self-service for common ops) |
| Stripe API quota | <1 call/customer/hour (with cache) — well below rate limits |

## 6. Risk Analysis

### Risks to APPROVE Option A

| Risk | Severity | Mitigation |
|------|----------|------------|
| Stripe API down → 503 returned to user | LOW | Cache 1h; show "try again em 5min" UX |
| Stripe SDK v82 → v83 breaking change auto-bumped by Renovate | LOW | EC-13 absorbed: pin `stripe-go/v82` em go.mod; major bump requires manual ADR |
| Customer without `stripe_customer_id` (Free tier) clicks Portal | MEDIUM | Return 400 `NO_STRIPE_CUSTOMER` with "Upgrade to Pro" message |
| Idempotency cache memory leak | LOW | Redis 1h TTL; bounded |
| Webhook + Portal-action race (cancel via Portal triggers webhook race) | MEDIUM | Existing webhook idempotency handles via Stripe event_id |

### Risks to DEFER

| Risk | Severity |
|------|----------|
| Pro tier launch promise (MEET-2026-05-12) un-delivered | HIGH |
| Support tickets accumulate (manual invoice/cancel requests) | MEDIUM |
| M10 audit score regression | MEDIUM |

## 7. Validation Plan

### Pre-deploy

- [ ] Unit tests pass (`go test ./api/internal/routes/billing/...`)
- [ ] Integration test against Stripe **test mode** (separate test API key)
- [ ] Error paths covered: NO_STRIPE_CUSTOMER, BILLING_SERVICE_UNAVAILABLE, IDEMPOTENCY_MISMATCH
- [ ] Idempotency cache key collision test (repeated call returns same URL within 1h)

### Post-deploy (staging soak 24h)

- [ ] Internal team click-through: open Portal → change payment method → close
- [ ] Stripe test mode shows action em dashboard
- [ ] No API rate limit hits (`Stripe-Rate-Limit-Remaining` header monitored)
- [ ] Cache hit ratio observed em Redis (`MGET portal:* | wc -l`)

### Prod cutover

- [ ] Helm value `stripe.environment: production` flipped
- [ ] Stripe **prod restricted key** configured via ESO Secret (with operator + sponsor witnessed)
- [ ] First customer Portal click monitored em real-time (operator on-call)
- [ ] If 5xx rate > 0 em first hour → rollback to placeholder

### Rollback procedure

If Stripe API integration breaks:
1. Revert Helm value `stripe.environment: production` → `placeholder`
2. Handler returns hardcoded dashboard URL (status quo)
3. Document failure mode + Stripe support ticket
4. Re-attempt after Stripe-side fix
