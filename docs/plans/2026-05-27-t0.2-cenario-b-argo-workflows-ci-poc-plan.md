# Plan: T0.2 Cenário B POC — Argo Workflows + Argo Events CI

> **Version 1.0** — Implementa o Cenário B ratificado em `MEET-2026-05-27-batch-sponsor-approvals` + `ADR-2026-05-27-T0.2-RATIFIED`: substitui o gap de PR-time enforcement (deixado pela remoção do GitHub Actions em 2026-05-23) com Argo Events Sensor escutando Gitea webhooks que dispara WorkflowTemplate parametrizado `quality-gate` rodando `loopzero-ops quality <gate-name>` no cluster de build. Outcome: 56 `pkg/quality/*` gates passam a ser PR-blocking sem reintroduzir GitHub Actions SaaS, sem expor a mgmt cluster (boundary preservada per SBR veto), e sem duplicar build engine (per GitOps technical correctness).

## Context

**O que existe hoje (AS-IS):**
- Argo Workflows v1.0.5 instalado em `build` cluster, namespace `argo`, usado exclusivamente para pipelines de build tenant
- 56 `pkg/quality/*` gates rodam via `task quality:gates` operator-driven local
- Zero PR-time enforcement — branch protection sem required checks
- Crons órfãos desde 2026-05-23: drill watchdog 6h, weekly soak Sunday, coverage Monday, deadline daily
- Cenário A (Gitea Actions in mgmt) **VETADO** por SBR (lateral movement to crown jewels)
- Cenário C (GHA SaaS) rejeitado por reverter decisão operator 2026-05-23

**Evidência motivacional:**
- M12 audit 2026-05-26 flagga "zero PR-time gate enforcement" como gap MEDIUM
- Maturity ceiling capped até CI exists (Rule 11 evidence T3 = "CI run" indisponível)
- `MEET-2026-05-27-batch-sponsor-approvals` ratificou Cenário B com conditions explícitas

**Decisão ratificada:**
- ADR `2026-05-27-T0.2-cenario-b-ratified.md` — Cenário B (Argo Workflows + Argo Events) selected
- 4/7 specialists explicit support (PSec, GitOps, PDR, SBR APPROVE)
- 0 vetos contra B

## ADRs

### D1 — Argo Events EventSource + Sensor pattern (não webhook-direct-to-server)

**Decisão:** EventSource (gitea-webhook) publishes em EventBus; Sensor (pr-trigger) subscribes + dispatches Workflow CR. NOT direct Argo Server webhook submission.

**Rationale:** EventSource/Sensor decoupling permite:
- Multiple consumers do mesmo webhook (futuro: trigger Slack, audit log, ChatOps) sem refactor
- Buffering durante outages do Argo Server (EventBus retém events)
- Filtering centralizado (regex no payload antes de Sensor disparar)
- Pattern alinhado com Intuit/Adobe reference architectures (per ADR research)

**Consequences:**
- Adiciona EventBus dependency (JetStream NATS — bundled em argo-events chart)
- 3 CRs por trigger (EventSource + Sensor + EventBus) vs 1 (webhook direct)
- Habilita futuro multi-consumer arquitetura sem rework

### D2 — WorkflowTemplate parametrizado, NÃO um WorkflowTemplate per-gate

**Decisão:** Single `quality-gate` WorkflowTemplate aceita parâmetro `gate-name`. Sensor dispara 1 Workflow com matrix (steps por gate) ou 1 Workflow per gate.

**Rationale:** PDR explícito ("56 gates ship as ONE parametrized WorkflowTemplate, not per-gate proliferation"). Per-gate templates = YAML sprawl proibitivo, maintenance hell.

**Consequences:**
- Single template a manter; new gate = 1 linha em quality-gate Workflow spec
- Trade-off: failure isolation per-gate menor (1 Workflow fails = whole CI fails, vs per-gate workflow). Mitigação: `continueOn.failed: true` em steps + final aggregator que pode falhar even se individual gate falha — ainda emitir status por gate.

### D3 — CI workflows em namespace dedicado `argo-ci` (NÃO `argo` shared)

**Decisão:** New namespace `argo-ci` em build cluster. CI workflows usam ServiceAccount + RBAC scoped to `argo-ci`. Tenant build workflows continuam em `argo`.

**Rationale:** Principal architect concern (boundary mitigation): blur entre Build Plane (tenant builds) e Developer Plane (PR enforcement) inaceitável sem isolation. Namespace isolation + NetworkPolicy resolve.

**Consequences:**
- Operator adiciona 1 namespace + RBAC + NetworkPolicy
- Failure isolation: CI workflow OOM não afeta tenant build pipeline
- `argo-workflows` controller serve AMBOS namespaces (single controller, RBAC scopes per ns)

### D4 — Branch protection required check name = `quality`

**Decisão:** Workflow exit handler posts Gitea Check status com fixed name `quality`. Branch protection requires check `quality` to pass.

**Rationale:** Single status name simplifica branch protection config + permite refactor interno do Workflow sem repointar branch protection rule. Operator pode futuro split em sub-checks (`quality/lint`, `quality/security`) — backward-compat via aggregated `quality` always present.

**Consequences:**
- Branch protection setup: 1 required check name forever
- Internal Workflow free to evolve without external coupling

### D5 — Cenário A POC files PRESERVED (NÃO DELETED)

**Decisão:** `infra/helm/gitea/values-actions-poc.yaml.disabled` + `.gitea/workflows/quality.yml.example` STAY no repo.

**Rationale:** Per ADR-2026-05-27-T0.2-RATIFIED Conditions § 6: "Cenário A POC files preserved as Cenário C fallback path documentation." If Cenário B execution fails post-30d trial, swap to Cenário C is mechanical (POC files runner-agnostic).

**Consequences:**
- 2 files dead-by-design no repo (`.disabled` + `.example` suffix protege contra accidental activation)
- Rollback path documented + grep-discoverable

## Edge Case Review (inline)

### MUST FIX absorbed inline

**EC-1:** EventBus pod restart drops in-flight events → PR receives no CI check → branch protection BLOCKS merge indefinitely.
- **Mitigation:** Persistent JetStream NATS (default in argo-events 2.4+) + retry on Sensor side. Documented in T6.1 runbook "Troubleshooting → EventBus down".

**EC-2:** Same PR receives multiple webhook events (open + sync rapid) → multiple parallel Workflow CRs racing → race condition on Gitea status update (last-write-wins).
- **Mitigation:** Sensor `triggers[0].argoWorkflow.parameters[*].dest` uses commit SHA as Workflow name suffix → idempotent (same SHA = same Workflow name, second submission noop). Documented in T3.2 Deep Dive.

**EC-3:** Workflow times out before status posting → PR stuck in "pending" check state.
- **Mitigation:** `onExit` handler runs ALWAYS (per Argo Workflows semantics). Even on Workflow `Failed` (incl timeout), onExit fires → status posted as `failure`. Tested in T4.1 TDD.

### SHOULD TEST

**EC-4:** Webhook secret rotation invalidates all in-flight CI runs.
- **Test:** ESO refresh detected → EventSource pod restart → in-flight events drop (acceptable, operator re-triggers via "Re-run" button)

**EC-5:** Gitea API rate-limit hits during status posting bursts.
- **Test:** Status posting script retries with exponential backoff (3 attempts, 5s/15s/60s).

### DOCUMENT

**EC-6:** Branch protection bypasses (admin merge) skip CI entirely.
- **Risk accepted:** Acceptable for emergency hotfix path. Documented in runbook.

**EC-7:** CronWorkflow drift if argo-workflows controller upgrades break CRD schema.
- **Risk accepted:** Pinned chart version + Renovate manages bumps. Operator validates post-upgrade.
