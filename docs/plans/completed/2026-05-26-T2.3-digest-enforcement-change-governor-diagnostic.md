## 1. Problem Statement

Today the 7 published chart deployment templates (`charts/loopzero-{api,cloud,app-operator,platform-operator,preview-operator,tenant-operator,dashboard}/templates/deployment.yaml`) emit image references with **mutable tag**:

```yaml
image: "{{ .Values.image }}:{{ .Values.tag }}"   # ← :v1.2.3 can be re-tagged
```

**Concrete attack:** Adversary with push access em DOCR re-tags `registry.digitalocean.com/loopzero-system/loopzero-api:v1.2.3` to point at malicious image. Next pod restart (HPA scale-up, eviction, OOM kill) fetches the new image, which is **signed with the attacker's keyless cert** (Fulcio happily issues a cert for ANY workload identity). Cluster admits the new image because policy only verifies signature, NOT digest immutability.

**Per CLAUDE.md "Known Systemic Patterns":** This is the "CF scan imports conflicting apex" class of vulnerability — silent re-binding of a reference layer.

## 2. Decision Required

**APPROVE migration to digest-pinned chart references + ClusterImagePolicy enforcement via progressive rollout** (warn-mode 7-day soak → enforce all-namespaces).

## 3. Tier Classification

**T2** — Helm modifications + admission policy + multi-chart coordination. Per `.claude/rules/pre-release-governance.md`, T2 requires:

## 4. Alternatives Evaluated

### Option A — Progressive ClusterImagePolicy rollout (RECOMMENDED — EC-5 of edge-case-review)

Three-protection migration over 7-day soak:

```
Phase 1 (this task ship):
  - 7 chart templates: prefer digest over tag
  - values.schema.json: oneOf [tag XOR digest] constraint
  - ClusterImagePolicy: mode=warn + namespaceSelector tenant-only
  - api/internal/argo/buildkit.go: emit digest output

Phase 2 (separate task after 7-day soak):
  - ClusterImagePolicy: mode=enforce + namespaceSelector all-namespaces
```

**Pros:**
- 7-day warn-mode soak catches every chart with `:tag` mutable em production
- namespaceSelector tenant-only initially shields admission-policies/monitoring/operator pods
- values.schema.json oneOf prevents `tag="" + digest=""` silent CrashLoop (EC-4)
- Each phase independently rollbackable

**Cons:**
- 2 separate sponsor reviews (Phase 1 + Phase 2 each need verify)
- 7-day calendar latency for soak before Phase 2
- During Phase 1, loopzero-system namespace still vulnerable to tag-reuse

**Effort:** ~4h engineering Phase 1 + 7-day soak + ~1h Phase 2 flip + audit

### Option B — Big-bang enforce on Day 1

Skip warn-mode soak; enforce all-namespaces immediately.

**Pros:**
- Faster to ship (~4h total)
- No intermediate "vulnerable in loopzero-system namespace" window

**Cons:**
- **HIGH risk of cluster-wide CrashLoopBackOff:** admission-policies, monitoring, operator pods using `:latest`/`:vN.Y.Z` rejected on next restart
- Recovery requires break-glass `kubectl --force` OR webhook bypass
- May leave cluster in unbootable state (chicken-and-egg: policy-controller can't recover if it itself is rejected)

**Verdict:** REJECTED — blast radius too high, no upside vs Option A 7-day soak.

### Option C — Skip digest enforcement entirely

Rely solely on cosign signature verification (T2.2) without digest enforcement.

**Pros:**
- Zero implementation work for this task

**Cons:**
- Tag-reuse attack still possible (re-tag with new attacker-signed image, both pass signature check)
- T2.2 (keyless) alone is necessary but not sufficient — Fulcio issues certs for any workload identity matching the regex
- Per defense-in-depth, identity + immutability are separate layers

**Verdict:** REJECTED — leaves attack vector documented em problem statement § 1.

## 5. Trade-offs (Option A)

| Dimension | Trade-off |
|-----------|-----------|
| Cost | $0 (chart template change + admission policy config) |
| Engineering effort | ~4h Phase 1 + ~1h Phase 2 = 5h total |
| Calendar time | 7+ days (mandatory soak between phases) |
| Operational complexity | +1 admission webhook to monitor (`loopzero_policy_violation_total`) |
| Backwards compat | Pre-release per ADR D1 — no constraint, but ALL 7 charts must migrate atomic |
| Defense-in-depth layer | Adds 3rd protection (schema oneOf + chart prefer-digest + admission enforce) |

## 6. Risk Analysis

### Risks to APPROVE (Option A)

| Risk | Severity | Mitigation |
|------|----------|------------|
| Phase 1 warn-mode misses a chart that fails on Phase 2 enforce | MEDIUM | 7-day soak + `loopzero_policy_violation_total` metric watch + grep audit pre-Phase 2 |
| values.schema.json oneOf rejects existing dev helm charts | LOW | EC-4 absorbed: oneOf constraint applied to schema, not template; existing charts with `tag` continue working |
| buildkit.go digest emission breaks Argo Workflow output schema | LOW | Workflow output is additive; existing consumers ignore new field |
| ClusterImagePolicy CRDs not installed on all clusters | LOW | policy-controller chart pre-existing; CRDs already deployed per CLAUDE.md (Sprint 6) |
| Operator forgets to flip Phase 1 → Phase 2 after 7-day soak | MEDIUM | Mark in task tracker; tenant pods stay vulnerable while in Phase 1 |

### Risks to DEFER (Option C — skip)

| Risk | Severity |
|------|----------|
| Tag-reuse attack vector preserved (defense-in-depth incomplete) | HIGH |
| T2.2 keyless cutover provides false sense of security | MEDIUM |
| Maturity audit gap (M06 + M07) persists | MEDIUM |

## 7. Validation Plan

### Phase 1 (warn-mode) pre-deploy

- [ ] Render tests PASS for all 7 charts (`task helm:test`)
- [ ] values.schema.json oneOf rejects `tag="" + digest=""` em fixture
- [ ] ClusterImagePolicy YAML valid against policy-controller CRD schema
- [ ] buildkit.go emits `digest` output em test workflow

### Phase 1 LIVE (7-day soak)

- [ ] Deploy ClusterImagePolicy em mgmt cluster
- [ ] Verify zero pod restarts triggered by policy
- [ ] Daily check: `loopzero_policy_violation_total{mode="warn"}` em Prometheus
- [ ] Each violation: identify offending chart + create issue → fix per-chart
- [ ] At day 7, expect zero outstanding warnings

### Phase 2 (enforce) deploy

- [ ] Flip ClusterImagePolicy `mode: enforce`
- [ ] Expand namespaceSelector to empty (all namespaces)
- [ ] Monitor pod restart cycle 4h
- [ ] Zero rejected admissions expected (per Phase 1 soak)

### Rollback procedure

If Phase 2 enforce causes pod admission rejections:
1. Edit ClusterImagePolicy: `mode: warn` (revert)
2. Identify rejected pods: `kubectl logs deployment/policy-controller`
3. Patch offending chart `Values.digest` field
4. Re-run Phase 1 soak for affected charts
5. Re-attempt Phase 2 after additional 3-day clean window

### Emergency break-glass

If cluster admission completely broken (policy-controller itself rejected):
1. SSH to mgmt cluster
2. `kubectl --context emergency delete clusterimagepolicy loopzero-digest-enforcement`
3. Document incident em `.claude/knowledge-base/reviews/`
4. Schedule full sprint to fix policy hierarchy
