**Date:** 2026-05-04 (Ralph loop iter 6 closure attempt)
**Plan version:** v1.4
**Operator:** Claude (Ralph loop autonomous execution)

## Purpose

Prove that the implementation lives by exercising one T3.2 special
validation criterion (a) — RFC 9457 problem+json shape — against the
local k3d running api. This is **smoke evidence** only; the full T3.2
gate runs via `.github/workflows/pkg-soak.yml` weekly cron (Friday
02:00 UTC) on production-equivalent fresh infra after CI rebuilds the
api image.

## Steps Performed

```bash
# Pre-check: api reachable on localhost:13001 (task doctor reported 30 PASS)
curl -sf http://localhost:13001/health    # → empty body, exit 0

# Trigger error path that should yield RFC 9457 problem+json
curl -si -X POST http://localhost:13001/api/v1/projects \
  -H "Content-Type: application/json" \
  -d '{}'
```

## Observed Output

```
HTTP/1.1 401 Unauthorized
Content-Type: application/json
Correlation-Id: 25d3d030-e791-4c45-a482-e8312eaabf71
Content-Length: 122

{"code":"UNAUTHORIZED","message":"Missing or invalid Authorization header. Use: Authorization: Bearer <token>"}
```

## Analysis

The response is the **pre-Stage C legacy format** (Content-Type
`application/json` + ToJSON shape `{code, message}`), NOT the post-
Stage C RFC 9457 shape (`application/problem+json` + fields
`{type, title, status, detail, code, instance}`).

**This is the expected outcome** — the api binary serving on
localhost:13001 was compiled **before** the iter 3 T2.3 Stage A+B+C
commits. Specifically:

- Local k3d cluster booted via `task setup` produces a stable api
  image; iter 3 changes were not rebuilt or rolled out.
- The on-disk api source code (after iter 3) DOES use
  `errorshttp.WriteJSON` in middleware (verified via grep).
- The on-disk pkg/errors/http registry covers `UNAUTHORIZED → 401`.
- Therefore, when CI rebuilds the api image, the response will
  match RFC 9457.

## What This Proves

1. **Implementation is live in the source tree** — middleware changes
   from iter 3 are committed and visible.
2. **Local infra is partially functional** — api responds at all.
3. **CI rebuild is load-bearing** — Stage C effects only manifest
   after a fresh build, exactly what `pkg-soak.yml` does.

## What This Does NOT Prove

- **It does not satisfy T3.2 special validation (a).** The gate
  requires a freshly built api binary serving RFC 9457 shape. This
  smoke check confirms the gate is meaningful (without rebuild, the
  shape is wrong) but the gate itself remains pending CI execution.
- **Other special validations (b) CB recovery, (c) kstatus
  conditions** also pending fresh infra + live operator pods.
