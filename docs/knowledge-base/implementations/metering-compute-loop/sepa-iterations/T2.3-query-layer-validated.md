## usage_records design map — surfaced while starting the wrapper (the wrapper is NOT mechanical)

Dispatch (confirmed from plan L101/L149/L231): the **worker (T3.1)** uses the Go clock to pick
`MeterCompute` (same-period) vs `MeterComputeSplit` (straddle); the DB `=`/`<>` predicates are the
SC-2 SAFETY NET (a wrong Go guess → 0-row HOLD, self-corrects next tick, never a mis-bill). So the
**T2.3 wrapper exposes both methods** (each its own tx: SET LOCAL + CTE + usage upsert); the worker
decides which to call.

Four usage_records details this deep-dive surfaced (one was a real bug):

1. **[BUG — FIXED + PG-REAL validated] `UpsertUsageRecord` conflict target.** `usage_records` has a
   UNIQUE index `idx_usage_tenant_metric_period (tenant_id, metric, period_start)` (000001). My query
   conflicted on `id` (fresh UUID/tick) → the 2nd write of a period would MISS the id-conflict and
   VIOLATE the unique index (hard error) every 60s tick. Fixed to `ON CONFLICT (tenant_id, metric,
   period_start) DO UPDATE SET quantity += EXCLUDED`. Validated: two writes same period → 1 row,
   quantity accumulates (5+7=12), first id kept.
2. **"one usage_records row/period" (plan L289) ⇒ the SPLIT writes TWO usage records** (tail→P1's
   period, head→P2's period), NOT one total. So `MeterComputeSplit` must return `tail_cost` and
   `head_cost` SEPARATELY (currently returns only the summed total), and the wrapper writes 2 usage
   upserts into the two periods. `MeterCompute` (same-period) writes ONE.
3. **Period boundaries must come from SQL, not Go** (EC-7 pure-UTC — Go date math risks DST/drift).
   So the meter queries should ALSO return the period boundaries the wrapper needs for the usage
   records: `MeterCompute :one` → `{delta, period_start, period_end}`; `MeterComputeSplit :one` →
   `{tail_cost, head_cost, p1_start, p1_end, p2_start, p2_end}`. Return shapes change scalar→struct.
4. **Wrapper never does Go date math** — it threads the SQL-returned boundaries straight into the
   usage upserts. `@id` = a fresh UUID (only used on first insert of a period).

## OPEN money question — needs guardian (RESOLVED above — kept for provenance)

`MeterComputeSplit`: `head = GREATEST(now() - metering_period_end(@expected), '0')`
is **NOT clamped by `@max_delta`**, whereas `MeterCompute` clamps `elapsed` to
`max_delta`. Normal operation (60s tick) → `head` is tiny, harmless. But a leader
resurrection after a long outage whose resumption tick straddles the month boundary
would bill an **unclamped** `head` → **over-billing** asymmetry vs the same-period path.

Question for state-guardian (bounded-over-billing, SC-adjacent) + tenant-guardian:
does ADR-9 intend `total = tail + head` clamped to `max_delta` (splitting the CLAMPED
gap across the boundary), or is the unclamped head accepted? This changes the split
CTE and the `MeterComputeSplit_TailToP1_HeadToP2` + `ClampsLongGap` tests.
