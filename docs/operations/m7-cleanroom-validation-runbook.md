# M7 Cleanroom validation + Sponsor JUNTOS — Operator Runbook

> **Canonical operator playbook for M7 of `qa-readiness-roadmap-2026-06-23`.** Per ADR `2026-06-23-validation-milestone-sponsor-hard-stop.md` § Decision Step 3. Sponsor JUNTOS is **HARD STOP** per `.claude/rules/cleanroom-up-live-test-mandate.md` INQUEBRÁVEL (sponsor verbatim 2026-06-10 + 2026-06-16) — operator runs Steps 0-6 alone (~3-4h), then sponsor sits down for Step 7 (~30min browser walkthrough).

## Pre-conditions (before scheduling sponsor)

- M7 preparation slice merged to main (this release).
- Operator has docker + k3d + tilt + task on PATH.
- Operator has `~/.loopzero/dev-credentials.json` mode 0600 with canonical fields populated.
- Operator has `~/.loopzero/cleanroom-unseal.json` (will be regenerated by Sub-step 2.5 — if exists from prior run, leave it).
- Operator has free wall-clock window of ≥ 4h for Steps 0-6 + ≥ 30min for Step 7 with sponsor.

## Step 0 — Pre-flight hermetic gate (~10 seconds — HARD STOP)

> **HARD STOP marker #1:** if pre-flight FAILs, **DO NOT** start the LIVE chain. Investigate the failing assertion FIRST. Running Steps 1+ with broken pre-flight wastes ~3-4h of operator time.

```bash
cd $REPO_ROOT
cd infra/tests && go test ./charts/ -run TestM7Preflight -count=1
```

**Expected:** `ok github.com/getloopscale/loopzero/infra/tests/charts <N>s` with 7/7 subtests PASS.

**If FAIL:** check which subtest failed; common causes:
- `TestM7Preflight_M1ToM6PlansExist`: a milestone plan was deleted/moved — restore or update test.
- `TestM7Preflight_RoadmapMilestoneStatesCanonical`: roadmap state drift from canonical; verify `git log -- .claude/knowledge-base/plans/qa-readiness-roadmap-2026-06-23.md`.
- `TestM7Preflight_ChainScriptsExist`: a chain script was renamed/moved — update runbook + test.
- `TestM7Preflight_PreparationArtifactsExist`: M7 preparation slice not yet merged — pull develop, verify.

Do NOT proceed to Step 1 until 7/7 subtests PASS.

## Step 1 — Cleanroom TOTAL (~30-45 minutes)

Destroys 4 k3d clusters + registry + Docker network, then recreates from scratch.

```bash
cd $REPO_ROOT
export LOOPZERO_HELMFILE_ENV=dev-public
task clean:all
task setup
```

**Expected:** `task setup` exits 0 after ~25min; 4 clusters Running; helmfile sync complete for 32 releases.

**If FAIL:** consult `.claude/skills/cleanroom/SKILL.md` for recovery procedures. Common cascade bugs are documented in CLAUDE.md § Common Mistakes (B-series + F-series + H-series + N-series entries).

## Step 2 — UP (~5-10 minutes — HARD STOP)

> **HARD STOP marker #2:** `task doctor` must return PASS=38+ FAIL=0. If FAIL > 0, investigate before proceeding — running the seeds against a partially-degraded cluster cascades failures.

```bash
cd $REPO_ROOT
tilt up &
# wait ~3-5min for hot-reload to settle
task doctor
```

**Expected:** `task doctor` reports `PASS=38+ FAIL=0` (exact count may vary as new checks land).

**If FAIL:** `kubectl get pods -A | grep -v Running` to identify degraded workloads; consult `.claude/rules/cleanroom-up-live-test-mandate.md § Worked example` for cascade-bug patterns.

## Step 3 — Post-Cleanroom seeds CANONICAL (~10-15 minutes — HARD STOP)

> **HARD STOP marker #3:** `--verify` must exit 0. If any of the 12-step seed chain fails, the LIVE side will silently break later — investigate NOW.

Per M2 v0.24.0: `seed-post-cleanroom-all.sh` is the canonical 12-step master orchestrator (Sub-step 2.5 auto + vault + minio + kratos + hydra + github + gitea + argocd + broker + vault-role + loki + tenant fixtures + chaos-mesh + argocd-token + vault-cross-cluster-addr + stripe-webhook).

```bash
cd $REPO_ROOT
bash infra/scripts/local/seed-post-cleanroom-all.sh --verify
```

**Expected:** all 12 steps exit 0; `--verify` probes each step's contract (e.g., Step 5 verifies `loopzero-api-github` Secret materialized; Step 15 verifies `loopzero-stripe-webhook` Secret canonical).

**If FAIL at a specific step:** review `seed-post-cleanroom-all.sh` step block + the failing seed script's own `--verify` output. Skip-flags are available (`--skip-vault`, `--skip-stripe`) but they leave gaps — only use for surgical re-runs after fixing root cause.

## Step 4 — DOGFOOD FULL (~60-90 minutes — HARD STOP)

> **HARD STOP marker #4 (combined):** DOGFOOD 13/13 PASS + live-proof 9/9 PASS + chaos 2/2 lifecycle GREEN. ANY failure here means the LIVE chain is broken — sponsor JUNTOS would expose the failure to sponsor's eyes (worst possible time to discover regression).

```bash
cd $REPO_ROOT
bash archive/canonical-tests-v1/scripts/local/dogfood-all.sh --live-only --json | tee /tmp/dogfood-all-live-$(date +%Y%m%d-%H%M%S).json
```

**Expected:** 13 per-journey dogfood wrappers all PASS (login, project-connect, deployments, scale, readiness, domains, environments, deploy-timeline, secrets, secrets-openbao, recovery, device, live-url).

**If FAIL:** read the per-wrapper logs at `/tmp/dogfood-all-*.log`; each wrapper exits 0/1/2 with stderr citing the failing scenario.

## Step 7 — SPONSOR JUNTOS browser walkthrough (~30 minutes — HARD STOP)

> **HARD STOP marker #4 (sponsor):** sponsor must be PHYSICALLY PRESENT (in person OR live screen share with synchronous verbal confirmation). Per mandate INQUEBRÁVEL, async OR pre-recorded approval is NOT acceptable.

Sponsor sits with operator. Operator opens `https://app-dev.loopzero.example` in browser. Sponsor walks through canonical journeys:

1. **Login** (J-01) — sponsor signs in via Google OIDC.
2. **Project connect** (J-09) — sponsor connects `getloopscale/loopzero-repotest` fixture repo.
3. **Deployment** (J-17) — sponsor triggers a deploy from a fresh PR; observes Live URL appear.
4. **Scale** (J-20) — sponsor increases replicas via dashboard; observes K8s converges.
5. **Audit log** (cross-cutting) — sponsor inspects audit events; expects no WHEN/ACTOR blanks; no SQL fragments exposed.
6. **Promote** (J-10) — sponsor promotes preview → production.
7. **Rollback** (J-19) — sponsor rolls back; observes UI honesty under transitional state.

**Sponsor verdict:** verbatim **"Funcionou!"** OR equivalent green-light phrase recorded in the GH closure issue.

**If sponsor says "Não funcionou" / "Tem problema com X":**
- Filed as new bug issue with `qa-readiness-followup` label.
- M7 remains 🟢 PREPARATION_COMPLETED in the roadmap.
- New cycle (discover → plan → implement → review → release) addresses the surfaced bug.
- Sponsor JUNTOS re-scheduled after fix lands.

After Step 7 GREEN:

1. Copy `.github/ISSUE_TEMPLATE/qa-readiness.md` body into a new GH issue:
   ```bash
   gh issue create --label qa-readiness --title "QA-readiness $(date -I) complete" --body "$(cat .github/ISSUE_TEMPLATE/qa-readiness.md)"
   ```
2. Fill the issue body with the LIVE run results + sponsor verbatim quote.
3. Edit `.claude/knowledge-base/roadmap-runs/M7-2026-06-23.md`: set `status: completed`, `sponsor_juntos_completed_at`, `sponsor_verbatim`.
4. Append to `CHANGELOG.md` `[Unreleased] § Added`: "QA-readiness milestone — Cleanroom TOTAL → DOGFOOD 13/13 → sponsor JUNTOS approved $(date -I)".
5. Edit `.claude/knowledge-base/plans/qa-readiness-roadmap-2026-06-23.md` § M7: flip section header from `🟢 PREPARATION_COMPLETED` to `✅ COMPLETED`; flip Status field.
6. Commit + invoke `/release` for the post-execution closure (bump minor — final QA-readiness milestone delivery).
